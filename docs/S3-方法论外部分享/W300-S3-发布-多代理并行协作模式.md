# 多代理并行协作模式——4 subagent 独立无共享状态的执行范式

> 轨标：外部分享

## 引子

在 AI 代理协作的工程实践中，如何在保证质量的前提下最大化吞吐量，始终是一个核心命题。串行单代理模式质量可控但效率受限；多代理并行模式能提升吞吐量，却容易因协调失控而出现质量塌陷——subagent 自报完成、实际交付缺失的"假收敛"现象，几乎是并行模式不可避免的副产物。

本文沉淀一种在长期实践中验证有效的并行范式——**4 subagent 独立无共享状态并行模式**。它通过"独立无共享 + 主代理统一 spot-check + 审查-收尾-沉淀闭环兜底"三层机制，在四路并行下既拿到吞吐量红利，又守住质量底线。下文从模式定义、适用场景、设计原则、执行流程、spot-check 策略、假收敛应对、闭环关系、实战案例八个维度展开，并附可复用清单。

## 一、模式定义

四 subagent 并行模式，指主代理同时分发 4 个独立 subagent 执行无共享状态任务的高效协作模式。

**边界条件**：4 个任务必须相互独立、无状态依赖、无文件冲突，主代理通过统一 spot-check 机制验证交付质量。

该模式区别于串行单 subagent 模式与三 subagent 并行模式，通过四路并行实现吞吐量最大化，同时以主代理 spot-check 与审查-收尾-沉淀闭环兜底保证交付质量，避免并行带来的质量塌陷风险。其本质是用"独立无共享"换吞吐量、用"主代理 spot-check"换质量可见性、用"闭环兜底"换质量底线。

## 二、适用场景

适用于 4 个独立任务无共享状态的场景，典型如：

- **4 篇独立主题文档的并行撰写**——如技术调研、模块设计、API 文档、测试方案等彼此无依赖的文档；
- **4 个独立页面或模块的并行开发**——页面间无共享状态、无路由依赖；
- **4 个独立模块的并行重构**——重构边界清晰、无交叉引用。

**不适用**于存在数据依赖、文件冲突或需要顺序执行的任务。

判断标准：4 个任务可在任意顺序下独立完成，且最终交付物可独立验证。若任务间存在共享状态或顺序依赖，应降级为串行或三 subagent 并行模式，避免并行冲突导致交付失败。

## 三、设计原则

三大设计原则：

1. **独立无共享**——4 个 subagent 任务边界清晰，无文件读写冲突、无状态依赖、无共享变量。这是并行模式成立的前提，一旦边界模糊，并行会退化为冲突。
2. **主代理统一 spot-check**——主代理对 4 个交付物执行统一五维度抽查（文件存在性、结构完整性、核心内容、footer 元信息、无 placeholder），避免 subagent 自报虚高。这是质量可见性的关键。
3. **审查-收尾-沉淀闭环兜底**——深度复检、收尾归档、方法论沉淀三环节形成质量闭环，确保并行模式下质量不打折。这是质量底线的保障。

三条原则层层递进：无共享是前提，spot-check 是过程，闭环是兜底。

## 四、执行流程

五步执行流程：

1. **主代理分发任务**——明确 4 个 subagent 的任务边界、交付物路径、质量要求，确保每个 subagent 收到完整且无歧义的指令；
2. **四 subagent 并行执行**——4 个 subagent 独立完成各自任务，互不干扰，主代理不介入执行细节；
3. **主代理 spot-check**——对 4 个交付物执行五维度抽查，不信任 subagent 自报；
4. **深度复检验证**——通过深度复检循环确保无假收敛，识别过度拟合与形式化交付；
5. **收尾归档与沉淀**——更新进度台账与记忆系统，将本轮经验沉淀为可复用方法论。

五步中，第 3、4 步是质量守门环节，不可省略；第 5 步是方法论资产化环节，决定了并行经验能否复用。

## 五、主代理 spot-check 策略

五维度抽查策略：

1. **文件存在性**——验证 4 个交付文件均实际创建于指定路径，防止 subagent"报喜不报忧"；
2. **结构完整性**——核对段落数、标题层级、footer 格式符合规范，防止结构残缺；
3. **核心内容**——抽查每段 100-200 字、无 TBD/TODO 等占位符，防止内容注水；
4. **footer 元信息**——验证版本号、关联文档、索引链接齐全，防止元信息缺失；
5. **无 placeholder**——全文扫描确认无待补充标记，防止形式化交付。

**五维度缺一不可，任一不达标即触发补齐流程。** spot-check 的核心原则是"不信任自报、只信任验证"——subagent 的"已完成"报告只是触发验证的信号，而非验证本身。

## 六、假收敛应对

假收敛指 subagent 自报完成但实际交付缺失的虚高状态，是多代理并行模式下最隐蔽的质量风险。并行 subagent 越多，假收敛的基数与隐蔽性越高。

应对策略：

1. **即时 spot-check**——主代理在 subagent 报告完成后立即执行五维度抽查，不信任 subagent 自报。假收敛的窗口期越长，纠偏成本越高；
2. **三件套补齐**——发现缺失时强制补齐文件、结构、内容三件套，确保交付完整。补齐不是修补，而是按标准重做缺失部分；
3. **进度台账核实**——核实任务计数器与实际交付一致，防止计数器虚高导致方法论失真。计数器虚高会使后续决策基于错误前提。

假收敛不可消除，只能通过"不信任 + 即时验证 + 强制补齐"三连击将其影响压到最低。

## 七、与审查-收尾-沉淀闭环的关系

审查-收尾-沉淀闭环构成质量保障的三层防线：

- **审查层（深度复检）**：负责深度复检，识别假收敛与过度拟合，是质量的"质检车间"；
- **收尾层（收尾归档）**：负责收尾归档，更新记忆系统与进度台账，是质量的"入库登记"；
- **沉淀层（方法论沉淀）**：负责将经验提炼为可复用模式，是质量的"资产化"。

四 subagent 并行模式通过该闭环实现"执行-验证-收尾-沉淀"全链路质量保障，避免并行模式下的质量塌陷，确保方法论可追溯、可复用。

换言之，并行模式解决了"做得快"的问题，spot-check 解决了"做得对"的问题，闭环解决了"做得久"的问题——三者共同构成多代理协作的完整质量工程。

## 八、实战案例：四篇独立主题文档的并行产出

以一次四篇独立技术调研文档的并行产出为例。四个主题分别记为主题 A、主题 B、主题 C、主题 D，四份调研文档相互独立、无共享状态、无交叉引用。

**执行过程**：

1. 主代理分发四个 subagent，各自负责一个主题，明确交付路径与五维度质量要求；
2. 四 subagent 同时执行，互不干扰；
3. 主代理对四份交付物执行五维度 spot-check，发现其中一份 footer 元信息缺失，触发补齐；
4. 深度复检确认四份文档无假收敛、无过度拟合；
5. 收尾归档更新进度台账，方法论沉淀为本模式。

**关键成功因素**：

- 主题间 genuinely 独立，无交叉引用与状态依赖——这是并行成立的前提；
- 主代理不信任自报，坚持五维度抽查——这是质量可见性的关键；
- 闭环兜底机制完整运转，而非流于形式——这是质量底线的保障。

该案例的可复用之处不在于"四个主题"本身，而在于"独立无共享 + spot-check + 闭环"三层机制的协同运转。

## 可复用清单

**分发前确认**：

- [ ] 4 个任务是否 genuinely 相互独立？
- [ ] 是否存在文件读写冲突？
- [ ] 是否存在状态依赖或顺序依赖？
- [ ] 每个交付物是否可独立验证？

**执行中监控**：

- [ ] 4 个 subagent 是否真正并行、互不干扰？
- [ ] 是否有 subagent 长时间无进展？

**交付后验证（五维度 spot-check）**：

- [ ] 文件存在性——4 个文件均实际创建？
- [ ] 结构完整性——段落、标题、footer 符合规范？
- [ ] 核心内容——无 TBD/TODO 占位符？
- [ ] footer 元信息——版本、关联、索引齐全？
- [ ] 无 placeholder——全文扫描通过？

**闭环兜底**：

- [ ] 深度复检是否确认无假收敛？
- [ ] 收尾归档是否更新进度台账？
- [ ] 方法论是否沉淀为可复用模式？

## 总结

4 subagent 独立无共享状态并行模式，本质是用"独立无共享"换吞吐量、用"主代理 spot-check"换质量可见性、用"审查-收尾-沉淀闭环"换质量兜底。三者缺一不可：

- 缺独立无共享，并行会退化为冲突；
- 缺 spot-check，质量会塌陷为自报虚高；
- 缺闭环兜底，经验会流失为一次性消耗。

当任务边界清晰、可独立验证时，该模式能将四路并行的吞吐量红利充分释放，同时守住工程质量的底线——这正是多代理协作从"能用"走向"可复用"的关键一步。
