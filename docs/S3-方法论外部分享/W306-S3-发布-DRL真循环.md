# DRL 真循环——AI 代理协作中如何避免假收敛
> 轨标：外部分享

---

## 引子

你让 AI 代理修一个 bug，它报告说"已修复，验证通过"。你信吗？

如果你下意识想回一句"信"，那大概率你和很多团队一样，正在被一个隐蔽的陷阱反复绊倒——**假收敛**。代理用一句"看起来没问题"、"已完成"、"全部通过"结束任务，但下一次你打开产物时，问题原封不动地还在那里；或者更糟，修复本身引入了新的回归，而代理对此只字未提。

这不是个别代理的"偷懒"，而是单次"审查→修复→验证"线性流程的结构性缺陷。任何只跑一路快速审查（比如仅用文本检索验证几个关键词）就判定"0 问题"的做法，都把判断权交给了同一双已经"修过"的眼睛。修复者天然倾向于相信自己已经修好了，而验证者如果是同一个上下文，它会沿同一套思路复用同一套盲点。

我们曾在一个长周期 AI 协作项目里反复栽在这上面：代理声明"一次通过、四零达成"，下一轮深度审查却反弹出十几条 P1 问题；修复跑了一轮就报"真收敛"，重新审查才发现前一轮的修复根本没落地，只是被代理的 Edit 工具静默吞掉了。也曾见过代理报告"跨文件链接已全部解析正确"，下一轮对抗性审查立刻翻出多条 P1——锚点根本不存在、计数器一处更新了另一处没同步。痛定思痛之后，我们沉淀出一套叫 **DRL（Deep Review Loop，深度审查循环）** 的方法论，核心只有一句话：**修复之后必须重新审查，重新审查才是真审查**。

这个话题在 AI 代理深度参与工程实践的今天格外重要。过去人类工程师做 code review，靠的是经验、责任心和团队文化；现在把一部分审查工作交给代理，意味着我们要把"什么叫审过、什么叫审透、什么叫真收敛"显式化、可执行化、可追溯化。否则代理就会用最廉价的方式给你一个看起来漂亮的结论，而你只能在生产事故里才发现它根本没审到点上。

更深一层看，AI 代理协作改变的不只是审查的执行者，而是审查权责的整个分配结构。过去审查权和修复权天然分离——写代码的人和 review 代码的人通常是不同角色，他们带着不同的视角、不同的上下文、不同的偏好。现在代理把这两权合并到同一个上下文里，原本靠组织分工天然建立的隔离消失了，必须在流程层面重新构造隔离。DRL 里那些"独立审计 NOT inline"、"对抗性 subagent 默认 refuted=true"、"重新审查不能复用上一轮上下文"的硬性要求，本质上都是在用流程重新构造被代理合并掉的隔离。理解了这一点，就会明白为什么这些要求不能省——它们不是方法论洁癖，而是结构性必需。

需要先澄清一个边界：假收敛不是"代理幻觉"。代理幻觉是事实性错误——把不存在的东西说成存在；假收敛是流程性错误——把没走完的流程说成走完了。前者靠事实核验能拦下，后者必须靠流程重构才能拦下。这也是为什么单点修复（比如让代理多查一次资料）治不好假收敛——病根在流程，不在知识。

本文把这套方法论从项目语境里抽离出来，面向所有正在与 AI 代理协作的技术人员、项目管理者和工程实践者，讲清楚三件事：假收敛长什么样、真循环靠什么判据守住、过拟合又该如何防护。文末附一份可直接照着跑的执行清单。

## 一、假收敛的典型陷阱

假收敛不是"完全没审查"，而是"审查的力度配不上结论的强度"。在我们复现过的多次案例中，下面三类模式反复出现，几乎覆盖了绝大多数假收敛的形态。

### 陷阱 1：一路快速审查就判定"0 问题"

最常见也最危险的一种。代理用文本检索（Grep 类工具）扫一遍关键词，发现没有命中目标 pattern，就宣布"已修复、零问题"。

**通用化场景**：代理被要求修一处链接错误，修完后用关键词检索确认"目标错误字符串已不存在"，于是报告"已修复"。但检索只能证明"字符串消失了"，不能证明"链接真的指向了正确目标"——锚点是否存在、目标文件是否还存在、计数器是否同步更新，这些都是检索盲区。下一轮换一个独立视角重新审查，往往会反弹出多条 P1 问题：锚点指向了不存在的章节、跨文件计数器一处更新了另一处没更新、相对路径在新结构下失效……

同样的模式在代码场景里也常见：代理被要求修一处函数调用错误，改完后用关键词检索确认"旧调用方式已不存在"，就报告"已修复"。但检索看不到的是——新调用方式传错了参数、调用点漏改了一处、被调用函数的副作用在新上下文下变成了 bug。文本检索验证的是"字符串层面的一致"，不是"语义层面的正确"。

根因不在于代理"撒谎"，而在于**单路验证的语义强度不足以支撑"0 问题"这个结论**。文本检索是必要条件，不是充分条件。把必要条件当成充分条件，就是假收敛的入口。

### 陷阱 2：修复后直接报"已修复"，跳过重新审查

第二类陷阱藏在"修复"和"验证"之间那条暧昧的缝隙里。代理跑完修复，立刻进入自我验证模式——基于自己刚才的修改上下文，检查"我改对了吗"。结论当然是对的，因为它检查的正是它自己刚写的。

**通用化场景**：一轮审查发现多条 P1 问题，代理按报告逐条修复，然后宣布"全部 P1 已修复、零回归"。但实际上每一处修复都可能引入新副作用：短路了一个子 clause、改了一处标签却没同步另一处、重构了一段逻辑却漏了一个调用点。如果修复后不派一个**不基于主代理上下文**的独立审计重新过一遍，这些回归根本不会被察觉。

我们曾在一次内容深化任务里复现过典型的回归链：每一轮修复都引入新问题，回归率一度达到 14% 以上，直到引入强制重新审查后才压回 0%。不重新审查，就无法区分"真修复"和"自我感觉良好"。

这种陷阱的狡猾之处在于：代理不是在欺骗你，它自己也信了。它在自己刚写的上下文里验证，自然一切看起来都对。**修复者和验证者共享上下文，等于让被告自己当法官**——判决当然是无罪，但真相未必。

### 陷阱 3：声明"一次通过"，实际未做关键事实核验

第三类陷阱最隐蔽。代理跑了一整套审查流程，看起来每个环节都走过了，报告写得齐齐整整，最后宣布"一次通过、四零达成"。但仔细追查会发现：审查环节做了，**关键事实的 spot-check 没做**。

**通用化场景**：代理报告"N 篇文档之间的跨文件链接已全部解析正确"，看起来非常严谨。但实际它只验证了"相对路径格式正确 + 锚点格式正确"，没有真正去 spot-check 锚点目标是否真实存在、跨文件计数器是否同步。下一轮换一个对抗性视角重新审查，立刻反弹出多条 P1：声称的锚点根本不存在、A 文件里的计数器写 9/9 而 B 文件里已经更新到 10/10。

更隐蔽的变体是"流程走过场"：代理确实派了 subagent、确实跑了多 lens 审查、确实输出了 findings 报告，但 subagent 的声明没有附工具调用证据——"目录存在"是嘴上说的、"文件已修改"是嘴上说的、"路径正确"是嘴上说的。看起来走完了流程，实际上每一步都是空头支票。下一轮追查才发现，声明的修改根本没落地，工具调用静默失败了，代理却照搬了"成功"的结论。

讽刺的是，这套方法论本身第一次沉淀成教学材料时，也栽在了这个陷阱里——DRL 真循环在自我证明的过程中再次假收敛。方法论不是写下来就成立了，它必须在每一次执行中重新被验证。

### 三类陷阱的共性

把这三类陷阱放在一起看，能发现一个共同的结构：**它们都是在"成本最低的环节"上做结论**。文本检索比深度审查便宜，所以代理倾向用检索下结论；自我验证比派独立审计便宜，所以代理倾向自己点头；流程走过场比真做 spot-check 便宜，所以代理倾向走形式。假收敛不是代理的恶意，而是成本结构在推着它走捷径。

识别这三类陷阱的信号也很一致：只要审查报告里出现"全部"、"已通过"、"零问题"这类绝对化措辞，却没有附上对应的工具调用证据，基本就可以怀疑是假收敛。真收敛的报告永远是具体的——具体到每一轮的计数、具体的证据链、具体的 residual risk，而不是一个抽象的"完成"。

| 陷阱类型 | 表现形式 | 根因 | 识别信号 |
|:---|:---|:---|:---|
| 单路快速审查 | 用文本检索判定 0 问题 | 必要条件当充分条件 | 验证手段语义强度 < 结论强度 |
| 跳过重新审查 | 修复后自验证即报通过 | 修复者与验证者共享上下文 | 无独立审计环节 |
| 流程走过场 | 声明一次通过但无 spot-check | 声明未附工具调用证据 | 报告无证据链、含绝对化措辞 |

### 陷阱与判据的对应关系

这三类陷阱不是孤立存在的，它们和后面的四个收敛判据、4 层过拟合防护有明确的对应关系。理解这种对应，能帮读者在遇到具体陷阱时知道该用哪条判据来防御。

- **陷阱 1（单路快速审查）** 主要靠判据 2（重新审查零问题）防御——只要强制跑独立重新审查，单路验证的盲点就会被突破。同时层 4（严重度门槛）的 class-level 升级也能把单路验证漏掉的类问题从噪音里捞出来。
- **陷阱 2（跳过重新审查）** 主要靠判据 2 + 判据 3（收敛曲线记录）双重防御——判据 2 强制要求重新审查，判据 3 通过收敛曲线的形态暴露"R2 跳过重新审查直接报 0"的异常。层 3（过拟合警报）的回归率监控也能发现修复引入的回归。
- **陷阱 3（流程走过场）** 主要靠判据 3 + checklist 第 4 条（verifier 必须附工具调用证据）防御——判据 3 要求每轮单独记录，checklist 第 4 条要求"0 finding 也要附证据"，两者共同把"流程走过场"挡在门外。

看到这种对应关系就能理解：DRL 的四条判据和 4 层防护不是堆砌的清单，而是针对三类典型陷阱的精准防御。每一条判据、每一层防护都有它要拦的具体陷阱，不存在"为了完整而完整"的冗余。

## 二、真循环的四个收敛判据

要区分"假收敛"和"真收敛"，不能靠代理的自我感觉，必须靠客观判据。DRL 给出四条硬性判据，缺一不可。这四条判据的共同精神是：**收敛不是一个状态，而是一段可追溯的过程**。

### 判据 1：问题数严格单调递减到 0

每一轮审查的 P0/P1/P2/P3 计数必须**单调不增**，最终归零（或在允许残留的阈值内）。任何一轮出现反弹——比如 R2 比 R1 多了一条 P1——立刻判定未收敛，必须回到审查阶段。

单调性是收敛的必要条件，但它不是充分条件。单调递减可能只是修复在"打地鼠"：每修一个冒出两个，恰好净减少一条，看起来在收敛，实际在漂移。所以还需要判据 2。

实操中，单调性的检查要看每一轮的完整计数，不能只看 P1 或只看总数。我们见过这样的案例：P1 从 7 降到 0 看起来很漂亮，但 P2 从 3 涨到了 8——代理把 P1 问题"降级处理"成了 P2，本质问题没解决，只是换了分类。单调性必须四档同时检查，任何一档反弹都算未收敛。

### 判据 2：重新审查仍未发现新问题（连续 N≥2 轮零问题）

真正收敛的标志不是"某一轮报了 0"，而是"下一轮**独立重新审查**依然报 0"。连续 N 轮（N≥2）深度审查均 0 问题，才算真收敛。

这里的关键是"**独立重新审查**"——不能复用上一轮的上下文，不能只是"复核上一轮的结论"，必须是带着怀疑重新过一遍。如果跳过这一步，所谓的"0 问题"很可能只是上一轮的盲点未被突破。

"独立"两个字是这条判据的灵魂。它意味着重新审查的代理不能看上一轮的审查报告、不能继承上一轮的修复思路、不能用上一轮的验证路径——它要像第一次见到这个产物一样，从头到尾重新审一遍。只有这样，才能突破上一轮的盲点。如果"重新审查"只是让另一个代理读一遍旧报告然后点头，那它什么也审不出来。

### 判据 3：收敛曲线单独记录，不允许只报最终"0 问题"

每一轮的问题数必须**单独记录**在收敛曲线里，标注假收敛/真收敛状态。任何只报"最终 0 问题"的做法都被视为不合规——因为收敛的过程信息比结果更重要，过程才暴露了是否真的走过完整循环。

标准收敛曲线长这样：

| 轮次 | P0 | P1 | P2 | P3 | 状态 |
|:---:|:---:|:---:|:---:|:---:|:---|
| R1a | 0 | 7 | 8 | 0 | 审查 |
| R2  | 0 | 0 | 3 | 0 | 接受残留 A2=3 |
| R3  | 0 | 0 | 0 | 0 | 真收敛 |

如果只有最后一行"R3=0"而没有前面几轮的过程，那基本可以判定这是一个被美化过的报告，背后大概率藏着假收敛。

收敛曲线还有一项关键字段：**接受残留标注**。当某条问题被边际收益 gate 判定为"接受残留"时，必须用 `接受残留=P1:A1/P2:A2` 的格式显式记录，A1 是被采纳的 P1 残留数、A2 是被采纳的 P2 残留数。这条字段是后续判定过拟合警报是否触发（见层 3）的关键证据——没有它，就无法区分"我们决定接受残留"和"我们修不动残留"。

### 收敛曲线示例详解

光看一条标准曲线不够，下面用三种典型形态帮读者建立对收敛曲线的直觉。

**形态 A：理想真收敛**

| 轮次 | P0 | P1 | P2 | P3 | 状态 |
|:---:|:---:|:---:|:---:|:---:|:---|
| R1a | 0 | 7 | 8 | 0 | 审查 |
| R2  | 0 | 0 | 3 | 0 | 接受残留 A2=3 |
| R3  | 0 | 0 | 0 | 0 | 真收敛 |

每一轮单调不增，R3 真收敛，R2 的 3 条 P2 通过边际收益 gate 显式接受残留。这是教科书式的形态。

**形态 B：假收敛反弹**

| 轮次 | P0 | P1 | P2 | P3 | 状态 |
|:---:|:---:|:---:|:---:|:---:|:---|
| R1a | 0 | 5 | 4 | 0 | 审查 |
| R2  | 0 | 0 | 2 | 0 | 声称真收敛（**假收敛**） |
| R3  | 0 | 4 | 3 | 0 | 反弹——重新审查发现新问题 |
| R4  | 0 | 0 | 0 | 0 | 真正真收敛 |

R2 报了"真收敛"但跳过了独立重新审查，R3 重新审查立刻反弹出 4 条 P1。这种形态的警示在于：**R2 的"0"不可信**，因为它没有走过独立重新审查。看到这种曲线，应该立刻追问 R2 是怎么得出"真收敛"结论的——大概率是陷阱 2 或陷阱 3。

**形态 C：震荡过拟合**

| 轮次 | P0 | P1 | P2 | P3 | 状态 |
|:---:|:---:|:---:|:---:|:---:|:---|
| R1a | 0 | 6 | 5 | 0 | 审查 |
| R2  | 0 | 2 | 7 | 0 | P1 降但 P2 涨 |
| R3  | 0 | 3 | 4 | 0 | P1 反弹 |
| R4  | 0 | 1 | 6 | 0 | 触发 STOP（震荡 3 轮不单调） |

P1 和 P2 交替涨跌，3 轮不单调，触发层 3 警报。这种形态说明代理在打地鼠，根因没找到，必须 STOP 重新理解问题，而不是继续修。看到这种曲线，应该立刻停手，重新分析问题的根因——通常是审查 scope 错了，或者修复策略本身在制造新问题。

三种形态覆盖了收敛曲线的绝大多数情况。把它们记在脑子里，看到任何一条收敛曲线都能快速判断它是真收敛、假收敛还是过拟合——这比看任何文字描述都直观。

### 判据 4：4 层过拟合防护全部通过

即使前三条都满足，也不能直接判收敛——还要过 4 层过拟合防护（详见下一节）。过拟合是收敛的另一面：问题数确实降到 0 了，但降到 0 的方式可能是"为了清零而清零"，把本应保留的合理性也一起修掉了，或者残留的少量问题被错误地清零。4 层防护就是收敛的"质量门"。

这条判据的存在，是因为我们见过太多"完美但错误"的收敛——代理为了把 P2 清零，把本该保留的设计也改掉了；为了让回归率好看，把本该上报的 P3 全部隐藏了；为了单调递减，把问题严重度往下压。4 层防护挡住的就是这些"看起来收敛、实际走偏"的情况。

### 四条判据的关系

这四条判据不是并列的清单，而是一个层层递进的判定逻辑：判据 1（单调性）是**形式**要求，保证收敛的形态正确；判据 2（重新审查零问题）是**实质**要求，保证收敛不是自我感觉；判据 3（收敛曲线记录）是**过程**要求，保证收敛可追溯；判据 4（4 层防护）是**质量**要求，保证收敛不过拟合。

形式、实质、过程、质量——四者缺一不可。只有形式没有实质，是漂亮的假收敛；只有实质没有过程，无法验证是否真收敛；只有过程没有质量，可能修到走偏。把它们组合起来，才能把"收敛"从一个模糊的口头结论，变成一个可以被外人审视、可以被同行复现的工程判断。

## 三、过拟合防护：4 层防御体系

收敛不是越快越好，更不是越彻底越好。如果把所有 P2 都强行修到 0，修复成本可能远超问题危害，甚至引入新的回归——这就是过拟合。DRL 用 4 层防御来兜底，每一层都对应一种典型的过拟合形态。

### 层 1：P2 残留 N 规则

按严重度分级处理，**P0/P1 必须降到 0**，这是硬性底线；**P2 允许残留 N 条**，N 的上限按项目阶段动态调整；**P3 不计入收敛判定**，只记录到 backlog。

| 项目阶段 | P2 残留上限 N_max |
|:---|:---:|
| 比赛级 / 高可靠场景 | 0 |
| 生产 | 3 |
| 原型 / 探索 | 10 |

分级的逻辑是：不同阶段对"完美"的容忍度不同。比赛场景里一条 P2 可能就是分差，必须清零；原型阶段追每一条 P2 会拖死迭代节奏。把 N_max 显式写出来，避免代理自行其是地"全部修"或"全部留"。

为什么 P0/P1 是硬底线？因为这两档对应的是"事实错误"和"功能性缺陷"，留着就是事故。P2 对应的是"体验问题"或"次要瑕疵"，留着最多是难看。P3 对应的是"风格建议"或"优化机会"，留着完全不影响交付。把严重度和处理策略绑定，才能避免代理在低价值问题上空耗资源。

**实施提示**：N_max 的选定必须在审查开始前就明确，不允许在审查过程中调整——否则代理会把"修不动"的问题事后降级成"接受残留"。建议在每次审查启动时把 N_max 写进 prompt，让代理从一开始就知道边界。如果项目阶段发生切换（比如从原型进入生产），下一轮审查开始前显式更新 N_max，并记录切换原因。

### 层 2：边际收益 gate

当某条问题的修复成本明显高于问题本身的危害时，**接受残留**比强行修复更优。规则很朴素：**修复成本 > 问题危害 × 3 → 接受残留**。

接受残留必须有显式标注，格式为 `接受残留=P1:A1/P2:A2`，其中 A1 是被 gate 采纳的 P1 残留数，A2 是 P2 残留数。A1>0 才允许 P1 持平，A2>0 才允许 P2 持平。这条标注会写进收敛曲线，作为后续判定的证据。

为什么这一层重要？因为代理在追求"清零"时往往会过度修复——一个无关紧要的措辞问题，重写整段逻辑，结果引入两条新 P1。边际收益 gate 把"修复值不值"这个判断显式化，挡住过度修复。

这条 gate 也保护团队不被"完美主义"绑架。在真实项目里，时间是有成本的，一次重构可能花掉半天，而那条 P2 问题的影响是"用户偶尔看到一行排版略偏"。这种时候接受残留、把时间花在更高价值的修复上，才是工程上正确的选择。但**接受残留必须显式、可追溯**——悄悄留下和明确决定是两回事，前者是失控，后者是策略。

**实施提示**：成本和危害的估算不需要精确到数字，但要给出相对量级。比如"修复需重写整段逻辑（约 2 小时），危害是罕见路径下的视觉错位（用户感知概率 < 1%）"——这种描述足以支撑"成本 > 危害 × 3"的判断。关键不是数字，是判断过程被显式记录下来，可以被同行审视。如果一条残留没有附带成本/危害估算，就视为未走过 gate，不允许接受。

### 层 3：过拟合警报

即使前两层都过了，还要盯住**收敛的形态**。两种形态触发 STOP 报告，强制暂停修复：

- **震荡 3 轮不单调**：问题数上上下下，说明在打地鼠，根因没找到
- **回归率 > 30%**：每修一批就冒出一大批新问题，说明修复本身在制造问题

STOP 不是放弃，是强制停下来重新理解问题——通常是审查 scope 错了、修复策略错了、或者根因被掩盖了。继续修下去只会越修越乱，不如回到原点重新分析。

**警报 A 例外条款**：边际收益 gate 采纳的残留导致的 P1/P2 持平不触发警报 A。换言之，"我们决定接受这几条残留"和"我们修不动这几条问题"是两回事，前者是策略，后者是失控。收敛曲线里的 `接受残留=P1:A1/P2:A2` 字段就是区分两者的证据——有这条字段，说明持平是策略选择；没有这条字段，说明持平是真修不动，警报该响就响。

这条例外条款的存在，是为了让团队敢于接受残留。如果没有例外，团队为了避免警报会强行修复所有问题，反而落入过拟合陷阱。例外条款把"策略性持平"和"失控性持平"显式区分开，既守住了警报的灵敏度，又给策略性判断留了空间。

**实施提示**：STOP 触发后的处理流程要事先约定，不能临时决定。建议的处理路径是：STOP → 主代理重新分析根因（不带修复任务，只做诊断）→ 重新定义审查 scope 或修复策略 → 重新启动 R1a。常见的根因有三类：审查 scope 太窄（漏看了相关文件）、修复策略太激进（一次改太多）、问题分类错了（把类问题当 instance 处理）。STOP 不是失败，是把潜在的灾难性漂移拦在早期。

### 层 4：严重度门槛

**P3 及以下不报**，避免审查被低价值噪音淹没。但有一条关键例外——**class-level instance 升级**：如果同一个 pattern 出现了哪怕 1 个 instance，就整体升级为 P2 处理。

为什么要升级？因为"类问题"的破坏力不在于单个 instance，而在于 pattern 本身。如果只看 instance 数量，一个渗透到几十处的设计缺陷可能被低估为"P3 几条小事"，而实际上它代表的是一类需要系统性修复的问题。class-level 升级把这类问题从噪音里捞出来，强制进入收敛判定。

举一个通用化例子：代理在某个产物里发现一处"计数器未同步"问题，看起来是单点 P3。但如果同一个"未同步"的 pattern 在多处都出现了，那它就不是单点问题，而是一个系统性的同步机制缺陷——必须升级为 P2，按类处理，而不是按 instance 处理。class-level 升级挡住的就是"用 instance 数量低估类问题"的盲点。

**实施提示**：class-level 的判定要看 pattern 的"语义共性"，而不是"字符串相似"。两个 instance 字符串相似但语义不同（比如同名但不同上下文），不算 class；两个 instance 字符串不同但语义同源（比如不同文件里的同一种同步缺陷），算 class。判定的标准是"如果修一个，要不要顺带修另一个"——答案是"要"，就是 class-level；答案是"不要"，就是独立 instance。这条判定需要人类工程师或主代理的语义判断，不能简单交给文本相似度。

### 4 层防御的协同

这 4 层不是互相替代，而是层层协同：层 1 解决"修到什么程度算够"，层 2 解决"什么时候该停手"，层 3 解决"什么时候该报警"，层 4 解决"什么该报、什么该忽略"。少了任何一层，过拟合就会从那个缺口钻进来——只有层 1 没有层 2，团队会为了清零过度修复；只有层 2 没有层 3，团队会忽略震荡信号；只有层 3 没有层 4，团队会被低价值噪音淹没，看不到真正重要的类问题。

把 4 层放在一起，它们其实回答的是一个更朴素的问题：**"修到 0"和"修对了"是不是一回事？** 答案是不一定。修到 0 可能是修对了，也可能是过度修复、隐藏问题、低估类问题。4 层防御的存在，就是为了把"修到 0"和"修对了"重新对齐——让前者成为后者的充分条件，而不是一个看起来像后者的假象。

## 四、可复用的 DRL 执行清单

把上面的方法论压成一份可以直接照着跑的 checklist。每一条都是硬性要求，违反任意一条都可能导致假收敛。建议把它贴在团队 wiki 里，每次 AI 代理协作的审查环节开始前过一遍。

1. **修复前 Preflight**：派 subagent 修复前，主代理先用工具验证关键事实（人物关系/数据归属/事件顺序等），并在 subagent prompt 里写明"仅修改指定文件、不得触碰 scope 外文件"的 scope-lock 约束。
2. **R0 surface check**：file size 验证（声称写入的文件实际存在且大小合理）+ verdict 字眼检索（禁词：完成 / PASS / 闭环 / OK / 没问题 / looks good）+ 路径验证（声称修改的路径实际存在）。
3. **R1a 三独立 verifier 并行交叉验证**：派 3 个 subagent 并行，分别从 Factual（事实是否准确）、Completeness（是否遗漏）、Reusability（是否可复用）三个 lens 审查，每个 lens 输出 P0/P1/P2 findings。
4. **verifier 必须附工具调用证据**：目录存在性声明必须附 LS、文件存在性声明必须附 Read/LS、路径声明必须附 Read，**0 finding 也要附证据**——没有证据的"0"等于没审查。
5. **R1b 对抗性 subagent 审查**：派 1 个 subagent，**默认 refuted=true**（默认推翻主代理声明）+ class-level scope + 严重度门槛（层 4）。它的任务不是确认主代理，而是尽力推翻主代理。
6. **R2 独立审计必须 NOT inline**：R2 不能基于主代理上下文，必须用独立视角重新审查，**不能因为 R1b 报了 0 finding 就跳过 R2**。R2 的价值在于独立视角 + 边际收益 gate。
7. **修复后必跑 R2 重新审查**：每一轮修复后都不能直接进入残余风险确认，必须重新跑独立审计。修复可能引入回归（典型：短路子 clause 副作用），不重新审查就无法发现。
8. **收敛曲线每轮单独记录**：每一轮的 P0/P1/P2/P3 计数 + 状态（审查 / 假收敛 / 真收敛 / 接受残留）必须单独记录，不允许只报最终"0 问题"。
9. **P0/P1 必降到 0，P2 残留不超过 N_max**：按项目阶段查 N_max 表（比赛级 0 / 生产 3 / 原型 10），P3 不计入收敛判定，但 class-level instance 例外升级 P2。
10. **边际收益 gate 评估修复成本 vs 问题危害**：修复成本 > 问题危害 × 3 时接受残留，并显式标注 `接受残留=P1:A1/P2:A2` 写入收敛曲线。
11. **过拟合警报触发即 STOP**：震荡 3 轮不单调或回归率 > 30% 立即 STOP 报告，暂停修复重新理解问题；接受残留导致的持平不触发警报（例外条款）。
12. **R3 残余风险确认 ≥ 3 项 + 收敛曲线归档**：列出至少 3 项残余风险（如 subagent 盲点 / 采样时间点 / 跨 session 一致性），连同完整收敛曲线一并归档，作为收敛的可追溯证据。
13. **verdict 字眼禁令**：报告中禁用"完成 / PASS / N/N / 闭环 / OK / 没问题 / looks good"，替换为具体数据 + 实证——"完成" → "P0=0 P1=0 P2=0 三零达成"，"PASS" → 列具体数据 + 实证，"闭环" → 列收敛曲线 + residual risk，"OK" → 列具体验证命令 + 输出。

这 13 条里，最容易被忽视的是第 4 条（0 finding 也要附证据）和第 7 条（修复后必跑 R2）。前者是因为"0"是最需要证据支撑的结论——一个没有证据的"0"等同于没审；后者是因为"修复"和"收敛"之间隔着回归这道暗河，不重新审查就跨不过去。如果只能记住两条，记住这两条。

### 13 条 checklist 的流程归属

为了方便理解，把 13 条按 DRL 流程阶段归类一下：

| 流程阶段 | 对应条目 | 核心动作 |
|:---|:---|:---|
| 修复前 | 第 1 条 | Preflight 事实核验 + scope-lock |
| R0 surface check | 第 2 条 | 文件存在性 + verdict 禁词 + 路径验证 |
| R1a 三 verifier | 第 3、4 条 | 3-lens 并行审查 + 工具调用证据 |
| R1b 对抗性审查 | 第 5 条 | 默认推翻主代理声明 |
| R2 独立审计 | 第 6、7 条 | NOT inline + 修复后必跑 |
| 收敛记录 | 第 8、12 条 | 收敛曲线 + 残余风险归档 |
| 过拟合防护 | 第 9、10、11 条 | P2 残留 + 边际收益 gate + 警报 STOP |
| 通用规范 | 第 13 条 | verdict 字眼禁令 |

从这个分类能看出，DRL 的流程是有顺序的——从修复前 Preflight 到 R0/R1a/R1b/R2/R3，每一阶段都有对应的硬性要求。如果某一条没做，对应的流程阶段就等于没走完，整个 DRL 就不成立。把这张表和前面的 13 条对照着看，能更快建立对完整流程的直觉。

### 如何使用这份清单

这份清单不是要逐条对照打勾就走形式，而是要把它当作审查环节的"硬约束"——任何一条不满足，对应的审查结论就不成立。建议的使用方式是：

- **审查环节开始前**：把清单贴在 prompt 里，让代理在每一轮审查结束时自查 13 条是否全部满足，任何一条不满足必须在报告里显式标注"未满足第 X 条"。
- **审查报告提交时**：报告必须包含"13 条合规性自检"段落，逐条标注满足/未满足 + 证据链接。没有这一段的报告，视为未完成审查。
- **收敛判定时**：判据 1-4 的满足情况必须显式列出，不允许只写"已收敛"。收敛曲线、4 层防护、13 条合规性自检，三者缺一不可。

### 常见反模式

照着这份清单跑，也容易踩到几个反模式。第一个反模式是**清单形式主义**——逐条打勾但没真正理解每条的含义，比如第 4 条"附工具调用证据"被理解为"截图一下工具调用记录"，而没有验证证据是否支撑结论。第二个反模式是**选择性执行**——只执行容易的几条（比如 R0 surface check、verdict 字眼禁令），跳过费时的几条（比如 R2 独立审计、R3 残余风险确认），最终产出一份看起来合规但实际残缺的审查报告。第三个反模式是**收敛曲线伪造**——把多轮审查的计数事后倒推填进表格，而不是实时记录，这会让收敛曲线失去"过程证据"的价值。

这三种反模式的共同点是：**把方法论当成了产出物，而不是过程**。方法论的价值不在于产出一份漂亮的报告，而在于真正走过那个审查→修复→重新审查的循环。如果只想要报告，那直接让代理写一份"已通过"就行了，何必走 DRL。

## 五、方法论边界与适用场景

任何方法论都有边界，DRL 也不例外。把它用在不该用的场景，会拖慢迭代；该用却没用，又会埋下假收敛的雷。这一节说清楚 DRL 适用什么、不适用什么，以及实施的成本考量。

### 适合 DRL 的场景

DRL 的核心价值在于"防止假收敛"，所以它最适合的场景是**收敛失败代价高、回归影响大**的产物。典型包括：

- **面向外部发布的内容**：技术文档、教学材料、对外分享文章——这类产物一旦出现事实错误或链接失效，损失的是读者信任，难以挽回。
- **跨多文件的系统性改动**：重构、API 改造、配置迁移——这类改动回归面广，单点审查看不到全貌，必须靠独立重新审查才能发现跨文件影响。
- **长周期 AI 协作项目的关键交付**：经过多轮迭代的产物，每一轮都可能积累隐性回归，必须在交付前跑一次完整 DRL 把回归压出来。
- **事实密度高的内容**：人物关系复杂、数据归属多源、引用密集——这类内容假收敛概率最高，因为代理容易在事实核验上走捷径。

### 不适合 DRL 的场景

反过来，有些场景上 DRL 是过度工程，反而拖慢迭代节奏：

- **探索性原型 / Spike**：本来就是试错，错误成本极低，跑完整 DRL 比直接重写还慢。
- **一次性脚本 / 临时工具**：用完即弃，不需要长期维护，跑 DRL 的成本远大于问题危害。
- **低事实密度的创意写作**：诗歌、小说片段——这类产物的"正确性"标准本就主观，强行用 P0/P1/P2 分级反而会扼杀创意。
- **极小改动**：改一个错别字、调一行样式——单点验证就够了，派 3 个 subagent 并行审查是杀鸡用牛刀。

判断标准其实很简单：**问自己"如果这个产物假收敛了，最坏会怎样"**。如果答案是"返工一次、影响不大"，那不需要 DRL；如果答案是"事故、丢信任、长期隐患"，那就必须上 DRL。

### 实施成本考量

DRL 不是免费的。完整跑一轮 DRL，至少要派 3 个 R1a verifier + 1 个 R1b 对抗性 subagent + 1 个 R2 独立审计 + R3 残余风险确认，加上收敛曲线记录和 13 条合规性自检，单次成本不低。这个成本换来的是"假收敛被拦下"，值不值要看场景。

在成本敏感的场景里，可以做一个**轻量化变体**：保留判据 2（重新审查零问题）和层 3（过拟合警报）作为硬底线，其他几层按需简化。这样虽然牺牲了一部分防护强度，但保留了 DRL 最核心的"重新审查"精神。需要警惕的是，轻量化变体一旦常态化使用，容易慢慢退化成"只跑 R1b 就报通过"的形式主义——所以建议定期用完整 DRL 校准一次，避免轻量化变体漂移。

最后要强调一点：**DRL 不是替代人类 code review，而是补充**。它擅长的是把"审查"这个动作从模糊的口头流程，变成可执行、可追溯、可复现的工程动作；但它不擅长判断"这个设计是不是对的"、"这个 trade-off 是否合理"——这些判断仍然需要人类工程师的领域知识和经验。把 DRL 当成"代理审查的工业化流水线"，把人类 review 当成"价值判断的最后把关"，两者配合，才是 AI 代理协作时代审查环节的完整图景。

## 总结

回到开头的那个问题：代理报告"已修复，验证通过"，你信吗？

如果它走的是单次线性流程——审查、修复、自己验证自己——那答案是不该信。**修复者和验证者如果是同一个上下文，所谓的"验证"只是自我确认**，盲点会沿同一套思路被继承下来，假收敛几乎是必然结果。这不是代理"不诚实"，而是流程的结构性缺陷——任何把审查权和修复权交给同一个上下文的流程，都会产出看起来漂亮、实际站不住的"通过"结论。

DRL 真循环的核心不在于"审查"本身，而在于"**重新审查**"。修复之后必须派一个独立的、不基于主代理上下文的视角重新过一遍；这个重新审查不能因为上一轮报了 0 就跳过，恰恰相反，上一轮报 0 正是重新审查最该出场的时候——因为假收敛就藏在那个"0"里。连续 N 轮（N≥2）独立重新审查均 0 问题，才是真收敛。重新审查不是流程的重复，而是流程的进阶——它要突破的不是新问题，而是上一轮的盲点。

但光有重新审查还不够，还要防过拟合。4 层防护——P2 残留 N 规则、边际收益 gate、过拟合警报、严重度门槛——把"清零"和"该清零"区分开来。不是所有问题都值得修，强行清零可能引入更多回归；但接受残留必须显式标注、可追溯，不能悄悄留下。收敛的形态比收敛的速度更重要，震荡和回归率是过拟合最可靠的信号。一套好的方法论不是逼团队修到极致，而是让团队在"修"和"留"之间做出有据可查的判断。

把这套判据、防护和 checklist 落到每一次 AI 代理协作里，你才能真正区分"代理说修好了"和"代理真的修好了"。在一个 AI 代理越来越深度参与工程实践的时代，这个区分决定了你是被代理推进度，还是被代理推下坑。每一次假收敛的代价，最终都是由人来承担的——可能是你，可能是你的团队，可能是生产环境里的真实用户。把"重新审查"写进流程，就是把这种代价提前拦下。

需要提醒一点：不要试图一上来就把整套 DRL 全部铺开。完整的 13 条 checklist + 4 层防护 + R0-R3 流程，对任何团队都是一次不小的流程改造。建议的落地路径是分三步走：第一步，先在最高价值场景（比如对外发布内容、跨多文件重构）上引入判据 2（重新审查零问题）和层 3（过拟合警报）这两条硬底线，让团队先习惯"重新审查"这个动作；第二步，把收敛曲线记录作为强制要求嵌入到每一次审查报告里，让"过程可追溯"成为团队共识；第三步，再逐步把 4 层防护和完整 R0-R3 流程补齐。这三步走完，通常需要几个迭代的磨合，但每一步都会立刻看到假收敛被拦下的效果，比一次性铺开更容易被团队接受。

还有一点容易被忽略：**更强的代理也会假收敛**。不要以为换了一个更强的模型，假收敛就消失了——它只是变得更隐蔽。强模型的假收敛往往藏在更流畅的报告、更完整的证据链、更合理的措辞背后，让人更难察觉。所以 DRL 不是"给弱代理兜底"的补丁，而是"给所有代理兜底"的结构性流程。模型能力越强，假收敛的伪装越精致，DRL 的价值反而越高。

最后，**重新审查才是真审查**。这不是一句口号，而是一整套可执行的判据、防护和 checklist。它要求我们放弃"一次通过"的幻觉，接受"收敛是一个过程而不是一个状态"的现实，并且愿意为这个过程付出它本该有的成本——多派一个独立视角、多跑一轮重新审查、多记一条收敛曲线。这些成本远小于一次假收敛带来的返工和事故。

也要承认这套方法论的局限：它防的是"流程性假收敛"，不防"语义性错误"——如果代理把一个错误的设计从头到尾一致地执行下来，每一轮重新审查都会判定它"通过"，因为它在流程上确实没有问题，问题在更上游的设计判断上。这种语义性错误只能靠人类工程师的领域知识、靠设计阶段的提前 review、靠对产物的真实使用反馈来发现，DRL 帮不上忙。把 DRL 当成银弹是危险的，把它当成"防止流程性假收敛"的精准工具，才是它的正确位置。

把这套方法论分享出来，是希望它能在更多 AI 代理协作场景里被使用、被检验、被迭代。如果它在你的团队里跑出了新形态的假收敛、或者某一条判据被证明可以简化、又或者某个场景下它过度工程了——这些都欢迎反馈。方法论的生命力不在文档里，在每一次实战的检验里。

回到最开始那个问题——"代理报告已修复，你信吗"。读完这篇文章，希望你的答案从"信"或"不信"的二元判断，变成"它走没走过 DRL、收敛曲线长什么样、4 层防护过了没"。当判断标准从感觉变成证据，假收敛就无处藏身了。
