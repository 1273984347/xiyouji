# 可视化测试计划——复杂 D3.js 可视化的四层测试体系
> 轨标：外部分享

## 引子

你做了一个复杂的 D3.js 可视化：几十个节点、数百条边、多个交互维度，力导向图、桑基图、雷达图、时间线并存在同一个页面里。本地跑起来很美，QA 一打开就崩了——空数据时 SVG 报错、移动端布局溢出、桑基图依赖加载失败时整页白屏、键盘用户无法触发 tooltip。这些 bug 大多不是逻辑错，而是边界场景没覆盖、四层测试没成体系。

可视化测试的难处，从来不是"写不出测试"，而是"不知道该测什么"。普通的单元测试只关心输入与输出的函数关系，可视化的输出却是像素、是 DOM 结构、是交互序列、是动画时序。一个 force simulation 节点的坐标是非确定性的，一个 tooltip 的位置依赖鼠标事件——这些都不适合用传统的断言去捕捉。

更麻烦的是，可视化的"正确"常常是契约性的：颜色映射是否与类别一致？数据维度数量是否与 KPI 卡片一致？排序规则是否与表头点击行为一致？这些是数据契约，不是视觉契约，但又必须在视觉层被验证。

本文沉淀一套在多个复杂可视化项目中反复打磨的四层测试体系——数据层、渲染层、交互层、视觉回归层——并把复杂可视化最容易踩的边界场景提炼成可复用清单。读者对象是前端工程师、可视化工程师与测试工程师。

需要说明的是，这套体系不绑定具体框架。文中的例子多用 D3.js 与 Playwright，但同样的四层划分也适用于 ECharts、Vega-Lite、Observable Plot，甚至 React/Vue 组件化的可视化。方法论是通用的，工具是可替换的。

## 一、可视化测试的独特挑战

可视化测试与普通单元测试的差异，可以从四个层面去理解。

### 视觉层

布局、颜色、尺寸——这些是可视化的"脸"。但像素级断言极易碎：字体渲染差异、子像素抗锯齿、浏览器版本差异都会让截图 diff 失败。正确做法是断言"结构存在"而非"像素一致"：力导向图里有 N 个 circle、N 条 line、N 个 text；桑基图里有 path 与 rect；雷达图里有 polygon。像素一致交给视觉回归层处理。

### 交互层

hover、click、drag、zoom——这些是可视化的"活"。但交互测试常常被忽略：表头点击排序是否生效？Enter/Space 是否触发同一行为？Space 是否会意外滚动页面？拖拽节点是否有键盘替代路径？这些不只是功能测试，更是无障碍测试。WCAG 2.1 SC 2.5.7 明确要求拖拽必须有键盘替代。

### 数据层

数据流、边界值、异常数据——这些是可视化的"骨"。可视化的崩溃，80% 来自数据：边的 source/target 指向不存在的 id；颜色字段与类别映射漂移；空数组触发 `||` fallback 的语义陷阱（空数组 truthy，`x || default` 不会兜底）；KPI 卡片数字与实际数据量不一致。这些都不是渲染问题，是数据契约问题，必须在数据层就被拦截。

### 性能层

大量节点、动画流畅度——这些是可视化的"气"。力导向图在 500 节点时是否还能稳定？动画在低端设备上是否掉帧？reduced-motion 下是否跳过动画？这些问题既影响体验也影响测试稳定性。force simulation 持续 tick 时截图，每次都会不一样——必须等 `alphaTarget(0)` 稳定后再断言。

这四层并非孤立。一个"颜色映射漂移"的 bug，可能是数据层的 color 字段错（数据层测），也可能是渲染层的配色函数错（渲染层测），还可能是视觉层的截图 diff 才看出来（视觉回归层测）。四层是互相补位的网，不是互相替代的锁。

## 二、四层测试体系

### 第一层：数据层测试（输入数据校验）

数据层测试不依赖浏览器，纯逻辑断言。它是最廉价也最高 ROI 的一层。核心校验范围：

- **顶层 key 完备性**：数据对象的所有必需字段都存在
- **字段类型与值域**：数值字段在合法区间（如评分 1-10、强度 1-100）
- **引用完整性**：所有边的 source/target 都在节点 id 集合内
- **唯一性**：节点 id 唯一、关联实体 id 唯一
- **枚举校验**：边的类型字段必须是预定义枚举之一
- **结构校验**：层级数据（如桑基图的 source → mid → target）的层级关系正确
- **颜色一致性**：节点的 color 字段与类别配色映射一致
- **KPI 一致性**：页面上的 KPI 数字（"X 维度"、"Y 关联"）与数据实际数量一致

数据层测试用正则解析 HTML 内嵌数据或直接读 JSON 即可，不需要 Playwright。这是 P0，必须最先实现。

### 第二层：渲染层测试（DOM/SVG 结构验证）

渲染层测试用 Playwright 启动浏览器，断言 DOM/SVG 结构而非像素。核心断言：

- **SVG 非空**：每个 SVG 里都有期望数量的元素（circle/line/path/rect/polygon/text > 0）
- **卡片渲染数量**：dim-card 的 DOM 节点数与数据量一致
- **表格渲染行数与列数**：summary-table 的行数、表头列数与数据一致
- **降级防御**：mock 库加载失败（如 `delete window.d3.sankey`）后，渲染函数应输出降级文案而非抛错
- **协议分支**：`file://` 协议下不应发起数据 fetch（否则会 404）
- **响应式断点**：375px 下网格 1 列、768px 下 2 列、1200px 下 4 列

渲染层测试是 P1。它捕捉"渲染崩溃"类问题，但不捕捉"像素漂移"。

### 第三层：交互层测试（用户操作模拟）

交互层测试模拟真实的用户行为序列。核心断言：

- **click 触发**：卡片 click 后 tooltip 出现且内容正确
- **键盘等价**：Enter 与 Space 都能触发同一行为；Space 不应滚动页面（preventDefault）
- **排序交互**：表头 click 后行顺序变化（升序↔降序）；表头 Enter/Space 同样生效
- **hover 反馈**：节点 hover 后 tooltip 出现
- **跨组件协调**：resize 触发 debounce 后所有 render 函数重渲染
- **键盘退出**：tooltip 应支持 ESC 关闭（这是常见缺口）

交互层测试也是 P1。它捕捉"功能回归"与"无障碍回归"。

#### 无障碍合约

复杂可视化的无障碍常常是重灾区。交互层测试应覆盖以下 WCAG 合约：

- **键盘可达**：所有交互元素（卡片、节点、表头）都可 Tab 到达，focus 可见
- **键盘等价**：click 行为必须有 Enter/Space 等价；Space 不应意外滚动页面
- **拖拽替代**：WCAG 2.1 SC 2.5.7 要求拖拽有键盘替代路径（如方向键移动节点）
- **ESC 关闭**：tooltip、modal 等浮层应支持 ESC 主动关闭，不能只靠自动隐藏
- **ARIA 角色**：tooltip 应有 `role="tooltip"` + `aria-live`；SVG 应有 `role="img"` + `aria-label`
- **对比度**：文字与背景对比度达 AA 标准（4.5:1 普通、3:1 大字号）
- **冗余编码**：颜色不应是唯一区分维度，应有文字标签或图案补充

### 第四层：视觉回归测试（截图对比）

视觉回归测试是 P2，也是最贵的一层。它捕捉前三层都漏掉的"像素漂移"。核心做法：

- **基线建立**：先在固定 viewport（如桌面 1280×800、移动 375×667）下截图作为基线
- **稳定后截图**：force simulation 必须等 `alphaTarget(0)` 稳定后再截，否则每次都 diff
- **reduced-motion 模式**：单独建一条基线，确保动画策略生效
- **图像 diff 工具**：用 pixelmatch 之类工具做像素 diff，设定阈值容忍子像素差异
- **基线更新流程**：基线变更必须 code review，不能自动覆盖

视觉回归测试的痛点是基线管理与易碎性。建议只在主流程截图，不要对每帧动画截图。

### 工具选型与文件组织

四层测试的工具选型建议：

- **数据层**：纯 Python/Node 脚本，pytest 或 jest，正则解析 HTML 内嵌数据或直读 JSON。无浏览器依赖，秒级跑完
- **渲染层 + 交互层**：Playwright（优于 Puppeteer，多浏览器支持更稳）。CI 中 `playwright install chromium --with-deps` 一次性装好
- **视觉回归层**：Playwright screenshot + pixelmatch 或 odiff。基线存仓库，diff 阈值 0.1%-0.5%

文件组织建议按层命名：`test_*_data.py` / `test_*_render.py` / `test_*_visual.py`，一眼看出层级与优先级。fixture 与测试分离，边界场景 fixture 单独目录。

### 数据策略

四层测试的数据策略要分层设计：

- **真实数据源**：HTML 内嵌的 `EMBEDDED_DATA` 对象或外部 JSON，作为单一数据源（single source of truth）
- **Mock 边界**：数据层测试不 mock，直接解析真实数据；组件测试 mock 库加载失败等异常场景
- **Canonical fixture**：一份完整的真实数据快照，作为渲染层与视觉回归层的基准
- **Edge-case fixture**：空数组、单节点、超大节点数、NaN/Infinity 等边界场景的迷你 fixture，独立存放
- **Mobile/narrow fixture**：不同 viewport（375/768/1200px）下的响应式测试
- **Stress/density fixture**：超大节点数下的性能测试，可与真实数据解耦

数据与渲染解耦是关键：HTML 内嵌数据应从外部 JSON 生成，这样数据层测试可直接读 JSON，不必解析 HTML。

### 层级优先级与 ROI

四层测试的投入产出比递减，建议按优先级实现：

| 层级 | 优先级 | 成本 | ROI | 拦截的 bug 类型 |
|------|--------|------|-----|-----------------|
| 数据层 | P0 | 低 | 极高 | 数据契约破坏、引用完整性、KPI 不一致 |
| 渲染层 | P1 | 中 | 高 | 渲染崩溃、降级缺失、响应式断点错 |
| 交互层 | P1 | 中 | 高 | 功能回归、无障碍回归、键盘合约破坏 |
| 视觉回归层 | P2 | 高 | 中 | 像素漂移、配色漂移、布局微移 |

数据层一个测试可能只写 5 行代码，却拦下一个"KPI 数字与数据量不一致"的生产事故。视觉回归层建基线、维护 diff 阈值、处理字体抗锯齿差异，投入是数据层的 10 倍，但只能拦下"像素漂移"类问题。所以——先 P0，再 P1，最后 P2。

## 三、复杂可视化的边界场景

复杂可视化最容易崩的不是主流程，而是边界场景。以下列举最常踩的几类，并给出测试策略。

### 空数据

`dimensions: []` 时，`x || default` 不会触发 fallback——空数组是 truthy。这是 JavaScript 的经典陷阱。测试策略：构造空数组 fixture，断言渲染函数输出"无数据"提示而非空白 SVG。修复建议：改为 `x?.length ? x : default`。

### 单节点

只有一个节点时，力导向图的 force simulation 可能因无引力而抖动；桑基图可能因无 link 而布局异常。测试策略：构造单节点 fixture，断言 SVG 不抛错、节点可见。

### 超大节点数

500+ 节点时，性能可能崩溃。测试策略：构造 stress fixture，断言渲染时间在阈值内（如 2s）。也可断言节点数超过阈值时启用画布渲染而非 SVG 渲染。

### 字体加载失败

Web Font 加载失败时，文字回退到系统字体，可能造成标签溢出或截断。测试策略：mock `document.fonts.ready` reject，断言 SVG text 元素仍渲染（即使字体回退）。视觉回归层可在字体未加载时跳过截图。

### 并发数据竞争

多个异步数据源同时加载时，先到先渲染可能导致后到数据覆盖前到数据。测试策略：mock 不同延迟的 fetch，断言最终状态一致；用 `Promise.all` 等所有数据到位后再渲染。

### 自引用

边 link 的 source 与 target 是同一 id。测试策略：数据层断言自引用被过滤或被标注；渲染层断言不出现 0 长度的自环线段。

### 循环引用

A → B → A 的循环。测试策略：数据层用 visited 集合检测循环并断言；渲染层断言布局不无限递归。

### 负值

数值字段为负（如强度 -5）。测试策略：数据层断言负值被拒绝或被夹紧到 0；渲染层断言 SVG 不出现负半径、负宽度的元素。

### NaN 与 Infinity

数值字段为 NaN 或 Infinity。测试策略：数据层断言被拒绝；渲染层断言 SVG 不出现 NaN 属性（如 `r="NaN"`）。

### 颜色映射漂移

节点的 color 字段与类别配色映射不一致。测试策略：数据层断言每个 category 对应的 color 与配色表一致；视觉回归层断言截图 diff 无颜色漂移。

### KPI 与数据量不一致

KPI 卡片显示"X 维度"但实际数据只有 Y 条。这是编辑决策还是 bug？必须文档化。测试策略：数据层断言 KPI 数字与数据量一致；若不一致，必须在测试中以"已知差异"形式文档化（说明口径区别）。

### 库加载失败

CDN 加载失败时，d3.v7 / d3-sankey 未定义。测试策略：mock `delete window.d3.sankey` 后调渲染函数，断言输出降级文案而非抛错。所有 SVG 都应有降级防御，不能只有桑基图有。

### 协议分支退化

`file://` 协议下意外发起 fetch 导致 404。测试策略：组件测试在 `file://` 下打开页面，过滤 CDN 请求后断言无数据 fetch。

### 键盘合约破坏

Enter/Space 不触发 tooltip，或 Space 滚动页面。测试策略：组件测试模拟 keydown，断言 tooltip 出现 + pageYOffset 不变。

### 动画时序异常

force simulation 未稳定时被截图，或动画在 reduced-motion 下未跳过。测试策略：等 `alphaTarget(0)` 稳定后再断言；reduced-motion 下断言无 transform 变化。

### 异步加载顺序

多组件依赖同一数据源，但各自独立 fetch，加载顺序不确定导致渲染不一致。测试策略：用 `Promise.all` 等所有数据到位后统一渲染；测试中 mock 不同延迟，断言最终状态一致。

### 主题切换无重绘

深色/浅色主题切换后，CSS 变量更新但 SVG 元素未重绘。测试策略：组件测试切换 `data-theme` 属性后，断言 SVG 元素的 fill/stroke 引用了 CSS 变量（而非硬编码颜色）。

## 四、可复用的执行清单

把上面的方法论提炼为可执行的 checklist，按层组织。

### 数据层（P0）

1. 顶层 key 完备性断言（所有必需字段存在）
2. 字段类型与值域断言（数值在合法区间、字符串非空）
3. 引用完整性断言（边的 source/target 都在节点集合内）
4. 唯一性断言（id 唯一）
5. 枚举与颜色映射断言（type 字段为预定义枚举、color 与类别配色一致）
6. KPI 一致性断言（页面 KPI 数字与数据量一致，或差异被文档化）

### 渲染层（P1）

7. SVG 非空断言（每个 SVG 有期望数量的元素）
8. 降级防御断言（mock 库加载失败后输出降级文案）
9. 协议分支断言（file:// 下不发起数据 fetch）
10. 响应式断点断言（375/768/1200px 下网格列数正确）

### 交互层（P1）

11. click + 键盘等价断言（Enter/Space 都触发同一行为、Space 不滚动）
12. 排序交互断言（表头 click/Enter/Space 切换排序）

### 视觉回归层（P2）

13. 桌面 + 移动基线截图
14. force simulation 稳定后截图（`alphaTarget(0)`）
15. reduced-motion 单独基线

### 发布前手动审查

16. SVG 标签无重叠、无截断
17. 配色 AA 对比度达标
18. 移动端表格不横向溢出
19. tooltip 不遮挡关键内容

## 确定性控制

可视化测试的另一个隐形难点是非确定性。force simulation 每次跑节点坐标都不一样，截图 diff 必然失败。必须做确定性控制：

- **Viewport 固定**：375 / 768 / 1280 三档
- **字体与主题 token 固定**：CSS 变量在 :root 锁定
- **Locale 固定**：排序用 `localeCompare('zh-CN')` 保证稳定
- **动画策略**：force simulation `alphaTarget(0)` 稳定后断言；reduced-motion 下跳过动画
- **Render-ready 信号**：暴露 `window.fetchStatus` + main 完成 Promise，测试等信号后再断言

## 显式不测

明确"不测什么"同样重要，避免测试套件臃肿与易碎：

- 不测 D3 / d3-sankey 库内部行为
- 不测 force simulation 的具体节点坐标（非确定性）
- 不对 tooltip 的精确像素位置做断言（依赖鼠标事件，易碎）
- 不对每帧动画截图（应等稳定后或固定种子）
- 不测已知的设计妥协（如全局暴露的排序函数，非回归风险）

## 发布门禁

四层测试体系的最终落点是发布门禁。建议分两档：

**合并前必过**

- 数据层测试全部 PASS（P0 数据契约）
- 渲染层测试全部 PASS（P1 组件测试）
- 全量 pytest / jest 通过
- 无障碍审查无 P0 问题

**发布前必过**

- 上述合并门禁全部通过
- 预发布截图无溢出
- 手动视觉审查：SVG 标签无重叠、配色达标、移动端不溢出

### 已知差异的文档化

复杂可视化常常存在"KPI 数字与数据量不一致"的编辑决策——例如标题写"多维度"但数据数组里只展开了一部分代表维度，其余在专题文档中。这不是 bug，是口径差异。但必须：

- 在测试中以"已知差异"形式文档化，写明口径区别
- 在 KPI 旁加 tooltip 说明口径
- 一旦未来口径统一，同步更新测试期望值

## 总结

可视化测试的核心矛盾是：可视化的"正确"是多层的——数据契约、DOM 结构、交互序列、像素一致——任何一层漏测都会让 bug 漏到生产。传统的单元测试只覆盖函数层，远远不够。

四层测试体系把可视化测试拆成数据层（P0，纯逻辑）、渲染层（P1，DOM/SVG 结构）、交互层（P1，用户操作）、视觉回归层（P2，截图对比），优先级与成本递增。数据层最廉价最高 ROI，必须最先实现；视觉回归层最贵最易碎，最后实现。

边界场景是复杂可视化的真正杀手。空数据、单节点、超大节点数、自引用、循环引用、负值、NaN/Infinity、颜色映射漂移、KPI 不一致、库加载失败、协议分支退化、键盘合约破坏——这些场景不主动覆盖，就会在生产被用户触发。

确定性控制是隐形基础设施。Viewport、字体、locale、动画策略、render-ready 信号——这些不做好，截图测试就会随机失败，团队会逐渐失去对测试套件的信任。

最后强调一句话：可视化测试需要数据 + 渲染 + 交互 + 视觉四层覆盖，缺一不可。只做单元测试会漏掉渲染崩溃，只做截图测试会漏掉数据契约，只做交互测试会漏掉像素漂移。四层成体系，才敢说可视化"测过了"。

落地时建议从数据层起步，先把 P0 的数据契约测试写全——这一步投入最小、回报最高，能拦下八成以上的生产事故。等数据层稳了，再补渲染层与交互层，最后才是视觉回归层。不要一上来就做截图测试，那是最贵也最易碎的一层，没有前两层打底，截图 diff 会沦为噪音。

可视化测试不是银弹，它不能替代 Code Review、不能替代设计审查、不能替代真实用户测试。但它能给你一个底线——保证每一次合并都不会悄悄打破数据契约、不会让 SVG 静默崩溃、不会让键盘用户失去操作路径。这个底线，是复杂可视化项目能长期演进的前提。
