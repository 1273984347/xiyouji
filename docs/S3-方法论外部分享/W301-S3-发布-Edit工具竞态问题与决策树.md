# Edit 工具竞态问题与决策树——同文件多 Edit 并行执行的静默丢失陷阱

> 轨标：外部分享

## 引子

当 AI 代理（Agent）开始承担越来越多的代码与文档修改工作，"工具返回成功"这句话正变得愈发不可靠。一个典型的场景：你让代理同时修改同一份配置文件的版本号、中段描述和尾部链接，三个 Edit 都返回成功，但你回读文件时发现，只有最后一次写入的修改还在——前两次被静默覆盖了。

这不是模型能力问题，也不是提示词写得不好，而是一类被广泛忽视的工程陷阱：**同文件多 Edit 并行执行时的写覆盖竞态**。它没有报错、没有异常、没有日志，唯一能发现它的方式是事后逐点验证。

本文沉淀一套可复用的方法论：从根因识别、决策树选择、到验证闭环，帮助 AI 代理协作和工程自动化场景下的从业者把这类"静默丢失"变成可控、可预防的工程问题。

---

## 一、问题背景

### 触发场景

主代理或子代理（subagent）在同一文件上并行执行多个 Edit 操作——例如同时修改配置文件的头部版本号、中段功能描述、尾部链接段。Edit 工具逐个返回成功，但实际文件中只有最后一次写入的修改生效，前面的修改被覆盖丢失。

### 典型表现

- Edit 工具返回成功，全程无报错
- 事后用检索验证时发现部分修改点未生效
- 重新读取文件，发现前序 Edit 的修改已被后序 Edit 覆盖

### 共同根因

Edit 工具在文件层面没有互斥锁。并行 Edit 同一文件时，每个 Edit 都基于同一份原始文件内容独立计算 diff，写入时后者整体覆盖前者，且无任何冲突检测机制。结果是：**前序 Edit 的修改被静默吞掉，过程不留痕迹**。

可以用一个 5Why 根因分析来锁定本质：

```
Why 1: 同一文件的多个 Edit 并行执行
Why 2: 各 Edit 基于同一原始文件内容独立计算 diff
Why 3: 各 Edit 写入时无文件级锁
Why 4: 后执行的 Edit 基于原始内容覆盖先执行的 Edit 结果
Why 5: Edit 工具无冲突检测，前序 Edit 静默丢失

根本原因：Edit 工具无文件级锁，并行写入无冲突检测
预防措施：同一文件的多个 Edit 串行执行 + replace_all 优先 + 逐点验证
```

---

## 二、核心铁律

### 处置原则

> 同一文件的多个 Edit 必须串行执行；若多行存在共同模式，用 `replace_all=true` 一次性处理。

### 当前会话立即验证原则

> 并行 Edit 同一文件后，必须对全部修改点逐点验证是否生效，发现丢失立即重新修复。

### 操作步骤

1. **识别同文件多 Edit 场景**：在派子代理或主代理自己执行 Edit 前，先识别是否会对同一文件做多次 Edit。
2. **改并行 → 串行**：同一文件的多个 Edit 必须改为串行执行（一个 Edit 完成后再执行下一个）。
3. **replace_all 优先**：若多行有共同模式（如统一替换版本号、统一替换链接前缀），用 `replace_all=true` 一次性处理。
4. **逐点验证**：Edit 完成后对所有修改点逐个检索，确认全部生效。
5. **发现丢失立即修复**：若验证发现部分修改丢失，立即重新执行该 Edit。

## 三、复现案例

下面三个通用案例覆盖了最常见的三类触发形态。它们不是孤立的偶发事件，而是同一根因在不同任务形态下的反复出现。

### 案例一：同一文档多处并行修改

**场景**：需要同时更新一份文档文件的头部版本号、中段功能描述、尾部链接段，共三处修改。

**操作**：子代理对同一文件并行下发了三个 Edit。

**结果**：三个 Edit 全部返回成功，但逐点验证时发现尾部链接段的修改丢失——前两个 Edit 的结果被第三个 Edit 基于原始内容整体覆盖。

**修复**：改为串行执行三个 Edit（头→中→尾依次完成），再次逐点验证全部通过。

**教训**：同一文件的多处修改，看似"独立"实则共享同一文件状态，并行即竞态。

### 案例二：结构化表格多行并行更新

**场景**：一份结构化表格文件需要同时更新三行（目录索引行、版本史行、当前结构行）。

**操作**：子代理对同一表格文件并行下发了三个 Edit，每个 Edit 改一行。

**结果**：三个 Edit 全部返回成功，但逐点验证时发现"版本史行"未生效——它被后两个 Edit 的整体写入覆盖。

**修复**：将三行更新改为串行多步 Edit，或对存在共同模式的行改用 `replace_all` 处理；再次验证全部通过。

**教训**：表格行虽逻辑独立，但物理上同处一个文件，并行 Edit 同样触发覆盖。

### 案例三：多文件批量尾部同步

**场景**：需要为一批文件（例如 6 个）的尾部批量追加相同模式的链接段。

**操作**：子代理并行处理多个文件，但在其中部分文件上对同一文件下发了多个 Edit（先追加链接，再调整格式）。

**结果**：多文件维度并行是安全的，但"同一文件内多 Edit 并行"的部分触发了竞态——前 3 个文件中有 2 个文件的链接段部分丢失。

**修复**：保留"多文件并行"，但把每个文件内部的多个 Edit 改为串行；逐点验证全部命中后才视为完成。

**教训**：多文件分发可以并行，但单文件内部仍需串行——这是决策树的关键分叉点。

### 复现频率声明

上述案例并非孤例。在持续的工程实践中，这类竞态以稳定的频率反复出现，且往往在事后逐点验证时才被发现。这说明它不是某次操作失误，而是一个需要制度化预防的系统性问题。

## 四、修复策略

### 三种处置方案

| 方案 | 适用场景 | 操作 | 优点 | 缺点 |
|:---|:---|:---|:---|:---|
| 串行 Edit | 同文件多 Edit 不可合并 | 一个 Edit 完成后再执行下一个 | 100% 避免竞态 | 速度慢 |
| replace_all=true | 多行有共同模式 | 一次 Edit 替换所有匹配 | 速度快 + 无竞态 | 仅适用共同模式 |
| 多文件分发 | 多文件各自单 Edit | 不同文件的 Edit 可并行 | 速度快 + 无竞态 | 仅适用多文件场景 |

### 决策树

```
是否同一文件？
├─ 是 → 是否多行有共同模式？
│       ├─ 是 → 用 replace_all=true 一次性处理
│       └─ 否 → 串行 Edit（一个完成后再执行下一个）
└─ 否 → 不同文件的 Edit 可并行执行（无竞态风险）
```

这条决策树是整套方法论的可复用核心：先按"是否同一文件"分叉，再按"是否有共同模式"二次分叉，三步之内必定能选出不引入竞态的处置方案。

### 验证流程

1. Edit 完成后立即对所有修改点逐点检索验证。
2. 若命中数 < 预期 → 立即重新执行丢失的 Edit。
3. 重新 Edit 后再次逐点验证。
4. 直到所有修改点全部命中，才视为完成。

## 五、预防措施

### 派子代理时

子代理的任务 prompt 必须显式包含约束：

```
子代理执行多 Edit 时：
1. 同一文件的多个 Edit 必须串行执行（一个完成后再执行下一个）
2. 若多行有共同模式，用 replace_all=true 一次性处理
3. Edit 完成后必须逐点验证所有修改点是否生效
4. 发现丢失立即重新执行该 Edit
5. 不可基于"Edit 工具返回成功"判断修改已生效，必须逐点验证
```

### 主代理自己执行 Edit 时

1. 识别同文件多 Edit 场景，主动改并行 → 串行。
2. 优先用 replace_all 处理共同模式。
3. Edit 完成后逐点验证。

### 与"配置变更验证"方法论协同

通用的"配置变更验证"方法论要求对关键修改做抽样验证（spot-check），本铁律则补充"并行 Edit 后必须逐点验证所有修改点"。两者互补：

| 方法论 | 验证对象 | 触发条件 |
|:---|:---|:---|
| 配置变更验证 | 前序会话报告"已落地"的修改 | 前序会话报告 |
| 并行 Edit 竞态（本方法论） | 当前会话并行 Edit 后的修改完整性 | 当前会话并行 Edit 同一文件 |

### 与"三段式协作闭环"协同

在"三段式协作闭环"的修复阶段中，子代理串行同步多文件（避免并行 Edit 竞态·本方法论）+ 主代理独立逐点验证全部命中，是修复阶段能否真正闭环的关键约束。本方法论是修复阶段的核心前置条件。

## 六、关联文档

### 方法论关联

- **配置变更验证方法论**：本方法论与之协同——前者验证"是否落地"，本方法论验证"并行 Edit 后修改完整性"。
- **文档同步方法论**：文档同步若涉及多 Edit，应直接套用本方法论的决策树。
- **三段式协作闭环**：修复阶段的关键约束，本方法论是其中"串行 Edit + 逐点验证"的依据。
- **子代理任务模板**：子代理 prompt 模板应内嵌本方法论的约束条款。

## 可复用清单

把上述方法论压缩成一张可随身携带的检查清单：

**执行前**
- [ ] 识别是否会对同一文件做多次 Edit？
- [ ] 若是，是否有共同模式可合并为 replace_all？

**执行中**
- [ ] 同一文件的多个 Edit 是否已改为串行？
- [ ] 多文件场景是否保留并行、单文件内部串行？

**执行后**
- [ ] 是否对所有修改点逐点检索验证？
- [ ] 命中数是否等于预期？
- [ ] 丢失的 Edit 是否已重新执行并复验？

**派子代理时**
- [ ] 子代理 prompt 是否内嵌了上述五条约束？

## 总结

"工具返回成功"不等于"修改已生效"。在同文件多 Edit 并行执行的场景下，前者几乎总是成立，后者却可能静默失败——这才是这类问题最危险的地方：它不报错，只丢失。

应对它的关键不是更聪明的模型，而是一套工程化的纪律：

1. **识别**：在执行前识别同文件多 Edit 场景。
2. **决策**：用决策树在"串行 / replace_all / 多文件分发"三方案中选出不引入竞态的处置。
3. **验证**：执行后逐点验证所有修改点，命中数等于预期才算完成。
4. **预防**：把约束内嵌进子代理 prompt，让纪律自动生效。

记住那条核心铁律：**同一文件的多个 Edit 必须串行执行；多行有共同模式，用 replace_all 一次性处理**。这条规则简单到容易被忽视，但它能在你不注意的时候，挡住一次无声的灾难。
