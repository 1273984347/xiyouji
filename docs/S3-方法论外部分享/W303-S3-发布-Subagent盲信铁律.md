# Subagent 盲信铁律——AI 代理协作中工具证据不可盲信的根因分析

> 轨标：外部分享

## 引子

在多代理协作的工程实践中，子代理（subagent）几乎已经成为一种标配组件：主代理把检索、验证、批量修改这类高重复度工作派发下去，子代理跑一圈工具、附上一段"已验证""未找到""0 finding"的报告，主代理据此决策下一步。

这套流程看起来很可靠——子代理的 prompt 明确要求"必须附工具调用证据"，报告里也确实贴出了搜索命令、命中数、文件路径。但真实工程中，一个被反复低估的风险正藏在这里：**证据本身也可能被误读，而"附了证据"恰恰让误读更难被发现**。

典型场景：子代理用 ripgrep 搜索某个标注是否存在，工具返回"binary file matches"而不显示具体行，子代理据此报告"未找到"。主代理一看 prompt 要求的证据齐备、命令也对，就采信了这个结论。但实际上目标内容就在那个被跳过的二进制文件里——子代理基于工具的有限输出，做了一个超出工具实际能力的判断。

这不是模型能力问题，也不是提示词写得不够好，而是一类被广泛忽视的工程陷阱：**子代理报告 ≠ 实际状态，附了工具证据也不等于证据可信**。它不报错、不告警，唯一能发现它的方式是主代理在关键路径上做独立的 spot-check。

本文沉淀一套可复用的方法论：从根因识别、不可盲信声明清单、决策树选择、到验证闭环，帮助 AI 代理协作和工程自动化场景下的从业者把这类"工具证据盲信"变成可控、可预防的工程问题。

## 一、问题背景

### 触发场景

子代理（subagent）报告以下声明时，主代理不可盲信：

- "已保护 X 不受影响"
- "未找到 X"
- "0 finding"
- "已验证 X"

子代理的 prompt 虽要求附工具调用证据，但证据本身仍可能被误读。最典型的形态是：子代理基于 ripgrep 的结果做判断——ripgrep 在检测到 NUL 字节后会跳过二进制文件，仅返回"binary file matches"而不显示具体匹配行——子代理据此报告"未找到 X"，而实际上 X 就在二进制文件中存在。

### 典型表现

- 子代理报告"未找到 / 0 finding / 已验证"，并附上完整的工具调用证据
- 主代理采信后推进决策，事后却发现结论与实际状态不符
- 重新独立 spot-check 时发现：子代理依赖的工具本身没问题，但工具输出被过度概括或语义误读

### 共同根因

子代理报告 ≠ 实际状态。子代理的工具调用证据可能基于以下三类误读：

- **工具输出被过度概括**：工具返回"binary file matches"不显示具体行，子代理概括为"未找到"
- **部分匹配结果的过度外推**：在部分文件中未命中，外推为"全局未找到"
- **上下文不足的语义误读**：匹配行存在但语义被错读，导致"已验证"实际并不成立

可以用一个 5Why 根因分析来锁定本质：

```
Why 1: 子代理报告"未找到 X"
Why 2: 子代理基于 ripgrep 的结果做判断
Why 3: ripgrep 检测到 NUL 字节后跳过二进制文件
Why 4: ripgrep 返回"binary file matches"而不显示具体行
Why 5: 子代理据此误判"未找到 X"，实际 X 在二进制文件中存在

  根本原因：子代理的工具调用证据可能被误读（工具跳过二进制文件是典型场景之一）
  预防措施：主代理在关键路径声明上必须执行独立工具调用 spot-check
```

## 二、核心铁律

### 处置原则

> 子代理报告中"已保护 / 未找到 / 0 finding / 已验证"四类声明，主代理必须用独立工具调用 spot-check 验证后再决策；不可仅因"附了证据"或"多个 verifier 一致"就采信。

### 不可盲信声明清单

> 主代理在以下子代理声明上必须执行独立工具调用 spot-check：

| 声明类型 | 默认风险 | 独立验证工具 |
|:---|:---|:---|
| "已保护 X 不受影响" | X 可能已被改动 | Grep / Read 验证 X 是否确实未变 |
| "未找到 X" | X 可能在子代理未覆盖的位置 | Python 脚本（二进制）/ Grep 范围限定 / Read |
| "0 finding" | 关键声明可能漏报 | 独立 Grep 验证关键声明 |
| "已验证 X" | 验证可能基于误读 | 独立工具调用复核 |

### 操作步骤

1. **识别关键路径声明**：在子代理报告中扫描"已保护 / 未找到 / 0 finding / 已验证"四类关键词。
2. **选择独立工具**：根据 X 的可能存在形态选工具——二进制文件用 Python 脚本读字节、文本文件用 Grep 范围限定、关键文件用 Read 直接读取。
3. **执行 spot-check**：用独立工具调用验证声明的真实性，与子代理报告逐项对照。
4. **发现误判立即纠正**：若 spot-check 发现子代理误判，立即纠正结论并重新执行相关步骤，不可因"附了证据"就放过。

## 三、复现案例

下面三个通用案例覆盖了最常见的三类触发形态。它们不是孤立的偶发事件，而是同一根因在不同任务形态下的反复出现。

### 案例一：搜索二进制文件被工具跳过

**场景**：需要确认若干 PDF 文件是否含某个特定标注。主代理派出多个 verifier 子代理并行检索。

**操作**：子代理使用 ripgrep 搜索标注关键词，工具返回"binary file matches"但不显示具体匹配行。

**结果**：多个 verifier 子代理一致报告"未找到该标注"（P1 级 finding），并附上了完整的搜索命令作为证据。

**主代理 spot-check**：识别为关键路径声明后，改用 Python 脚本直接读取 PDF 文件的字节流，定位到目标标注确实存在（在文件末尾的字节区间内）。

**修复**：推翻子代理误判，标注实际存在，P1 finding 不成立。

**教训**：工具返回"binary file matches"不等于"未找到"——子代理基于工具的有限输出做了超出工具能力的判断，"附了证据"反而让误判更具迷惑性。

### 案例二："0 finding"漏报关键问题

**场景**：主代理派子代理对一批改动做深度复查（Deep Review），子代理返回"0 finding"，并附上完整的检索证据。

**操作**：主代理识别"0 finding"为关键路径声明，触发 spot-check。

**结果**：主代理用独立 Grep 抽样验证关键声明时，发现多处子代理未覆盖到的问题——"0 finding"实际并非 0。

**修复**：补全子代理漏报的问题，重新执行修复流程。

**教训**："0 finding"是最容易被盲信的声明之一——它听起来像是一个明确的结论，实际上可能只是检索范围、检索关键词或上下文窗口的限制。

### 案例三：多 verifier 一致的"假共识"

**场景**：多个 verifier 子代理并行验证同一声明，全部返回一致结论。

**操作**：主代理本可因"多 verifier 一致"直接采信，但识别为关键路径声明后仍触发独立 spot-check。

**结果**：spot-check 发现所有 verifier 共享同一类工具的同一类局限（如都依赖 ripgrep 跳过二进制文件），导致"一致"实际上是"一致地误判"。

**修复**：改用不同类型的工具（Python 脚本 / Read）独立验证，推翻"假共识"。

**教训**：多个子代理一致 ≠ 真共识。当 verifier 共享同一类工具局限时，"一致"只是同一根因的多次复制，主代理必须用**不同类型的工具**做交叉验证。

### 复现频率声明

上述案例并非孤例。在持续的工程实践中，这类盲信以稳定的频率反复出现，且往往在主代理事后 spot-check 时才被发现。这说明它不是某次操作失误，而是一个需要制度化预防的系统性问题——只要子代理还在用工具、主代理还在采信"附证据的报告"，这条铁律就始终有效。

## 四、修复策略

### 三种独立工具调用 spot-check

| 工具 | 适用场景 | 操作 | 优点 |
|:---|:---|:---|:---|
| Python 脚本 | 二进制文件（PDF / 图片 / 压缩包等） | 读取文件字节，统计目标字符串出现位置 | 不受 ripgrep 二进制跳过影响 |
| Grep 范围限定 | 文本文件上下文验证 | `Grep "X" -A N -B N` 验证上下文 | 验证匹配是否在预期上下文 |
| Read | 关键文件直接读取 | 直接 Read 文件相关行 | 100% 准确，但仅适用小范围 |

### 决策树

```
子代理报告声明类型？
├─ "未找到 X" + X 可能在二进制文件 → Python 脚本读取字节验证
├─ "未找到 X" + X 在文本文件 → Grep 范围限定验证
├─ "已保护 X 不受影响" → Grep 验证 X 是否确实未变
├─ "0 finding" → Grep 验证关键声明
└─ "已验证 X" → Read 关键文件相关行

是否多 verifier 一致？
├─ 是 + 共享同一类工具 → 必须换不同类型工具交叉验证
└─ 是 + 使用不同类型工具 → 可降低 spot-check 抽样比例
```

这条决策树是整套方法论的可复用核心：先按声明类型选工具，再按"是否多 verifier 一致 + 是否共享工具局限"二次判断，三步之内必定能选出不引入盲信的验证路径。

### 典型案例处置流程

| 步骤 | 动作 | 结果 |
|:---:|:---|:---|
| 1 | 子代理报告"未找到 X" | 多个 verifier 一致 |
| 2 | 主代理识别为关键路径声明 | 触发 spot-check |
| 3 | 改用 Python 脚本读取二进制文件字节 | 在文件末尾字节区间确认 X 存在 |
| 4 | 推翻子代理误判 | X 实际存在，子代理漏报 |
| 5 | 纠正 P1 finding | finding 不成立，相关修复步骤回滚 |

## 五、预防措施

### 派子代理时

子代理的任务 prompt 必须显式包含约束：

```
子代理报告"未找到 X"时：
1. 必须明确说明搜索范围（哪些文件 / 哪些行范围）
2. 必须明确说明使用的工具（Grep / Read / Python 脚本）
3. 若搜索二进制文件，必须用 Python 脚本而非 ripgrep
4. 报告"0 finding"时必须附完整搜索证据（搜索命令 + 命中数 + 搜索范围）
5. 不可基于"binary file matches"结果判断"未找到"，必须改用 Python 脚本验证
```

### 主代理自己执行 spot-check 时

1. **关键路径声明必 spot-check**：子代理报告中"已保护 / 未找到 / 0 finding / 已验证"四类声明，无一例外。
2. **二进制文件必用 Python 脚本**：不可依赖 ripgrep——"binary file matches"是一个被严重误读的输出。
3. **多 verifier 一致必换工具交叉验证**：当多个子代理一致时，必须确认它们没有共享同一类工具局限。
4. **spot-check 后再决策**：未 spot-check 不可基于子代理报告做关键路径决策。

### 与"配置变更验证"方法论协同

通用的"配置变更验证"方法论要求对前序会话报告的修改做抽样验证，本铁律则把"抽样验证"的思路延伸到子代理报告——两者本质都是"工具证据不可盲信"：

| 方法论 | 验证对象 | 触发条件 |
|:---|:---|:---|
| 配置变更验证 | 前序会话报告"已落地"的修改 | 前序会话报告 |
| Subagent 盲信铁律（本方法论） | 子代理报告"未找到 / 已验证"等声明 | 子代理关键路径声明 |

### 与"多代理并行协作"协同

在多代理并行协作模式中，主代理统一 spot-check 是质量兜底的核心机制。本铁律补充了 spot-check 的具体执行标准——尤其是"多 verifier 一致时必须换工具交叉验证"这一条，直接对应并行模式中最容易出现的"假共识"风险。

## 六、关联文档

### 方法论关联

- **配置变更验证方法论**：本方法论与之协同——前者验证"是否落地"，本方法论验证"子代理报告是否可信"。
- **多代理并行协作模式**：本方法论是其中"主代理统一 spot-check"环节的执行标准。
- **子代理任务模板**：子代理 prompt 模板应内嵌本方法论的五条约束条款。
- **深度复查闭环**：深度复查中的 verifier spot-check 是本方法论的下游应用。

## 可复用清单

把上述方法论压缩成一张可随身携带的检查清单：

**派子代理前**
- [ ] 子代理 prompt 是否内嵌了"未找到 X"五条约束？
- [ ] 是否明确要求子代理搜索二进制文件时改用 Python 脚本？

**收到子代理报告时**
- [ ] 是否扫描了"已保护 / 未找到 / 0 finding / 已验证"四类关键词？
- [ ] 关键路径声明是否已触发 spot-check？

**执行 spot-check 时**
- [ ] 是否按决策树选了独立工具（Python 脚本 / Grep 范围限定 / Read）？
- [ ] 多 verifier 一致时，是否换不同类型工具交叉验证？
- [ ] spot-check 结果是否与子代理报告逐项对照？

**决策前**
- [ ] 是否所有关键路径声明都已 spot-check 通过？
- [ ] 发现误判的声明是否已纠正并重新执行相关步骤？

## 总结

"附了工具证据"不等于"证据可信"。在子代理承担越来越多检索、验证、复查工作的今天，前者几乎总是成立，后者却可能静默失败——这才是这类问题最危险的地方：它不报错，只误导。

应对它的关键不是更聪明的模型，也不是更长的提示词，而是一套工程化的纪律：

1. **识别**：在子代理报告中扫描"已保护 / 未找到 / 0 finding / 已验证"四类关键词。
2. **决策**：用决策树在"Python 脚本 / Grep 范围限定 / Read"中选出独立验证工具。
3. **交叉**：多 verifier 一致时，必须换不同类型工具做交叉验证，识破"假共识"。
4. **预防**：把五条约束内嵌进子代理 prompt，让纪律自动生效。

记住那条核心铁律：**子代理报告 ≠ 实际状态，附了证据也不等于证据可信——主代理在关键路径声明上必须做独立 spot-check**。这条规则简单到容易被忽视，但它能在你不注意的时候，挡住一次由"假共识"和"工具输出误读"联手酿成的静默灾难。
