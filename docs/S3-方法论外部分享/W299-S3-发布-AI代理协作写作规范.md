# AI 代理协作写作规范——避免 LLM 输出反模式的六类纪律

> 轨标：外部分享

## 引子

把写作交给大模型，省下的是打字时间，赔上的常常是读者信任。

任何一个长期与 LLM 协作的工程师都会撞上同一组症状：文档读起来通顺、规范、面面俱到，却始终在原地打转——每段都在复述标题，每节都在自我介绍，每个结论都用"不是 A 而是 B"的句式包装一遍，最后再来一段"我们将持续优化"。这类文本不违反任何语法规则，却系统性地消耗读者的注意力。

问题的根因不在模型能力，而在纪律缺位。LLM 默认倾向"显得深刻"而非"给出判断"，倾向"全面覆盖"而非"一次性陈述"。如果不显式约束，它会稳定地生产出 heading-echo、meta-narration、空洞强调词、伪装成散文的命令式清单。

本文沉淀自长期 AI 代理协作的写作实践，将 LLM 最容易踩中的反模式归为六类纪律：段落级、句子级、格式、内容体、默认不创建的章节、任务描述。每条规则都附违规示例与修复路径，可直接作为 prompt 附件、code review 检查项或团队写作规范。

## 一、段落级反模式

段落是 LLM 最容易"灌水"的层级。以下四类模式一旦出现，整段几乎必然贬值。

| 规则 | 描述 | 违规示例 |
|:-----|:-----|:---------|
| **禁止 heading-echo** | 段落首句不得复述或解释标题已表达的内容。应以事实、数据或判断开头。 | ❌ "本章介绍用户增长策略。" / "本节将分析系统架构的演进路径。" |
| **禁止 meta-narration** | 不得使用自指式叙述描述文本即将做什么。直接进入实质内容。 | ❌ "下面我们来看…" / "接下来将详细分析…" / "让我们考察…" |
| **禁止"不是…而是…"修辞框架** | 不得使用"不是…而是…" / "真正的问题不是…而是…" / "不仅仅是…更是…" / "本质上不是…而是…"等纯粹为了显得深刻的对比结构。读者通过内容判断文本价值，而非作者的自我定位。直接陈述真实判断，不依赖对比拐杖。 | ❌ "这不是一篇新闻解读，而是一篇从热议反推逻辑的复盘。" → ✅ 直接给出复盘逻辑 |
| **一次性陈述规则** | 一个结论在其规范位置完整出现一次。其他章节引用时必须贡献新证据或新角度，绝不只是换词重述。 | ❌ 引言说"A是核心壁垒"，正文说"A构成关键护城河"，结论说"A最终成为不可替代的优势" |

**实战要点**：heading-echo 是 LLM 最顽固的惯性。即便在 prompt 中明确禁止，模型仍会在长文档后半段悄悄复发。根治办法是在 review 阶段对每段首句做单独审查——若删掉首句后段落信息密度反而上升，该句必删。

## 二、句子级反模式

句子层的反模式更隐蔽，但累积效应最显著：一篇文档读起来"虚"，多半是这三类结构在作祟。

| 规则 | 描述 | 修复 |
|:-----|:-----|:-----|
| **禁止 dummy-verb 结构** | 消除"进行"/"开展"/"实施" + 名词的模式。直接使用动词。 | "进行分析" → "分析"；"开展调研" → "调研"；"实施优化" → "优化" |
| **禁止不可验证的"确保"** | "确保"后跟不可验证的目标时，替换为可量化标准。 | ❌ "确保用户体验良好" → ✅ "页面加载 ≤ 2s，操作反馈 ≤ 200ms" |
| **禁止空洞强调词** | 删除"非常"/"极其"/"高度"/"显著"等未跟量化证据的强调词。 | ❌ "显著提升了效率" → ✅ "处理时间从 4.2s 降至 1.1s" |

**实战要点**：dummy-verb 在中文 LLM 输出中尤其密集，根因是训练语料中"进行 + 名词"的频率远高于单动词。把它当作 code review 的 lint 规则来执行：全文搜索"进行""开展""实施"，逐个判断能否压缩为单动词。不可验证的"确保"则更危险——它把承诺伪装成了声明，一旦写进交付物，就成了无法验收的债务。

## 三、格式纪律

格式不是装饰，是负载信息的信道。滥用加粗等于让加粗失效，滥用 emoji 等于让信号变噪声。

| 规则 | 描述 |
|:-----|:-----|
| **加粗范围** | 加粗保留给：专有名词、工具/命令名称、关键警告。不得在行文中用加粗表示修辞强调——靠句法结构传达重要性。限制：每节 ≤ 3 个加粗跨度。 |
| **禁止加粗+斜体堆叠** | `***text***` 禁止使用。 |
| **禁止 emoji（除非要求）** | 文档不得包含 emoji 或装饰性 Unicode 符号（✅❌⚠️ 仅在清单/诊断场景允许，用户面向的交付物不允许）。 |
| **标题无标点** | Markdown 标题不得以句号、冒号或问号结尾（例外：真正的疑问标题）。 |

**实战要点**：每节 ≤ 3 个加粗跨度这条上限，比直觉更严苛。LLM 倾向把每个关键名词都加粗，结果整段全是高亮、等于没有高亮。审查时若某节加粗超过 3 处，优先保留指向"读者必须记住的专有名词或警告"的那 3 个，其余降级为普通文本。

## 四、内容体反模式

内容体层面的反模式决定了文档是"可读"还是"可扫读"。下表左侧是 LLM 默认产物，右侧是应当替换成的形态。

| 避免 | 优先 |
|:-----|:-----|
| 伪装成散文的命令式清单 | 描述性、解释性语言 |
| 翻译腔（生硬直译） | 目标语言地道自然的表达 |
| 无上下文的术语堆砌 | 术语首次出现时附简短行内解释 |
| 过度压缩的要点风暴 | 逻辑流重要时用流畅段落 |
| 空洞最高级（"世界级"/"尖端"） | 具体、有证据支撑的声明 |
| 公式化残段（"参考资料"/"致谢"/"附件列表"） | 仅在明确需要时包含 |
| 修辞式或说服性标题 | 描述性、中性标题 |
| 生硬、官僚或过度抽象的措辞（"进行赋能"/"实现闭环"/"显式标注"） | 非专家首读可理解的朴素对话式措辞 |
| 造词过载——堆叠自创抽象名词（"飞轮"/"入口层"/"会话层"） | 每段最多 1 个自创抽象；其余用具体描述替代 |
| 同一结论换词重复 3 次（引言摘要 ≈ 核心判断 ≈ 结论） | 结论在规范位置陈述一次；其他章节引用须加新证据或新角度 |

**实战要点**：造词过载是技术写作的隐性杀手。LLM 极爱自造"飞轮""闭环""入口层"这类听起来有结构的抽象名词，再用三个段落围绕它打转。审查时若发现一段内出现两个以上自创抽象，强制要求作者用具体描述替换其中至少一个。同一结论换词重复三次则更难自查——它读起来像在推进论证，实则在原地踏步。

## 五、默认不创建的章节

LLM 有强烈的"补全结构"冲动：给定一个主题，它会本能地补出"参考资料""致谢""附件列表"等公式化残段。这些章节在 95% 的场景下不创造价值，只制造滚动距离。

除非用户明确要求，不创建以下章节：

- "图表与附件" / "附件列表"
- "参考资料" / "References" / "Bibliography"
- "致谢" / "Acknowledgments"
- "数据源" / "Data Sources"
- "XX清单" / "XX Checklist"

**实战要点**：这条规则看似简单，执行时却常被"反正写了也无害"的心态稀释。事实上每多一个空壳章节，读者对全文信息密度的预判就下调一档。若某章节无法用一句话回答"读者读完它会获得什么具体信息"，就该删掉而非补全。

## 六、任务描述反模式

最后一类反模式不在文档里，而在"写给 agent 的任务描述"里。当任务描述本身被企业行话污染，agent 产出的文档几乎必然继承同样的问题。

委派给 agent 或规划内容时，**禁止**使用清单式、企业行话或工作狂式语言：

❌ **禁止措辞**：
- "可操作"/"可执行"/"检查清单"/"可参考"/"定期复盘"/"x 天行动计划"
- "actionable checklist"/"30-day action plan"/"weekly review cadence"
- 将人类体验框架为可优化工作流

✅ **应自然表述**：直接进入实质思考，不预设框架。

**实战要点**：这一条是六类纪律中杠杆最大的一条。任务描述是 agent 的"系统提示词"，描述里的每一个"赋能""闭环""显式标注"都会被放大到最终文档的每一节。在写任务描述前先做一次自我审查：把所有"可 XX"形容词、所有"X 天行动计划"句式删掉，看剩下的实质要求是否还成立——通常会成立，且更清晰。

## 可复用清单

把以下清单贴到 agent 的 prompt 附件、code review 模板或团队写作规范的尾部，可一次性拦截绝大多数 LLM 输出反模式。

**段落级**
- [ ] 每段首句不复述标题、不自我介绍
- [ ] 不出现"下面我们来看""接下来将"等 meta-narration
- [ ] 不出现"不是…而是…"对比框架
- [ ] 同一结论只在其规范位置陈述一次

**句子级**
- [ ] 无"进行/开展/实施 + 名词"的 dummy-verb 结构
- [ ] "确保"后跟可量化标准
- [ ] 无"非常/极其/高度/显著"等无证据强调词

**格式**
- [ ] 每节加粗跨度 ≤ 3
- [ ] 无 `***text***` 加粗+斜体堆叠
- [ ] 用户面向交付物无 emoji
- [ ] 标题不以句号、冒号结尾

**内容体**
- [ ] 无伪装成散文的命令式清单
- [ ] 术语首次出现附行内解释
- [ ] 无"世界级/尖端"等空洞最高级
- [ ] 每段自创抽象名词 ≤ 1
- [ ] 同一结论不换词重复 3 次

**章节**
- [ ] 未创建"参考资料/致谢/附件列表/数据源/XX清单"等公式化残段

**任务描述**
- [ ] 任务描述中无"可操作/可执行/检查清单/X 天行动计划"等企业行话
- [ ] 任务描述未将人类体验框架为可优化工作流

## 总结

LLM 不会自己长出写作纪律。它默认产出的，是"看起来深刻、读起来空转"的文本——结构齐全、措辞工整，却把读者的注意力浪费在 heading-echo、meta-narration、dummy-verb 和换词重复上。

六类纪律的本质，是把"显得深刻"的诱惑替换为"给出判断"的要求，把"全面覆盖"的冲动替换为"一次性陈述"的克制。这套纪律不是写作技巧，而是 AI 代理协作时代的工程规范——和 lint 规则、code review 检查项一样，应当前置到 prompt、嵌入到 review 流程、固化到团队标准里。

纪律的回报是可量化的：读者读完一段就能获得一个可被引用的判断，读完一节就能带走一个可被复用的结论，读完一篇就能验收一组可被检验的承诺。这恰恰是 LLM 协作写作本应交付、却最容易被默认输出稀释掉的价值。
