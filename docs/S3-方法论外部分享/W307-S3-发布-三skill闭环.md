# 三 skill 闭环——AI 代理协作中审查-收尾-沉淀的完整循环

> 轨标：外部分享

## 引子

如果你正在用 AI 代理（agent）承担一段持续数小时、横跨多个会话的工程任务，那么一个无法回避的问题会很快浮出水面：**当一个任务"看上去做完了"，谁来审查它真的做对了？谁来把这次任务的痕迹收尾归档？谁来把过程中撞过的坑沉淀成下次可以复用的经验？**

这三件事听起来像是同一个"完成"动作的自然延伸，但在实际工作流里，它们往往被压缩成一个步骤——交给代理自己说一句"已完成"，然后进入下一个任务。结果是：审查形同走过场，收尾留下半拉子档案，经验根本没沉淀下来。下一次会话开启时，代理对上一次的撞坑一无所知，同样的问题在新的会话里被重新踩一遍。

我们在多个长周期协作项目里反复验证过这个现象：**审查、收尾、沉淀这三件事一旦被合并或跳过，跨会话的经验复利就会断裂**。代理可以很高效地完成单次任务，但无法把"完成"沉淀为"能力"。复利消失，代理永远停留在第一个会话的水平。

本文记录的，是我们为解决这一问题沉淀出的一套方法论——**三 skill 闭环**：用一个审查 skill、一个收尾 skill、一个沉淀 skill 组成单向循环，把"完成"扩展为"完成 → 验证 → 归档 → 经验化 → 反向喂回协议层"的完整链路。它不依赖某个具体框架，也不绑定任何项目，是一套可以被复用到任何"AI 代理 + 长周期工程协作"场景的协议。

需要强调的是，这里的"skill"是一个抽象概念——它可以是一个提示词模板、一段可调用的子流程、一个独立的 agent 角色，或是一份写在文档里的可执行清单。本文关心的是**三件事的职责边界与联动规则**，而不是它的具体实现载体。

---

## 一、为什么需要三 skill 闭环

### 单 skill 的局限

如果只用一个 skill 试图覆盖"完成"的全过程，最常见的三种失败模式是：

- **只审查不收尾**：代理在审查中发现了一堆问题并修复，但修复结果没有同步到项目记忆文件。下一个会话开启时，代理读到的是修复前的状态，要么重复审查、要么基于过时信息做决策。
- **只收尾不审查**：代理把工作日志、状态、产出物归档得很整齐，但归档的内容本身没有经过验证。"看上去落地了"和"真的落地了"之间隔着一道鸿沟——典型表现是上一会话报告"修复已完成"，下一会话一查发现根本没改。
- **只沉淀不闭环**：代理把这次的经验教训写进了经验档案，但经验档案没有反向喂回审查协议。下一次审查依旧沿用旧规则，刚刚沉淀下来的"撞坑模式"在新会话里再次出现，审查 skill 自己却识别不出来。

这三种失败模式共同指向同一个根因：**审查、收尾、沉淀是三种不同的认知活动，它们的输入、输出、判定标准都不一样**。审查关心"是不是真的对了"，收尾关心"是不是真的留下了"，沉淀关心"下一次能不能避免"。把它们合并成一个动作，必然有一两项被牺牲。

### 闭环断裂的代价

闭环断裂的代价不是立刻显现的，而是在跨会话接续时集中爆发：

- 代理读到的项目状态与实际状态不一致，基于错误前提做出决策
- 同一类问题在多个会话里反复出现，每次都"重新发现"
- 经验档案越来越厚，但实际工作流没有任何改变——经验变成了死文档
- 协议层长期不升级，审查 skill 的判定规则停留在第一版，无法识别新的反模式

更隐蔽的代价是**信心流失**：当协作方多次经历"代理说做完了但实际没做完"之后，对代理产出的信任会下降，进而要求更多的人工复核——这恰好抵消了使用代理的初衷。

三 skill 闭环的目标，就是用一套明确的协议把这三件事**强制分离、强制串联、强制反向喂回**，让"完成"成为一个可被验证、可被归档、可被复用的状态。

## 二、三 skill 各自的职责

### 1. 审查 skill（deep-review-loop，起点）

**职责**：对代理当前会话的产出做严肃的多轮审查，输出真收敛 / 假收敛的判定。

**输入**：本会话的产出物（代码、文档、配置等）+ 项目当前的协议层规则。

**输出**：
- 一份分级问题清单（通常分为必须修复、允许残留、不计入三档）
- 真收敛判定（必须满足：必须修复项归零 + 残留项在阈值内 + 至少若干条残留风险记录）
- 残留风险列表（喂给沉淀 skill 的问题预防维度）

**关键约束**：
- 收敛判定不能由代理自己说了算，必须有独立的验证视角（可以是子代理、独立提示词、或人工抽查）
- 必须记录"收敛曲线"——也就是每一轮审查后问题数的变化，避免"一轮就通过"的假收敛
- 残留风险必须显式列出，不能为追求"全绿"而隐藏

**为什么是起点**：审查是闭环的入口。没有真收敛，后续的收尾和沉淀都是在为假象服务。

### 2. 收尾 skill（mem-wrap-up，中段）

**职责**：在审查真收敛后，把本会话的产出、状态、痕迹完整归档到项目记忆层，并反向验证收尾本身没有遗漏。

**输入**：审查 skill 的真收敛报告 + 本会话的所有产出物。

**输出**：
- 项目记忆文件的健康检查报告
- 一份本会话的工作日志（结构化、可被下一会话读取）
- 一份沉淀原料（喂给沉淀 skill 的经验候选条目）
- 反向验证报告（确认收尾动作本身没有漏项）

**关键约束**：
- 收尾不是简单的"写日志"，必须包含对记忆文件一致性的检查
- 必须有一个**反向验证步骤**——收尾完成后回头检查"我刚归档的东西是不是真的在文件里"
- 收尾中产生的审计发现，要作为沉淀 skill 的输入

**为什么是中段**：收尾连接审查与沉淀。它把审查的结论转化为可被未来会话读取的状态，同时为沉淀提供原料。

### 3. 沉淀 skill（self-evolution，末端 + 反向喂回）

**职责**：把本会话的经验（成功的、失败的、一次性工具）提炼为可复用的经验条目，并在发现审查流程本身存在反模式时，反向喂回审查 skill 的协议层。

**输入**：收尾 skill 的沉淀原料 + 审查 skill 的残留风险 + 一次性工具。

**输出**：
- 经验复用条目（喂给下一会话的预防策略）
- 问题预防条目（基于残留风险和审计发现）
- 一次性工具沉淀（可被未来会话直接调用的工具化产物）
- **协议升级建议**（识别审查流程本身的反模式，反向喂回审查 skill）

**关键约束**：
- 沉淀不是"写感想"，每条经验必须有明确的复用场景和触发条件
- 沉淀 skill **不能直接驱动审查 skill**——它只能通过协议层反向喂回
- 协议升级必须有毕业判据（同类经验多次复现后才升级，避免一次性事件污染协议）

**为什么是末端**：沉淀是闭环的出口，也是下一轮闭环的入口。它把单次经验转化为协议层的进化。

### 三 skill 之间的关系图

```
审查 skill（起点）
    ↓ 真收敛报告 + 残留风险
收尾 skill（中段）
    ↓ 沉淀原料 + 审计发现 + 一次性工具
沉淀 skill（末端）
    ↓ 协议升级建议
反向喂回审查 skill 的协议层（下一轮闭环）
```

**严格单向**：禁止反向执行。沉淀 skill 不能直接驱动审查 skill，必须通过协议层间接升级。这个约束的意义在于——经验沉淀需要时间检验，不能因为一次撞坑就立刻改协议，否则协议层会被噪声淹没。

## 三、闭环不可断裂的铁律

### 铁律：跳过任一 skill，视为闭环断裂

这是整套方法论里最硬的一条规则。无论出于什么理由（"这次任务很简单"、"时间紧"、"上一次已经沉淀过了"），只要跳过了审查、收尾、沉淀中的任何一个，整个闭环就视为断裂，必须立即补跑被跳过的 skill。

### 为什么不能跳

每一项的跳过都会带来特定的失败模式：

- **跳过审查**：收尾归档的是未经验证的产出。下一会话基于错误前提工作。
- **跳过收尾**：审查的结论没有落地到记忆文件。下一会话读不到这次的状态变更。
- **跳过沉淀**：本次的撞坑没有进入经验库。同类问题在下一会话重复出现，协议层永远不升级。

### 通用化案例

**案例 A：只审查不收尾**

某项目在一次较大的功能扩展后跑了完整的审查，确认所有 P1 问题都已修复。但由于时间紧，团队跳过了收尾步骤，没有把"哪些文件被改了、改了什么"同步到项目记忆文件。下一个会话开启时，代理读到的是扩展前的状态，基于这个错误前提对功能做了进一步的"优化"——结果把已经修复的问题又改回去了。

**案例 B：只收尾不审查**

某次任务结束后，代理认真写了工作日志、更新了状态文件、归档了产出物。一切看起来很完整。但因为跳过了审查，归档的内容里包含一个隐藏问题：上一会话报告"修复已完成"，实际只是改了文档描述，代码本身没动。下一个会话继承了这个"看似完成实则未完成"的状态，问题在更晚的阶段才暴露，回溯成本远高于当时审查。

**案例 C：只沉淀不闭环**

某团队把每次会话的撞坑都认真写进了经验档案，档案越来越厚。但因为经验没有反向喂回审查协议，审查 skill 依旧用第一版的规则工作。一个已经在档案里出现多次的"代理系统性编造行号"反模式，在新会话里再次发生，审查 skill 完全没有识别——因为这个反模式不在它的判定规则里。

### 铁律的执行机制

铁律不是一句口号，它需要有执行机制来保障：

- **运行时检查**：每次触发闭环时，验证是否按声明顺序执行了三个 skill
- **跳过即补跑**：发现跳过任一 skill，立即补跑，不允许"下次再说"
- **显式声明**：三 skill 的闭环关系必须常驻在每次会话都会注入的上下文里，不依赖代理"想起来"

最后一点尤其重要。如果闭环关系只写在某个文档里，代理在忙起来的时候很容易"忘"——所以它必须被注入到每次会话的初始上下文中，作为一个不可移除的背景约束。

## 四、版本联动检查

### 问题：三 skill 任一升级时的漂移风险

三 skill 闭环不是静态的——每个 skill 都会迭代，迭代时可能引入新的概念、新的步骤编号、新的判定维度。如果三个 skill 各自升级、互不同步，就会出现**联动漂移**：

- 审查 skill 升级了新的防护层，但收尾 skill 还在引用旧的层编号
- 沉淀 skill 升级了新的维度编号，但审查 skill 的反向喂回路径还指向旧维度
- 协议层概念从一个 skill 流失到另一个 skill 时，语义发生了偏移

### 联动检查机制

任一 skill 升级时，必须执行以下联动检查：

1. **动态读取当前版本的全部概念定义**：从被升级 skill 的协议头部，提取所有以特定前缀开头的条目（如"防护层 N"、"维度 N"、"步骤 N"）。**不硬编码具体编号**——避免未来从 4 层升级到 5 层、6 层时检查规则失效。
2. **交叉检索联动编号**：用动态提取到的关键词，在其他两个 skill 的文档里检索，确认所有联动编号都指向当前版本的概念。
3. **确认概念引用未漂移**：三 skill 间共享的概念（如严重度分级、收敛判据、残留阈值）必须语义一致。
4. **漂移则同步更新**：发现任一处漂移，同步更新所有 skill 的联动声明，并 bump 版本号。

### 为什么强调"动态读取"

这是这套机制里最容易踩坑的一点。一个直观但错误的做法是：在联动检查规则里写死"检查防护层 1/2/3/4 是否一致"。这种写法在当前版本有效，但一旦协议升级到 5 层，检查规则就会漏掉第 5 层——而漏掉的那一层，恰恰是新升级的、最容易出现漂移的一层。

正确做法是：检查规则本身也是动态的——它先读取当前协议层有哪些层定义，再用读到的层名作为检索关键词。这样无论协议升级到第几层，检查规则都能自动覆盖。

### 当前会话立即验证

修改任一 skill 后，**必须在当前会话内立即派子代理做运行时自检**，不把验证推到未来会话。

理由很直接：推到未来 = 不确定性累积，当前消除 = 不确定性归零。

自检的内容通常是：派一个子代理模拟跑一轮审查，验证它的提示词里是否真的包含了当前协议层的所有关键字段，并产出一份"四项是否全部触发 + 触发证据"的自检报告。任一项未触发，立即修复，不结束当前会话。

## 五、可复用的执行清单

以下是这套方法论提炼为可执行 checklist 的版本，共 10 条。可以直接复制到团队的工作流约定里：

### 启动阶段

1. **声明闭环常驻**：在每次会话都会注入的上下文里，写明"本工作流执行三 skill 闭环：审查 → 收尾 → 沉淀 → 反向喂回"，作为不可移除的背景约束。

2. **确认当前协议版本**：会话启动时，读取三个 skill 的当前版本号和协议层定义，确认三者的联动编号一致。发现漂移立即同步，不带着漂移开始工作。

### 执行阶段

3. **审查先行**：任何"完成"声明之前，必须经过审查 skill 的多轮审查。收敛判定必须包含收敛曲线（每轮问题数变化），不接受"一轮就通过"。

4. **真收敛判据**：必须修复项归零 + 残留项在阈值内 + 至少若干条残留风险显式列出。三条同时满足才算真收敛，缺一不可。

5. **收尾紧跟审查**：审查真收敛后立即触发收尾，不间隔其他任务。收尾必须包含记忆文件一致性检查和反向验证步骤。

6. **收尾反向验证**：收尾完成后，回头检查"刚归档的内容是不是真的在文件里"——用关键词检索验证归档落地，不依赖代理的自我报告。

7. **沉淀紧跟收尾**：收尾完成后立即触发沉淀，把本会话的经验提炼为可复用条目。每条经验必须有明确的复用场景和触发条件。

### 闭环阶段

8. **跳过即补跑**：发现跳过任一 skill，视为闭环断裂，立即补跑被跳过的 skill。不接受"这次简单所以跳过"的理由。

9. **协议升级走毕业判据**：沉淀 skill 发现的反模式，不能立刻改协议。必须同类经验多次复现后才升级协议层，避免一次性事件污染协议。

10. **当前会话自检**：修改任一 skill 后，当前会话内立即派子代理做运行时自检，不把验证推到未来会话。自检未通过不结束会话。

### 一句话总结这 10 条

> 审查要真、收尾要全、沉淀要反喂回；跳过要补、版本要联、自检要当场。

## 总结

三 skill 闭环的核心洞察很简单：**审查、收尾、沉淀是三种不同的认知活动，不能合并**。审查关心"是不是真的对了"，收尾关心"是不是真的留下了"，沉淀关心"下一次能不能避免"。把它们压缩成一个动作，必然有一两项被牺牲，而牺牲的代价会在跨会话接续时集中爆发。

这套方法论的价值不在于"发明了三个 skill"——任何团队都可以有自己的审查、收尾、沉淀实现。它的真正价值在于**明确了三件事的职责边界、强制串联的执行规则、以及反向喂回的协议升级路径**。有了这套协议，"完成"就不再是一个代理自报的状态，而是一个可被验证、可被归档、可被复用的工程产物。

特别值得强调的是**反向喂回**这一环。没有反向喂回，沉淀 skill 就只是一个越来越厚的经验档案，永远不反作用于审查协议。有了反向喂回，每一次撞坑都在升级下一次审查的判定规则——经验从"死文档"变成"活协议"，复利才开始累积。

最后，这套方法论本身也是迭代的。它在多个项目里被反复验证、修正、升级，每一次完整的闭环执行都在反向喂回它的协议层。如果读者要在自己的协作场景里落地，建议从最简版本开始——先把"审查 → 收尾 → 沉淀"三件事明确分离，再逐步加入反向验证、版本联动检查、当前会话自检等机制。**不必一次到位，但闭环不可断裂**——这是唯一不能妥协的规则。

审查-收尾-沉淀，缺一不可。
