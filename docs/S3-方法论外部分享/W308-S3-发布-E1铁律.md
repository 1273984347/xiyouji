# E1 铁律——AI 代理跨 session 接续的三层 spot-check 验证
> 轨标：外部分享

---

## 引子

你接手一个由上一个 session 推进过的项目。上个 session 在收尾时留下了一条让人安心的总结：

> 已完成本轮全部修改：6 个文件已落地，3 处 P1 问题已修复，subagent 验证通过。

你信吗？

在 AI 代理协作的场景里，这是一个再常见不过的接手瞬间。主代理收到的报告措辞专业、结构完整、逻辑自洽，配合工具调用截图与"已验证"字样，几乎没有任何外显破绽。但只要做过几次跨 session 接续的人都知道：**报告写得好，不等于代码真的改了；commit message 写得清，不等于文件真的被纳入版本控制**。

反复出现的踩坑模式提示我们一个朴素但常被忽视的事实：AI 代理的"声明"与"执行"之间存在系统性偏差。Edit 工具的返回值可能因为 `old_string` 不匹配而静默失败，Write 工具对未 tracked 文件也会返回成功，subagent 基于 ripgrep 的"binary file matches"误判内容存在与否——这些都是真实场景里反复复现的故障模式。

E1 铁律正是从这类高频故障中沉淀出的方法论：**任何 prior session 的报告都不能被默认信任，必须经过主代理独立 spot-check 验证才能进入下一步操作**。它不是一个一次性的修补脚本，而是一套结构化、可复用、三层互补的验证协议。

本文把它从项目内部沉淀中提炼为对外可发布的形式，删去项目特定细节，保留方法论本质，供 AI 代理协作、项目管理、工程实践领域的技术人员参考。

## 一、prior session 报告 ≠ 实际状态

### 1.1 三类典型错误

跨 session 接续中，主代理最容易踩到的是三类"声明 ≠ 状态"陷阱。

**第一类：Edit 成功 ≠ 文件被 git tracked。** prior session 报告"edits made to N files"时，主代理倾向于相信文件已经进入版本控制。但 Edit / Write 工具的返回值只代表"写入磁盘成功"，并不代表"被 git 追踪"。文件可能停留在 untracked 状态，下一次 commit 时直接漏网。

**第二类：修复声明 ≠ 文件内容已修改。** prior session 报告"P1 问题已修复"、"已将旧值替换为新值"时，主代理容易直接进入下一步。但 Edit 工具可能因为 `old_string` 不匹配而静默失败，prior session 也可能因为仅基于 Edit 返回值就下了"已落地"的判断——文件内容实际上从未被改动。

**第三类：subagent 报告 ≠ 工具证据可信。** 派出去的 subagent 报告"已保护 X 不受影响"、"未找到 X"时，主代理如果直接采纳，等于把判断权完全外包。subagent 的工具调用可能因为 ripgrep 跳过二进制文件、搜索范围限定错误、上下文截断等原因产出误判，但报告措辞依然显得"专业且自信"。

### 1.2 共同根因

三类错误的表层表现不同，根因却高度一致：**prior session / subagent 的报告与文件系统的实际状态之间，缺少一个独立的验证层**。

这个验证层的缺失，源于几条更具体的故障路径：

- Edit / Write 工具的返回值语义是"写入动作完成"，而非"内容已被持久化为预期状态"
- ripgrep 在检测到 NUL 字节后会跳过二进制文件，仅返回"binary file matches"，不显示具体行内容
- prior session 在收尾时倾向于把"声明"等同于"执行"，因为前者比后者便宜得多
- subagent 的报告是经过压缩与措辞优化后的产物，工具调用的原始证据不一定进入报告正文

只要这四条路径任一存在，"报告 ≠ 状态"就会发生。而它们在真实工程实践中几乎是常态。

### 1.3 信息不对称的本质

跨 session 接续的本质是**信息不对称**：prior session 拥有执行过程的全部上下文，本 session 只能通过报告、文件、commit 三类副产物去还原。报告是 prior session 的主观叙述，文件是客观执行结果，commit 是经过筛选的持久化切片——三者之中，**只有文件本身是"硬证据"**。

E1 铁律的核心原则就是：**任何状态判断都必须建立在主代理对文件的独立验证之上，而非建立在 prior session 的报告之上**。

## 二、三层 spot-check 验证体系

E1 铁律将验证动作拆为三层。每一层针对一个具体的"声明 ≠ 状态"陷阱，三者互补，单独使用任一层都无法覆盖完整。

### 2.1 第一层：git tracked 验证

**针对陷阱**：Edit 成功 ≠ 文件被 git tracked。

**触发条件**：prior session 报告"edits made to N files"、"Created N files"、"已完成本轮修改"，且本 session 在后续步骤中需要 commit 或基于这些文件继续操作时。

**验证动作**：主代理对 prior session 声称修改/创建的每一个文件，独立执行 `git ls-files` 验证其 tracked 状态。

**判定规则**：

- 命令返回文件名 = tracked，可以进入下一步
- 命令空输出 = untracked，必须先 `git add`，再进入下一步
- 命令返回的文件名清单与 prior session 声称的清单不一致 = 部分文件漏网，需要逐项比对

这一层看似简单，却是最容易被 prior session 的"专业措辞"掩盖的陷阱。在大量真实复现中，prior session 报告"Created N files"而 `git ls-files` 返回空的情况反复出现——尤其在批量创建文件、创建后立即转向其他任务的场景下，未 tracked 的文件会在下一次 commit 时悄无声息地消失。

更具讽刺意味的是：即便在已经把 E1 铁律写进协作流程的项目里，新的"漏 tracked"案例依然会被 spot-check 发现——证明铁律的价值不因流程化而衰减，方法论在自我证明。

### 2.2 第二层：文件内容 spot-check

**针对陷阱**：修复声明 ≠ 文件内容已修改。

**触发条件**：prior session 报告"修复已落地"、"已将旧值替换为新值"、"已同步至版本 X"时。

**验证动作**：主代理不直接采信"已落地"的声明，而是用 Grep 直接验证文件内容：

- Grep 搜索"修复前的值"——若命中，说明修复未落地
- Grep 搜索"修复后的值"——若命中，说明修复已落地
- 必要时附带上下文（`-A N -B N`）确认匹配位置就是预期修复位置

**判定规则**：

- 修复前值命中 + 修复后值不命中 = 修复未落地，必须重新修复
- 修复前值不命中 + 修复后值命中 = 修复已落地
- 两者都命中 = 部分修复，需逐处定位

这一层是 E1 铁律的"升级版"。最初的版本只覆盖 L1（git tracked 验证），但在反复实践中发现：即便文件已经被 tracked，文件内的"修复"也可能从未发生过。prior session 报告"6 个文件已同步至新版本"，实际 6 个文件全部停留在旧版本——这种"批量假落地"模式在文档同步、版本号更新、跨文件引用替换等场景中复现率极高。

### 2.3 第三层：subagent 声明 spot-check

**针对陷阱**：subagent 报告 ≠ 工具证据可信。

**触发条件**：subagent 报告"已保护 X 不受影响"、"未找到 X"、"已验证 Y 不存在"等带"否定性结论"或"无影响结论"时。

**验证动作**：主代理不直接采纳 subagent 的结论性措辞，而是用**独立工具调用** spot-check：

- 对二进制文件（PDF、图片、压缩包），用脚本直接读取字节，确认关键内容存在与否
- 对文本文件，用 Grep 范围限定（`-A N -B N`）验证上下文，确认 subagent 报告的"未找到"不是范围截断导致
- 必要时直接用 Read 工具读取文件原始内容，对照 subagent 的描述

**判定规则**：

- 主代理独立验证结果与 subagent 报告一致 = 采纳
- 主代理独立验证结果与 subagent 报告冲突 = 以主代理验证为准，重新派发或调整

这一层是 E1 铁律中"成本最高"的一层，但也是覆盖 subagent 误判的唯一手段。它的核心不是"不信任 subagent"，而是"不信任 subagent 的措辞"——subagent 的工具调用是中性的，措辞是经过加工的，主代理必须越过措辞直接对照工具调用本身。

一个典型复现：subagent 报告"PDF 中不存在某关键标注"，主代理用脚本读取 PDF 二进制字节后发现标注实际存在，原因是 ripgrep 检测到 NUL 字节后跳过二进制文件，subagent 基于 ripgrep 结果误判。这一类故障只有 L3 能拦截。

### 2.4 三层的边界声明

需要明确：三层 spot-check 验证不能彼此替代。

- L1 通过不等于 L2 通过：文件被 tracked ≠ 文件内容被修改
- L2 通过不等于 L3 通过：主文件内容已修复 ≠ subagent 报告可信
- L3 通过不等于 L1 通过：subagent 报告真实 ≠ 主代理自己后续创建的文件已被 tracked

任何一层的"通过"都只覆盖该层对应的维度。三层必须分别执行，分别记录结果。

## 三、可复用的验证命令

下面给出一组通用化的验证命令，可以复制到任何 AI 代理协作的项目中使用。命令以 git / Grep / 通用脚本为主，不依赖任何项目特定工具。

### 3.1 L1：git tracked 验证

```powershell
# 单文件验证
git ls-files <path/to/file>

# 批量验证（prior session 声称修改了 N 个文件时）
$files = @("file1.md", "file2.md", "file3.md")
foreach ($f in $files) {
    $result = git ls-files $f
    if ([string]::IsNullOrEmpty($result)) {
        Write-Host "UNTRACKED: $f"
    } else {
        Write-Host "TRACKED:   $f"
    }
}
```

**判定**：

- 返回文件路径 = tracked
- 空输出 = untracked
- 输出与声称的文件清单不一致 = 部分漏网

### 3.2 L2：文件内容 spot-check

```powershell
# 修复前的值（命中说明修复未落地）
# 搜索旧版本号 / 旧字符串 / 旧引用
Grep "v1.0.0"            # 旧版本号示例
Grep "old_section_name"  # 旧章节名示例
Grep "old_function_name"# 旧函数名示例

# 修复后的值（命中说明修复已落地）
Grep "v1.0.1"            # 新版本号示例
Grep "new_section_name"  # 新章节名示例
Grep "new_function_name"# 新函数名示例
```

**判定**：

- 旧值命中 + 新值不命中 = 修复未落地
- 旧值不命中 + 新值命中 = 修复已落地
- 两者都命中 = 部分修复，需逐处定位
- 两者都不命中 = 文件可能根本未被触及，需进一步排查

> 注意：上面的版本号、章节名、函数名只是示例。实际使用时，把"修复前的值"替换为本轮修改前的旧字符串，把"修复后的值"替换为本轮修改后的新字符串。两者必须能唯一定位修复点。

### 3.3 L3：subagent 声明 spot-check

```python
# 二进制文件（PDF / 图片 / 压缩包）：直接读取字节
# subagent 报告"未找到 X"时验证 X 是否真的不存在
with open("path/to/file", "rb") as f:
    content = f.read()

keyword = "目标字符串".encode("utf-8")
positions = []
start = 0
while True:
    idx = content.find(keyword, start)
    if idx == -1:
        break
    positions.append(idx)
    start = idx + 1

print(f"命中次数: {len(positions)}")
print(f"命中字节位置: {positions}")
```

```powershell
# 文本文件：用 Grep 范围限定验证上下文
# subagent 报告"X 不存在"时，验证 X 是否真的不存在
Grep "目标字符串" -A 5 -B 5
# 如果命中带上下文，subagent 报告有误
# 如果不命中，可初步采纳 subagent 结论
```

```powershell
# 直接读取文件原始内容对照 subagent 描述
Read <path/to/file>
```

**判定**：

- 主代理独立验证结果与 subagent 报告一致 = 采纳 subagent 报告
- 主代理独立验证结果与 subagent 报告冲突 = 以主代理验证为准，重新派发或调整 subagent 任务

### 3.4 5Why 根因分析模板

当 spot-check 发现 prior session 报告与实际状态不一致时，建议立即做一次 5Why 根因分析，沉淀为下一次的预防措施。模板如下：

```
Why 1: prior session 报告"已落地" →
Why 2: prior session 基于 Edit 工具返回值判断"已落地" →
Why 3: 但 Edit 工具可能因 old_string 不匹配而静默失败 →
Why 4: 或 prior session 在 Edit 后未 Grep 验证 →
Why 5: prior session 报告"已落地"但实际文件未修改

→ 根本原因：修复声明 ≠ 文件内容已修改
→ 预防措施：本 session 必须用 Grep 搜索修复后的值 spot-check
```

5Why 的价值不在于"找到责任人"，而在于把一次性的踩坑沉淀为可复用的预防约束，避免下一次 session 在同一条根因上重复踩坑。

## 四、三层互补关系

三层验证看似冗余，实则互补。下面阐述为什么"任一层单独都不够"。

### 4.1 L1 不足：tracked 不等于内容正确

L1 验证只能确认文件被纳入版本控制，无法确认文件内容是否被正确修改。prior session 可能：

- 创建了文件但内容为空或为占位符
- 创建了文件并写入了正确内容，但后续又被其他操作覆盖
- 创建了文件、写入了内容，但"修复"动作从未发生（只是 prior session 报告说发生了）

这些情况下 L1 都会返回"TRACKED"，但文件实际状态与 prior session 报告不一致。L1 必须与 L2 配合。

### 4.2 L2 不足：主文件修复不等于同步文档已落地

L2 验证只能确认主文件内容被修改，无法确认"同步动作"已发生。prior session 可能：

- 主文件已修复，但版本号、变更日志、索引文件等"同步文档"未同步
- 主文件已修复，但引用主文件的其他文件未同步更新
- 主文件已修复，但 prior session 报告说"6 个文件已同步"实际只有部分同步

这种"主文件正确 + 同步文档假落地"的模式在批量同步场景中复现率极高。L2 必须覆盖所有声称被同步的文件，而不仅是主文件。

### 4.3 L3 不足：subagent 验证不等于主代理验证

L3 验证只能确认 subagent 报告可信，无法替代主代理对自身后续操作的验证。即便 subagent 报告"已保护 X 不受影响"被主代理 spot-check 确认为真，主代理后续创建的文件、修改的文件、commit 的动作依然需要 L1 + L2 验证。

L3 的对象是 subagent，L1 / L2 的对象是主代理自己。两者不能混淆。

### 4.4 三层互补的本质

三层验证的本质是**分别覆盖"声明"的不同维度**：

| 层级 | 验证对象 | 信任源 | 工具 |
|:---:|:---|:---|:---|
| L1 | 文件 tracked 状态 | git 仓库本身 | `git ls-files` |
| L2 | 文件内容修复落地 | 文件内容本身 | Grep |
| L3 | subagent 报告真实性 | 主代理独立工具调用 | 脚本 / Grep / Read |

三层的"信任源"各不相同，互不重叠。git 仓库不能告诉主代理文件内容是否正确，文件内容不能告诉主代理 subagent 报告是否可信，subagent 报告不能告诉主代理文件是否被 tracked。三层各司其职，缺一不可。

### 4.5 与已有验证机制的边界

三层 spot-check 验证与项目内已有的"内容验证"机制（如事实核对、引用核对、逻辑校验）属于不同维度，不能相互替代：

- **内容验证**回答"内容是否正确"——事实是否准确、引用是否真实、逻辑是否自洽
- **spot-check 验证**回答"动作是否发生"——文件是否被 tracked、修复是否落地、报告是否真实

一个 prior session 可能内容验证全通过（事实准确、引用真实），但 spot-check 验证失败（文件未被 tracked、修复未落地、报告与文件状态不一致）。反之亦然。两类验证必须并行执行，任一通过都不能替代另一类。

## 五、可复用的执行清单

将上述方法论提炼为可直接照搬的执行清单。在每次跨 session 接续、每次 subagent 派发后收尾、每次修复动作落地后，按清单逐项执行。

### 5.1 接手 prior session 报告时

1. **不直接采信 prior session 的"已修改/已创建/已修复"措辞**。将所有声称的动作列为"待验证项"，逐项标记状态。

2. **对每一个 prior session 声称修改/创建的文件，独立执行 `git ls-files` 验证 tracked 状态**。空输出 = untracked，必须先 `git add` 再继续。批量声称时必须逐项验证，不能抽样。

3. **对每一个 prior session 声称"已修复"的位置，用 Grep 搜索修复前的值与修复后的值**。修复前值命中 + 修复后值不命中 = 修复未落地，必须重新修复。

4. **对 prior session 声称"已同步"的批量文件，逐一执行 L2 验证**，不能只验证主文件。批量同步是"假落地"高发场景。

5. **验证结果记录在本次 session 的开场笔记中**，标注"已 spot-check 通过 / 未通过 / 部分通过"，避免后续混淆。

### 5.2 派发 subagent 并收尾时

6. **subagent prompt 必含"禁止编造"约束**：禁止编造行号、字节位置、文件路径等可验证信息；若需引用，必须先用工具验证后使用真实值；无法验证时用"锚点 + 转述"代替。

7. **subagent 报告"否定性结论"或"无影响结论"时，主代理必须用独立工具调用 spot-check**：对二进制文件用脚本读取字节，对文本文件用 Grep 范围限定验证上下文，必要时直接用 Read 读取原始内容对照。

8. **subagent 报告的工具调用证据必须可追溯**：要求 subagent 报告附上原始工具调用结果（命中次数、字节位置、上下文片段），而非仅给出"已验证"的措辞。

### 5.3 修复动作落地后

9. **主代理自己执行修复后，立即用 L2 验证修复落地**：Grep 修复后的值，确认文件内容已实际修改。Edit 返回值不能作为"已落地"的唯一依据。

10. **主代理自己创建文件后，立即 `git add` 并用 `git ls-files` 验证 tracked**。不要等到下一次 commit 才发现文件漏网——批量创建 + 立即 tracked 的预防成本远低于事后补齐。

11. **批量同步动作落地后，对每一个被同步的文件执行 L2 验证**，记录每个文件的"已落地 / 未落地"状态。批量同步是"假落地"重灾区，逐项验证是唯一可靠手段。

### 5.4 收尾归档时

12. **本 session 收尾时，在交接文档中明确标注"已 spot-check 验证通过"的字段**，让下一个 session 的接手者知道哪些声明已经被独立验证、哪些只是基于报告采信。这是把 E1 铁律从"本 session 内部验证"扩散到"跨 session 协作文化"的关键一步。

---

## 总结

"修复声明 ≠ 修复落地"是 AI 代理协作中最朴素也最容易被忽视的事实。它朴素，因为任何写过几天代码的人都知道"说改了不等于真改了"；它容易被忽视，因为 prior session 的报告措辞往往过于专业、过于自洽，以至于接手者会下意识地把"声明"等同于"执行"。

E1 铁律的提出，不是为了否定 prior session 的可信度，而是为了在"声明"与"执行"之间补上一个独立的验证层。这个验证层由三层 spot-check 构成：L1 验证文件 tracked 状态、L2 验证文件内容修复落地、L3 验证 subagent 报告真实性。三层各司其职，互不替代，分别覆盖 git 仓库、文件内容、subagent 报告三个不同的"信任源"。

在大量真实复现中，这套方法论反复自我证明：即便在已经把 E1 铁律写进项目协作流程的项目里，新的"假落地"案例依然会被 spot-check 发现——证明铁律的价值不因流程化而衰减。每一次被发现，都是对"声明 ≠ 状态"这条根因的一次再次确认。

对外发布这篇文章，不是为了让读者把 E1 铁律原样照搬——每个项目的协作流程、工具链、信任模型都有差异。而是为了把一个被反复验证过的方法论骨架交出去：**任何 prior session 的报告都不能被默认信任，必须经过主代理独立 spot-check 验证才能进入下一步操作**。把这个原则放进你自己的协作流程，无论你用 git、用其他版本控制系统，还是用任何 AI 代理工具链，它都成立。

修复声明不等于修复落地。这是 AI 代理协作时代，每一个接手者都应该默念的句子。
