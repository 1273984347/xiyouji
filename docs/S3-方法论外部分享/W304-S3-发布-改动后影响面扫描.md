# 改动后影响面扫描——三步法 + 五类典型影响面的同步更新纪律

> 轨标：外部分享

## 引子

让 AI 代理改一个文件，它通常改得很干净——目标文件本身是对的，diff 也漂亮。但当你顺着下游引用读过去，问题就浮现了：标题改了，索引文件还指向旧标题；路径移了，README 里的链接还在原地；接口签名变了，调用方仍然按旧签名传参。

这不是模型能力不足，也不是提示词没写清楚，而是一类被广泛低估的工程陷阱：**改动后影响面未扫描**。代理默认把"改动"理解为"修改目标文件本身"，而不是"修改目标文件 + 同步所有受影响的下游引用"。结果是：目标文件正确，下游文件长期保留旧值，且无任何报错——唯一能发现它的方式是事后用检索工具逐点验证。

本文沉淀一套可复用的方法论：**三步影响面扫描法 + 五类典型影响面分类**，帮助 AI 代理协作、项目管理和工程自动化场景下的从业者把"改动 ≠ 仅修改目标文件"变成一条可执行、可验证、可移植到子代理 prompt 的纪律。

---

## 一、问题背景

### 触发场景

主代理或子代理（subagent）修改一个文件/组件后，未扫描所有依赖该文件/组件的其他文件。典型表现：

- 修改了某文件的标题/路径/版本号，但下游引用该标题/路径/版本号的文件未同步更新
- 修改了某组件的接口/签名，但调用该组件的文件未同步更新
- 修改了某文档的结构，但索引文件（README/STRUCTURE/file-index）未同步更新

### 典型表现

- 修改文件 A 后，文件 B/C/D（引用 A 的标题/路径/版本号）仍保留旧值
- 事后用检索验证时发现下游引用未同步
- 用户/接手者阅读下游文件时发现引用与实际不符

### 共同根因

主代理改动时只关注"被修改的文件本身"，未执行影响面扫描检查"依赖该文件的其他文件是否需要同步更新"。**改动 ≠ 仅修改目标文件，还包括所有受影响的下游文件。**

可以用一个 5Why 根因分析来锁定本质：

```
Why 1: 主代理修改文件 A 后未扫描影响面
Why 2: 主代理只关注"被修改的文件本身"
Why 3: 主代理未识别"改动 ≠ 仅修改目标文件"
Why 4: 主代理未执行检索工具搜索下游引用
Why 5: 下游引用文件保留旧值，用户/接手者阅读时发现引用与实际不符

根本原因：改动时未执行影响面扫描，仅关注目标文件本身
预防措施：改动后必须检索被修改属性值的所有引用，同步更新下游文件
```

## 二、核心铁律

### 改动后影响面扫描原则

> 修改一个文件/组件后，必须扫描所有依赖该文件/组件的其他文件是否受影响，若受影响必须同步更新。

### 操作步骤

1. **识别改动点**：明确本次改动修改了哪些文件/组件的哪些属性（标题/路径/版本号/接口/签名/结构）
2. **检索搜索引用**：用全文检索工具搜索被修改的属性值，列出所有引用该属性的文件
3. **逐文件判断**：判断每个引用文件是否需要同步更新
4. **同步更新**：对需要同步更新的文件执行编辑
5. **抽样验证（spot-check）**：验证所有引用文件的属性值已同步为新值

## 三、复现案例

下面三个通用案例覆盖了最常见的三类触发形态。它们不是孤立的偶发事件，而是同一根因在不同任务形态下的反复出现。

### 案例一：文档标题改名后索引未同步

**场景**：将一份文档的标题从"快速开始"改为"入门指南"，对应文件本身修改完成。

**操作**：代理仅修改了文件本身的标题字段，未扫描其他引用该标题的文件。

**结果**：项目根目录的 README 索引、文档目录结构表、反向文件索引仍然显示"快速开始"。新成员按 README 跳转时找不到对应文件，误以为文档已删除。

**修复**：用全文检索搜索"快速开始"关键字，列出 README、目录索引、反向索引三个引用文件，逐个替换为新标题"入门指南"，再次检索确认无残留。

**教训**：标题是文档的"对外契约"，下游所有引用方都依赖该契约；改标题必须扫面，不是改完文件就结束。

### 案例二：版本号升级后历史段被错误覆盖

**场景**：将某组件的版本号从 `v1.2.0` 升级到 `v1.3.0`，需要同步更新所有引用该版本号的文件。

**操作**：代理用全文检索搜索 `v1.2.0`，找到 5 个引用文件后一次性全部替换为 `v1.3.0`。

**结果**：CHANGELOG 历史段中 `v1.2.0` 的发布记录被错误覆盖为 `v1.3.0`，导致历史版本发布时间线丢失。

**修复**：区分"现役引用"与"历史引用"——README 头部、目录结构表中的版本号属于现役引用，同步更新为新版本；CHANGELOG 历史段、版本史中的版本号属于历史引用，保留旧版本号。再次检索确认现役引用已同步、历史引用未误改。

**教训**：版本号扫描必须区分历史 vs 现役，不能"一次 replace_all 全搞定"。

### 案例三：组件接口签名变更后调用方未更新

**场景**：将某工具函数的签名从 `getUser(id)` 改为 `getUser(id, options)`，文件本身已修改并提交。

**操作**：代理修改了函数定义文件，但未检索调用该函数的其他文件。

**结果**：3 个调用该函数的文件仍按旧签名调用，运行时未报错（因为 `options` 参数在新签名中是可选的），但实际行为已与预期不符——调用方未传递预期的配置项。

**修复**：用全文检索搜索 `getUser(` 关键字，列出所有调用文件，逐个判断是否需要补充 `options` 参数；对需要补充的调用方执行编辑，再次检索确认全部调用已同步。

**教训**：接口/签名变更最危险——既不会立即报错，也不会立即被发现，是"沉默的下游失配"的典型形态。

### 复现频率声明

上述案例并非孤例。在持续的工程实践中，这类问题以稳定的频率反复出现，且往往在用户/接手者阅读下游文件时才被发现。这说明它不是某次操作失误，而是一个需要制度化预防的系统性问题。

## 四、修复策略

### 三步影响面扫描法

| 步骤 | 动作 | 工具 |
|:---:|:---|:---|
| 1 | 识别改动点（哪些文件/组件的哪些属性被修改） | 人工判断 |
| 2 | 检索被修改属性值的所有引用 | 全文检索（搜索旧值） |
| 3 | 同步更新下游引用文件 + 抽样验证 | 编辑 + 检索验证 |

### 五类典型影响面分类

| 改动类型 | 影响面 | 同步操作 |
|:---|:---|:---|
| 修改文件标题 | README 索引 / 目录结构表 / 反向文件索引 / 引用该标题的文档 | 检索旧标题，同步更新 |
| 修改文件路径 | README 索引 / 目录结构表 / 反向文件索引 / 引用该路径的链接 | 检索旧路径，同步更新 |
| 修改版本号 | README 头部 / 目录结构表 / 变更日志当前段 / 反向文件索引 | 检索旧版本号，区分历史 vs 现役 |
| 修改组件接口/签名 | 调用该组件的所有文件 | 检索旧接口/签名，同步更新 |
| 修改文档结构 | README 索引 / 目录结构表 / 反向文件索引 | 检索旧结构引用，同步更新 |

### 版本号扫描的"历史 vs 现役"区分原则

影响面扫描中，版本号是最容易出错的一类。原因在于它跨两类引用：

- **现役引用**（README 头部 / 目录结构表 / 变更日志当前段）——表示"当前是什么版本"，必须同步更新为新版本号
- **历史引用**（变更日志历史段 / 版本史）——表示"过去发布过什么版本"，必须保留旧版本号

正确做法：检索到旧版本号后，逐条判断属于现役还是历史，现役同步更新、历史保留不动。**不能用 `replace_all` 一次性替换所有匹配项**，否则会误改历史记录。

## 五、预防措施

### 改动后必执行操作

1. **识别改动点**：明确本次改动修改了哪些属性
2. **检索搜索引用**：用全文检索工具搜索被修改属性值的所有引用
3. **同步更新下游**：对需要同步更新的下游文件执行编辑
4. **抽样验证**：验证所有引用文件的属性值已同步为新值

### 与"配置变更验证"方法论协同

通用的"配置变更验证"方法论要求对前序会话报告"已落地"的修改做抽样验证。本方法论则补充"改动后下游引用是否同步"，两者互补：

| 方法论 | 验证对象 | 触发条件 |
|:---|:---|:---|
| 配置变更验证 | 前序会话报告"已落地"的修改 | 前序会话报告 |
| 改动后影响面扫描（本方法论） | 改动后下游引用是否同步 | 当前会话执行了改动 |

### 与"双索引可追溯"实践协同

在维护"正向时间线（变更日志）+ 反向文件索引"的双索引实践中，若修改某文件的标题/路径/版本号，必须同步更新双索引。本方法论是双索引维护的执行层约束——双索引的"同步"动作本身就是影响面扫描的产出之一。

### 派子代理时

子代理的任务 prompt 必须显式包含约束：

```
子代理修改文件后：
1. 必须识别本次改动修改了哪些属性（标题/路径/版本号/接口/签名/结构）
2. 必须用全文检索搜索被修改属性值的所有引用
3. 必须同步更新下游引用文件
4. 必须抽样验证所有引用文件已同步为新值
5. 不可仅修改目标文件而不扫描影响面
```

## 六、关联文档

### 方法论关联

- **配置变更验证方法论**：本方法论与之互补——前者验证"前序报告是否落地"，本方法论验证"改动后下游引用是否同步"。
- **版本号同步方法论**：版本号扫描时区分"历史 vs 现役"，是本方法论在版本号场景下的细化规则。
- **双索引可追溯实践**：本方法论是双索引维护的执行层约束，双索引的"同步"是影响面扫描的产出之一。
- **子代理任务模板**：子代理 prompt 模板应内嵌本方法论的约束条款，让纪律自动生效。

把上述方法论压缩成一张可随身携带的检查清单：

- [ ] 版本号场景：是否已区分"现役引用"与"历史引用"？

**执行后**
- [ ] 是否已对需要同步的下游文件执行编辑？
- [ ] 是否已用全文检索抽样验证所有引用已同步为新值？

- [ ] 子代理 prompt 是否内嵌了上述五条约束？

## 总结

"修改了目标文件"不等于"改动已完成"。在 AI 代理协作的工程实践中，前者几乎总是成立，后者却可能长期处于半完成状态——目标文件正确，下游引用滞后，且整个过程无报错、无异常、无日志。这才是这类问题最危险的地方：**它不报错，只留下不一致的债务**。

应对它的关键不是更聪明的模型，而是一套工程化的纪律：

1. **识别**：在改动前识别修改了哪些属性，预判可能受影响的下游文件类型。
2. **扫描**：改动后用全文检索搜索被修改属性值的所有引用，逐文件判断是否需要同步。
3. **同步**：对需要同步的下游文件执行编辑；版本号场景下区分历史 vs 现役，避免误改历史记录。
4. **验证**：抽样检索所有引用文件，确认已同步为新值、无旧值残留。
5. **预防**：把约束内嵌进子代理 prompt，让纪律自动生效。

记住那条核心铁律：**修改一个文件/组件后，必须扫描所有依赖该文件/组件的其他文件是否受影响，若受影响必须同步更新**。这条规则简单到容易被忽视，但它能在你不注意的时候，挡住一次跨文件的沉默失配。
