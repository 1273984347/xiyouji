# 文档同步区分历史 vs 现役——Grep 搜索旧值的陷阱与三步分类法

> 轨标：外部分享

## 引子

当 AI 代理（Agent）开始承担版本发布、配置变更、文档同步等工程化任务时，"用 Grep 搜索旧值，再逐一替换为新值"几乎是它最本能的工作方式。看起来既高效又严谨——直到有一天你回读 CHANGELOG，发现历史变更日志里那条"v1.0 升级到 v1.1"的记录，被悄悄改成了"v1.2 升级到 v1.3"。

历史被重写了，而且没有任何报错。

这不是模型幻觉，也不是提示词缺陷，而是一类被广泛忽视的工程陷阱：**Grep 搜索旧值会同时命中两类语义截然不同的条目——"现役描述"与"历史变更日志"**。前者必须更新为新值，后者必须原样保留。如果不加区分地"全部替换"，就会破坏历史事实的完整性。

本文沉淀一套可复用的方法论：从两类条目的本质区别、三步分类法、五类典型文件分类、到 Grep spot-check 双向验证，帮助 AI 代理协作与工程自动化场景下的从业者把这类"无声的历史重写"变成可控、可预防的工程纪律。

---

## 一、问题背景

### 触发场景

版本 bump 后做文档同步（README 头部 / 结构表格 / CHANGELOG 当前段 / 反向索引文件）时，主代理常用 Grep 搜索旧版本号或旧值，以确认"哪些位置需要更新"。Grep 返回结果中既包含**当前版本段（现役描述）**也包含**历史变更日志段（历史事实）**。

若主代理不区分两类条目，把历史变更日志中的旧版本号也"修复"为新版本号，会破坏历史事实的完整性——CHANGELOG 中"上一个版本发布于 X"的历史记录不应被改成"上一个版本发布于 Y"。

### 两类条目的本质区别

| 类别 | 典型位置 | 描述内容 | 处置 |
|:---|:---|:---|:---|
| 历史条目 | CHANGELOG 历史段 / 结构文档版本史历史行 | 描述"某历史版本当时的状态" | 保留旧值（历史事实不可改） |
| 现役描述 | README 头部 / 结构文档当前表格 / CHANGELOG 当前版本段 | 描述"当前状态" | 必须更新为新值 |

### 共同根因

Grep 是无状态文本匹配，无法区分"该条目描述当前状态还是历史状态"。主代理必须基于条目所在**语义位置**做判据，不可基于"是否命中旧值"做判据。

可以用一个 5Why 根因分析来锁定本质：

```
Why 1: 主代理用 Grep 搜索旧值准备更新
Why 2: Grep 返回结果同时命中历史段和现役段
Why 3: 主代理基于"是否命中旧值"判据决定是否更新
Why 4: 该判据无法区分历史事实与现役描述
Why 5: 主代理把历史变更日志中的旧版本号一并改成新版本号

根本原因：Grep 无状态文本匹配，不可基于"命中旧值"做更新判据
预防措施：必须基于条目所在语义位置（历史段 vs 现役段）做判据
```

## 二、核心铁律

### 判据

> 该条目是否描述"当前状态"？
> - 是 → 更新为新值
> - 否（描述历史某版本状态）→ 保留旧值

### 操作步骤

1. **Grep 搜索旧值**：列出所有命中位置
2. **逐条分类**：基于命中行所在的语义段落判断——README 头部 / 结构表格 / CHANGELOG 当前段 = 现役；CHANGELOG 历史段 / 版本史历史行 = 历史
3. **更新现役条目**：Edit 现役描述为新值
4. **保留历史条目**：不动历史变更日志中的旧值
5. **Grep spot-check 双向验证**：搜索新值确认现役条目已更新 + 搜索旧值确认仅剩历史条目命中

第 5 步的"双向"是关键：只验新值会漏掉"历史段被误改"的情况，必须再验旧值确认它仅出现在历史段中。

## 三、复现案例

下面两个通用案例覆盖了最常见的两类触发形态。它们不是孤立的偶发事件，而是同一根因在不同任务形态下的反复出现。

### 案例一：三文件同步中的历史段误改

**场景**：版本升级后，需要同步更新 README 头部、结构文档表格、CHANGELOG 当前段三处现役描述。

**操作**：主代理用 Grep 搜索旧版本号以定位需要更新的位置。

**结果**：Grep 返回 30 余处命中，主代理初版处置一度把所有命中位置全部 Edit 为新版本号——其中包括 CHANGELOG 历史段中上一版本的发布记录。事后基于"该条目是否描述当前状态"判据重新分类，才把历史段恢复为旧值。

**修复**：逐条分类后，现役 6 处更新为新值，历史 24 处保留旧值；Grep 双向验证通过。

**教训**：Grep 命中数 ≠ 需要更新的位置数。"命中旧值"只是发现候选位置，不可作为"必须更新"的判据。

### 案例二：跨会话报告"已落地"实际停留在旧值

**场景**：前序会话报告"6 个文件已同步到新版本"，主代理接管后发现实际全部停留在旧版本号——典型的"假收敛"现象。

**操作**：主代理用 Grep 搜索旧版本号，准备把旧值改为新值。

**结果**：Grep 同时命中 CHANGELOG 历史段（上一版本的发布记录，应保留）与 README / 结构文档的现役描述（应更新）。主代理逐条分类后，更新现役描述为新值、保留历史段旧值，并对 30 处新值命中做 spot-check 验证全部通过。

**修复**：现役条目全部更新为新值，历史条目原样保留；双向 Grep 验证旧值仅剩历史段命中。

**教训**：跨会话的"假收敛"叠加"Grep 命中两类条目"陷阱，会让问题更隐蔽——必须既验"新值是否落地"，又验"旧值是否仅剩历史段"。

### 复现频率声明

上述案例并非孤例。在持续的工程实践中，这类"历史段被误改"以稳定的频率反复出现，且往往在事后双向验证时才被发现。这说明它不是某次操作失误，而是一个需要制度化预防的系统性问题——尤其在 AI 代理协作场景下，Grep 是代理最常用的定位工具，陷阱触发概率被显著放大。

## 四、修复策略

### 三步分类法

| 步骤 | 动作 | 工具 |
|:---:|:---|:---|
| 1 | Grep 搜索旧值，列出所有命中位置 | `Grep "旧值"` |
| 2 | 逐条分类：现役描述 vs 历史条目 | 人工判断（基于语义位置） |
| 3 | 仅更新现役描述，保留历史条目 | Edit + Grep spot-check 双向验证 |

三步之内必定能完成分类与处置：第 1 步发现候选，第 2 步分类，第 3 步处置并验证。整套方法论的可复用核心就在这三步。

### 五类典型文件分类

| 文件 | 现役部分 | 历史部分 |
|:---|:---|:---|
| README | 头部"当前版本" | 无（README 不保留历史版本号） |
| 结构文档（STRUCTURE） | 表格当前结构 | 版本史段（各历史版本行保留原值） |
| CHANGELOG | 当前版本段 | 历史版本段（保留原值） |
| 反向索引文件 | 当前索引 | 历史变更记录（保留） |
| 项目说明 | 当前项目说明 | 无 |

这张表是分类时的快速参照：前四类文件**同时存在现役部分与历史部分**，是陷阱高发区；后两类文件只有现役部分，相对安全。但"相对安全"不等于"无需分类"——任何 Grep 命中都必须经过语义位置判断。

### 错误示例与正确示例

| 错误处置 | 正确处置 |
|:---|:---|
| Grep 旧值命中 30 处，全部 Edit 改为新值 | 逐条分类：现役 6 处更新为新值，历史 24 处保留旧值 |
| 把 CHANGELOG 历史段的旧版本号改为新版本号 | CHANGELOG 历史段保留旧版本号（历史事实） |
| 把结构文档版本史历史行的版本号改成当前版本 | 版本史历史行保留原版本号（历史事实） |
| 只验新值命中数，不验旧值剩余命中 | 双向验证：新值命中数 = 现役条目数 + 旧值仅剩历史段命中 |

## 五、预防措施

### 文档同步前必读

1. **Grep 搜索旧值只是发现候选位置**，不可作为"必须更新"的判据
2. **逐条分类是必须步骤**，不可省略——任何"全部替换"的诱惑都要拒绝
3. **历史变更日志条目永远保留旧值**，这是历史事实完整性的硬约束
4. **Grep spot-check 必须双向**：既验新值落地，又验旧值仅剩历史段

### 与"假收敛验证"方法论协同

通用的"假收敛验证"方法论要求对前序会话报告"已落地"的修改做 spot-check，本方法论则补充"Grep 命中旧值后如何处置"。两者互补：

| 方法论 | 验证对象 | 触发条件 |
|:---|:---|:---|
| 假收敛验证 | 前序会话报告"已落地"是否真实 | Grep 搜索新值 spot-check |
| 历史vs现役分类（本方法论） | Grep 搜索旧值的命中结果如何处置 | 逐条分类（历史 vs 现役） |

前者验证"是否落地"，后者验证"如何处置命中结果"。在跨会话场景下，两者往往同时触发——前序会话假收敛遗留旧值，当前会话用 Grep 搜索旧值时又面临历史段与现役段的区分。两套方法论联合使用，才能形成完整的"发现 → 分类 → 处置 → 验证"闭环。

### 与"配置变更 spot-check"方法论协同

通用的"配置变更 spot-check"方法论要求关键修改后做抽样验证。本方法论补充：spot-check 时必须**双向验证**——

- 搜索新值：确认现役条目已更新（落地验证）
- 搜索旧值：确认仅剩历史条目命中（历史完整性验证）

只做单向验证会漏掉"历史段被误改"的情况，这是本方法论最容易被忽视的细节。

## 六、关联文档

### 方法论关联

- **假收敛验证方法论**：本方法论与之协同——前者验证"是否落地"，本方法论验证"如何处置命中结果"。
- **配置变更 spot-check 方法论**：本方法论补充其验证维度，要求 spot-check 双向（新值落地 + 旧值仅剩历史段）。
- **深度复检循环方法论**：文档同步维度应用本方法论，作为复检循环的关键检查项。
- **协作闭环方法论**：收尾阶段的文档同步应直接套用本方法论的三步分类法。
- **双索引可追溯方法论**：双索引维护时区分历史 vs 现役，本方法论是其前置约束。

## 可复用清单

把上述方法论压缩成一张可随身携带的检查清单：

**执行前**
- [ ] 是否已识别本次同步涉及哪几类文件？（参考五类典型文件分类表）
- [ ] 是否已明确哪些文件同时存在现役部分与历史部分？

**执行中**
- [ ] Grep 搜索旧值后，是否逐条分类（现役 vs 历史）？
- [ ] 是否拒绝了"全部替换"的诱惑？
- [ ] 历史变更日志条目是否原样保留旧值？

**执行后**
- [ ] 是否做了 Grep spot-check 双向验证？
- [ ] 新值命中数是否等于现役条目数？
- [ ] 旧值是否仅剩历史段命中（确认历史段未被误改）？

**派子代理时**
- [ ] 子代理 prompt 是否内嵌了"逐条分类 + 双向验证"约束？
- [ ] 是否明确告知子代理"历史变更日志条目永远保留旧值"？

## 总结

"Grep 命中旧值"不等于"必须更新该位置"。在文档同步场景下，前者几乎总是同时命中现役描述与历史变更日志，后者却只能针对现役描述——这才是这类问题最危险的地方：它不报错，只重写历史。

应对它的关键不是更聪明的模型，而是一套工程化的纪律：

1. **识别**：在执行前识别本次同步涉及的文件类别，区分"只有现役部分"与"现役+历史并存"两类。
2. **分类**：用三步分类法对每一条 Grep 命中做语义位置判断——现役段更新，历史段保留。
3. **验证**：执行后做 Grep spot-check 双向验证——新值落地 + 旧值仅剩历史段。
4. **预防**：把约束内嵌进子代理 prompt，让纪律自动生效。

记住那条核心铁律：**Grep 搜索旧值只是发现候选位置，逐条分类才是处置判据；历史变更日志条目永远保留旧值，spot-check 必须双向**。这条规则简单到容易被忽视，但它能在你不注意的时候，挡住一次无声的历史重写。
