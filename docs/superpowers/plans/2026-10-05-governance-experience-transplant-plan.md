## 一、移植方法与总原则

1. **逐项对照 xiyouji 现状，已有的明确不移植，只立经核实的缺口**（§二对照 + §2.7 不移植表）；
2. **每条新门禁必须自带负样本自证（违例必红、恢复必绿）**——本仓第 25/27/28 门禁已有 `--self-test` 先例，沿用该纪律；
3. **每条新规则在仓内必须有唯一权威位置，其他文件锚定引用**（防双头漂移）；
4. **触及铁律 8 管控文件（verify_delivery.py）以本方案为用户批准载体**：拍板后仅允许「新增门禁段 + 段计数上报行 + 收尾自洽断言」，不碰既有检查逻辑（W576 修 bump_version 先例：管控文件改动须用户明示批准）；
5. 收官判据 = §五。

### T3 verify_delivery 本体段计数自洽锁（VERIFY_SECTIONS）

- **改动文件**：仅 `scripts/verify_delivery.py`。
- **内容规格**：①模块顶部 `EXPECTED_SECTIONS = N`（N = 落地当日 `# ----` 阻断段实数，当批复测）；②每段段首新增一行计数上报（`section("<段名>")` 或等价最小形态——`section()` 为 3 行闭包，命中即记名）；③收尾 `sys.exit(main())` 之前追加断言：实跑段名集合 ⊇ 预期段集合，缺任一即 `fail("门禁段实跑 N ≠ 声明 M：缺 <段名>")`（核心 FAIL 非 0 阻断已满足）。若盘点发现某段存在条件跳过形态，该段上报点置于跳过分界之前并在段名表登记为恒跑——**禁止把「跳过」计为「通过」**。
- **验收标准（含负样本自证）**：1) 全量跑输出与改动前逐字一致 + 恰新增 1 行自洽声明行，exit 0；2) 负样本：临时注释掉任一段的上报行 → exit 非 0 且点名缺段；恢复 → exit 0；3) 第 31 槽（T2）门数真值与 EXPECTED_SECTIONS 对拍一致（两任务互为印证）。
- **边界**：不碰任何既有检查逻辑与词表；不改输出行文（除新增 1 行）。
- **规模**：半个 session。

### T4 CI 加固（SHA 钉死 + permissions 收敛 + security dispatch）

- **改动文件**：`.github/workflows/` 5 个 yml + `.github/workflows/README.md`（头部版本行随批级联）。
- **内容规格**：①全部 `uses:` 改 commit SHA 钉，注释保留 tag 名（`actions/checkout@<SHA> # v7`）——**SHA 用 `git ls-remote` 实测取得，禁凭记忆转录**（GateKeeper workflow 同款纪律）；②逐 workflow 盘点所需最小权限并顶层声明 `permissions:`（pages.yml 既有声明保留；upload-artifact/deploy-pages 等所需权限按官方文档逐一对，改后实跑验证，不凭印象写死）；③security.yml 补 `workflow_dispatch:`；④dependabot github-actions ecosystem 不动（SHA 钉兼容，其 PR 会带 tag 注释）。
- **验收标准**：1) 推送后 5 个 workflow 全绿（本批为配置类改动，无负样本步骤——如实声明，验收 = 全 workflow 实跑绿 + diff 逐行人工复核）；2) `grep -rn "uses:.*@v" .github/workflows/` 0 命中（全 SHA 钉复核）；3) 连续 2 批推送 CI 绿（防一次性侥幸）。
- **边界**：不改触发条件语义（push/PR/schedule/paths 全保留）；不动 concurrency 与步骤逻辑。
- **规模**：1 个 session（含等 CI 跑完）。
