# 多 Agent 同仓协作干扰治理路线图

> **版本**：v1.0（2026-10-14 · W740 入库）。**定位**：决策 + 实施文档——不追求穷举，只保留能决策、能执行、能退出的内容。**来源**：用户下发的多 Agent 干扰治理穷举分析（A–P 十六类 + 元层/架构层/战略盲区/第一性原理四轮）经「做减法」收敛；机制层第一项（对账表 touches + preflight 交集拒绝）已由 W739 落地。**维护契约**：度量结论回写 §2、路线状态回写 §3（☐→✅）、日志表 §8 追加式；结构性修订须对账表登记 `type=rule-change` 独占批。

## 0. 决策摘要（五条·先读这里）

1. **不追求零干扰**。干扰不可能的三条件（单 Agent / 状态不可变 / 窗口为零）在本项目物理上不可满足——目标是「干扰频率 × 损失」最小化，接受不完美。
2. **暂不 worktree**。W698 评估关闭维持不变；重启条件 = safe_commit 自动重试频率 > 1 次/周（当前远未达到）。
3. **唯一写路径是第一原则**。共享可变状态（级联面/对账表/门禁自洽锁）只走 batch_cascade 单写路径 + 主 Agent 串行；子 Agent 只并行独立内容块（W671 三场景升格为总纲，见 §1）。
4. **只对高频高损建机制**。先跑两周干扰日志测出 N/p/T（§2），不看实测数据不排机制优先级——工作量估计必须含六文档/门禁/对账表级联同步成本，纯编码工时是误导。
5. **机制必须有生命周期**。每个机制登记时同时登记触发条件、验收指标、退出条件（§5）；每季度主动减量（§6）——对抗门禁/S 卡/BL/坑位清单的单侧熵增。

## 1. 总纲（第一性原理·所有机制的上位依据）

- **干扰的字面定义**：一个 Agent 的行动破坏了另一个 Agent 的**意图**——三要素 = 意图 / 行动（读+写）/ 破坏（读到 v1、写回时抹掉 v2）。
- **干扰在物理上不可能的三条件**：① 只有一个 Agent；② 状态不可变（append-only）；③ 读→写窗口为零。三者均不可满足（LLM「感知-思考-行动」的思考时间是硬约束）→ **完美协作不存在，只有最优不完美**。
- **频率模型**：`干扰频率 ∝ N × p × T`（N=并行 Agent 数，p=行动落在共享面的比例，T=读→写窗口时长）。**T 最易降（行为性：可见性压缩窗口），p 难降（结构性：架构分片），N 由吞吐需求决定**。
- **唯一写路径 > 多写者 + 检测**：`batch_cascade.py` 的本质不是自动化省工，是把多 Agent 对六文档的并行写**降级为单写者**——用结构消除问题，而非用检测压制问题。这是本项目已在执行的最高维解法，本路线图所有 P1/P2 机制都只是它的补充。
- **对账表的升级方向**：从「记录认领」到「预判冲突」的调度表——W739 touches 列 + 交集拒绝已落地第一步；调度语义（给定在途批次集合 + 新批次意图 → 判定能否起批）由 preflight `--touches` 承担。

## 2. 度量前置：两周干扰日志（唯一先行动作）

> **不看 N/p/T 实测值，任何机制优先级都是猜测。** W739 当日已实证一次 A 类事件（并行会话在两次 git 调用间完成 W738 收官推送）——说明 N≥2 是现实，但频率与损失未知。

**记录方式**：本批次起，任何会话遭遇干扰事件（含未造成损失险情）即在 §8 表格追加一行；跨会话共享、git 持久化。

**录入触发（强制·保证日志不空表）**：任何会话出现以下三种情况之一，**必须**在 §8 追加一行——① 开工 `git status` 发现「非本会话变更」；② 收工 `safe_commit` 触发重试；③ preflight 交集拒绝触发。

**复盘责任人**：2026-10-28 复盘批由当周主会话负责计算 N/p/T 并回写本节判定表；**空表本身也是有效结论**（两周零事件 = 共享面事件低于阈值 → P1 缓建坐实）。

**W820 补登（口径加严·治「不完整被误读为低发」）**：`空表是有效结论` 只在**登记完整**的前提下成立——表**不完整**（应有登记行而缺失）**同样不是有效结论**，不得据此坐实 P1 缓建。实证：2026-10-17~10-20 四天 128 提交零登记（原表停更于 10-16 最后一行），其间实际发生 ≥2 次强制触发事件（W812 撞号让号 / W815 preflight 交集拒绝，均有 commit 信息实证）——若按残表计算 N/p/T，会把高发期误判为低发期并错误坐实 P1 缓建。故 10-28 复盘时须先验**登记完整性**（对照 §2 强制触发三项逐条回查该窗口提交与门禁输出），完整性不达标时判定为**度量失败**并重记，**不得据残表做 P1 触发决策**。

**字段**：日期 / 会话 / 事件类（§7 四组编号）/ 共享面 / 读时状态 / 写时状态 / 损失与返工（分钟）。

**度量产出（2026-10-28 复盘批计算）**：
- **N** = 同时活跃会话数（按天取 max，日志「会话」列去重计数）
- **p** = 涉共享面事件数 ÷ 总批次数（近似）
- **T** = 典型会话时长（小时级即高危）
- **损失** = 返工分钟数合计 + 撞号/覆盖事件次数

**判定规则（度量驱动 P1 触发）**：
| 观测结果 | 动作 |
|---|---|
| N≥2 且共享面事件 ≥2 次/两周 | P0 剩余项全量推进 + write_receipt 提前实施 |
| 共享面事件 <1 次/两周 | safe_commit + touches 已足够；write_receipt 缓建（登记观察） |
| 出现「同时写同一文件双方都过收据」零窗口事件 | 才考虑文件锁类硬约束（当前判定不值得） |

## 4. 不建机制清单（登记即止）

以下方向**明确不做**，升级条件统一为「3 个月内实际发生 ≥2 次」（§5）：

- 逻辑时钟 / 向量时钟（单机多进程收益配不上复杂度）
- worktree 每会话一树（W698 已评估关闭）
- 事件溯源 + 派生视图全量重构（六文档改 append-only 架构·工期周级）
- 41 门禁收敛为 3–5 条不变式（门禁是实现层，砍掉即失去机器验证）
- OS 级文件锁（flock 类·跨平台复杂收益小）
- 跨机分布式一致性问题（单机多 Agent 前提下不存在）

## 5. 验收与退出（对抗机制自身的熵增）

**运行指标（每两周干扰日志复盘时核对）**：safe_commit 自动重试次数/周；touches 交集拒绝次数/周；干扰日志事件数/周；返工分钟数/周。

**解析鲁棒性指标**：touches 状态判定必须剥离 Markdown 强调符（当前实现 `re.sub(r"[\s*]+")` 全星号+空白剥离），并保有 `**已收官**`/单星/空白变体回归测试（`test_inflight_with_bold_status` 族·12 单测内）；**任何对账表排版变更后必须重跑该测试**——否则下一次「排版美化」会静默击穿在途判定（失效方向双向危险）。

**退出条件（三件套之二·缺一不可）**：
- 机制 3 个月无触发事件 → 降级为 AGENTS §4.3 坑位登记（撤工具保留纪律）。
- 门禁 6 个月无真实命中 → 评估退役（第 16 门禁退役为唯一先例，此条将其常态化）。
- S 卡关闭 6 个月 → 复核吸收路径是否仍成立；BL 冻结超 6 个月 → 复审或移除。

## 6. 减量周期（季度·首个窗口 2027-01）

每季度第一批（对账表登记 `type=减量`）主动砍：
1. 无命中门禁退役评估（§5 标准）；
2. 无消费者的 stats key 删除（有声明无读取即候选）；
3. 已吸收且过复核期的 S 卡归档；
4. 闭合 BL 移除；
5. pitfalls 坑位清单去重合并。

这是现有 41 门禁体系唯一没有的机制——门禁只会被创建，从未被系统性清理。
