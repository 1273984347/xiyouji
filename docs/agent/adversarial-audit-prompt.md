# 对抗式审查派发模板（W1000 沉淀 · 触发器 scripts/check_audit_trigger.py）

> **上次校准：W1022**（校准含义见文末「模板自身的维护」；超 20 批未校准应触发复核）
>
> **何时用**：触发器 ≥20 批点名时，或重大机制落地后主动派发。派发者 = 任意会话，
> 被派发者 = subagent（general-purpose），**只读不改**——审查者不修复，修复由派发会话
> 按发现清单执行（审查与修复分离，防「自己查自己改」的宽容偏差）。
>
> **为什么是「一个」subagent**：A–G 七项存在**交叉印证**（例：B 项看到 `i/lf w/crlf`，
> 才能与 D 项的 `open(...,"w")` 串成「eol 契约背离」这条 P2；拆开则各自只看到一半）。
> 该并行的是**穷举取证**，不是判断——切分方法与派发骨架见
> [parallel-evidence-template.md](parallel-evidence-template.md)。

## 派发 prompt 模板（复制后把「被审查声明」换成当期实际）

```text
你是资深审查员，对 D:\xiyouji 仓库（Windows，git-bash 环境）做一次严格对抗式审查。
只读不改——你的职责是找问题、给证据，不修复。凡声明过的事情都要对拍实况，
凡新代码都要读实现找缺陷。

## 背景（被审查对象）
<当期批次声明清单：每个批次一行「W###：声称了什么」，不信任这些声明，亲自验证>

## 必查清单（逐项执行，给命令输出作证据）
A. 仓库完整性：git status / git log -5 / HEAD 与 origin 关系 / git ls-files --eol 全量行尾普查
B. 守恒对拍：各治理文件正本+归档合看，抽查 5 个迁移样本逐字节比对
C. 门禁实跑：verify_delivery --scope docs 与 --scope full、check_doc_size_budget、
   check_gov_doc_claims、check_parser_anchor_coverage、check_doc_sync、各触发器 --self-test
D. 代码审查（读源码找缺陷·重点边界与并发）：<当期新增/改动的工具清单>
E. 文档三层一致性：AGENTS 铁律与计数 / CLAUDE.md ≤60 行 / pitfalls 分节计数 / 脚注五态
F. 同族残留：活性文档「只进不出」症状 / 正本指针目标存在性
G. 多 Agent 并发现场：最近提交交错 / 在途改动 / index.lock

## 输出要求
1. 总体判定（一句话）
2. 发现清单按严重级：P0（阻断/丢失/假绿）P1（真缺陷尽快修）P2（应修不急）P3（备注）
   ——每条带证据（文件:行号或命令输出）与建议修法
3. 声明与实况不符项单列（「声明 X·实测 Y」格式）
4. 通过项简列（一行一件）
注意：tmpe/ 为 gitignore 本地临时区不算发现；archive/ 追加式不改写是设计；
并行会话在途痕迹如实报告但不计 P 级（除非造成实际损坏）。绝对不要修改任何文件。
```

## 派发会话的收尾义务

1. 审查报告回来后 **P0/P1 立即修，P2 同批或次批修，P3 甄别留痕**（铁律 14）；
2. 修复与审查登记**同一批次号**落台账，认领行**必须在状态列写事件 token「对抗审查已派发」**（主题/摘要列写不算——描述本机制的行会自伤命中）（触发器只认 token，不认泛词「对抗式审查」——W1003 起：泛词会出现在「修审查问题」这类非派发行里，按字样判定会被静默重置计数）;
3. 修复批 CHANGELOG 段带「声明与实况不符项」小节（如 W998 先例）；
4. subagent 报告原文不入库（本地件），证据行号摘进 CHANGELOG 段即可。
5. **给历史事件补 token**（W1021 实证·坑表第 118 条）：凡「以登记 token 为事实源」的周期触发器，
   首次上线时历史事件必然没打过 token ⇒ 器会立刻报「从未做过」假警。**建器与补 token 必须同批**。
6. **在途不计事件**（W1022 实证·本模板曾漏）：认领行在派发时就写「在途（…已派发）」，
   若判据只认 token 字样，**写一行在途登记即可永久压制该哨**（实测把「已 23 批」压回 0）。
   事件语义应是「完结」而非「开始」。
7. **回写模板**（本节是被 W1022 审查发现后才补的）：审查结束后自问一句——
   「本次是否产生了应回写本模板的新检查项？」有则**就地并入对应小节并全篇去重**，
   同时更新头部校准戳；无则不动。只把教训写进 CHANGELOG 而不回写模板，下批照旧会漏。

## 模板自身的维护

- **校准戳**：头部「上次校准：W####」。判据 = 自该批起又过了多少批；≥20 批未校准即应复核
  （与触发器同阈值，避免出现「模板比项目老一代」）。
- **每条检查项可追溯**：新增项须标来源批次（如「W1022 补」），便于判断是否过期。
- **数字必须现测**：模板里写死的槽数/阈值/文件名会随批次漂移（实证：`verify_delivery` 已 52→57 段、
  坑表 115→118 条）。回写时**先实跑再落笔**，不要沿用上一版的数字。
- **不另立补充篇**：就地并入保持单一权威，另起「补充/后续」会造成第二事实源。

## 成本与节奏参考

- W998 首跑：subagent 约 40 分钟 / 3.9M tokens / 59 次工具调用，覆盖 A-G 全项；
- 20 批阈值下约每周触发一次（按当前并行节奏）；重大机制落地后可主动提前派发。
