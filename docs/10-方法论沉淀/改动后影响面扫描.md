# 改动后影响面扫描

> 改动后必须扫描影响面，避免副作用。修改一个文件/组件后，必须检查所有依赖该文件/组件的其他文件是否受影响

> 当前复现计数器：1/1 证据（2026-07-22 首次）
> 严重度：中等（影响改动完整性 + 跨文件一致性）
> 最新案例：2026-07-22 首次复现（修改某文件后未扫描依赖文件，导致下游引用未同步更新）

## 一、问题背景

### 触发场景

主代理或 subagent 修改一个文件/组件后，未扫描所有依赖该文件/组件的其他文件。典型表现：

- 修改了某文件的标题/路径/版本号，但下游引用该标题/路径/版本号的文件未同步更新
- 修改了某组件的接口/签名，但调用该组件的文件未同步更新
- 修改了某文档的结构，但索引文件（README/STRUCTURE/file-index）未同步更新

### 典型表现

- 修改文件 A 后，文件 B/C/D（引用 A 的标题/路径/版本号）仍保留旧值
- Grep 验证时发现下游引用未同步
- 用户/接手者阅读下游文件时发现引用与实际不符

### 共同根因

主代理改动时只关注"被修改的文件本身"，未执行影响面扫描检查"依赖该文件的其他文件是否需要同步更新"。改动 ≠ 仅修改目标文件，还包括所有受影响的下游文件。

---

## 二、核心铁律

### 改动后影响面扫描原则

> 修改一个文件/组件后，必须扫描所有依赖该文件/组件的其他文件是否受影响，若受影响必须同步更新。

### 操作步骤

1. **识别改动点**：明确本次改动修改了哪些文件/组件的哪些属性（标题/路径/版本号/接口/签名/结构）
2. **Grep 搜索引用**：用 Grep 搜索被修改的属性值，列出所有引用该属性的文件
3. **逐文件判断**：判断每个引用文件是否需要同步更新
4. **同步更新**：对需要同步更新的文件执行 Edit
5. **Grep spot-check 验证**：验证所有引用文件的属性值已同步为新值

### 5Why 根因分析

```
Why 1: 主代理修改文件 A 后未扫描影响面 →
Why 2: 主代理只关注"被修改的文件本身" →
Why 3: 主代理未识别"改动 ≠ 仅修改目标文件" →
Why 4: 主代理未执行 Grep 搜索下游引用 →
Why 5: 下游引用文件保留旧值，用户/接手者阅读时发现引用与实际不符

  根本原因：改动时未执行影响面扫描，仅关注目标文件本身
  预防措施：改动后必须 Grep 搜索被修改属性值的所有引用，同步更新下游文件
```

## 四、修复策略

### 三步影响面扫描法

| 步骤 | 动作 | 工具 |
|:---:|:---|:---|
| 1 | 识别改动点（哪些文件/组件的哪些属性被修改） | 人工判断 |
| 2 | Grep 搜索被修改属性值的所有引用 | `Grep "旧值"` |
| 3 | 同步更新下游引用文件 | Edit + Grep spot-check |

### 典型影响面分类

| 改动类型 | 影响面 | 同步操作 |
|:---|:---|:---|
| 修改文件标题 | README 索引 / STRUCTURE 表格 / file-index / 引用该标题的文档 | Grep 搜索旧标题，同步更新 |
| 修改文件路径 | README 索引 / STRUCTURE 表格 / file-index / 引用该路径的链接 | Grep 搜索旧路径，同步更新 |
| 修改版本号 | README 头部 / STRUCTURE 表格 / CHANGELOG 当前段 / file-index | Grep 搜索旧版本号，按 E2 铁律区分历史 vs 现役 |
| 修改组件接口/签名 | 调用该组件的所有文件 | Grep 搜索旧接口/签名，同步更新 |
| 修改文档结构 | README 索引 / STRUCTURE 表格 / file-index | Grep 搜索旧结构引用，同步更新 |

### 与 E2 铁律协同

E2 铁律要求"区分历史 vs 现役"。本铁律在影响面扫描时若发现版本号引用，需按 E2 铁律区分：
- 现役引用（README 头部 / STRUCTURE 表格）→ 同步更新为新版本号
- 历史引用（CHANGELOG 历史段 / STRUCTURE 版本史）→ 保留旧版本号

## 五、预防措施

### 改动后必执行操作

1. **识别改动点**：明确本次改动修改了哪些属性
2. **Grep 搜索引用**：用 Grep 搜索被修改属性值的所有引用
3. **同步更新下游**：对需要同步更新的下游文件执行 Edit
4. **Grep spot-check 验证**：验证所有引用文件的属性值已同步为新值

### 与 Preflight 三轨验证协同

Preflight 三轨验证（W076 首次落地）后必执行操作中包含本铁律：
- 轨 1：内容验证（DRL R1b/R2）
- 轨 2：git tracked 验证（E1 铁律）
- 轨 3：影响面扫描（本铁律）

三轨互补，任一轨不替代其他轨。

### 与双索引可追溯改造协同

双索引（CHANGELOG 正向时间线 + file-index 反向文件索引）维护时，若修改某文件的标题/路径/版本号，必须同步更新双索引。本铁律是双索引维护的执行层约束。

### 派 subagent 时

subagent prompt 必含约束：

```
subagent 修改文件后：
1. 必须识别本次改动修改了哪些属性（标题/路径/版本号/接口/签名/结构）
2. 必须 Grep 搜索被修改属性值的所有引用
3. 必须同步更新下游引用文件
4. 必须 Grep spot-check 验证所有引用文件已同步为新值
5. 不可仅修改目标文件而不扫描影响面
```
