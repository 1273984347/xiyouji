# CI 提速与门禁健壮性方法论

> **定位（W1068 建）**：把「CI job 怎么提速」与「门禁/依赖怎么不假绿」两件事的方法固化。
> **谁该读**：要改 CI 工作流、要让某个 job 变快、或遇到「CI 红了但看不出为什么」的人。
> **一句话**：**提速的前提是判据强度不降；门禁的前提是它自己先可被验证。**

---

## 一、提速四步序（按性价比，不按直觉）

改 CI 耗时前，**先量化「纯等待下限」**——它决定了你最多能省多少：

```
纯等待下限 = 页面数 × 每页固定等待 ÷ 并发数
```

本项目实证（暗色门禁）：782 页 × 4.7 s ÷ CONC 3 = **20.4 分钟**（实际 29–33 分钟）。
⇒ 天花板已知（并发拉满也只到 20.4 分钟），才知道必须改「等待」本身而不只是加并发。

按性价比排序（**越靠前越划算、越安全**）：

| 序 | 手法 | 收益 | 风险 | 本项目实证 |
|---|---|---|---|---|
| 1 | **固定等待 → 按需等待**（轮询至状态稳定，落定即采样） | 最大 | 低（须保留上限兜底） | 暗色审计：固定等待 → `waitForStable`/`waitForChange` |
| 2 | **加并发**（CONC 3 → 6） | 中 | 低 | 每页独立 context 时天然可并发 |
| 3 | **拆分片并行**（CI matrix） | 大 | 中（须合并产物后统一判定） | 暗色门禁拆 4 片（按**索引取模**负载均衡） |
| 4 | **减少重复执行**（同一件事只跑一次） | 极大 | 低 | contract smoke 从「4 分片各跑一遍」改为「只跑 shard 0」 |

**实测收益**：暗色门禁全链 **40.5 分钟 → 6 分 59 秒（≈5.8×）**。

### 1.1 两条容易踩的坑

- **分片用「索引取模」而非「连续切片」**：页面耗时分布不均，连续切片必有长尾，取模则负载自然均衡。
- **分片产物必须「合并后统一判定」**：判定语义要与改前完全一致；合并 job 对「一个分片都没找到」必须 **fail-closed（退出码 2）**，不得当「零命中」。

### 1.2 重复执行往往是最大的浪费

本项目里 contract smoke（file:// 全站冒烟）原先**每个分片各跑一遍全站 857 页** ⇒ 4 倍重复。
把它改成「只跑 1 片」比任何并发优化都划算。**先找重复，再找瓶颈。**

## 二、提速的验收纪律：新旧对照，不是「跑通即可」

改了等待/并发/分片逻辑后，**用同一批真实页面跑改动前后两版，逐页对比关键字段**（缺陷数 / 错误数 / 布尔标记），必须**完全一致**。

本项目实证：暗色审计新旧对照 5 页，`invisibleShapes / lowContrastText / errors / fatal / isDarkBg` 全部相同；contract smoke 新旧对照 20 页，`shapes / errors` 20/20 一致。

### 2.1 对照实验的三条纪律（都是本项目踩出来的）

1. **两版脚本放同一目录**——node/python 的模块解析按脚本位置逐级上溯，放到 temp 目录会让旧版 `require('playwright')` 解析不到 ⇒ 旧版直接崩、无产出 ⇒ **误判成「判据不一致」**。
2. **各读各自实际的产物路径**——旧版不支持 `--out` 时产物写默认路径，照抄新版的路径读 ⇒ 读到空文件。
3. **对照脚本自身须校验「产出行数 > 0」**——否则「脚本崩了」会被当成「判据变了」。

### 2.2 判据强度不降是前提

「按需等待」的关键在于**落定才采样 + 保留上限兜底**：永不落定时行为与原来持平。
**任何提速都不得让「漏检」成为代价**；若某个提速必须放宽判据才能达成，那是判据设计问题，不是提速问题。

## 三、门禁健壮性：四条让「假绿/假红」现形

### 3.1 判据必须能被证伪（负样本必红）

每条判据都要配负样本自测：**能判红才算数**。本项目 `scripts/check_action_refs.py` 的自测形态：

- 负样本必红：39 位 hex / tag 引用 / 7 位短 SHA / 40 位低熵 ghost SHA
- 正样本必绿：40 位合法格式 / 仓内真实存在的 ref

⚠ **自测夹具不得硬编码任何 SHA 字符串**——gitleaks 按熵值筛，高熵合成串必被拦 ⇒ 用低熵串 + 运行时从仓内文件抽取。

### 3.2 先怀疑判据，再动产品代码

本项目一天内被自己的判据骗两次：① 把「任何非 0 退出码」当「SHA 不存在」⇒ 一度准备去「修」4 处**真实存在**的 SHA；② 修完仍误判 ⇒ 根因又是判据自身的正则把**子目录 action**（`owner/repo/subdir@ref`）当仓库名。

⇒ **假阴性会诱使人改坏本来正确的代码。** 判据报错时，第一步是**复现判据本身**（同一目标换第二种方式验），不是改产品代码。

### 3.3 「查不到」≠「不存在」

任何依赖外部 API 的判据：

- **双 endpoint 复核**：两个都报「不存在」才判不存在；
- **404 与 422 都要算「不存在」**（SHA 格式合法但仓库无此 commit 时 GitHub 返回 422）；
- **限流 / 网络 / 解析失败一律算「无法判定」** ⇒ fail-closed 报出，但**不得据此改代码**；
- **外部 API 的可用性不应成为 PR 的单点阻塞**（CI 模式可降级为 WARN），但「判定为不存在」仍应阻断。

### 3.4 守卫必须独立于被守卫

语法守卫（工作流可解析性）若住在被守卫的工作流里，等于没有守卫——被守卫的坏掉时守卫自己不启动。
本项目把它独立成 `.github/workflows/workflow-lint.yml`，并要求**负样本实证**（把文件还原成坏形态 ⇒ 守卫必须报错并指到行号）。

## 四、CI 依赖红线：action ref 必须是真实存在的完整 SHA

### 4.1 症状与定位口诀

**「Set up job」阶段 1 秒内 failure（Checkout 都没跑）** ⇒ 优先查该 job 引用的 action ref 能否解析，
**而不是查基础设施**（runner 分配 / 限额 / 并发排队 / 僵尸 run 全都会误导）。

定位命令：`gh api repos/<owner>/<repo>/commits/<sha>`；
错误原文 `Unable to resolve action … unable to find version …` 即为编造或截断的 SHA。

本项目实证：W1066 批新增 merge job 时写入了一个 **39 位（少 1 字符）的编造 SHA** ⇒ 该 job 在 set-up 阶段直接失败，
症状看起来像 GitHub 基础设施故障，排查了 runner 分配、API 限流、并发排队、僵尸 run 四条路径全部无果。

### 4.2 修法与根修

- **不新造 SHA**：优先复用**仓内已验证存在**的同名 action SHA。
- **配机器判据**：形态判据（离线·零外部依赖·每次 PR 恒生效）+ 存在性判据（联网·双 endpoint 复核）。
- **子目录 action 解析**：仓库名只取 `owner/repo` 前两段，子目录不参与 API 路径拼接。

### 4.3 环境层（与仓库无关，勿写进 CI 排障结论）

Windows 上 `git push` 报「Failed to connect to github.com:443」但 `gh api` 正常 ⇒ 根因是 **git 的 OpenSSL TLS 指纹被中间层拒**：

```
git -c http.sslBackend=schannel -c http.version=HTTP/1.1 push origin <branch>
```

诊断顺序：① `gh api` 判「全网断还是仅 git 断」；② `Test-NetConnection <host> 443` 区分 TCP / TLS 层；
③ 看系统代理 `ProxyEnable`/`ProxyServer`；④ 依次试 schannel → HTTP/1.1 → 显式 proxy。

## 五、paths 过滤的陷阱：提速 ≠ 缩小验证面

给 workflow 加 `paths` 是最常见的「提效」手法，但**它缩小的是触发面，也可能是验证面**。

加过滤前必须先答：**这个 workflow 的 job 覆盖面是什么？过滤后会不会漏检？**

本项目实证：`security.yml` 里有 **brand guard（扫全仓含 archive/）** 与 **XSS detect（`--all`）** 两个 job，
`ci.yml` 含**分支保护 required check**（Delivery Gate + Unit Tests）⇒ 这三个 workflow **刻意不加 paths**：
过滤会让「某些改动不被验证」，违反「判据强度不可降」，也会让 required check 在某些 PR 上不产生 ⇒ **PR 永久卡住**。

真正该加的是：**触发面与覆盖面一致**的工作流——
① 审查类 workflow 的 paths 补上「它自己依赖的脚本」（漏了就等于「改了门禁脚本却不触发门禁」）；
② 只关心工作流文件自身的工作流（触发面 = `.github/workflows/**` + 判据脚本）。

⚠ 另一个常见误区：以为「每笔 push 都全量跑」是 workflow 配置问题。
**根因往往是提交节奏**——连续多笔推送会触发多轮全量 CI，并发限额把前几轮直接掐掉（cancel 非 verdict，纯白跑）。
**根治手段是把多笔压成一笔（批次纪律），不是加过滤。**

## 六、收官自查清单（改完 CI 后逐条过）

- [ ] 纯等待下限量化过了吗？提速空间的上界是多少？
- [ ] 提速是否只改「等待/并发/分片/重复」，没有放宽任何判据？
- [ ] 新旧对照做了吗？逐页关键字段完全一致？
- [ ] 对照实验三条纪律都守住了（同目录 / 各自产物路径 / 产出行数 > 0）？
- [ ] 每条判据都有负样本？夹具低熵且不硬编码？
- [ ] 判据误报时，先复现判据本身了吗？
- [ ] 依赖外部 API 的判据：双 endpoint + 404/422 + 无法判定不阻断？
- [ ] 新增/修改的 action ref 都是真实存在的完整 SHA？仓库名取前两段？
- [ ] 加 paths 前核过 job 覆盖面与 required check？
- [ ] 分片产物合并后统一判定，且「零分片」是 fail-closed？
