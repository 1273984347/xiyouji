### 3.3 S-01 批量文件变换优化方案

**现状**：正则/脚本批量替换 85-520 页，效果取决于对页面结构的理解深度。三次返工根因各异：
- 漏 add（W654）：非级联批量页改动未被级联清单覆盖
- 漏 --（W655）：脚本拼接时 token 纯名未补前缀·静态门禁全绿但渲染全黑
- 净增 31 行（W660 试点）：内联副本比原块大——形态选择错误

**差距**：缺乏「生成后必须渲染实测」的强制步骤。静态门禁（CSP/语法/覆盖率）全绿但渲染全黑的案例证明静态验证不足。

**优化措施**：
1. 转换脚本必须输出触达文件清单（W654 教训·已写入 AGENTS §4.3 但需入脚本自动化）
2. 转换脚本必须附带 playwright 单页探针（W655 教训·新增步骤）
3. 形态选择前置论证：内联 vs src·内联 vs 模板——用试点页实测行数变化决定（W656 净增 31 行教训）
4. 批量改动 → 级联清单 + 非级联清单双轨输出

**可衡量目标**：返工率从 3/6=50% 降至 ≤10%（10 批内 ≤1 次返工）·CI 首过率从 4/9=44% 提升至 ≥80%

**时间表**：W661 内完成脚本改造·W662 起所有批量变换批按新流程执行

**责任人**：AI Agent（脚本改造与探针编写）·项目 Owner（验收）

**验收标准**：连续 5 个批量变换批零返工·CI 首过率 ≥80%

### 3.4 S-03 跨会话并行协作优化方案

**现状**：pathspec 提交互斥模式有效（W650/W654/W656 三次实践零冲突），但缺乏「对方是否仍在工作」的判断机制——W659 后 PD-1b 在途曾阻塞 B-5 提交 12+ 小时。

**优化措施**：
1. `git log --oneline -5` + `gh run list --limit 3` 识别并行增量（已有·保持）
2. 新增：检查 `git status --short` 中是否有非本会话暂存文件（有→让行）
3. 新增：轮询 HEAD 30 分钟无变化则判定对方已收工·可安全接手
4. pathspec 提交后 `git log --oneline -1` 确认只有本方文件

**可衡量目标**：跨批冲突率从 1/2=50%（PD-1b 曾阻塞）降至 0

**责任人**：AI Agent

**验收标准**：连续 3 次跨会话并行零冲突

## 7. 工作流优化方案

### 7.1 核心流程：批量页面变换（SC-01·本周期 6 次）

**现有流程（文字描述）**：
```
[需求] → [写转换脚本] → [跑脚本改 N 页] → [静态门禁(CSP/语法/覆盖率)] → [暗色审计(可选)] → [级联 dry-run] → [级联 apply] → [verify 全量] → [commit] → [push] → [CI]
```

**各环节标注**：

| 环节 | 耗时 | 资源 | 责任人 | 输入 | 输出 |
|---|---|---|---|---|---|
| 写转换脚本 | 10-30min | AI Agent | AI | 需求+页面结构理解 | 转换脚本 |
| 跑脚本 | 1-5min | Python | AI | 脚本+页面文件 | N 页已修改 |
| 静态门禁 | 5-15min | Python+Node | AI | 修改后页面 | OK/FAIL |
| 暗色审计 | 5-20min | Playwright+http.server | AI | 修改后页面 | OK/FAIL |
| 级联 | 3-5min | Python | AI | spec.json | 13 文件 |
| verify | 3-5min | Python | AI | 全仓 | OK/FAIL |
| commit+push | 2-5min | git+网络 | AI | 暂存区 | 远端 commit |

**瓶颈识别**：
1. **暗色审计**（5-20min）：全量 86 页 Playwright 渲染是耗时最长环节——但 W654/W655 证明**跳过这步会漏掉渲染回归**（黑块），不可省略
2. **写转换脚本**（10-30min）：需理解页面结构→设计替换规则→处理边界情况——认知密集
3. **静态门禁 + verify**（8-20min）：30 条门禁逐跑·不可省略但可并行

**优化建议**：

| # | 措施 | 预期效果 | 责任人 | 验收 |
|---|---|---|---|---|
| 1 | 转换脚本自动输出触达清单+playwright 探针（消除「漏 add」和「漏渲染验证」两类返工） | 返工率 50%→≤10% | AI Agent | 连续 5 批零返工 |
| 2 | 暗色审计 --limit 抽样（6 页）替代全量（86 页）作预检·CI 全量兜底 | 审计时间 20min→3min | AI Agent | CI dark gate 零新增连续 3 次 |
| 3 | 静态门禁并行跑（CSP/语法/覆盖率/sitemap 四项互不依赖·可 subprocess 并行） | 门禁时间 15min→8min | AI Agent | 结果一致 |
| 4 | 级联落盘清单自动生成 git add 命令（消除手工拼命令漏项） | 漏 add 率 0%·命令准备 3min→0 | AI Agent | 清清单与实际 add 面一致 |

### 7.2 核心流程：门禁设计与挂载（SC-02·本周期 3 次）

**现有流程**：
```
[缺口发现] → [写检查脚本] → [自检] → [挂载 verify] → [全量首跑] → [基线冻结或直FAIL] → [级联] → [commit+push] → [CI]
```

**优化建议**：

| # | 措施 | 预期效果 |
|---|---|---|
| 1 | 门禁脚本标准化模板（含 --gate/--self-test/--report 三模式·wrapper 防静默跳过） | 新门禁开发时间 30min→15min |
| 2 | 基线格式标准化（page::message 统一·剥 FAIL 前缀·CRF 清洗） | 基线操作错误率→0 |
| 3 | wrapper 防静默跳过模板化（crash 即拦+汇总行校验） | 静默跳过率→0 |

### 7.3 整体效率提升测算

**基线**（本周期实测）：
- 11 批 · 4 天 · 平均 0.36 天/批
- 返工 4 次（追加自纠） · 占批次 36%
- CI 首过率 5/11 = 45%

**优化后预估**：
- 返工率 → ≤10%（批量变换安全框架消除两类高频返工）
- CI 首过率 → ≥80%（并行门禁+清单自动化+渲染探针）
- 整体效率提升 = 返工减少 26% × 每次返工平均 0.2 天 = **节省 0.9 天/4 天周期 ≈ 22%**

> 达到「效率至少提升 20%」的目标。测算模型：节省天数 = (旧返工率-新返工率) × 批次数 × 平均返工耗时 + (旧首过率-新首过率) × CI 修复平均耗时。假设每批 0.36 天、每次返工 0.2 天、每次 CI 修复 0.1 天。

### 7.4 本章结论

瓶颈=暗色审计耗时（不可省略但可抽样预检）和返工率（可通过安全框架消除）。优化后整体效率提升约 22%，达到 20% 目标。

### 7.5 待确认事项

- 并行门禁是否受 Python GIL 限制（subprocess 不受 GIL·可并行）
- --limit 抽样 6 页是否足够代表 86 页（统计抽样置信度待计算）
