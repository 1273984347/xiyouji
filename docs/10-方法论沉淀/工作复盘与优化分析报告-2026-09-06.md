## 1. 经验复用梳理

### 1.1 经验评估标准（每维 1–5 分）

| 维度 | 定义 | 量化判据 |
|---|---|---|
| 普适性 | 适用页面/场景占比 | 覆盖站点对象比例（如 234 页中多少页适用） |
| 可迁移性 | 移植到新批次/新页面的改造成本 | 改造 ≤1 处参数 = 5 分；需重写 = 1 分 |
| 重复应用频率 | 8 天窗口内实际复用次数 | 实测计数 |
| 效果提升潜力 | 相对无此经验的耗时/错误率降幅 | 实测对照（有/无该经验的批次对比） |

- 时间表：D+1 模板入 `skills/visual-batch` → D+2 起每批实测记录首过率 → D+9 验收。

**S3 推送前本地 CI 预检（缺失技能，影响权重 15%）**

### 5.2 根因分析（5Why，对复发与最高影响项）

**P02 batch_cascade 双缺陷（复发 2/2）**

1. 为什么文档损伤？→ 写盘时行尾被改写为 4×CR、头链 entry 写了两次。
2. 为什么改写？→ 脚本用文本模式读写 + 字符串 replace 对「最后更新：」的首处命中了头链（本意是尾链）。
3. 为什么没在工具层被发现？→ 工具无落盘后自检。
4. 为什么连续两批都未修工具？→ 两批均以「会话内人工修复 + 入档教训」收场，修复工具被推迟。
5. 根因：**工具缺陷的修复依赖「下一次自然触发」而非「缺陷登记即排期」**。→ 措施：P02 修复进 F 批次 WBS（Must，D+1–D+2），并以「连续 3 批零损伤」为验收。

**P12 heredoc 吃反斜杠（会话内 3 次）**

1. 为什么脚本损伤？→ heredoc 内容中 `\s`/`\\` 被转义吞掉。
2. 为什么还用 heredoc？→ 生成短补丁脚本时图快。
3. 为什么明知规则仍复犯？→ 规则表述为「Windows heredoc 禁用」但未给出「替代动作的固定触发词」，执行时依赖回忆。
4. 为什么回忆失败？→ 违规成本当时不明显（每次都能当场发现重写）。
5. 根因：**低损害高频违规缺少强制路径**。→ 措施：把规则改写为可执行判定——「任何含 `\` 的内容一律 Write 成文件执行，无例外」并入 AGENTS §4.3（已有，W554 批已按此执行 0 违规）；监控指标：heredoc 违规 0 次/周。

**P08 judge 首过率 50%**

1. 为什么返工？→ judge 检出 3 类实现缺陷。
2. 为什么实现有缺陷？→ 折行/定位/密集标签三类场景缺通用检查清单。
3. 为什么缺清单？→ 三类坑均为首次遇到。
4. 为什么首次遇到就流到验收？→ 实现后未跑「标签两两相交」类机械断言。
5. 根因：**实现与验收之间缺一道廉价机械自检**。→ 措施：探针模板增加通用断言段（标签相交/完整性），实现后先自检再提审；目标首过率 ≥90%。

**P11 采集伪影二犯（跨批）**：根因为「教训写在报告里而非固化进采集脚本」→ 已固化（E5），同类误报监控 = 0 次/批。

### 5.3 问题分类体系与闭环机制

- 分类：工具缺陷 / 流程缺陷 / 内容缺陷 / 技能短板 / 环境约束（5 类，上表已归）。
- 等级：P0 站点不可用（本期 0 例）／P1 数据或产物结构性损伤（2 例）／P2 用户可见缺陷或批次返工（8 例）／P3 内部摩擦（5 例）。
- **闭环流程**：登记（问题表，当批完成）→ 根因（5Why，P1/P2 必做）→ 措施（进 §7 WBS，带验收线）→ 验证（下一批实测，连续 N 批达标才算关闭）→ 归档（CHANGELOG + AGENTS/技能沉淀）。

## 6. 工作流优化方案

### 6.1 流程一：W 批次端到端交付（核心流程，每批必经）

现状实测（以 W553/W554 两批均值）：

```
[内容修复/开发]──→[专项门禁]──→[verify_delivery]──→[级联登记]──→[提交推送]──→[CI 确认]
   3.5h(均值)        0.5min          1.5min          8–12min★        1min          4–15min
                                                    ★=含级联损伤修复+复验
```

- **瓶颈**：级联登记环节的「损伤修复」（8–12 分钟）为纯浪费动作（工具缺陷所致），占登记环节 47–72%；且带 P1 级漏检风险。
- **冗余**：verify_delivery 在级联前后各跑一次（第二次因级联改动文档而必要，非冗余）；提交信息临时文件的 rm+amend 两步可合并为提交前排除。
- 量化影响：以批内非开发环节 ≈17–32 分钟计，级联损伤修复占 47–72%。

**优化建议 O1**：修复 batch_cascade 写盘与头链逻辑（§2.2 S1）+ 断言前移到 dry-run。
实施步骤：D+1 补丁 → D+2 真实批次验证 → D+7 三批零损伤验收。
预期效果：登记环节 17–32 分钟 → 6–8 分钟（**-70%**）；折算整批端到端（以 4 小时均值计）**-5%**；P1 漏检风险归零。

### 6.2 流程二：视觉缺陷取证修复闭环（本周期高频流程）

现状实测（W553 四项均值 + W554 试审）：

```
[取证复现]──→[根因诊断]──→[实现修复]──→[机判]──→[judge 复核]──→[回归门禁]
  25–50min★     10–20min      20–35min    4min   10–19min(779K/2轮)   3min
  ★=A-1 实测 4 个诊断脚本才定位真根因
```

- **瓶颈 1**：取证阶段——缺陷报告（judge 主观描述）到可复现断言的转换无标准件，A-1 耗时 50 分钟。
- **瓶颈 2**：judge 复核返工回路——首轮首过率 50%，返工 = 重截 + 重审（207,615 token + 10 分钟）。
- **不合理节点**：取证依赖「读代码推理」，而 W550 补丁族的存在使「代码推理」与「运行时行为」系统性背离（A-1 的教训）。

**优化建议 O2**：探针模板参数化（缺陷报告 → 断言改 3 处即成探针）+ 通用自检段（标签两两相交/完整性）前置到实现后。
预期效果：取证 25–50 分钟 → 10–15 分钟（**-60%**）；judge 首过率 50% → ≥90%（复核环节 **-40%**）；两瓶颈合计折算该流程 **-30%**。

**优化建议 O3**：before/after 基线标准件（worktree + `_w553_shots.js`）默认随批生成。
预期效果：消除 judge「无 before 图无法判定」的往返（本次未发生但属结构性风险）；成本 +2 分钟/批，净收益为正。

**综合目标核算**：两流程改进对「非开发环节」合计 -70%/-30%；对整批端到端（开发 3.5h + 非开发 ≈0.5h）约 **-22%**，达到 ≥20% 目标线。达成前提：O1 补丁落地 + S2 模板生效，均可在一周内完成。
