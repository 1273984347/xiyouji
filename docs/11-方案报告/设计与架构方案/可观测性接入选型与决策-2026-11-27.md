## 1. 执行摘要（先给答案）

### 1.1 一句话结论

**把 LLM 观测面建在项目自己的零依赖本地 trace 上（方案 D），不引入 Langfuse Cloud 或自建 Langfuse 作为常驻架构。** 决定性理由不是依赖体积（实测仅 15–67 个 npm 包，可接受），而是**云端任何档位的数据留存期都低于项目法定的审计留存下限**（30 天 / 90 天 vs ≥ 180 天），且两个既有架构裁定已明文否决付费 APM / SaaS 监控。

### 1.2 决策要点

| 项 | 结论 |
|:---|:---|
| 观测面载体 | 本地结构化 trace（同构于 `server/audit.ts` 的 JSONL 体系，复用 `compliance/retention.ts` 留存与销毁） |
| 新增运行时依赖 | **0 个** |
| 新增常驻服务 | **0 个** |
| 首批施工（W1334） | usage 前置：承接 provider 回传的 token 用量并落结构化日志（已完成，见 §6.1） |
| Langfuse 定位 | **仅作临时排障开关**（默认关闭），不作默认架构；开启需用户单独批准（铁律 16-⑦） |
| MCP 只读接入 | 已在协议层验证可用，但**与方案 D 常态互斥**（§7） |

### 1.3 明确不做

- 不把 Langfuse SDK 作为默认依赖塞进 `streamChat` / `agentLoop` 主路径。
- 不引入 ClickHouse / Redis / 对象存储（自建 Langfuse 的最小栈，与裁定 2 正面冲突）。
- 不在本批改造 `metrics.ts` 的进程内窗口语义（首 token SLO 口径保持不变）。

## 3. 约束基线（决定性的三条）

### 3.1 两条架构裁定

[系统架构方案-分层模块与部署-2026-10-20.md](系统架构方案-分层模块与部署-2026-10-20.md) 的五条根本裁定中：

> 裁定 2：存储沿用「Git 文件树 + JSON + 单文件 SQLite」三件套，**不引入外部数据库/缓存/对象存储**
> 裁定 5：**监控即门禁**：零付费前提下，把可观测性做进门禁与 CI；**付费 APM/SaaS 与「极低成本」冲突**

[系统架构方案 v2-目标态与落地路线-2026-10-25.md](系统架构方案v2-目标态与落地路线-2026-10-25.md) 对这两条明确标注 **「保持」**，并再次写明「不引入付费 APM / SaaS 监控 —— 与『成本敏感 + 私有化』冲突」。

**含义**：Langfuse Cloud 不是新提法，是已被否决过一次的方案的重新提出。推翻它需要新证据；本次评估的新证据（成本、留存）方向相反。

### 3.2 留存期：数量级差距，不是边界擦碰

[retention.ts](../../../xiyouji-agent-web/server/compliance/retention.ts) 按方案 §12.5 落码的留存口径（环境变量只能调高，低于下限直接拒绝启动）：

| 数据类别 | 留存要求 |
|:---|:---|
| 审计事件 | **硬下限 180 天** |
| L3 会话与消息 | 90 天活跃 / 归档 180 天 |
| L2 反馈 | 365 天 |

Langfuse Cloud 各档（2026-11-26 实取 <https://langfuse.com/pricing>）：

| 档位 | 月费 | 额度 | 数据留存 | 是否满足 180 天下限 |
|:---|:---|:---|:---|:---|
| Hobby | 0 | 5 万 units | **30 天** | 否（差 6 倍） |
| Core | $29 | 10 万 units | **90 天** | 否（差 2 倍） |
| Pro | $199 | 10 万 units | 3 年 | 是 |

**结论**：「先用免费档试试」在合规口径上不存在——一旦把工具调用轨迹（含 `path` / `command` / `cwd`，定为 **L4 敏感**）外发到云端，180 天可溯源即刻断裂，而这正是项目反复强调的「可溯源到发布批次 W###」。

### 3.3 一个必须先修的前置缺陷

改造前，[openai-compat.ts](../../../xiyouji-agent-web/server/engine/openai-compat.ts) 对 usage-only chunk 直接 `continue`，请求侧也未带 `stream_options.include_usage` ⇒ **provider 回传的 token 用量被整块丢弃，项目连成本维度都没有数据**。这一项与选哪个平台无关，是任何方案的前置条件，故列为 W1334 首个施工项。

## 4. 四方案对比与实测数据

### 4.1 依赖实测（`npm install --dry-run`，非估算）

| 接入形态 | 新增包数 | 备注 |
|:---|:---:|:---|
| `langfuse`（旧 JS SDK 3.39.2） | **3** | 零 OTel peer；未标记 deprecated |

| `@opentelemetry/sdk-node` + OTLP 导出（标准 OTel 路线） | **67** | 走自建后端时的通用栈 |

### 4.2 方案对照

| 方案 | 新增依赖 | 新增常驻服务 | 月成本 | 合规留存 | 与裁定 2 / 5 |
|:---|:---|:---|:---|:---|:---|
| A · Langfuse Cloud + 现代 SDK | 15 包 | 0 | 0 → $29 → $199 | **不达标**（≤90 天） | 冲突 |
| B · 自建 Langfuse | 15 包 | **6 个**（PG / ClickHouse / Redis / S3 / web / worker） | 机器成本 | 自主可控 | 与裁定 2 冲突 |
| C · OTel → 自建轻量后端（Tempo/Jaeger） | 67 包 | 2–3 个 | 机器成本 | 自主可控 | 与裁定 5 冲突 |
| **D · 本地结构化 trace** | **0** | **0** | **0** | 复用 `retention.ts` | **符合** |

### 4.3 容量估算（数量级判断用）

假设（来自架构方案：DAU 百级）：每问 1 根 span + 约 2 轮 ×（1 generation + 1 tool）≈ 5 条观测。

- 100 DAU × 3 问/日 = 300 问/日 ⇒ 约 **1,500 条观测/日** ⇒ 约 **4.5 万 units/月**，贴着 Hobby 免费线；
- 问答量翻倍即破线，且 `units` 与观测条数的换算以控制台 Usage 页为准（见 §8 未验证项）。

**含义**：这不是"可能付费"，是"按设计必然付费"。

## 5. 决策：方案 D，以及 A/B/C 被排除的理由

### 5.1 采纳 D

**本地结构化 trace**：把 agent 循环的轮次、工具调用、耗时、token 写入与 `audit.ts` 同构的 JSONL 面，复用既有留存/销毁/合规降级机制。

| 维度 | 判定 |
|:---|:---|
| 依赖与运维 | 零新增依赖、零常驻服务 |
| 合规 | 数据不出域；留存期与 `retention.ts` 同一口径，180 天下限自洽 |
| 与裁定 5「监控即门禁」 | 同向：观测数据进仓内面，可被既有脚本聚合与门禁消费 |
| 代价 | 无 UI、无跨会话在线检索、无数据集/评估在线管理（见 §5.3 的替代） |

### 5.2 排除理由（逐条，供后续 Agent 复用，避免重复提议）

| 方案 | 排除理由（一句话） |
|:---|:---|
| A 云端 | 留存期最高 90 天 < 180 天下限；付费档 $199/月违反「极低成本」；数据出域违反 L4 分级 |
| B 自建 Langfuse | 需 Postgres + ClickHouse + Redis + S3 + web + worker 六件，正是裁定 2 点名禁止的三类外部存储 |
| C 标准 OTel 自建 | 67 包 + 2–3 个常驻后端，与裁定 5「零付费 / 不做常驻 APM」冲突，且功能面小于 B |

### 5.3 被 D 放弃的能力与替代路径

| 放弃的能力 | 替代 |
|:---|:---|
| trace 可视化 UI | 现有 `/api/audit` 读取 + 脚本聚合；需要图形时临时起本地静态页读 JSONL |
| 数据集在线管理与评估页面 | 已有 [golden-50.jsonl](../../../xiyouji-agent-web/evals/golden-50.jsonl) + [run_eval.mjs](../../../xiyouji-agent-web/evals/run_eval.mjs) 三规则机判，结果 JSON 落盘即可 |
| Prompt 版本标签 | Prompt 仍在 [config.ts](../../../xiyouji-agent-web/server/config.ts) 内，版本随 Git 批次号走（W### 即版本） |
| 在线异常聚合排序 | 本地脚本按 `level=error` 聚合；样本量（百级 DAU）不需要 OLAP |

## 7. 与 Langfuse MCP 只读访问的关系

必须说清的一点：**MCP 只读链路已验证可用，但它只读 Langfuse 的数据。方案 D 的数据不在 Langfuse 里。**

| 组合 | 后果 |
|:---|:---|
| D（无开关） | MCP 常驻无实用价值（永远读到空项目） |
| D + 临时开关 | 排障期间 MCP 可用；平时零依赖（推荐形态） |
| A 为默认 | MCP 可用，但违反 §3 三条约束 |

已完成的接入件（用户级 `profiles.toml`、拟写入的 `.trae/mcp.json` 配置）在开关模式下仍有效，无需拆除；但**不应**把"MCP 已接好"当成"应当常有数据"的理由。

另有一处已实证的兼容性事实，供后续排查时省时：Langfuse Cloud 自 2026-11-16 起旧路由失效，任何基于 SDK 5 以前写法的脚本会报 `AttributeError: 'TraceClient' object has no attribute 'list'`；langfuse-mcp 0.14.0 已内置 v2 回退，直连 SDK 时须改走 `api.observations.get_many`。
