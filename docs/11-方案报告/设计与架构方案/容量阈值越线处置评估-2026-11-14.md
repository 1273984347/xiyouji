## 1. 执行摘要（先给答案）

### 1.1 一句话结论

**两项越线的根因都不是「页面失控」，而是「机制常数 × 阈值口径」的错配：#1 的 8 页越线拆成三类——search 两页可机械外置真修复、relationships 两页受数据回退铁律保护、reader 四页是内容固有体积；#2 的 21 页越线中共享内联基线块（47–52 KB）就占掉阈值的 78–87%，是机制常数而非页面异常。⇒ 推荐「一个执行批（search 索引外置）+ 一个裁决批（两条阈值口径修订）」，两者均需用户批准后动工。**

### 1.2 处置组合（推荐）

| 序 | 动作 | 类型 | 效果 | 批准门槛 |
|:--:|:---|:---|:---|:---|
| **E** | **search 索引外置**：把 `site/data/search.html` / `site/en/search.html` 内联 `<script>` 中的索引段（347,664 B / 366,532 B）外置为同目录本地 JS（`search-index-zh.js` / `search-index-en.js`），`<script src>` 引入；gate 46 扫描域随迁；容量 #4 口径诚实纳入索引文件 | 执行批 | #1 越线 8 页 → 6 页；search 两页降到 ~112 KB / ~70 KB | §6.3「搜索索引改动」= 用户批准（本报告即申请） |
| **R** | **阈值口径修订**：#1 上限 200 KB → 512 KB 硬线 + 200 KB 软线（越软线报清单不判红）；#2 改「页特有内联 CSS ≤ 60 KB + 共享基线块 ≤ 56 KB」双口径；测量器 #1/#2 增报越线页清单与计数（不再只报 max） | 裁决批 | #1 / #2 全部合规且保留预警可见性；页面与机制零改动 | 方案 v2 §8.3 修订 = 用户批准（铁律 16-⑦） |
| — | T-1 远端 tag `v2.3.0` 清理 | 独立项 | — | **仍待用户单独批准**（本批不动） |

**不推荐**（评估后排除，理由见正文）：抽离 21 页页特有 CSS（破坏自包含一致性且未来复发）、压缩 relationships 的 EMBEDDED 数据（收益 ~-25% 仍 >200 KB 且高 churn）、reader 长文分页（产品形态改动，超出阈值治理范围）。

### 1.3 明确不做

- 不引入任何框架运行时（施工手册 B1 硬边界）。
- 不改 `inline_css.py` 全站内联机制（810/861 页的共享基线是既定架构，不是缺陷）。
- 不外置任何 EMBEDDED 图表数据（AGENTS §4.1 数据回退铁律 + 第 9 槽双形态判据）。
- 不动 reader 产品形态（分页 / 懒加载属内容产品决策，不在阈值治理范围）。

## 3. #1 逐类评估（S / R / C 三类）

### 3.1 S 类 · search 两页（可执行真修复）

**拆解（2026-11-13 实测）**：

| 页 | 总体积 | 内联 `<script>` 块 | 其中索引段（SEARCH_INDEX:BEGIN/END） | 其中本页 app 逻辑 | 外置后预估 |
|:---|---:|---:|---:|---:|---:|
| `site/data/search.html` | 460,148 B | 404,842 B | **347,664 B**（`SITE_SEARCH_INDEX_ZH`·已是紧凑 JSON，零压缩空间） | 57,099 B（`doSearch`/`setBanner`/深链） | **~112.6 KB** |
| `site/en/search.html` | 436,477 B | ~383 KB | **366,532 B**（`SITE_SEARCH_INDEX_EN`） | 16,258 B | **~70.0 KB** |

**修复方案**：索引段（含 SEARCH_INDEX 标记对）原样外置为 `site/data/search-index-zh.js` 与 `site/en/search-index-en.js`（各自与页面同目录），页面以 `<script src>` 在 app 逻辑之前引入。

**可行性逐条核验（2026-11-13 实测）**：

| 判据 | 现势 | 结论 |
|:---|:---|:---|
| CSP | `search.html` meta 实测 `script-src 'self' 'sha256-…'` | **'self' 已放行**本地外链 JS ⇒ CSP 面零新增（内联块缩小后按惯例重跑 `generate_csp.py`） |
| `file://` 直开 | 经典脚本相对路径 `src` 在 file:// 下可用 | **不破** file:// 铁律；索引不是 `EMBEDDED_DATA` 图表回退（该页本就无 fetch+EMBEDDED 双形态契约） |
| 零外域 | 同目录本地文件 | **不破**（无任何新外域） |
| 消费方 | 页内 app 逻辑直接读常量；`text-search-app.js`（2.07 MB）是 `text-search.html` 的独立实现，与 search.html 无引用关系（双向 grep 实测 0 命中） | 外置后加载顺序（索引先于 app 逻辑）保持语义等价 |

**连锁面（执行批必须同批处理）**：

1. **gate 46 随迁**：`check_search_index_fresh.py` 判据域为两页内联常量 + BEGIN/END 标记对 ⇒ 扫描域改指两个外部 JS（标记对随迁保留），页面侧增「`<script src>` 引用存在」检查；自测 6 例 fixtures 同步改写。改判据面必须同批补负样本（防「索引被手删」判据失效）。
2. **容量 #4 口径诚实化**：索引文件是站内搜索自有字节 ⇒ 计入 #4（`text-search-app.js` 2.07 MB + 索引 714,196 B ≈ **2.75 MB / 3 MB**，余量 ~8%）。**若不计入则是「指标搬家式假改善」**——#1 的字节转到了 #4 的盲区。余量从 30.9% 收窄到 ~8%，#4 成为下一个需盯的指标（如实登记，不掩盖）。
3. **生成器写回点**：`_gen_search_index.py` 的 `build_block()` 输出目标从「页面内联块」改为「独立 JS 文件 + 页面引用行」；索引新鲜度语义不变（仍按 docs/ 实况全量重算）。

### 3.2 R 类 · relationships 两页（受铁律保护，走口径裁决）

- 大头 = `const EMBEDDED = {…}`（`site/data/relationships.html` 实测最大内联脚本 268,428 B·**JS 对象字面量非纯 JSON**·pretty-print 4,784 行）。
- 压缩评估：程序化紧凑化需 JS 解析器（非 `json.loads` 可处理），收益估 −20%~−35%；即便 −35% ≈ 238 KB，**仍 > 200 KB，不解决问题**；且 EMBEDDED 回退是 AGENTS §4.1「数据回退铁律」的载体（file:// 直开保障 + 第 9 槽双形态判据），外置 = 破铁律。
- **裁定建议**：不压、不外置；其体积合理性交给 #1 口径修订（§4 方案 α′ 的 512 KB 硬线覆盖）+ #3 全站体积约束兜底。

### 3.3 C 类 · reader 四页（内容固有体积，拆包无意义）

- 四页**零内联脚本**；以 `紧箍儿的内侧-器物传记.html` 为例：426,293 B = 内联 CSS 52,015 B + **正文等 ~374 KB**。体积即文章本身。
- 「拆包」对内容页只有一条路 = 长文分页 ⇒ 产品形态改动，收益（加载时间）与代价（阅读连续性、生成器改造、623 页 reader 全链回归）不成比例。
- **裁定建议**：同 R 类，交给 #1 口径修订；reader 页的加载体验已有 LHCI 性能预算面兜底。

## 4. #2 机制评估与三案对比

### 4.1 根因结构（数字实证）

| 层 | 实测 | 说明 |
|:---|---:|:---|
| `site/tokens.css` 源 | 26,098 B | 设计令牌正本 |
| `site/system.css` 源 | 42,081 B | 组件层正本 |
| 页面共享内联块（INLINED） | **47,084 B**（数据页实测） | 经 `inline_css.py` 内联进每一页 |
| 全站内联 CSS > 50 KB 的页 | **810 / 861** | 共享基线块本身就 ≈ 50 KB ⇒ **机制常数** |
| 阈值 60 KB 的占用 | 基线占 78–87% | 页特有预算实际只剩 ~8–13 KB |

**结论**：60 KB 阈值制定时（v2 §8.3·2026-10-25）未按「全站内联机制」的基线校准——它对「总内联 CSS」口径**先天失准**，21 页越线是机制常数 × 页特有样式叠加的必然结果，不是 21 个页面各自的过错。

### 4.2 三案对比

| 案 | 内容 | 页面改动 | 一致性 | 判定 |
|:--:|:---|:---|:---|:---|
| **A（推荐）** | **口径修订为双指标**：① 页特有内联 CSS ≤ 60 KB（按 `<!-- INLINED CSS -->` 标记配对扣除共享块·W1019 已立该识别判据可复用）；② 共享基线块 ≤ 56 KB（机制预算·现值 47.0–52.0 KB，余量 ~8%） | **零页面改动** | 机制不动；页特有增长信号保留（21 页中最大页特有 ~27.9 KB，余量 2.15×） | ✅ 根因对位 |
| B | 抽离 21 页页特有 CSS 至本地 `.css`（`<link>` 引入·file:// 可用） | 21 页 ×（删 style 块 + 增 link + 新增 21 个 css 文件 + CSP 重生成） | **破坏「页面自包含」一致性**（840 页内联 / 21 页外链双态）；豁免标记（e-track-exempt）随块迁移需逐页核对；未来新页会复发 | ❌ 高 churn 低收益 |
| C | 总阈值 60 KB → 80 KB 一刀切 | 零 | 简单，但页特有增长信号被整体埋掉（机制常数与页面预算混在一个数里） | ❌ 掩盖信号 |

> 案 A 的双口径把「机制成本」（共享块，应受机制预算约束）与「页面成本」（页特有，应受页面预算约束）分开记账——这正是本次越线暴露出的口径缺陷。

## 5. 处置建议与批次拆分

### 5.1 批次 E：search 索引外置（执行批·需用户批准后占号）

| 栏 | 内容 |
|:---|:---|
| 范围 | `site/data/search.html`、`site/en/search.html`、新增 `search-index-zh.js` / `search-index-en.js`、`scripts/_gen_search_index.py`（写回点）、`scripts/check_search_index_fresh.py`（判据域 + 自测 6 例 + 负样本）、`scripts/check_capacity_budget.py`（#4 口径纳入索引文件） |
| 验收 | ① 两页 ≤ 200 KB（预估 ~112.6 / ~70.0 KB）；② `file://` 双击检索可用（索引加载 + doSearch 实测）；③ gate 46 新鲜度判据全绿（含「索引被手删」负样本被抓）；④ CSP 0 漂移；⑤ #1 越线 8 → 6 页；⑥ #4 如实计数（≈2.75 MB·余量 ~8%·如实登记） |
| 批准门槛 | §6.3「搜索索引改动」= 用户批准 + `file://` 验证 |

### 5.2 批次 R：阈值口径修订（裁决批·需用户批准）

| 栏 | 内容 |
|:---|:---|
| #1 修订（推荐 α′） | 硬线 200 KB → **512 KB**（现 max 449.4 KB·余量 14%）；增**软线 200 KB**——越软线报页清单与计数、不判红（保留预警可见性，防「硬线放宽 = 静默放行」） |
| #1 修订（备选 α） | 分类上限：常规页 200 KB 不变；`site/reader/**` 与 EMBEDDED 数据回退页 512 KB。判别逻辑复杂一档，收益与 α′ 相同 ⇒ 列备选不推荐 |
| #2 修订（推荐 A） | 双口径：页特有内联 CSS ≤ 60 KB + 共享基线块 ≤ 56 KB（识别复用 `<!-- INLINED CSS -->` 标记配对判据） |
| 测量器（两案共同验收） | #1/#2 增报**越线页清单与计数**（不再只报 max）——根治 §2.2 的登记面失真 |
| 落点 | 方案 v2 §8.3 阈值表修订（保留旧值沿革注记）+ `check_capacity_budget.py` 口径实现 + 阈值表「当前值」全部改由测量器产出 |
| 批准门槛 | 方案 §8.3 修订 = 用户批准（铁律 16-⑦：阈值与豁免同族，只增不减为默认） |

### 5.3 顺序与依赖

E 与 R 相互独立、可任意先后；**先 R 后 E** 的好处是 E 收官时 #1 判定直接用新口径（少一轮旧口径红）；**先 E 后 R** 的好处是裁决时 S 类已落定、512 KB 硬线的余量计算更真实。两者都待用户批准，不预设顺序。
