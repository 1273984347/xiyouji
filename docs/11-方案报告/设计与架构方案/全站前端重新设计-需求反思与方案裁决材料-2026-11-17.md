## 2. 底层需求：用户真正想解决什么

### 2.1 症状 → 原因 → 目标 三层拆解

- **症状（用户说出来的）**：「全站前端网页样式不好，要重新设计」
- **中间层原因（用户推断的）**：「现在的样式语言是错的 ⇒ 换一套新的皮肤」
- **底层目标（需要验证的）**：「这个站 875 页、90 个可视化页、629 篇解读，在**读者真正打开它的那 30 秒里**是否显得可信、专业、可信服」

### 2.2 用证据检验「皮肤是原因」这一假设

**假设检验（可证伪）**：若样式层是主因，则「换一套设计语言」应显著提升站点质量。

**反证 1 — 规模反比**：875 页里 **reader 族 636 页（72.7%）**是长文阅读（site/reader/ch001.html 等），它们的痛点是**排版节奏与阅读经济性**（正文 17px / 行高 1.85 / 单栏 65–75 字/行），不是「皮肤好不好看」。v3 原设计（只做 landing + dataviz 两页样板）**对 reader 族完全空白**。
**反证 2 — 缺陷分布**：W1259 的 15 项发现里，**11 项与视觉方向无耦合**（数据层 6 + 判据扩面 5）。换皮治不了「EN 页显示中文数据」。
**反证 3 — 绘制层不可见**：标签裁切/重叠 87–108 页，根因是**各页 d3 绘制参数逐页自造**（轴组类名逐页不同：chart-axis / bar-axis / curves-axis），CSS 覆写层**在原理上无法消除**——W1261 正是因此把「十族画法改造」列为遗留。
**反证 4 — 成本反比**：把 61.87 MB 内联 CSS 全部重写一遍，成本远高于「改两份源文件 + 跑 inline_css.py --force」。

**结论**：**样式不是主因，而是唯一成本最低、见效最快的那一层**。把它当唯一动作，是把「手段」当「目标」。

### 2.3 站点的真实使用画像

从项目自身数据看：站点是「一源多形的《西游记》数字人文读本」——**629 篇解读文档 + 90 个可视化 + 100 回逐回解读 + 138 页英文版**。它的价值主张是「**把解读过程本身整理出来**」，读者是**长文连续阅读者**（reader 族 73%）。这决定了两件事：

1. **reader 族（636 页）才是主战场**，任何设计方向必须先回答「长文怎么读」，而不是「首页怎么好看」；
2. **数据的可信度是设计的前提**——一个视觉精美但 EN 页显示中文数据、图表标签被裁切的站点，读者的信任会被内容层击穿。

## 3. 最强反对者视角：挑战「采纳 v3 + 分批落地」这个方案

按要求，先假设我认为最合理的方案是错的。

### 反对 1：v3 是**另一个 subagent 的自述产物**，采信它是否等于重复 W1261 的错误？
W1261 的教训正是「盲审判拒收」。**对策**：本批**独立复跑**了它的两个机器脚本（不采信自述）——audit.py 20 项全 PASS、palette_check.py 52 对全 PASS；并**独立渲染** 3 族 × 明暗 2 态 × 双视口 = 12 组截图，0 控制台错误、0 横向滚动、底色读数证明明暗态真实不同。**但仍缺一项**：v3 未接受过**独立盲审代理**的证伪式审查。⇒ 落地前必须补。

### 反对 2：v3 覆盖的类族只有 **51 / 953（5.4%）**，现役 system.css 也只有 91 / 953（9.5%）——**两者都远不足以管住 875 页**。
这暴露真问题：**站点的样式治理本身就是薄弱的**。875 页实际用 953 个 class，公共层只覆盖 9.5%，其余 90.5% 是页面私有样式。⇒ **「换一套皮肤」的期望收益被样式治理水平卡住上限**。这是必须写进方案的硬约束，不是可以忽略的细节。

### 反对 3：v3 缺 15 个现役在用的令牌（container-content / danger-bg / gap-base / gap-block / gap-hero / grid-gutter / indent-2 / indent-3 / info-bg / leading-heading / ok-bg / radius-lg / space-11 / text-step-5 / warn-bg）——直接换 tokens.css 会让这 15 处**回落到未定义**。
⇒ 落地必须**先补齐令牌再换肤**，不能直接覆盖。

### 反对 4：「reader 族是主战场」这个判断，会不会错了？
站点的分发线仍处冻结（30 日 UV 未达标，内容扩容冻结），若流量主要来自**首页与看板**而非长文，则优先做 reader 是错的。
**对策**：本批**不预设立场**，而是把「三类页面族（root / data / reader）× 明暗双态」的样板全部做出并交用户裁决优先级——**这是用户才知道的答案（真实使用场景）**。

### 反对 5：跨领域有没有更好的解法？
- **设计系统演进史（Airbnb / Shopify Polaris / Material Design）**：共同点不是「推倒重来」，而是 **① 令牌层定义语义 ② 组件层固定交互 ③ 迁移层按族推进 ④ 旧样式冻结不删**。**v3 的「两层语域」正是材料侧的正确抽象，但落地必须走「组件族 + 逐族迁移」，不是「替换全站 CSS」**。
- **学术出版业（校勘本）**：正文与神注用不同字体与字号，同一册书内并置——这正是 v3 的「工具语域 / 原文语域」在书籍媒介上的成熟形态。可作文化叙事上的背书。
- **博物馆展陈（素墙挂画）**：墙面极简、展品浓烈、画框是接缝——v3 的「素墙 + 画框」结构与之同构，且**已经在样板上目视成立**。
- **反面教训（大爆炸式重写）**：跨 875 页、61.87 MB 内联、93 个冻结令牌名、43 个冻结类名、74 槽门禁的存量系统，**大爆炸重写的失败率极高**——W1261 的复核轮与两轮盲审判 FAIL 就是实证。**绞杀者模式（Strangler Fig）**才是正解：新语言逐族接管，旧样式保留兜底，可随时回退。

## 4. 最优解：三层动作，按「是否解决用户真实痛点」排序

### 层 A · 换肤（用户明说要做）——但收缩为「设计系统换代」而非「推倒重来」

- **A1 令牌层换代**：v3 令牌（135 个）**补齐 15 个现役缺口**后，作为新一档取值并入 site/tokens.css；**旧令牌名就地重定向**（沿用 W1261 已验证的做法：改写原声明而非追加第二套，否则导出器生成 _override_2 键击穿「暗色计数」门禁）。
- **A2 公共壳换代**：v3 的 110 类 system.css 并入 site/system.css，保留 93 个冻结令牌名与 43 个冻结类名接口不变。
- **A3 三族样板先行**：root（落地）/ data（可视化）/ reader（长文，本批新增）各一页真实样板，明暗双态 + 375px。
- **A4 绞杀者迁移**：按族逐批接管，每批可回退；**不追求单批全站**。

### 层 B · 真正影响可信度的缺陷根修（比换肤更该先做）

- **B1 数据层 P0**（W1259）：EN 站 13 页 / 38 个 fetch 指向中文数据集 → http(s) 生产形态下「英文外壳 + 中文数据区」。
- **B2 mock 回退**：3 页 EMBEDDED 实为 mock 假数据（真值 53 地点 → mock 5 地点；40 人物 → mock 15）。
- **B3 绘制层**：十族画法 + 标签避让（87–108 页裁切/重叠）+ 122 页 axis 统一 + 26 页 colorMap 字面量令牌化。

### 层 C · 验收基础设施（缺了就只能靠人眼）

- **C1 视觉回归基线**：CI 现有 screenshot-review.yml 只做**结构扫描 + 表格未包裹检测**，**无像素级/结构级 diff 基线**——所以 W1261 才会「改完靠用户实拍才发现」。
- **C2 类族覆盖门禁**：新增「公共层覆盖率」判据（当前 9.5%），把「样式治理」变成可量化的持续指标，而不是一次性工程。
- **C3 渲染态目视**：任何视觉改动，**主会话必须亲自看渲染图**（E-244 教训，本批已按此执行：探针 0 错误但暗色态未生效、页脚破版，两处均由目视发现）。

### 4.1 为什么层 B/C 不能省

**换皮只改「看起来」，层 B/C 改「是什么」和「怎么被验收」。** 若只做 A 而不做 B/C：站点会「更精致但仍不可信」，且下一次改版仍需人眼救火——**重复 W1261 的循环**。跨领域经验反复指向同一结论：**外观统一度提升的边际收益递减，而缺陷密度与验收能力的收益递增**。
