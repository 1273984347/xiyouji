## 1. 为什么路线是「打磨」而不是「重设计」（三条实测依据）

1. **地基是好的**：机器判据层 82 段 0 FAIL（verify_delivery --scope auto）· CSP 874 页 0 漂移 · 链接 30441 条 0 broken · 双协议/双态/375px 全部实测通过。
2. **身份是唯一的**：四轮方向里只有现役达成「暖承载 + 冷数据」（56.1% / 19.5%）；甲乙两轮修正版都未达标（详见 W1264 裁决材料 §5.5）。
3. **真正的问题是工程债 + 残留缺陷**：公共层只管住 11.9% 的类（每页私有样式 73,679 B）⇒ 改版成本高、拼贴感复现；另有 15 项已核验缺陷（数据层与可读性）尚在。

⇒ **打磨 = 把现役语言在全站落实到位：统一版面形态 + 清掉残留缺陷 + 补齐防线。**

## 4. 每批通用验收口径（不可协商）

1. **机器判据**：verify_delivery --scope auto 核心 0 FAIL ＋ 该批新增/扩展判据**自带负样本自证**（违例必红、恢复必绿，留证文件）。
2. **目视亲验**（E-244）：视觉类改动**必须由主会话打开渲染图看**；探针数字只作辅助，探针全绿 ≠ 页面没坏；抽最剧烈 1–2 页。
3. **双协议**：凡以 fetch 装载数据的页面，file:// 与 http:// 各跑一次，比对图元数 / 正文行集合 / 正文 CJK 计数。
4. **双态**：明暗两态各自渲染验，以底色读数为主证（平色页字节差可能仅几百字节）。
5. **体积**：单批内联 CSS 增量 ≤ 0（归并批除外，归并批须给出体积变化实测）。
6. **提交**：显式 pathspec ＋ git commit -F <file>；本批 spec 的 file_index_rows 必须覆盖全部暂存件（第 51 槽硬拦）。

## 5. 边界与未验证项（禁当成已知）

1. **标签裁切的根修方案未定**：绘图层边距自适应 vs 公共层规则 —— W1266 开工前必须先实读绘图代码再定，**禁凭推测改 172 个图表面**。
2. **是否转外部共享 CSS 未决**：可降体积约 92%，但会改变 875 页加载结构与 file:// 形态 ⇒ 须单独立项评估，不在本清单默认范围。
3. **公共层归并到 40% 的可达性未验证**：须在 W1267 先验一页样板再铺。
4. **双协议普查依赖本地 http 服务**：未起服务时须走 file:// 并在结论里明示口径（渲染态普查探针默认 http 且不 fail-closed 已登记为 G5 待修项）。
5. **EN 站 138 页的判据扩面后可能暴露存量违例**：先冻结基线再逐步收敛，禁一上来就判红整站。
