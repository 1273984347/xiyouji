一、整体分层（L0–L4 + 双横切面）

依赖单向向下。治理面（门禁 + 批次台账）与合规面（分级 + 审计）横切各层，而非独立层——做成独立层会迫使 L0–L3 反向依赖它，破坏单向依赖。

二、模块拆分与依赖

六个模块组、21 个模块。M-A 内容组不依赖任何组；M-B 交付组不依赖服务/数据/合规组；合规组可依赖全部组，但其余组不得依赖其内部实现。

三、数据流（四条主链路）

链路 ① 内容生产是唯一事实源路径；链路 ③ 问答交互是唯一有状态、唯一出网的路径；链路 ④ 合规审计横切所有数据面。

四、存储演进路线

v2 的核心修订：W821 曾裁定「不采纳 Postgres」，其理由写的是「当前 DAU 百级、站点零服务端」。规模前提被改写后，W821 自己写明的档 2 触发条件已命中 ⇒ 档 2 由「触发后建设」提前为「本批启动」。

五、故障域降级拓扑

两条降级主线：向下（PG 不可用 ⇒ 问答不可用，静态站零影响）与向左（LLM 不可用 ⇒ 退化为「只检索」，仍返回可溯源引用）。审计环节在所有路径末端，且其失败不静默。

六、私有化部署拓扑

10 台以内、全部自建、不用托管服务。成本敏感口径下：数据库自建 1 台 4C8G、反代用系统 Nginx、监控用门禁报告 + 自建审计流水、推理用内网端点。

七、相对 W821 的修订裁定

三条根本裁定保持；存储裁定的规模前提被改写，故修订。修订依据是 W821 自己写明的触发条件命中，不是偏好之争。

#W821 原裁定v2 裁定变更根因
1依赖单向向下，产物不得反向成为事实源保持与栈、规模均无关，是最稳的底层约束
2存储沿用 Git + JSON + 单文件 SQLite，不引入外部数据库修订原理由写「当前 DAU 百级、站点零服务端」，前提被规模改写
3扩展走三档触发式演进，不预先建设档位前移档 2 触发条件按新规模已命中 ⇒ 由「触发后」提前为「本批启动」
4容灾主战场是降级可用而非备份恢复保持 + 加一条PG 引入后备份恢复重回主战场（静态站仍以降级为主）
5监控即门禁，零付费前提下不做付费 APM保持 并强化成本敏感约束未变；合规审计面成为第二观测面

八、数据分级与合规缺口

四级分级是 v2 相对 W821 的最大结构性增量——W821 全文无分级概念。右侧为逐项对应现役实证的整改清单。

级别名称判定标准本项目落点存储要求传输要求
L1公开已公开发布、泄露无损失原著原文、解读文档、公开可视化数据Git 明文无特殊要求
L2内部仅内部可见、泄露有轻微损失反馈数据、构建元数据、内部报告DB 明文或列级加密内网即可
L3受限泄露有实际损失会话与消息（含用户提问内容）、检索上下文列级加密必须 TLS
L4敏感泄露有重大损失或触法审计事件、密钥、凭证加密存储 + 只追加必须 TLS
