## 1. 理念

把站点做成**一本可以翻阅的数据终端**，而不是一个「讲故事的网站」。

暗色为**默认**界面，亮色是可切换的选项——这条决定把整个方向和现站区隔开：现站是浅底纸感的学术展示页，本方向假设读者坐在终端前，一行行读数据、用命令行式的短标签扫读结构。

三条自定的语言规则贯穿全页：

| 规则 | 落地方式 | 例 |
| --- | --- | --- |
| 终端前缀 | 标签与面板序号带 `>` / `NN/` 前缀 | `> 031  9,041`、`03/` |
| 章节即索引 | 坐标轴用两位数回次而非「第031回」 | `01/` `11/` `31/` |
| 数据即终端输出 | 数值一律等宽 + 千分位分隔 | `742,357` `47.35%` |

## 2. 色彩理由

### 2.1 表面与三色

| 令牌 | 暗色 | 亮色 | 角色 |
| --- | --- | --- | --- |
| `--bg` | `#0D1117` | `#FFFFFF` | 站点底色 |
| `--panel` | `#161B22` | `#FFFFFF` | 面板卡片 |
| `--panel-2` | `#1C2129` | `#F6F8FA` | 面板内二级块 |
| `--border` | `#30363D` | `#D0D7DE` | 1px 边框 |
| `--c-cyan` | `#2DD4BF` | `#0F766E` | 主序列（叙述 / 正面 / 主折线） |
| `--c-magenta` | `#F778BA` | `#A626A4` | 次序列（对话 / 负面 / 峰值标注） |
| `--c-amber` | `#E3B341` | `#9A6700` | 第三序列（韵文 / 均值参考线 / 警示） |

**为什么是这三色**：青 / 品红 / 琥珀是终端配色的经典三原色，语义上与「终端输出」天然契合，且三者在色相环上彼此远离（≈170° / ≈330° / ≈45°），即使在 1.75px 描边宽度下也不会互相混淆。

**亮色不是暗色的反色**：亮色态是**独立的一套令牌**（`[data-theme="light"]`），三色各自换成同色相的深色版本（青→`#0F766E`、品红→`#A626A4`、琥珀→`#9A6700`），以保证在白底上仍有 4.8:1 以上的图形对比度。全程**未使用 `filter: invert()`**。

**低填充 + 高亮边**：柱形与环段用 12%–16% 透明度的同色填充 + 1.5px 实色描边（外加一层 3.5px 低透明度 halo 描边模拟「弱发光」）。这是本方向与「实心色块」最大的差异：暗底上密集的实心色块会互相干扰，低填充只留轮廓，数据靠描边而非面积区分。

### 2.2 三色互撞的处理（契约明令要求）

同一张图里三色共存时有两条硬规则：

1. **不同线型分层**：折线图主序列是青色**实线**，均值参考线是琥珀**虚线**（`stroke-dasharray: 4 3`）。线型不同 ⇒ 即使色相接近也不会读混。
2. **同图只让两色同框**：环形图的三段（正/中/负）之间留 2.5px 面板底色间隙（`--arc-gap`），把相邻色块物理隔开。

## 3. 字体理由

| 用途 | 字体栈 | 理由 |
| --- | --- | --- |
| 数据 / 坐标轴 / 标签 / 标题 | `--font-mono`：ui-monospace, JetBrains Mono, Cascadia Code, Consolas… | 等宽让数字**竖向对齐**，扫读时能按列比大小；标题加 `.04em` 字距产生终端感 |
| 正文 / 说明 / 脚注 | `--font-sans`：system-ui, PingFang SC, Microsoft YaHei… | **硬要求**：中文等宽字体缺字时会掉进 fallback，字宽忽宽忽窄，正文可读性会崩 |

等宽只用于「需要按列比较的数字」和「需要终端感的地方」，所有连续阅读的段落一律无衬线。这是本方向最关键的一条取舍——纯等宽站点在中文语境下不可用。

## 4. 图形语言

| 图 | 形式 | 要点 |
| --- | --- | --- |
| 01/ 每回叙述与对话字数 | 堆叠柱（100 回） | 叙述=青在下、对话=品红在上；低填充+高亮边；直接标注替代图例框；**只标最高的一回** |
| 02/ 对话字数占比 | 折线 + 极淡面积填充 | 青色实线为主序列，琥珀虚线为全书均值；**只标峰谷两点** |
| 03/ 韵文密度 | 柱 | 只列有韵文的 8 个回次（其余 92 回为零，画出来是一排空柱）；并列峰值合并为一个标签 `> 07–08  5 首` |
| 04/ 对白情绪分布 | 环形（donut） | 标签放**环外**并配折线引线；外侧标签做垂直最小间距（19px）推挤 |

### 4.1 标签零裁切 / 零重叠的做法

这是本方向明确要修掉现站缺陷的地方，做法是三条：

1. **轴刻度动态抽稀**：`pickTicks(n, span, minGap)` 按可用宽度与最小标签间距计算步长，100 回只标约 20 个刻度（`01/ 06/ 11/ …`），而不是硬编码 100 个。
2. **数据标签只标极值**：每图最多 1–2 个数据标签，且永不与轴标签共享基线位置。
3. **绘制后按屏幕坐标纠偏**：`clampLabels()` 用 `getBoundingClientRect()`（含全部祖先变换）与 SVG 客户端矩形比较，把越界标签推回视窗内。

> **踩坑记录**：首版 `clampLabels()` 用 `getBBox()` 取包围盒，而 `getBBox()` 返回的是**父级 `<g>` 的局部坐标**——y 轴刻度位于 `g` 左侧（局部 x 为负），被误判为「越出视窗」而右推约 27px，正好压住均值标签，导致 1 处重叠（主会话探针实测 ratio 0.52）。改为屏幕坐标后归零。**教训：SVG 局部坐标 ≠ 视窗坐标**，判定越界必须用客户端矩形。

### 4.2 图标

8 枚全部**重绘**（未沿用现站 `site/static/icons/ui/` 的 path）：

- 24×24 视窗，描边 **1.75px**，`fill="none"`、`stroke="currentColor"`、round 端点、`aria-hidden="true"`
- 坐标**直接对齐栅格**：最大绘制范围 `x∈[3.5,20.5] / y∈[3.5,20.5]`，加 0.875px 描边后视觉边距仍 ≥ 2.6px
- **不使用** `transform="translate(...) scale(...)` 缩放凑合（现站图标普遍如此）
- 几何方正少圆弧：放大镜用圆角矩形、图表用直角柱、地球用正交经纬

## 6. 已知代价与风险（诚实交代）

本方向是三个候选里**风险最高**的一个：终端风与《西游记》的题材气质距离最远，中文长正文最易翻车。以下逐条交代代价、已经用哪些手段规避、规避到什么程度、以及**还剩什么风险**。

### 6.1 中文正文的可读性代价（本方向最大的翻车点）

**代价是什么**：等宽字体是终端风最显眼的语言特征，而中文语境下等宽字体（中文全角字形）天然比日韩文字宽，行长一旦偏长，右侧留白会参差不齐；同时等宽字体没有连字与语境压缩，中文连续段落的字面密度偏高、笔画更「挤」。在深色底上，这种「挤」会被霓虹色描边与网格线进一步放大，长段落阅读时极易疲劳。

**本方向用「正文换无衬线」规避到了什么程度**：

- **只把标题、章节号、数据、坐标轴、标签、tooltip 数值交给等宽**；所有叙述性文字（导语、面板说明、脚注、tooltip 的文字标签）一律走 `--font-sans`（system-ui / PingFang SC / 微软雅黑）。
- 正文行宽限制在 `max-width: 62ch`，行高提到 **1.75**（远高于常见的 1.5），并按无衬线的实际行高而非等宽的标称行高排版，避免基线错位。
- 面板说明、脚注等次级文字**不叠加字距**，只保留 1.75px 描边与 1px 边框的「终端装饰」，避免正文区被等宽特征污染。

**还剩什么风险**：

1. **「半等宽」带来的语气不一致**。同一界面里标题是等宽、正文是无衬线，这个断裂是刻意的（换取可读性），但视觉上并非无缝——**长页面里这种断裂会反复出现**，读者可能感到「不像同一个东西」。若强行把正文也改回等宽，可读性会立刻塌陷（本方向不建议）。
2. **中文等宽字体覆盖不足**。`--font-mono` 栈里的中文回退（Cascadia Code / Consolas）不含中文字形，实际落到系统中文字体，**汉字未必等宽**——因此本方向把所有汉字都排除在等宽区之外，只让**数字与短标签**承载等宽感。代价是「终端感」在中文段落处被切断，整页不是纯粹终端气质。
3. **长正文页未经验证**。本页正文最长不过两三行。**一旦要落地含长篇中文正文的页面（人物志、章节导读、评论长文），无衬线 + 1.75 行高 + 62ch 行宽是否仍偏舒适，本批没有数据支撑**，需要单独做阅读测试（建议：至少 15 分钟连续阅读 + 中文行长扫描），不能直接外推。

### 6.2 暗色为默认，对「白天在明亮环境阅读」的访客是否友好

**结论：这一项对本方向是不利因素，且不能靠「提供亮色切换」完全抵消。**

- **对比度上限被压低**。暗底正文对比度上限约 7.7:1（本页实测），而浅底纸感版可达 14.6:1+。在手机屏、户外或高亮度显示器上，深底背景会被环境光「抬灰」，**细字号的轴刻度（11px）与 1.75px 描边最先失真**。
- **暗色在明亮环境下的额外问题**：OLED 屏上深色块与白色窗口并排时会产生「光晕 / 拖影」错觉；长时间阅读深底 + 高饱和青品红，比浅底 + 低饱和更易视觉疲劳。
- **已做的缓解**：① 暗色是**可选而非唯一**——亮色是一套独立令牌（不是 filter 反色），可一键切换且经 `localStorage` 记忆；② 暗色下所有正文/标签实测 >= 4.5:1、图形 >= 4.87:1，余量充足；③ 弱发光描边只用**低透明度描边**而非 `box-shadow` 光晕，避免亮环境下的过度刺目；④ 未使用大面积纯黑（`#0D1117` 而非 `#000`）以减轻光渗与拖影。
- **仍未解决的**：**没有做「首次访问跟随系统 `prefers-color-scheme`」**。当前策略是「暗色为默认 + 用户可切」。若最终采用本方向铺开全站，建议改为「首次访问跟随系统 -> 用户手动切换 -> 记忆偏好」，否则白天访客要每次手动点一次开关。这是**待改进项，不是已解决项**。

### 6.3 若站点未来新增大量非图表内容页，终端语言会不会失真

**结论：会失真，且这是本方向扩展时最先崩掉的地方。**

本样板里终端语言之所以成立，是因为**页面本身就是数据**：`>` 前缀、`01/` 章节号、等宽数字、刻度尺坐标轴，全都在承载真实信息。但把这套语言铺到大量非图表页（人物小传、章节导读、诗词全文、评论文章、学术说明）时会立刻出现三个问题：

1. **前缀与章节号失去信息量**。`> ` 和 `01/` 在数据页是「指向某个数据序列」，在叙事页会退化成**纯装饰噪音**——满屏 `>` 只会显得廉价。**建议：叙事内容页取消前缀与章节号，只保留等宽数字与面板边框。**
2. **等宽数字会与正文争夺注意力**。人物传记里出现等宽的生卒年、卷次尚可（强化「这是一份记录」的气质），但若正文标题、引用、注释全部等宽化，读者会用「读日志」的心智去读文学文本，**认知负荷升高**。
3. **暗底 + 面板卡片不适合长篇阅读**。终端风的 1px 边框、面板化卡片是为「可扫读的短信息块」设计的；长篇正文放进这个容器里，会显得被网格切割、缺少纸张的连续感。

**因此本方向的适用边界建议（供铺开决策参考）**：

| 页面类型 | 建议 |
| --- | --- |
| 数据看板 / 图表页 / 数据目录 | **完全适用**（本样板即此类） |
| 索引页、检索结果、列表页 | **适用**（保留暗色、等宽数字、`>` 前缀） |
| 人物小传、章节导读（中等长度） | **部分适用**：用无衬线正文、不加前缀、弱化面板边框 |
| 长篇评论、诗词全文、学术长文 | **不建议**沿用本方向；建议保留现站浅底纸感，或至少强制切到亮色态并改用衬线正文 |

### 6.4 其他已知代价

1. **三色在密集数据下有相互干扰风险**。本方向靠「低填充 + 线型分层 + 段间隙」压住了当前四张图，但**新增第五张图或更换数据密度后需重新验证**——这套规则不是自动成立的。
2. **深色态打印与截图分享不友好**。深底页面打印成浅色、或被截图贴进浅底文档时，会出现大面积反色块；亮色态的存在只能部分缓解。
3. **与项目文化气质有距离**。西游记题材天然偏古典、纸本、竖排；终端风把「数据终端」置于「刻本」之上，是一次**明确的取舍而非融合**。
4. **等宽标题对中文标题不友好**。标题用等宽 + 字距模拟终端感，但中文标题字距放开后会略显松散；短英文/数字标题效果最好，长中文标题一般。
5. **交互反馈弱**。终端风天然偏静态，本方向的 tooltip、hover 高亮都是**附加**的轻量反馈，没有做命令面板式的交互增强，深度可玩性低于现站某些专页。
6. **深色底纹网格的视觉噪声**。页面背景铺了 32px 的极淡网格线，在暗态下它是「终端感」的来源，但也让大面积背景略「脏」，且在低质量屏幕上可能产生摩尔纹。已通过把网格色压到 `#21262D`（与面板仅 1 级差）来控制，但**未做不同 DPI 与缩放比下的复测**。
