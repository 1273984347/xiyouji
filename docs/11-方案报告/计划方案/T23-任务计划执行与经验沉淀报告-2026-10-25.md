### 2.3 实跑抓出的真缺陷（3 个 · 静态层查不出）

**缺陷 1 · 默认权限缺 `FOR ROLE`（静默失效）**

- 病根：`ALTER DEFAULT PRIVILEGES IN SCHEMA public …` 不带 `FOR ROLE` ⇒ 默认权限挂在**执行该语句的角色**（`postgres`）名下 ⇒ 由**应用账号**创建的表**拿不到**只读账号的 SELECT。
- 实测现场：`pg_default_acl` 两条记录 `for_role = postgres`；业务表由 postgres 建所以"看起来有权限"，但这是**碰巧**，不是机制。
- 危害形态：**不报错**。只读账号在业务表建出来之前一切正常，建出来之后才静默失去读权限。
- 固化：校验器 C5「全部带 FOR ROLE」（按条数比对·排除注释行）+ 变异 M18。

**缺陷 2 · 授权晚于建表（顺序错）**

- 病根：引导脚本先建 `schema_migrations`、后设默认权限 ⇒ 该表落在授权之前。
- 实测现场：`schema_migrations` 的 `relacl` 为空（默认）⇒ 应用账号读它报 `permission denied for table schema_migrations`。
- 固化：校验器 C5「先设默认权限后建表」（按**代码行偏移**比对顺序）+ 变异 M19。

**缺陷 3 · 记账表所有权不属于应用账号（迁移序列跑不起来）**

- 病根：记账表由超级用户 `postgres` 建 ⇒ 迁移序列以应用账号执行时，`0001_baseline.sql` 里的 `COMMENT ON TABLE schema_migrations` 直接报 **`must be owner of table schema_migrations`** ⇒ 迁移序列**根本跑不起来**。
- 为什么静态层查不出：这不是**形态**问题（没有禁用的字符串、没有危险的语句），而是**所有权**问题——只能靠真跑暴露。
- 固化：引导脚本补 `ALTER TABLE schema_migrations OWNER TO ${APP_USER}` + 校验器 C5 + 变异 M22。

### 2.4 偏离预期的一次（测试隔离）

契约测试首跑在 PG 侧失败：`同 message_id 覆盖后不应残留 up`，实际 4。

- 真实原因**不是**后端缺陷：契约测试当时直接跑在**业务 schema** 上，`feedbackSummary(30)` 把**已迁移进来的 4 行真实反馈**算进了断言；且断言前提（空库）不成立。
- 修法（不是把断言改松）：给 PG 后端加 `schema` 隔离能力（`search_path`），契约测试跑在专用 schema `storage_contract_test`，用完 `DROP SCHEMA … CASCADE`。
- **教训**：这不是"测试环境问题"，是**测试前提没被满足**——把"隔离"当洁癖会付出假失败的代价，把"隔离"当前提才有意义。

## 5. 经验沉淀

**5.1 经验条目总表**

| 编号 | 经验 | 适用场景与边界 | 量化效果 | 证据来源 | 可迁移性 |
|---|---|---|---|---|---|
| E-01 | **接口形态必须由「最贵的那个后端」决定** | 任何抽象层设计；边界：后端能力相当时无须取舍 | 规划期「调用点零改动」的假设被证伪 ⇒ 3 个调用点必须改（加 `await`） | 本批 D-03 决策 + §2.2 返工 1 | 高——跨语言跨项目通用 |

| E-03 | **断言命中注释 = 恒真**（第三次实证） | 任何做源码文本匹配的校验器；边界：目标文件无注释时无效 | 计数型断言漏注释 ⇒ M0 基线假红 ⇒ 掩盖 M17/M20 真实结论 | 本批 §2.2 返工 3 + `strip_ts_comments()` | 高 |

**5.2 逐条展开**

**E-01 · 接口形态必须由「最贵的那个后端」决定**

抽象层最容易被设计成「照着最便宜的后端定形状」。本批的教训是反过来的：SQLite 走 better-sqlite3 是同步 API，PG 走网络协议而 Node **没有同步 PG 驱动**——若按 SQLite 定同步接口，PG 后端只能是假的（内存镜像或阻塞式自研协议栈）。⇒ 接口定为异步，SQLite 后端的实现体仍是同步调用，只是包在 `async` 里。
代价是 3 个调用点必须加 `await`（规划期 AC-02 的「零改动」被证伪）；收益是后端可换而业务逻辑不动。
**推广**：设计抽象层时先问「最贵的后端能不能满足这个形状」，而不是「最便宜的后端长什么样」。

**E-02 · 权限模型有三层：建表者 / 所有者 / 默认权限**

本批的三个授权缺陷恰好对应三层：`ALTER DEFAULT PRIVILEGES` 决定**建表者**名下新建对象的默认权限（必须带 `FOR ROLE` 才指得对人）；表**所有者**才有权 `COMMENT`/`ALTER`（`must be owner`）；`GRANT` 决定**既有表**的显式权限（默认权限只覆盖未来新建）。
三层任一缺失的后果是**静默**的——不报错、不抛异常，只是「读不到了」或「跑不起来」。
**推广**：部署脚本涉及多角色时，把这三层当**三个必填项**逐条断言，别指望一条 `GRANT` 兜底。

**E-03 · 断言命中注释 = 恒真（第三次实证）**

这是本仓教训的第三次复现（W897 的分隔符、W927 的裸词、本次的注释行）。本批踩了两次：① 数 `ALTER DEFAULT PRIVILEGES` 时把头注里那次也算进去 ⇒ 基线假红 ⇒ **掩盖了 M17/M20 的真实结论**；② 校验「迁移器只读打开源库」时命中的是**文档注释里的示例代码**，真代码改成可写也照样报绿（变异 M17 rc=0）。
**修法**：`strip_ts_comments()` 统一剥离注释后再匹配；计数型断言一律只取代码行。
**推广**：任何做源码文本匹配的校验器，**第一件事是把注释剥掉**——否则你匹配到的可能是文档而不是代码。

**E-04 · 测试隔离是前提，不是洁癖**

契约测试首跑失败（`actual=4`）时，最省事的做法是把断言改松。但那 4 行是**已迁移进来的真实反馈**——真把断言改松，就等于让"测试污染业务数据"这件事长期存在。正确修法是给 PG 后端加 `schema` 隔离（`search_path`），让契约测试跑在自己的 schema 里。
**推广**：断言失败时先问「**这个前提在测试环境里成立吗**」，而不是「断言是不是写严了」。

**E-05 · 「静态绿」不等于「能跑」**

静态校验 94/94 全绿时，迁移器仍然报 `must be owner of table schema_migrations`。原因是这个缺陷**不是形态问题**——没有禁用字符串、没有危险语句、没有任何"看起来不对"的地方，只有真跑才会暴露。
**推广**：把每一条静态断言按「它能证明什么 / 不能证明什么」分开记账；不能证明的（所有权、运行时语义、跨版本行为）必须留一条真跑项。

**E-06 · 对账要比集合**

行数相等是**最弱**的验收：删一行补一行仍相等。本批的对账做三件事——行数（最弱）+ 主键集合逐位比对（证明"搬的是同一批数据"）+ 逐行内容摘要（证明"内容也没错"）。实测中它直接抓出目标库每表多 1 行的污染。
**推广**：任何"搬迁/同步/迁移"类交付，验收至少要比集合而非计数。

**E-07 · ESM 把接口当值导出**

`export { DbFeedback } from "./types.js"` 在 ESM 运行时直接抛 `does not provide an export named`，而 `tsc` 在未开 `isolatedModules` 时**不报错**。本批是集成测试的 4 个红当场抓到的。
**推广**：TS + ESM 项目里，类型一律用 `export type`；CI 上开 `isolatedModules` 能把这类问题提前到编译期。

**E-08 · 抽象层不是转发**

如果两个后端各写各的测试，抽象层就只是一层转发——没人能证明"换后端后行为不变"。本批的契约测试是**同一套断言**跑两个后端；因此它才有资格叫"契约"。
**推广**：抽象层的验收方式只有一个——**同一套用例，多个实现**。
