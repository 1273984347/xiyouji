## 执行摘要

仓库体积是本项目唯一长期越线的方案阈值项（§8.3 评审阈值 1 GB）。本批先用**取证**判定成因，
再用**用户批准的改写历史 + LFS 迁移**落地，并把「历史改写必然打断的审计追溯链」一并修复。

- **取证**：`.git` 1198.8 MB 全在历史对象；全量 blob 58,842 件 / 逻辑 5,499.5 MB（delta 压缩率 4.6×）；
  **最大单体仅 24 MB** ⇒ 无误提交巨型文件 ⇒ 膨胀来自「同一路径反复改写」（CHANGELOG 927 版本 225.8 MB /
  file-index 842 版本 150 MB / 台账 940 版本 141.6 MB）⇒ 不改历史的手段（gc + repack）最多到 1.13 GiB，
  **仍越线 13%** ⇒ 改写历史是唯一达标路径 ⇒ 用户批准。
- **迁移**：`git lfs migrate import --include="assets/promo/**" --exclude="**/*.md"` ⇒ 55 s 重写 1900 个 commit；
  LFS 对象 614 件 / 1.1 GB **全部上传远端**（rc=0）；工作区经 `git lfs checkout` 恢复真实内容（magic 校验通过）。
- **hash 回填**：1898 条映射（改写前后同源 ref 按序配对）⇒ **单 pass 最长匹配**回填 1529 处 / 172 文件 ⇒
  复核三面全绿（旧 hash 残留 0 · 混合串 0 · 真失效引用 0）。
- **安全论证**：Pages 发布路径是 `site/`（仓根 assets/ 不在发布物内）· 三个扫描器只扫源码扩展名（png/jpg 不在扫描面）·
  门禁读 assets/ 的只有 md（已排除）⇒ **迁移对 Pages 与 CI 门禁零影响**。

## 二、执行记录

**A1 取证**：`git count-objects -vH` → 单 pack 1194.5 MB；`git cat-file --batch-all-objects` → blob 58,842 件 /
逻辑 5,499.5 MB；`git rev-list --objects --all` + 路径聚合 → 主因是同路径反复改写。

**A2 迁移**：本地 mirror 备份（1,162.8 MB）→ `git lfs migrate import --include="assets/promo/**"
--exclude="**/*.md" --include-ref=refs/heads/main --include-ref=refs/heads/feat/w1207-c8-placeholderize --yes`
（55 s）→ `git lfs install` + `git lfs checkout`（324 对象 / 414 MB，magic 校验通过）→ `git lfs push --all origin`
（614 件 / 1.1 GB，rc=0，5.3 MB/s）。

**A3 回填**：映射来源 = 改写前备份 ref 与改写后 ref 按提交顺序配对（`git lfs migrate` **不留** `refs/original/*`，
故用备份 mirror 作旧线来源）⇒ 1898 条映射 ⇒ **单 pass 最长匹配**回填 1529 处。

**A4 零影响核验**：Pages 发布路径 = `site/`（`pages.yml` 的 `path: site`）⇒ 仓根 `assets/` 不进发布物；
三个扫描器 `SRC_SUFFIX` 只含源码扩展名 ⇒ png/jpg 不在扫描面；门禁读 assets/ 的两处（`perf_optimize.py` 的
`font-subset-guide.md`、设计资产清单的 `assets/design/README.md`）都是 md ⇒ 已排除 ⇒ 迁移零影响。

## 四、复盘

### 做对的

1. **先取证再动手**：若凭直觉直接 force-push 改写历史而不判定成因，会在不知收益的情况下破坏追溯链。
2. **迁移范围逐面核依赖**：Pages 发布路径、扫描器扩展名白名单、门禁读 assets/ 的具体路径——三处都核过才动手。
3. **备份先行**：改写前先做本地 mirror clone（1,162.8 MB）⇒ 回退底稿就在手边；回填出问题时正是靠它原样恢复。

### 做得不好的（风险与偏差记录）

1. **回填第一版用了子串替换**（`short[old[:7]] = new[:7]`）⇒ 8/9 位引用被换成「混合串」；第二版逐条修又级联歧义；
   最终靠「从备份恢复 + 单 pass 最长匹配」才干净 ⇒ **代价是一轮返工**（沉淀为 E-226）。
2. **验证器自身误报**：判定「混合串残留」时把「新 hash 前 8 位」与混合串同形 ⇒ 72 处假阳性 ⇒ 先自证判据再下结论。
3. **`git lfs migrate` 为被排除路径自动加的 `**/*.md !text`** 会压制 W993 立的「md 一律 LF」机制 ⇒ 已修正，但若不读
   `.gitattributes` 就会漏。

### 7.2 决策记录与理由

| 决策 | 理由 |
|:---|:---|
| 迁移范围限定 `assets/promo/**` 并排除 md | 该范围占逻辑体积 1,143 MB（非 delta 友好 ⇒ 物理收益最大）且被门禁/CI 零依赖；md 被 `perf_optimize` 与设计资产清单读取 ⇒ 必须保持真实内容 |
| 先上传 LFS 再推历史 | 指针指向不存在的 LFS 对象 = 仓库损坏 ⇒ 上传 rc=0 是推送的前置条件 |
| 改写前做本地 mirror 备份 | 唯一的回退底稿；回填出问题时正是靠它原样恢复 |
| 回填用单 pass 最长匹配 | 短前缀替换是自指操作（替换结果可能再次成为替换源）⇒ 必须单 pass |
| 旧远端分支暂不删 | 需先 force-push main 让新历史成为主线；且 24 个分支是否全部已合并需逐个核 |

### 7.4 方案可行性自评

§8.3「仓库体积 ≤ 1 GB」是本方案唯一长期越线项。本批证明：**越线成因是「同一路径反复改写」而非巨型文件**，
因此「gc / repack」类手段只能到 1.13 GiB，而**改写历史 + LFS 迁移是唯一达标路径**（本次实测达成逻辑侧目标，
远端体积待 force-push 后由平台回收旧对象）。方案可行性自评结论：**路径已验证可行，落地待最后一步授权**。
