### 2.3 关键设计决定

1. **修复脚本用 Python 而非 shell**：初版写成 .sh，但本机 Windows **无 bash**（WSL 未装）⇒ bash -n 语法校验不可执行，
   违反「落盘即校验」纪律 ⇒ 改写为 Python 实现（可 py_compile + ruff + 本地实跑 + 可加单测），workflow 调用改为
   python scripts/ci_repair_apt_mirror.py。
2. **候选源链用实测验证而非盲目替换**：替换后必须 apt-get update 成功才采用；全部候选失败时打 warning 并以 0 退出
   ⇒ 修复层永不掩盖后续步骤的真实失败语义。
3. **第 71 槽接 ci_sim 而不是只等 Delivery Gate**：CI Sim job 不碰 apt ⇒ 即使 runner 的 apt 源仍不可达，
   第 71 槽在 CI 侧仍有独立执行证据 ⇒ 机制层的覆盖不再单点依赖易失败的外部安装步骤。
4. **标签判据只放宽低风险形态**：scope 段逗号分隔（fix(ci,w1191):）纳入；**描述段 W 号形态不纳入**
   ——放宽它会把「在途批的号被别批提交描述段开头提及」误判为已提交 ⇒ 削弱铁律 24 的并行 touches 交集拒绝。
   该形态登记为下批待办并写明可选方向，不假装已解。
5. **CHANGELOG 历史段不改写**：W1209 段的过时陈述订正写在**本批 W1211 段**里，原文保留 ⇒ 不篡改历史记录。
6. **回填类一律并入在途批**：W1209 订正 + Backlog 对账 + 坑表 E-227 全部并入 PR #171 同一分支，不另开 PR。

## 四、复盘

**做对的**：把「CI 红了」当归因题而不是当修复题——先拿父提交基线对照失败 job 集合与报错逐字，
一步就定性为存量环境故障，避免了「反复改代码试错」。修复层与机制层分开做：
apt 回退解决「这次能不能跑通」，ci_sim 接槽解决「以后这类槽的 CI 证据会不会再次为零」。

**踩到的四个坑**：

1. **本机无 bash ⇒ shell 脚本无法校验**：.sh 初版写完才发现 Windows 侧只有 WSL 提示、无 bash 可执行
   ⇒ bash -n 不可用 ⇒ 违反「落盘即校验」。**教训**：仓内新增脚本若需要语法级校验，选本机可校验的语言。
2. **判据口径比案例窄**：批次标签正则只认「括号内恰好是 w+数字」，而仓内真实形态还有 scope 段逗号分隔
   ⇒ P-43-01 反填对半数批次判「无批次标签提交」⇒ 修实例时才发现覆盖面不足。
3. **注释与实现不符**：wnum_commit_index 的注释写「一笔提交含多个批次标签时各号各计一笔」，
   实现却只 search 一次 ⇒ 一笔跨批提交只计一号。**教训**：注释里的契约要用回归锁钉住，否则它会悄悄变成谎话。
4. **Backlog 触发器对在途行不认 token**：状态列以「在途」开头的行被跳过 ⇒ token 必须在收官状态列里写
   ⇒ 本批开工期必然红一次，属设计如此（对账批自身就是被点名的那批）。

**未做（不假收敛）**：① 批次标签的「描述段 W 号形态」仍不识别（放宽会削弱并行保护）⇒ 已登记下批待办并写明可选方向；
② 复盘触发器 T1/T2/T3 全触发（距上篇复盘 5 天 / 52 批 / 122 提交）⇒ 本批未认领复盘批，登记下批；
③ PR #171 的合并待 CI 绿后由用户裁决（本批只推不合并）;
④ apt 回退只能缓解 Azure DNS 不可达，若故障源换成别的域名，候选链需再扩。

**可迁移的三条**（跨项目通用）：

1. **CI 红灯的第一动作是找基线 run，不是找自己改了什么**：对照**失败 job 集合**与**报错逐字**，
   判定「本批引入」的充要信号是出现基线没有的新 job 或报错文本不同。
2. **新增门禁槽必须自问「CI 侧谁会真的执行它」**：若唯一覆盖者依赖易失败的外部安装步骤，
   该槽的 CI 证据等于零；把纯 Python 判据接进预演清单才是可持久的证据面。
3. **口径放宽要看它削弱了什么**：批次标签从「窄」放宽到「宽」会同时削弱在途批的并行防护 ⇒
   放宽前先问「这个口径保护着谁」，不能只问「这个口径漏了谁」。
