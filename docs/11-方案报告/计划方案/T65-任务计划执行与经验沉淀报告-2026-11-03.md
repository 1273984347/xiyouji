## 1. 执行前计划

### 1.1 范围与边界

| 做 | 不做 |
|---|---|
| 新增版本面**幂等**推进器（纯替换型字面量：README 抬头 / STRUCTURE 头部 / 项目说明头部与列表行 / CITATION.cff / workflows README 两处区间 / 交接文档「当前进度」标题与「当前 HEAD」句） | 不动页面内容逻辑（零页面内容逻辑改动）· 不碰 CHANGELOG 段与 file-index 段的插入（属级联职责）· 不碰页脚链/里程碑块/头链（属追加型内容） |
| 级联工具的版本面改为调用共享模块 | 不重写级联的段面（插段逻辑保持原样·避免非幂等面被误用） |
| 收官链加 versions 步 + add 收尾 | 不改「csp 恒末位」的实质（csp/cspcheck 仍为末两步）· 步数由 8 变 9 且位置固定在 stats 之后 |
| 本批不新增坑表条目 | 不占任何 E-NN（并行会话实占 E-133~E-140）· 教训落本报告 §5（归集去向见 §2.2 B-05） |

### 1.2 关键设计判断

**为什么把「版本面」独立成幂等模块，而不是给收官链加一步就完事**：根因在级联工具的**面耦合**——版本面字面量与段插入被绑在同一条非幂等命令里（段已存在即断言失败）⇒ 落段后单独同步版本面无路可走 ⇒ 必须先把「版本面」从「段插入」里解耦出来，收官链才有可复用的版本面推进步。

**幂等怎么判定**：替换结果与原文相同 ⇒ 分两种情况——① 该处文本本就等于目标态（**幂等命中**）；② 正则在该文件里根本匹配不到（**失配**）⇒ 用「正则能否匹配」把两者区分开：匹配得到 ⇒ 幂等命中（零变化）；匹配不到 ⇒ fail-closed 报错（不得静默当作「已是目标」）。

**共享模块 vs 两份实现**：级联原本自带一套版本面改写 ⇒ 若新模块另写一套 ⇒ 两份实现必然漂移 ⇒ 本批把级联的版本面**改为调用共享模块**，保留「只引用不复制」原则。

## 4. 复盘

### 4.1 做对了什么

- **先做只读勘察再动手**：写任何代码前把级联的 8 个面函数全读完 ⇒ 定位到「面耦合」这个真根因，而不是直接在收官链里加一步。
- **幂等判定区分「已是目标」与「正则失配」**：这是幂等实现最容易糊弄过去的地方——两者都表现为「替换后没变化」⇒ 用「正则能否匹配」区分，否则失配会被静默当成「已是目标」而永不报错。
- **把静默失效当阻断项处理**：B-02（add 步不检查 rc）不是「顺手修一下」，而是「不修则整条收官链在含未创建文件时永远漏 add 且无红灯」⇒ 根修并加负样本。

### 4.2 该改什么

- **交接文档的字面量面仍混在 _face_handover 里**（里程碑块/头链 prepend/轮转 与 「当前进度」「当前 HEAD」两句同面）⇒ 版本面模块目前只覆盖了其中两句 ⇒ 下一批应把该面拆成「追加型内容面」与「字面量面」两块。
- **跨 clone 占号区不可见**：本批实测 reserve_w.py 对他方在途行报「无占号支撑」⇒ 跨 clone 撞号只能靠台账认领行 + 书面回执 ⇒ 建议把该 WARN 判据改为「跨 clone 场景不判红」（属仓内判据面·本批未动·已在 §5 登记）。
