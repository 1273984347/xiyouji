## 执行摘要

本批不碰页面与判据，只做一件事：**把「CI 侧教训」从文本层升级为机器层**。

1. **取证**：W1286 期间 CI 29 个 run（21 success / 6 failure / 2 cancelled），带 Delivery Gate 的主 run **实跑 6 轮、前 5 轮没绿**；坑表 415 条里 **118 条（28%）** 涉及 CI/门禁 —— 「CI 出问题」是本仓最高频坑类，**却仍在本批复发两次**（E-303、E-308）。
2. **三条根因**：① 既有 CI 教训是**文本层**（给人看）不是**机器层**（拦得住），且是「先红后记」；② 既有 `scripts/ci_sim.py --full` 只跑**本地工作树**门禁，**不复现 CI workflow 的步骤序列** ⇒ 只在 CI 侧发生的缺陷本地永远测不出；③ 本批引入新组合（探针报告**首次入库** ⇒ 「CI 现跑产物 + 已入库产物」第一次同时成立）⇒ 既有条目不适用。
3. **两项整改**：① CI 的 Delivery Gate 前加「**工作树干净断言**」（`git status --porcelain` 非空即红）⇒ 任何 CI 步骤改动了入库文件而未还原**当场红**；② `ci_sim.py` 增 `--ci-steps`（复现 CI 前置序列：重生成产物 → graphic/body 探针现跑 → 还原产物 → 干净断言），并把 worktree 检出改 **LF** 对齐 CI blob。
4. **自我认错**：本批推了 **7 笔** ⇒ **CI 轮数 = 提交数**，违反既有口径「一批 = 一轮 CI / 一次 push 带齐全部内容」；且推前**未跑**既有 `ci_sim.py`。本批起钉回：**一批 = 一轮 CI**，根修合并进主体提交。

   ```yaml
   - name: Assert clean worktree before delivery gate (W1287·E-308 机器化)
     run: |
       dirty="$(git status --porcelain)"
       if [ -n "$dirty" ]; then
         echo "::error::工作树非干净：CI 步骤改动了入库文件且未还原（须 git checkout -- 还原，或把该步骤产物写到非入库路径）"

         exit 1
       fi
   ```

### 红队复核（同批·第一性推演后补做）

**触发**：用户要求「先假设方案是错误的，站在最强反对者角度找反例」⇒ 对本批方案逐条攻击并**实测**。

| 攻击点 | 结论 | 证据 / 修法 |
|---|---|---|
| 断言漏检未跟踪文件 | **成立** | 实测：干净 worktree 里新建未跟踪文件 ⇒ 断言仍 rc=0 ⇒ 修：并上 git ls-files --others --exclude-standard（现已 rc=1 判红） |
| run_all 产物非确定性 ⇒ 断言 CI 恒红 | **不成立** | 实测幂等：同一 commit 连跑两次生成器，diff 均为空 |
| 断言会被环境差异误伤 | **基本不成立** | 产物幂等 + 已刷新入库 ⇒ 风险窗口小 |
| 回落解析掩盖真断链 | **成立** | 修：回落须「去掉全部上跳后的纯相对路径在仓内存在」⇒ 区分语境错位与真外部路径；命中输出 [NOTE] 可见 |
| 「可机器化者一律断言」纪律本身有害 | **成立** | 补：断言须正负样本自测（否则产出「为过门禁而加的形式检查」） |
| ci-steps 是 opt-in ⇒ 仍靠自觉 | **成立** | 补：--push-gate + 仓内 .githooks/pre-push ⇒ 物理约束 |
| **优先级误判** | **成立** | 本批做的是「让 CI 侧缺陷可被发现」，但用户问的是「CI 为什么跑这么多次」⇒ 发现 ≠ 减少轮次；真正的解药是把反馈回路从远端搬回本地（推前闸门） |

**第一性结论**：CI 轮数的根因不是纪律松，是**反馈回路的位置与延迟**（唯一反馈通道是「推 ⇒ 等 20-30 分钟 ⇒ 看结果」⇒ 该延迟反向塑造「一改一推」的行为）。故修法主体是**把验证搬回本地并保证等价**，断言与仿真器只是配套。
