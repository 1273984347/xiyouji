## 三、施工

1. **工具根修（治本·口径同源）**：`scripts/archive_segments.py::plan()` 的 `moved_ws` 原按 `hits[keep:]` 计（把「末尾文件级块」**之下**的段也算进迁出段表）⇒ 与实际迁出块（止于 `tail_start`）**口径不一致** ⇒ `assert len(moved_in_block) == len(moved_ws)` 在该边界**必然触发**。修法：`moved_ws` 只计**实际落在迁出区间 [cut, tail_start) 内**的段 ⇒ 与 `moved_in_block` 同源 ⇒ 断言恒成立。
2. **回归锁（3 例·含负样本）**：新增 `tests/unit/test_archive_segments_plan_scope.py`——① 末尾块沉底时其下段**不得**计入段表 ② 段表长度 == 迁出块实算段数（原断言的同源前置条件）③ 无末尾块的常规形态**行为不变**（防回归）。
3. **台账 hash 回填**：`ledger_backfill.py --w 1291 --hash df8bab1c9 --status "已收官（…CI 六作业全绿…）"` ⇒ 状态列保留详细终态结论（**未用 `--from-git`**·它会覆盖状态列并抹掉结论·W1289 教训）。
4. **待裁决项（本批只定位·不擅改）**：「两面同下界」判据在两面号集合不同时不可达 ⇒ 两条候选修法见 §八 决策记录 D-01（改判据口径 / 修 CHANGELOG 结构）⇒ **两者都触及禁改面或结构面 ⇒ 须用户批准** ⇒ 本批如实登记。

## 六、经验沉淀

- **「同一命令在某些参数下成功、某些参数下必红」⇒ 先怀疑口径不一致，别怀疑规模**：本例分段迁 17 段成功、7 段必红 ⇒ 直觉会归因「迁出规模/段表计数」；实测逐项对比才见真因——**段表比迁出块多算 3 段**，多算的段在「末尾文件级块」之下（起点 > tail_start）⇒ 是**区间口径**问题。
- **「文件级块沉在段区中间」是级联滚动的已知副作用，但它与归档工具的尾部保护假设相冲突**：工具假设文件级块在末尾 ⇒ 其下的段永远迁不出 ⇒ 连带「两面下界对齐」在号集合不同时不可达 ⇒ **结构性欠账要显式登记为裁决项**，不要用「跳过自检」长期掩盖。
- **台账 hash 回填必须用显式 `--hash` + `--status`**（保留状态列的详细终态结论）⇒ `--from-git` 会覆盖状态列把结论抹成「已收官（hash·git 反填）」。
