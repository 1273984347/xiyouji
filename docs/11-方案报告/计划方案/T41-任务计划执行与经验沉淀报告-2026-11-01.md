## 0. 背景与结论速览

### 0.1 问题的真实形状

用户问「哪些事能沉淀成可复用的 Skill」，隐含前提是「内容还不够固化」。**实查结论相反：这个仓的内容固化度已经很高，高到几乎不缺内容，缺的是「挂载」**。

三组实测数据：

1. **内容侧已饱和** —— `docs/agent/` 10 件（2 份清单模板 + 4 份角色职责书 + 门禁全量定义 + 坑表全量）、`docs/10-方法论沉淀/` 28 篇深度篇、`.agent/skills/` 1 件 Skill 体。`batch-closeout-checklist.md` 是 9 步有序清单且明写「顺序本身有依赖」；`gate-triage-template.md` 是五步法 + 四条红线 + 高发误判表。**这两份已是 Skill 形态，只差换载体重排**。
2. **重复度已可量化** —— 346 个批次标题里「门禁」命中 43 次（12.4%，最高频主题）、「审查」20、「归档」19、「复盘」13、「复核」12、「对账」12、「素材」12、「计数」11。全文动作短语侧 `verify_delivery` 326 次、`batch_cascade` 142、`check_doc_sync` 91、`lint_links` 75、`generate_csp` 71、`preflight_check` 70、`stats.py` 61。
3. **挂载层是断的** —— 全仓唯一的 Skill `puti-shouye` 位于 `.agent/skills/`，而 **W1034 批已实测确认：该路径不自动加载，系统自动加载只认用户级 `skills/` 目录**；该目录实测 `Test-Path` = False（根本不存在）。`.gitignore` 第 214–216 行已放行 `.agent/skills/**`（文件确实进 git、多 Agent 拿得到），**但没有任何 Agent 会在动手前自动读它** —— 它靠 `AGENTS.md` 的一行指针 + 主动查阅生效。

⇒ **核心判断：Skill 化的瓶颈不在「写什么」，在「放哪儿」。**本批不建 Skill 的价值在于先把落位这道题解掉——否则再写 8 个 Skill 也一样是「已建未上架」。

### 0.2 一句话结论

- **Skill 候选 8 项已排出序**：S1 批次收官流水线 → S2 门禁红灯定位 → S3 并行取证 → S4 对抗审查派发 → S5 计数对账 → S6 素材成套 → S7 任务分级 → S8 引文探针（**不独立成 Skill，并入 puti-shouye**）。详见 §6。

## 1. 计划：排序判据（先定义，再排序）

用户要求「重复做、步骤固定的优先」。这两条不足以定序（例：「引文探针」重复度低但步骤固定度极高；「批次收官」重复度与固定度双高但已有 9 步 checklist 固化成本最低）。故本批先立 **4 条可复算判据**，再对每个候选逐条打分：

| 判据 | 代号 | 量化口径（可复算） |
|---|---|---|
| **重复度** | D | 该类工作在 CHANGELOG 346 批次标题中的命中次数 + 全文动作短语命中次数 |
| **步骤固定度** | F | 能否写成「有序 + 不许跳步 + 每步有可判定验收」；已有 checklist/职责书 = 高 |
| **素材成熟度** | M | 仓内是否已有可 1:1 搬运的模板文档（决定固化成本） |
| **失效代价** | C | 漏做/做错的代价：白跑门禁 · 真缺陷被压成假绿 · 结论带偏 |

> **判据纪律**：排序表每行都标出证据出处（文件路径 + 命中次数），**禁凭印象排序**；负样本意识——若某候选 D 高但 C 低（如 `gen_sitemap`），显式记为「不入选」并写明理由，不静默丢弃。

## 4. 复盘

### 4.1 做对了什么

- **先立判据再排序**，避免了「凭印象列清单」——这也正是本项目坑表反复记的那类坑（判据先于结论）。
- **用实测替代记忆**：频次全部来自探针实跑，不手数（`checkpoint` 纪律：计数必须实算，手算必错——坑表 E-1024 同族）。
- **识破了问题的真实形状**：用户问「哪些事能固化」，若直接列 8 个 Skill 清单，会错过「挂载层断裂」这个真正的瓶颈——那才是「为什么 puti-shouye 存在了却没人用」的答案。

### 4.2 走过的弯路（留痕）

| # | 弯路 | 修正 |
|---|---|---|
| 1 | 首次 bash 用了 `cd /d/xiyouji && …`（bash 语法）——本机是 PowerShell，报 `找不到路径 D:\d\xiyouji` | 改 `git -C D:\xiyouji …`；第二条命令因 `cd` 触发安全策略拦截（`write/delete targets cannot be verified safely after a command working directory change`）⇒ **凡 bash 命令内不做工作目录切换** |
| 2 | `Get-ChildItem "%USERPROFILE%\.minimax" -Directory \| Select-Object Name` 返回空（管道+格式化组合下输出丢失） | 改 `ForEach-Object { $_.Name }` + 独立 `Test-Path`，一次拿到 12 个目录名 + 目录不存在的事实 |
| 3 | 查 skills 目录时 glob `skills/**/*` 返回 "No files matched" —— 若就此下结论会误判「目录存在但为空」 | 补 `Test-Path` 交叉验证 ⇒ 真相是**目录根本不存在**，两者结论完全不同（附件 §6.3 的复现命令 `Get-ChildItem` 在目录不存在时会报错而非返回空） |
| 4 | **误判 `git commit -- <pathspec>` 的取源语义** —— 以为 pathspec 提交取**索引**内容（于是放心做了索引层精确裁剪），实际它取**工作树**内容 ⇒ 索引层的裁剪被整个绕过 | 提交前复验「索引不含 W1073 行」通过 → 提交后 `git show HEAD:台账` 却含该行 ⇒ **判据通过但结果相反**，是「判据验的是 A、操作做的是 B」的典型 | 查 `git commit` 文档语义（pathspec 形式 = "records the content of the files that match the pathspec without recording the changes already added to the index"）⇒ **共享文件的「部分提交」在本仓当前无可用路径**（见 §12.2 R-10） |

### 4.3 本批最值得记的一条

> **「内容已固化」不等于「经验会生效」——中间隔着一层挂载。**
> 本仓用 181 条坑表 + 28 篇方法论 + 9 步收官清单证明了一件事：**经验写下来不难，难的是让它在动手前自动出现在上下文里。**`puti-shouye` 是仓内唯一 Skill，它的存在证明了固化是可能的；它的**不被加载**证明了固化的最后一公里才是瓶颈。
> ⇒ 推广：**评估「某经验是否已固化」时，必须验「加载路径」而不是「文件存在」。**判据 = 改一次文件后，一个不做额外指引的新 Agent 能否在动手前看到这条经验。

## 5. 经验沉淀

| # | 经验 | 落点 | 状态 |
|---|---|---|---|
| E1 | **挂载层断裂**：载体存在 ≠ 经验生效；Skill 化的瓶颈是加载路径而非内容 | 本报告 §0.1/§4.3 + 仓内坑表（见下） | 待落坑表（下一批同批落） |

| E3 | **`Test-Path` 与 `Get-ChildItem` 必须交叉验证**：目录不存在时后者报错、glob 返回 "No files matched"，三者语义不同，混用会把「不存在」误判成「为空」 | 本报告 §4.2 | 待落坑表 |

### 7.1 一个结构性建议
