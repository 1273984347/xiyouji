### 1.2 关键设计判断

**为什么是「行锚定 + 尾部锚点断言」而不是「字符集校验」**：把描述的字符集收紧（如禁分号/右括号）只是治标——描述性文本的标点种类不可穷举，且约束会外溢到写报告的人。⇒ 正解是让正则**对描述内的标点不敏感**（行锚定）⇒ 并用**尾部锚点唯一性断言**把「正则提前闭合」这一残余风险从「静默产出坏文本」变为「显式 fail-closed」。

**为什么把编号规则段上限划进版本面**：它本质是**跨文件的现役字面量**（W001-W####），原先搭在级联的段插入里 ⇒ 段插入非幂等 ⇒ 每次落段都要手工/就地改 ⇒ 与「版本面」职责重复。⇒ 划入版本面后：级联与收官链共用同一实现（单一事实源），且**今后随版本面自动推进，不再需要手工 bump**。

**为什么版本面必须单调（低号批不回退）**：版本面表达的是「**现在是什么**」⇒ 只能指向**最高号**批次。而落段批号与合并次序可以不一致（并行会话乱序合并：对方 W1118 先合入 main，我方 W1117 后落段）⇒ 若沿用「推进到本批号」的语义，README / STRUCTURE / 项目说明 / CITATION / workflows README / HANDOVER / 编号规则段会被**整体回退**到低号，抹掉已合并批次的现役标记。⇒ 正解：推进器改为**单调**——目标批号 ≤ 该文件现役批号 ⇒ 该文件**零变化**（不回退·也不 fail-closed）。

**为什么段落在降序位而不是顶置**：仓内既有工具 `backfill_changelog.py` 明文规定「段按批号降序排列·新段插在第一个号小于自己的段之前·当前态六面只指向最高号」，并对段序做**严格降序断言**⇒ 顶置会直接破坏该工具不变量（且下次补段即断言失败）。⇒ 本批段落 W1118 之下、W1116 之上；版本面保持 W1118 不动（与 backfill 的「只升不降」同名规则一致）。

## 4. 复盘

### 4.1 做对了什么

- **对方实证即查即复现**：不辩解、不推诿，5 分钟内定位到「描述匹配段过窄」这一根因，并把对方提供的**第二、第三个触发样本**直接转为验收用例。
- **把「字符集约束」升级为「正则鲁棒 + 尾部断言」**：治标（禁字符）会外溢到写报告的人；治本（行锚定 + 尾部断言）让描述里的标点不再是隐形阻断点。
- **按「职责归属」而非「按文件」划界**：编号规则段上限是**跨文件现役字面量**，划进版本面后级联与收官链共用实现 ⇒ 顺手消灭了「手工 bump」这一环（这也是我方 W1117 批对并行会话 W1116「登记面一致性闸」的直接受益点）。
- **跨批改动他人断言时要求留痕三要素**：接受技术必要性，但要求写明「改哪批哪个断言 · 理由 · 新表述原文」⇒ 两批文档不各说一套。
- **先查工具语义再决定段位**：先前「把本批段顶置」的直觉方案，若落地会破坏 `backfill_changelog.py` 的严格降序断言（工具不变量）⇒ 读工具实现后改为「按号序降序插段 + 版本面单调」⇒ 既保工具不变量，又保现役面不被回退。
- **把门禁的隐含假设当缺陷面查**：第 51 门禁的归属判定隐含「新增批必是顶段」这一假设 ⇒ 在低号批后落段时该假设失效 ⇒ 扩展归属识别（新增段集合）而非绕过门禁 ⇒ 判据强度不降（仍要求索引 ⊆ 归属批 spec）。

### 4.2 该改什么

- **「幂等」这类声明应当由工具自己保证可验**：本批之前，两批的幂等声明都只验了「主流程跑一次」⇒ 漏掉形态面。⇒ 建议把「二次推进零变化」做成**收官链末位的一道闸**（与并行会话 W1116 的两道闸同族）⇒ 否则每个新面都要靠人记得验。
- **占号取号口径与顶段推进耦合**仍未解（本批靠手工登记绕过）⇒ reserve_w 的 --w 显式占号参数仍未落地。
- **段面（CHANGELOG / file-index 段数窗口回窗 · 段登记 · 段插入幂等）仍不在收官链内** ⇒ 本批靠「backfill 补段 + 两面各腾一段 + 段重建」三步走通（工具已支持，但收官链尚未编排）⇒ 归集：把「腾窗 → 补段 → 段重建」收进收官链的一段幂等子命令。
- **`git checkout -- <path>` 恢复的是暂存区版本而非 HEAD 版本**：本批撤销「手工顶置段」时因此撤销无效，并连带触发「混合行尾」断言（W706 判据）⇒ 正确写法是 `git checkout HEAD -- <path>`（或 `git restore --source=HEAD --staged --worktree`）⇒ 已登记为跨项目教训。
