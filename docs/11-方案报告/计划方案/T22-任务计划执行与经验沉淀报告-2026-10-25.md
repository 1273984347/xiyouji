### 1.5 问题界定：四个环节各缺一种保证

共享面不是「一个文件」，而是**四个串联环节**，每环缺不同的保证：

| 环节 | 现有机制 | 缺的那一环 | 实证 |
|:--|:--|:--|:--|
| ① 台账·取号 | `preflight_check.py` 取 max(W)+1 | **非原子**——两会话可同时算出同一个号 | W928 撞号（架构会话 × 布局会话） |
| ② 台账·写行 | 无 | **行级独占**——两方同时改台账会 lost update | 两方同时 `git add` 台账即覆盖 |
| ③ 台账·回填 | 无强制 | **收官不回填 = 永久挡路** | W928 早已提交收官，状态列仍「在途」⇒ W930 全工序就绪却被 preflight 拒绝开工 |
| ④ CHANGELOG·顶段+1 链 | `batch_cascade` 单写级联面 | **立段的串行化**——立段时顶段须等于上一提交 | 立段顺序错即两个同号段 / 顶段链断裂 |

### 1.6 三层方案与本次取舍

| 层 | 内容 | 判定 |
|:--|:--|:--|
| 层 1 | **规则三条**写入 `docs/00-导读/文档规范.md` §11.0 | ✅ 采纳（零脚本改动、零并行风险） |
| 层 2 | **3 个机检判据**（A 取号原子性 / B 回填独占 / C 收官回填体检） | ✅ 采纳 |
| 层 3 | 台账与 CHANGELOG 写入收敛到单写者服务 + 文件锁 | ❌ 不采纳（改动面覆盖全部并行会话，收益/风险比不划算） |

**判据 B 的形态调整（基于实测）**　原设想做成「preflight 见台账有他方未提交改动 ⇒ FAIL」。实测后否掉：台账两类写入性质不同——**纯追加**（新增认领行）行级独立、可并发；**回填**（改既有行）会 lost update、必须互斥。做成「台账脏 ⇒ FAIL」会卡住自己（W930 实证：台账脏但实为合法在途）且与「立即开工」自相矛盾。⇒ 互斥放进回填工具的**行指纹校验**；preflight 侧只出 NOTE 提示「提交时勿整文件 `git add`」。
**判据 D / E 的由来（本批自证修复）**　两处缺陷由**他人实测报出**与**本批自身实跑**共同暴露：**D**——架构会话（W934 批）实测报出「`_split_touches` 不剥反引号，而台账 touches 列的路径带反引号 ⇒ 与命令行传入的无反引号路径字面不等 ⇒ `touches_conflict` 恒返空 ⇒「PREFLIGHT PASS·无交集」在真实撞面时**假绿**」；**E**——修复 D 后本批立即实跑，发现交集拒绝把「台账认领行」与「方案报告 README 登记行」当普通共享面 ⇒ **每个批次都要写这两面 ⇒ 交集在准入阶段恒红 ⇒ 纪律被架空**。⇒ D 的修法：`_split_touches` 具备**反引号感知**（反引号内内容整体取一个 token）；E 的修法：**登记类共享面排除**出交集拒绝，并发保障改由「纯追加 + 精确暂存 + 回填行指纹」承担。

1. **三类症状各有一个判据兜住**：撞号（判据 A，实战拦停 1 次）、丢写（判据 B，9 组负例全红）、伪阻塞（判据 C，8 项负例全红）；

### 5.2 逐条展开

**E-01 · 共享面纪律要按操作性质分层**　同一个文件里，「新增一行」与「改一格」的风险完全不同：前者行级独立、并发安全；后者会 lost update。把两者合并成一条「文件脏就 FAIL」的规则，会把合法并发一并卡死（实测：台账因 W931 在途而脏，但那是合法在途）。**判据**：先问「这次写会不会覆盖别人写过的字节」——不会 ⇒ 可并发；会 ⇒ 必须互斥。

**E-02 · 乐观并发优于加锁**　「登记即占号」若用文件锁/分布式锁，跨会话跨机器的可靠性成本高；若用乐观并发（登记后复跑「我是不是最新登记者」），实现只有十几行，且撞号在登记前即暴露。**代价**：要求工作流固化为「登记 → 提交 → 复跑」，与「先跑 preflight 再登记」的旧流程不兼容 ⇒ 需以 NOTE 形式渐进迁移。

**E-03 · 收官回填三件套 + 事后体检**　共享仓里，「收官」若只体现在 git 历史而不回填登记行，该批会**永久占着 touches 挡死后来者**，而门禁只显示「与在途 WNNN 冲突」，真实原因不可见。**解法双保险**：流程上要求三件套齐（hash 非占位 + 状态以「已收官/已闭环」开头 + touches 终值），机制上配一个事后体检脚本（现役段 W 号逐个查）。体检脚本**不挂阻塞段**——否则只是把伪阻塞从 preflight 挪到门禁。

**E-04 · 事实状态 ≠ 字段状态**　当判定依据是登记行字段时，必须先分清两种「冲突」：**真并行写**（两方同写同一共享面，需要串行等）与**字段滞后**（对方早已收官、只是没回填，需要催回填）。后者若按前者处理（干等），批次会被无限期挂起。

**E-05 · 反向验证的三条纪律**　① 变异前断言目标串存在；② 变异后断言内容已变且原串已消失（**同名串在别处先命中 ⇒ 变异打空**）；③ 变异体**崩溃**与「判据失效」必须分开判读——本批曾因变异副本 import 依赖缺失而崩溃，被误读成「判据被移除」从而判为通过。**推广**：任何「注入故障→看测试变红」的验证，都要问一句「红是因为判据生效，还是因为脚本崩了」。
