**一句话结论**：用户先报「Workflow Lint 失败」，追出的是**两层**根因（远端脚本缺 `--ci` 参数 + 脚本 `--api` 强制要求 token 与 workflow「刻意不带 token」的设计直接矛盾）——只补参数、推送 64 个提交，周级扫描仍会红；随后用户追加「把 GitHub 上面的 Security and quality 里的所有问题一并解决」，实测三张面板（Dependabot 65 条、Code scanning 95 条、仓库安全配置 3 项缺口）后确认**真实未修只有 26 条**，其中 17 条是「本地早已修好但 64 个提交未推送」所致，推送即消；真正要动手的是 6 条归档脚本假阳性、4 项 Scorecard 治理、依赖版本对齐，以及**推 main 前必须清偿的 7 条存量 CI 红灯**。

**核心判定（四条）**：

1. **W1190 的根因是两层，不是参数缺失一层** —— `--ci` 参数早在 W1155（本地 commit `6d66773e`）就修好了，但本地 main 领先远端 64 个提交且全部未推送 ⇒ 远端每周一 03:00 UTC 必然复现同一失败（run #42605193188 实证：`unrecognized arguments: --ci`·退出码 2）。更关键的是第二层：脚本入口对 `--api` 强制要求 token，而 workflow 注释明写「刻意不带 token：目标仓库均为 public，匿名读即可」⇒ **把 64 个提交全推上去，这个 job 仍然是红的**（本地实跑 `py -3 scripts/check_action_refs.py --api --ci` → 退出码 2）。这是「补丁加补丁」的典型形态：只让报错消失、没消除产生它的结构性原因。
2. **GitHub 面板上的多数告警是「已修未推送」的投影** —— Code scanning open 的 26 条里 15 条 `PinnedDependenciesID` + 2 条 `TokenPermissionsID` 对应的代码本地早已修复（全部 `uses:` 钉 40 位小写 hex SHA、release/stale 已有 `permissions:` 块）；Dependabot 37 条 Pillow/pillow 的 `vulnerable_version_range` 全为 `< 13.0.0` 而清单已钉 13.0.0。**判定依据是 API 实查而非印象**，处置动作是「先推送让平台重算」而不是「逐条 dismiss 掩盖」。
3. **6 条 CodeQL 告警是假阳性，处置口径与仓内既有 28 条同族一致** —— 全部落在 `archive/scripts/batches/` 的一次性归档脚本；四条实证：该正则是**选取** `<script>` 块而非剥离标签（真实危害是「不可信 HTML 剥标签后残留」）、输入为本仓自产 HTML（861 页大小写敏感扫描 `<SCRIPT` 命中 0）、输出不是 HTML、归档位已被 ruff 与 CI 排除 ⇒ 以 `won't fix` 关闭，open 26→20。
4. **推 main 之前必须把存量 CI 红灯清零** —— 全量 pytest 实测 7 failed / 1520 passed；其中 `AGENTS.md` 体积超 48KB 预算（51273 B）、台账数据行 61 > 窗口 60、glossary 新页未入可视化基线与朱砂实底面、`verify_delivery.py:1604` 的跨行高危正则、统计事件 `--check` 断言，以及三处口径数字漂移。这 7 条与本批改动无因果关系，但会让推送后的 CI 红灯掩盖真实信号 ⇒ 连带清偿。

**本批产出**：① W1190 脚本侧 `api_auth_decision()` + workflow 侧 `GH_TOKEN: ${{ github.token }}` 注入（两侧同修）；② W1191 仓库安全配置 2 项开启 + 6 条假阳性告警关闭 + Scorecard 4 项治理 + 依赖版本对齐；③ 7 条存量 CI 红灯清偿（AGENTS 正本省 4571 B、台账归档 3 行、三处数字漂移订正）；④ CodeQL action v3→v4；⑤ 本报告 + 台账两行 + CHANGELOG 两段 + HANDOVER 更新。
