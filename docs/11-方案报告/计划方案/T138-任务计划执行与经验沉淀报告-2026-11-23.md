## 二、根因取证

1. **伪血缘的分布实测**（git ls-files + 内容扫描）：目录件 236 目录 / **406 件**带「生成时点：2026-10-18」或「生成日期：2026-10-18」⇒ 分布在 **221 个目录**。
2. **为什么 refresh 清不掉**：跑 refresh 实测输出「将写入/已写入文件数：1（index.md 0 · README.md 1）」+「GitHub 主页展示位保护跳过 **43** 个」⇒ **根因真相（对抗审查 P1-3 纠正）**：生成器 _process_one 与 _report 的 buckets 解包顺序**互为镜像**（既有缺陷）⇒ 统计输出全反：「将写入 1 件」实为 showcase 跳过数（实测 showcase 保护仅 **1 件**）、「保护跳过 43 个」实为**将被重写的 43 件**⇒ 原推断**不成立** ⇒ **refresh 一次即重写 440 件 ⇒ 伪日期一次全清**（实测残留 0）· 本批已同批修该契约错位。
3. **真机制复核**（对照遗留总账 L-08「更深根因」段）：生成器写盘**已是**显式 LF（W1307 已治）⇒ 剩余真问题只剩**硬编码日期**这一层（CRLF 那层已消）。
4. **所有权判定的连带约束**：refresh 所有权判定 = 「含『生成来源：scripts/gen_folder_docs.py@』」**或**「内容 == 当前渲染」⇒ 一旦去掉 INDEX.md 的「生成时点」行而**不**补标记，旧件既无标记又与新渲染不等 ⇒ 会被判**人工维护件**跳过 ⇒ 存量 INDEX.md 永远刷不掉 ⇒ 故本批对 INDEX.md 改为**写「生成来源」标记**（非托管目录则走一次性订正脚本删元信息）。
5. **E 号占用实测**：六正本 + 归档层最大 E 号 = **315**，而 E-297~E-300 已被「数据 / 内容可信度」组占用 ⇒ 本批取 **E-316~E-320**。
