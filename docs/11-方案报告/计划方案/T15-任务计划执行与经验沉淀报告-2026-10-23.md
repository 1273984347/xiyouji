## 一、执行摘要

**背景**：《取经录》是一源多形的数字人文项目——615 篇解读文档 + 87 个 D3.js 可视化页 + 133 个数据维度 + 桌面版安装包，线上 GitHub Pages 部署。内容资产已成体量，但**对外只有一个 GitHub 仓库主页与一个站点首页**——没有一件可拿在手上、可贴进群聊、可印出来递出去的「宣传件」。用户 2026-10-23 要求补上这一层，并指定四件事必须规划到位：卖点提炼与信息层级、版式栅格、配图与图标、联系方式区块，且正反面内容分工清晰。

**用户四问拍板（问卷原文口径）**：

| 问 | 用户选择 | 落地含义 |
|:---|:---|:---|
| 投放场景 | 「通用大众：双轨兼容，读者分层引导；学术/机构推介：突出可引用性与数据资产。**两个都需要**」 | 不出两套印刷品，改为**一套两页内做双轨分层**：正面 = 大众读者路径，背面 = 学术与机构路径 |
| 成品形态 | 「HTML 源 + PDF + PNG **三件套全要**」 | 一份 HTML 源（`@page` 打印样式）→ 浏览器导出双面 PDF + 正反两张 PNG |
| 配图素材 | 「复用站素材 + **生成 1 张专属主视觉**」 | 站内 24 卡片图 / 12 概念图 / 6 hero / logo 全套取用，另生成 1 张主视觉 |
| 联系方式区块 | 「全套：链接 + 下载 + Issue + 许可证 + 引用格式」+「加『透明与许可』小字块」 | 五件套 + 透明小字块；**二维码未圈选 ⇒ 不做** |

**本批动作（五项）**：

1. **卖点提炼**：从仓库实证口径（非宣传话术）压出 6 条可核卖点，分配到正面（3 条）与背面（4 条学术资产）。
2. **信息层级**：正面 4 级（L0 品牌 / L1 主张 / L2 证据 / L3 卖点 / L4 行动），背面 5 级。
3. **版式栅格**：A4 竖版 210×297 mm，页边 14 mm，**统一 12 栏基准**，栏距 4 mm，槽宽 11.5 mm，正反两页共用一套栅格。
4. **配图与图标**：1 张新生成主视觉（宣纸底浓墨剪影）+ 站内素材复用 + 10 枚内联 SVG 图标（线性墨色 2 px + 朱砂点睛）。
5. **联系与行动区块**：链接 / 三平台下载 / Issue / CITATION.cff / 双协议 / 透明与许可小字块。

**关键判断**：**「双轨」不靠出两套单页，靠一页两层的分工实现**——正面负责「让人想点进去」，背面负责「让机构敢于引用」。两页共用一套栅格与一套视觉令牌，视觉上是同一件物料，职能上是两条路径。

## 四、决策记录与理由

| # | 备选方案 | 选择方案 | 选择理由 | 权衡 | 可复用结论 |
|:---|:---|:---|:---|:---|:---|
| D-01 | 出两套单页（大众版 / 学术版） | **一套两页内做双轨分层** | 用户答「两个都需要」，同时限定「一套宣传单页」+「正反面内容分工清晰」⇒ 双轨 = 两面的职能分工 | 放弃「两套独立物料」的投放灵活性，换取一次设计与一次导出 | 需求里的「都要」先看它与「一套」的措辞是否冲突；冲突时按**分工**解释，不擅自放大工程量（派生路径留在 §10.3） |
| D-02 | A5 横版 / 社媒长图 | **A4 竖版** | A4 是中文印刷单页的事实标准；竖版利于「主张 → 证据 → 卖点 → 行动」纵向叙事 | 舍弃了横版的横向叙事优势与长图的社媒原生比例 | 印刷物料默认 A4；社媒版用同一正面的 PNG 二次裁切派生 |
| D-03 | 设计工具直接出图 | **HTML 源为唯一真源**，PDF/PNG 由脚本导出 | 可改文案后一条命令重出三件套；HTML 源能直接 `file://` 双击预览；印刷精度由 PDF 承担 | 多一道导出工序，换来可复算与可维护 | 凡「同一内容要出多种格式」，先立唯一真源再导格式，别反过来 |
| D-04 | 正面 12 栏 / 背面 8 栏 | **统一 12 栏跨正反两页** | 两侧共用一套栅格 ⇒ 翻面时网格对齐，读起来是「同一件物料」 | 背面内容量不均，12 栏下需精细分配 span | 同一件的多个版面共用一套栅格，是「一套物料」观感的来源 |
| D-05 | 深底浅墨主视觉 | **浅底浓墨** | 印刷单页底色浅（省墨、可手写批注）；深底在纸上发闷且吃墨。浓墨区在浅底上才成剪影 | 浅底主视觉与页面底色存在色差，需额外做色归一化 | 印刷物料的配图先问「这张图叠在浅底纸上成立吗」 |
| D-06 | 站字体（`site/static/fonts/` 子集件） | **仓内完整字集**（思源宋体 VF） | 站字体按站内用字子集化，新文案必含子集外字 ⇒ 掉字回退；系统栈字形与设计稿不一致 | PDF 体积涨到 6.1 MB，换来零缺字与字形一致 | 用子集化字体做**新文案**前，先验该字集是否覆盖新字 |
| D-07 | 单页进 `site/` 建页 | **单页落 `assets/promo/`** | 单页是物料而非站点页面 ⇒ 不触发 sitemap / 导航 / 站内门禁的接入要求，也不污染站内导航 | 少了站内导航入口（靠对外分发触达） | 物料与站点页面分目录放，别为「统一」把物料塞进站点 |
| D-08 | 图标字体 / 外库 | **手写内联 SVG** | file:// 铁律要求零外域依赖；图标字体需额外子集化与授权 | 手写 SVG 少了现成图标的打磨度，换来完全可控 | 印刷物料的图标一律内联 SVG：可改、可印、零请求 |
| D-09 | 做两个二维码 | **不做二维码** | 用户问卷未圈选该选项 ⇒ 按字面执行 | 放弃了扫码直达的便利 | 未被点选的选项不做——物料类尤其忌讳「顺手加」 |
| D-10 | 二进制产物不入库 | **入库** | 交付物需跨 session 可复算、可回溯；体积控制在 6.1 MB | 仓库体积增加 8.9 MB | 小体量物料可入库；大体量（如 400 MB 截图集）不入库 |

| # | 经验 | 适用场景与边界 | 量化效果 | 证据来源 | 可迁移性 |
|:---|:---|:---|:---|:---|:---|
| E-01 | **CSS Grid 的 `1fr` 轨道下限是 `min-content`，长 URL 会把邻栏挤成一条**（`1fr` = `minmax(auto,1fr)`，auto 下限 = 内容 min-content；item 的 `min-width:0` 不等于轨道下限） | 任何用 CSS Grid 排版且栏内含 URL / 代码 / token 的场景；不适用于纯文本等宽栏 | 本批 `.g7` 由 40px 恢复至约 380px（恢复 9.5 倍）；CTA 块高由 345px 降至 149px | `scripts/_w892_probe.mjs` 探针输出 + 拼版目视 | 跨项目通用（印刷版式 / 仪表盘 / 落地页同源） |
| E-02 | **flex 容器的子项默认 `flex-shrink: 1`，固定 height 会被压扁** | 页面级纵向 flex 容器里放固定高媒体块；不适用于显式设了 `flex-shrink: 0` 的场景 | 主视觉由 118px 恢复至设定值 257px（恢复 2.2 倍） | 同上探针（`getComputedStyle` 取值与 CSS 声明值不符） | 跨项目通用 |
| E-03 | **判「内容是否溢出容器」不能用子块高度合计，也不能用 `scrollHeight`** | 任何「固定画幅 + 打印/导出」场景；不适用于无固定容器高的流式页面 | 首轮口径误判「零溢出」而实际溢出 39px / 42px；改判据后定位准确，两面各压 39 / 42px 至 0 | `scripts/_w892_probe.mjs`（末子元素底边 − 内容底边） | 跨项目通用 |
| E-04 | **`file://` 下 `@font-face` 相对路径不可靠，印刷件导出应起本地静态服务器** | 任何用 `@font-face` + 相对路径 + headless 导出 PDF 的场景；不适用于 CDN 字体 | 导出探针从「字体未加载」变为「思源宋体已加载」，PDF 字形与设计稿一致 | 导出脚本探针输出（`document.fonts.check`） | 跨项目通用（CI 出 PDF / 出图流水线同源） |
| E-05 | **生成素材与页面底色有色差时，用「色归一化」而非硬贴** | 生成图要嵌入既有设计系统时；不适用于本来就要独立成图的素材 | 纸色由 `#EDE4D2` 归一到 `#FAF7F0`（与页面底色零色差）·朱砂占比 0.153%·亮度剖面无规则线 | PIL 逐像素计数 + 逐行亮度剖面 | 跨项目通用（素材接线 / 主题化统一） |

**E-07 · 生成物与派生值必须在「目标提交树」环境里生成，不能在工作树生成后再剔除**
现象：共享工作树里想「把某批的条目从生成物里去掉」，用正则切数组（`\[.*?\]`）改 JSON → 遇到嵌套 `]` 即截断 ⇒ 内联脚本语法错误 → 连带 CSP 漂移、索引块对不齐、多个门禁判红；同一批还出现「目录清单提交了含他方未入库文件的刷新版」「派生值改完到提交之间被并行批改回」两种同类竞态。
正解：**在 `git worktree` 干净检出里跑生成器，产出即正确**（不含他方在途件、无竞态、无需剔除）；生成完把差异文件拷回主工作树提交。
配套纪律：**「CI 侧绿」只能由全量门禁在干净检出上出具**，抽查外推是本批真实踩过的坑（§7 R-15）。

**E-06 · 派生统计值必须按「目标提交检出后的 HEAD 实况」写，不能按当前磁盘实算**
现象：共享工作树里有并行批的未入库文件时，磁盘实算比 CI-HEAD 实况多，本批按磁盘实算写 `report_docs=53`，而 CI 侧实况是 52 ⇒ 干净检出后第 31 门禁 C5d 判红。
正解：写值前先问「**目标提交检出后，这件文件在不在？**」——不在的（他方在途）不计入；已在本批键值范围内的才写。验证手段：**用 `git worktree add --detach` 干净检出 HEAD 跑 `stats.py --check`**（本批即靠它定位）。
配套：提交后必须做一次「CI 侧预演」（worktree 干净检出 + 跑关键门禁），否则「本地绿 / CI 红」只能靠推送后才发现。

**经验沉淀补充说明**：E-01 ~ E-03 的共同教训是同一件事的三面——**版式问题必须用探针量，不能靠目测**。本批三轮修正全部由探针驱动，其中第 3 轮更是先发现自己用错了「溢出」口径，再据此定位真实溢出量。E-06 则是同一原则的另一个侧面——**派生值与生成物必须按「目标状态」核对，而不是按「当前状态」核对**。
