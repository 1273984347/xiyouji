## 四、P1 级发现

### P1-1 · music-structure 中英双页相位真值互斥 —— 根因在真值源缺 3 回

**四处真值实测**（`site/data/music-structure.html:1934` EMBEDDED_DATA 单行超长 JSON；`site/en/music-structure.html:1910-1912`）：

| 口径 | ZH 页 | EN 页 |
| --- | --- | --- |
| 可见文案 | 序曲 12 · 交响 **85** · 尾声 3（L1832 / L2301） | Overture 12 · Symphony **85** · Coda 3（L1813） |
| 数据源 phase_distribution | 序曲 12 / 交响 **82** / 尾声 3 | Overture 12 / Symphony **85** / Coda 3 |
| 数据源 total_chapters | **97** | **100** |
| rhythm 数组实测 | **97 条**（序曲12 / 交响82 / 尾声3） | **97 条**（Overture12 / Symphony**82** / Coda3） |

**根因（唯一根，不是四处各说各话）**：真值源 `scripts/output/data/chapter_rhythm.json` **本身只有 97 条**，缺第 **26 / 31 / 40** 回。⇒ 82 = 85 − 3（恰为缺章投影），97 = 100 − 3。两页 rhythm 数组逐条一致（缺 26/31/40），**唯一分歧点是 EN 页手改了 summary 值**。

**作者本意判定**：作者本意是 **85**（= 序曲 1-12 共 12 + 交响 13-97 共 85 + 尾声 98-100 共 3 = 100 回）。四条互相印证：

1. 乐章划分自洽：`chapter_movement.json` 定义第一乐章 1-12(12) · 第二乐章收徒 13-22(10) · 第三乐章八十一难 23-97(75) · 第四乐章尾声 98-100(3)；rhythm 把 13-22（收徒）也标为"交响" ⇒ 交响段 = 13-97 = **85**。
2. 图表相位带按 85 绘制：`site/data/music-structure.html:1964-1968` 的 phases 硬编码 序曲 1-12 / 交响 13-97 / 尾声 98-100，渲染标签为「交响 · 第13-97回」。
3. 收徒段 13-22 共 10 回在数组中完整存在，与 movement 划分无重复无缺漏 ⇒ 缺章全部落在 23-97 段内（75 − 3 = 72），10 + 72 = 82，与数组实测吻合。
4. 真值 summary 本身即 97/82 ⇒ 82 是数据缺口的被动结果，非编辑口径。

**影响面**：

- **X 轴刻度不受影响**：x 域硬编码 `d3.scaleLinear().domain([1,100])`（L1961）、刻度固定 11 个（L1996）⇒ 刻度不错位、不少刻。
- **绘图受影响但不致错**：分段折线在缺章处形成 3 段空档；数据点按数组逐条绘制 ⇒ 实测 `#rhythm-svg` 的 **circles = 97**（应 100），少 3 个高亮点。
- **页内自相矛盾**：`site/data/music-structure.html:2295` 用 `rhythmData.length`（=97）计算占比，同页 KPI 却写「100 回」⇒ 高潮榜写"占全部 97 回的 X%"。
- **读者按带标签计数得 85、按数据点数得 82**，两数同时出现在同一页。

**建议修法**：在**生成器侧**补齐 `chapter_rhythm.json` 的第 26/31/40 回并重生成 `music_structure_summary.json`（total_chapters=100、交响=85），同步回灌两页内嵌副本；**禁止页面手改 summary 数值**（EN 页的 100/85 即为手改产物）。只修页面不改真值源 = 债务展期。

### 探针法层面的四条教训（可复用）

1. **探针自身必须留「假阳性处置」记录**：本批 4 次假阳（reduced-motion 守卫 / 内嵌≠真值 / 徽标态 / fetch 目标缺消费键）全部由**探针口径**造成，非站点缺陷。若只记录「发现 14 项」而不记录「其中 4 项是探针错」，后续维护者会照着错误结论去改正确的页面。⇒ **纪律：任何自建探针的命中项，必须先回答「这个判据凭什么认为它是缺陷」，再进报告**。

2. **正则要避开「键名 vs 值」与「CSS 样式行 vs DOM 元素」两类陷阱**：
   - 徽标：`data-status="live"` 在 CSS 选择器与 DOM 属性里同形 ⇒ 只认「带 `data-status-badge` class 的标签」。
   - 路径：`loadJson(path, EMBEDDED.key)` 的第二参是**回退值**不是路径键 ⇒ 「目标 JSON 顶层键 vs 页面消费键」的比对前提根本不成立。
   ⇒ **纪律：判据的语义前提要先在源码层确认，再批量应用**。

3. **JS 对象字面量不是合法 JSON**：站内 `EMBEDDED_DATA` 常带无引号键与尾逗号 ⇒ 直接 `json.loads` 必失败（探针第一版据此误判「数据不存在」）。需先做「标识符补引号 + 去尾逗号 + 单引号转义」的宽松预处理。

5. **改提交信息时 `git commit --amend --only <pathspec>` 会把该提交的其余文件从 HEAD 弹掉**（W1259 实证·已复原）：本批为修正三个同标题的提交信息而用 `--only`，结果 444e137cf 中 11 件（坑表计数 330→332 等）被弹出 HEAD。⇒ 复原正解：`git reset --soft HEAD~1` → 用**带完整 pathspec** 的 `git commit` 重建 → `git diff <原 hash> HEAD -- <文件>` 逐个核对内容无丢失。⇒ **纪律：改提交信息优先用 `git commit --amend -m … -- <全部原文件>` 保持文件集不变；确需缩小文件集时先记录原文件集并在事后逐文件核对**。
4. **git `core.quotePath` 会让中文路径形态失配**：`git diff --cached --name-only` 默认把中文路径转义成八进制形态，而 spec 里是原始中文 ⇒ 第 51 槽判「索引含 spec 之外的文件」假红 7 件。⇒ **纪律：任何以 git 输出与仓内清单比对的自检，取数一律加 `-c core.quotePath=false`**。
