## 四、七项核查逐条裁定

### 4.1 依赖锁定——不成立·余两项登记 BL-30

CI 安装路径实证（ci.yml/security.yml）：`pip install -r scripts/requirements.txt`（L299/L320·清单全 `==` 精确钉版·P2-7 供应链决策·CVE 驱动更新有记录）、`npm ci --prefix scripts`（L340/L380·`package-lock.json` 在库）、`npm --prefix xiyouji-agent-web ci`（L401·lockfile 在库）。**pip-audit/npm-audit 的审计对象是这三份锁定清单，不是浮动快照**；npm audit 且是 `--audit-level=high` 硬阻断。

残余两项（登记 BL-30，均为小额）：
- E2E job `npm install playwright @playwright/test`（ci.yml:47）**未钉版**，与 scripts/package.json 的 `^1.63.0` 不一致——浏览器版本随 CI 日期浮动；10 个视觉基线长期稳定说明容差内未见影响，但口径应统一；
- 依赖清单分散三处（scripts//agent-web//site 零依赖）无根级指针——README/CONTRIBUTING 加一行索引即可。

### 4.2 门禁阻断语义——不成立（数字过期·分布已答）

- 数量：现势 50 槽，非 43（§3.1）；
- 阻断分布：**全 fail 无 warn 级、无 `--warn-only` 模式**；豁免走基线（机器对账可审计），不走 CLI 开关——评审担心的「警告级门禁约束力趋零」与「noqa 白名单绕过」在本仓的对应形态是基线豁免，其增减全部留痕 CHANGELOG；
- 误报修复路径：每门禁自带注入式 self-test 负样本（例：第 43 槽 12 例、第 31 槽 18 例、第 45 槽 7 例）；门禁自身缺陷走批次清理（W788 刚删两处死代码·零行为变化论证三核查）；
- 内容/数据**语义层**硬门禁 8 项：第 19 术语一致性、第 20 原著引文硬验证、第 24 图表静态自洽、第 25 数据内容一致性、第 31 文档口径体检、第 9 数据漂移（共路深比对）、第 43 可视化数据断言（V1–V5 真实渲染）、第 39/40 故事内时间线与 chapter_stats 双源同步——评审问「多少项是内容语义层」，答案是 8/50，其余为格式/结构/加载/链接/安全层；
- 「exit 0 的 verdict 不能 gate CI 步」旁证：那描述的是 `--judge` 纯判据注入面（pytest 消费），门禁路径是「末行汇总 + 进程退出码」双签，不存在该漏洞。

### 4.3 视觉回归——部分成立（分层已建·更新不自动）

- 覆盖面属实：`tests/e2e/baseline/` 共 **10** 个 PNG（index/dashboard/chapter-stats/hardships/journey-spacetime/timeline/character-dynamic-network/character-sentiment-arc/monster-hierarchy-network/narratology-16d-network·W236-E 5→10），即 10/87 可视化页有像素基线；
- 但语义层不靠像素：87 页全量跑第 43 门禁 V1–V5（今日实跑 V1 ok=87/fail=0、V2 ok=86、V3 ok=78/na=9、V4 ok=70/na=17、PROBE ok=87）+ 857 页截图审查（G1–G5）——三层分工：像素基线管样式回退（10 关键页）、语义断言管数据↔渲染一致（87 页）、截图门禁管运行时缺陷（857 页）；
- 基线更新策略：`node tests/e2e/test_visual.js --update-baseline` 是**手工命令**，CI 无任何自动更新路径；baseline 目录带 README + index 文档——评审担心的「CI 失败后跑更新命令批量吞基线」在自动化侧不存在，吞的风险在人工侧，由批次纪律对抗（W788 实证：857 页逐页 fails 比对通过后才收工）；
- 残留真问题：色阶映射/桑基流逻辑确实无机器校验（V3/V4 是代理指标）——同 BL-26 族，不设工程关闭项。

### 4.4 agent-web 安全边界——部分成立·本轮唯一实质增量（BL-29）

- 在案证据：38 个 node --test 用例（tools 26/audit 7/citationGuard 5）接 CI；engine.smoke 常驻冒烟；W757 CI 接线断言（D2 修复·「建置即绿」）；W681 CodeQL 42 告警首账清零（api_server realpath 边界 + CORS 常量化 + /api/* 限流）；W411/W412 DOMPurify/SSE 超时/鉴权加固批次记录；
- **缺口实证**：对三个测试文件做攻击面关键词扫描（cors/CORS/timeout/top_k/topK/ssrf/SSRF/rate/limit），命中仅出现在实现注释层，**测试用例层零命中**——即评审点名的三类负向测试（模拟 CORS 预检绕过、超大 RAG top_k、超时未清理的 SSE 连接）不存在；
- 含义：W411/W412 的修复目前只有「提交信息」形式的记录，无回归测试固化——后续重构回退这些修复确实可能无人察觉；
- 处置：登记 **BL-29**（补负向测试 + CI 接线·列为下个 agent-web 触及批的伴随项）。这是本轮审查对仓库的**唯一实质性新贡献**。

### 4.5 测试覆盖率——不成立（上轮成立项·本轮已闭）

- 上轮判定「成立」的真实缺口（无覆盖率配置、数字缺席）已由 **W776 外部评审 A-01 立项执行**关闭：pytest.ini L16 起有完整口径决策（不设门禁的三失真实证 + 替代资产清单）；
- 评审的「可配置性陷阱」（`.coveragerc` 的 fail_under 不被 pytest 读取）：本仓无 `.coveragerc`、无 fail_under、无 --cov——陷阱无从触发；
- 评审的「line coverage 对 D3 交互分支无解释力」：正是 W776 决策失真原因②（E2E 双轨制）的同义表述——已被吸收为「不设单一数字门禁」的论据而非缺口。

### 4.6 脚本注册表——不成立（机制已存在且机器强制）

- 「45 个归档脚本」数字本轮属实（`archive/scripts/*.py` = 45）；
- 评审的关键追问「是否存在脚本注册表」：**存在**——`scripts/output/script-coverage-baseline.txt`（43 条·四分类：①一次性/取证/人工审阅 ②会话直接执行 ③发布链/CI 编排 ④浏览器/布局）+ 第 42 门禁（根级脚本四面〔tests/verify/CI/Makefile〕无引用且未登记者 FAIL）；
- 事前收敛还有 tmpe TTL 桶（一次性脚本用后即弃或归档·gitignore）；「新门禁都写新脚本而非扩展现有」的倾向部分存在（41 个 check_* 脚本），但注册表 + 覆盖门禁使「必须通过的 vs 可忽略的」对机器可判——新贡献者的读法依赖 README/index.md 而非穷举文件。

### 4.7 sync_docs.py——部分成立（批判对象半退役·状态未决）

- 评审的「只更新第一次出现」担忧对该脚本不适用：sync_docs.py 是**校验器不改写**（exit 0/1）；文档改写面在 batch_cascade，其版本行替换全部带 `count==1` 断言（fail-closed，锚点失配即中止而非静默跳过）；

- 处置：登记 **BL-31**（退休 / 接线 / 修复三选一·由用户裁决时机）。活跃同职责门禁 check_doc_sync 的健康度不受影响（18 负样本 + 双接线）。
