## 1. 执行摘要

### 1.1 一句话结论

**这个项目的治理纪律极强，但缺一次「编译」——所有下游产物（站点页面、英文镜像、数据副本、导航注册、CSP 哈希、版本指针）都是 Markdown 真载体的手工派生物，耦合的真实形态不是「模块互相 import」，而是「物理复制 + 靠门禁定期校准」。复制速度已超过校准覆盖面，这是当前全部硬伤的共同根因。**

### 1.2 五条关键判定

| # | 判定 | 一句话依据 |
|:--|:---|:---|
| 1 | **不是「架构差」，是「无构建系统」** | 857 个 HTML 全部内联同一份 CSS（1415 个 style 块共 18.9 MB，占站点 50.9 MB 的 37%）；改 `tokens.css` 一行 → 重写 330 页 → 必须重算 856 页 CSP 哈希 → 约 1,190 个文件产生 diff |
| 2 | **门禁机制设计优秀，覆盖面止步于「文档面」** | 47 条编号门禁 / 52 段 / 表驱动编排 + 段自洽锁 + 4 级 scope 分级；但站点页面上的聚合数字不在任何扫描域（`site/index.html` 写「772 篇」·实测索引 834 条·差 62） |
| 3 | **Web Agent 是全仓质量最高的一层** | 80 文件 12,153 行、无 god file（最大 557 行）、`server/index.ts` 从 646 行拆到 102 行、安全边界扎实；其硬伤集中在**检索层缺失**与**零重试零续传**，不是结构问题 |
| 4 | **数据副本已发生实质漂移且无门禁** | `site/data/json` 47 个文件中 **24 个与 `scripts/output/data` 同名文件内容不同**（138 KB 不一致），两道门禁都不覆盖这条副本链 |
| 5 | **真正该修的第一梯队只有 4 件事** | ① 站点聚合数字定点门禁 ② Agent 检索域收窄到 git 跟踪文件 ③ SSE 补 `id:` 与重试退避 ④ 单一副本源（数据）——都不需要推翻现有架构 |

### 1.3 明确不做（避免范围蔓延）

- 本批**不改** `site/` 任何页面、**不改** `xiyouji-agent-web/` 任何代码、**不改**管控脚本（`scripts/verify_delivery.py` 等按 [文档规范 §11.2](../../00-导读/文档规范.md) 禁擅改）——**这是评审批，不是施工批**。
- 不建议「全面引入构建系统」——与 [W818 选型批](../设计与架构方案/静态站前端框架化选型对比-2026-10-20.md) 的「维持现役原生管线 + 新页局部构建化」结论一致，见 [§7](#7-与既有方案的关系)。
- 不对未验证项下结论（见 [§8](#8-本批未验证项)）。

### 2.2 评审方法（自证纪律）

1. **只读取证**：本批不修改被评审对象；所有数字来自实跑命令（附录 A 给出复算命令），不接受「凭印象」的数字。

## 4. 五维发现

### 4.1 模块耦合

**判定：耦合不是「模块间依赖过深」，而是「同一事实源被物化成多份副本且副本之间靠定期校准维持一致」。**

| # | 硬伤 | 证据 | 级别 |
|:--|:---|:---|:--:|
| C-1 | CSS 单一事实源被复制到全部页面 | 857/857 页带内联 `<style>`，1,415 块共 18.9 MB（站点 37%）；单页副本 48,947 B | **P0** |
| C-2 | 数据副本链三层且已漂移 | `scripts/output/data` 135 → `site/data/json` 47 → 页面内嵌 144 页；**同名 47 个中 24 个内容已不同** | **P1** |
| C-3 | 英文站 138 页零生成器 | 全 `scripts/` 无任何写 `site/en` 的生成器，只有 `validate_en.py` 等校验器 | **P1** |
| C-4 | 导航注册面手工且脚手架已失效 | `new_page.py` 锚点不存在；tag-cloud / dashboard / site-map / index 四份手抄注册表并存 | **P1** |
| C-5 | 前后端两份「真相」已漂移 | 系统提示词前后端各存一份且文字已不同（`server/config.ts` "CHANGELOG.md 现役段" vs `src/hooks/useAgents.ts` "README.md 顶部"）；前端工具名词表覆盖旧 SDK 的 12 个名字，与后端现役 6 工具有 3 个对不上（`write_file` / `glob` / `run_command` 全落 generic 渲染） | **P1** |
| C-6 | 路由层直连 DB，无仓储层 | `routes.ts` 11 处 `db.*` · `chat.ts` 8 处；`db.ts` 单文件 264 行承担全部持久化 | P2 |
| C-7 | 分析类脚本复制粘贴 | 26 个类目录 / 30 个脚本 / 9,674 行；`build_summary` 在 **13 个文件**同名重复实现 | P2 |
| C-8 | 平台级与页面级 CSP 两套策略 | `site/_headers` 与 `generate_csp.py` 的外域白名单口径相反 | P2 |

### 4.2 性能瓶颈

**判定：站点侧是「体积」问题（37% 是重复 CSS），Agent 侧是「阻塞」问题（1.4 秒同步冻结事件循环），门禁侧是「反馈周期」问题（2.4–2.6 分钟）。**

| # | 硬伤 | 证据 | 级别 |
|:---|:---|:---|:--:|
| P-1 | Agent 工具每次全仓同步扫描 | 11,407 文件 / 2.6 GB；`readdir` 1,044 ms + `statSync` 11,409 次 378 ms，同步跑在主事件循环 → 单次工具调用冻结整个 HTTP 服务 1.4 s | **P0** |
| P-2 | 检索域被非内容文件污染 | 扫描范围内含 `.git` 260 MB · `tmpe/` 890 MB · 本地 PDF 库 566.8 MB · 桌面端 dist 550.8 MB | **P0** |
| P-3 | 门禁套件 2.4–2.6 分钟/次 | `--scope auto` 156.7 s / 143.7 s；`a11y_audit` 50.1 s + `lint_links` 27.4 s 占一半 | **P1** |
| P-4 | 大页面首屏重 | `site/en/relationships.html` 403 KB（内联 JS 303 KB / 8 块）；搜索页内联整包索引（zh 262 KB / en 282 KB）首屏急加载 | P2 |
| P-5 | DB 查询无上界 | `db.ts` 0 处 LIMIT/OFFSET；`/api/sessions` N+1 | P2 |
| P-6 | 工具层 fs 全同步 + 审计同步追加写盘 | `readFileSync` / `writeFileSync` / `appendFileSync` 均在请求路径 | P2 |

### 4.3 可用性隐患

**判定：站点侧「用户可见的错值」与 Agent 侧「整轮丢失」是两个真问题；而 `file://` 降级姿态实际是好的（不是问题）。**

| # | 硬伤 | 证据 | 级别 |
|:---|:---|:---|:--:|
| A-1 | 站点聚合数字与真实索引不一致且无门禁 | `site/index.html` 写「全站 **772 篇**解读文档」，实测内嵌搜索索引 **834 条**（第 46 门禁自己报「zh 834 条」）→ 差 62 | **P0** |
| A-2 | dashboard 同节两套计数并存 | 引言「615 篇（A2 44 / A3 215 / A4 209 / A5 34）」vs 卡片 `.value` 实测 `100/43/199/199/22/12`（旧世代值，Σ=575） | **P0** |
| A-3 | 问答链路零重试零退避零续传 | 上游非 2xx 直接抛错 → 统一吞成「服务器内部错误」；`retry`/`backoff` 0 处实现；SSE 无 `id:` → 断流整轮作废 | **P0** |
| A-4 | CSP 漂移的失败形态是「静默空白」 | 856 页各持独立哈希集；任一页内联脚本改动而漏跑 `generate_csp.py` → **该页整段脚本被拒**（图表空白，不报错） | **P1** |
| A-5 | 默认免认证 | `AGENT_WEB_TOKEN` 未设即不注册鉴权中间件；仅靠回环绑定 + Host 白名单 + 30 req/min 三层兜底（本机工具可接受，外部署即失守） | **P1** |
