## 一、结论摘要

**总判定：表结构本身没有"设计错了"的问题——三张表的划分、范式选择、字段类型选择基本是对的。真正的风险集中在三处"声明了但没生效"的约束：外键强制（`ON DELETE CASCADE` 从建库至今一次都没执行过）、`feedback` 唯一索引（维度选错，允许同一消息同时 up 与 down）、迁移机制（不存在）。这三处叠加放大出一条可复现的数据串档路径：旧会话正文会泄漏进新建的同名会话。**

**建议先修"正确性"再修"性能"**——索引与分页的收益是渐进的，而 P0 四项在数据量上来后不可逆。

| 级别 | # | 问题 | 实测证据（2026-10-20） |
|:---:|:---:|:---|:---|
| **P0** | 1 | 外键强制从未启用 → `ON DELETE CASCADE` 是死代码 | `PRAGMA foreign_keys = 0`；删会话后消息 before=2 / after=2；写入父会话不存在的消息**被接受** |
| **P0** | 2 | `clearAllData()` 不清 `feedback` → 清库后反馈全部悬空 | 清库后 `sessions=0 / messages=0 / feedback=1`，悬空反馈行 = 1 |
| **P0** | 3 | `feedback` 唯一索引维度错 → 同一消息可同时 up + down | 同一 `message_id` 并存 `[('f1','up'), ('f2','down')]` |
| **P0** | 4 | 客户端可控主键 + 孤儿行 → 旧会话历史泄漏进新会话 | 重建同 id 后 `getMessagesBySession` 返回 `('old-msg','SECRET OLD CONTENT')` |
| **P1** | 5 | 会话列表 N+1，且全量物化 `content`+`tool_calls` | 65 会话 → 66 次查询 / 物化 129 行；合成 2000 会话 103.8 ms vs GROUP BY 2.1 ms |
| **P1** | 6 | 会话列表无 LIMIT、无分页，前端一次性拉全量 | 5 万会话：无索引无 LIMIT 81.63 ms → 有索引 + LIMIT 50 **0.06 ms** |
| **P1** | 7 | 缺 4 个关键索引，3 处查询走临时 B 树排序 | `EXPLAIN QUERY PLAN` 三条查询均含 `USE TEMP B-TREE` |
| **P2** | 8 | `created_at` 无格式约束 → 时间窗口静默漏行 | 边界 `2026-09-20T18:00:00.000Z`，`2026-09-20 19:00:00` 被**误排除** |
| **P2** | 9 | JSON 存 TEXT 无校验 + 消费端裸 `JSON.parse` | `routes.ts:200` 无 try/catch；一行脏数据 → 整个会话读取 500 |
| **P2** | 10 | 长度/枚举约束只在 Zod 层，DB 层零防线 | `validation.ts` 有 max，DDL 无对应 CHECK |
| **P3** | 11 | 无迁移框架，`PRAGMA user_version = 0`，异常被吞 | `db.ts:65-74` try/catch 包裹 ALTER TABLE |
| **P3** | 12 | `CREATE TABLE IF NOT EXISTS` 对已有库永远无效 | 改定义后重跑，`PRAGMA table_info` 仍为 `['id','a']` |
| **P3** | 13 | JSON 列无 schema 版本 / 无软删 / UUID 文本主键 | 静态分析（§六） |

**正面结论（同样经实测）**：现役数据**零违规**——129 条消息的时间戳 100% 为严格 ISO-8601 Z 格式，58 条 `tool_calls` 100% 为合法 JSON 数组，会话内时间戳并列 = 0（排序稳定），`integrity_check = ok`，`freelist_count = 0`。即：**缺陷全部是"机制缺失"而非"数据已脏"**，现役库此刻无需数据修复。

## 二、审查对象与基线

### 2.1 存储层构成

全仓关系型存储仅一处：`xiyouji-agent-web/server/db.ts`（SQLite · better-sqlite3），3 张表、11 个导出函数。全部 SQL 集中在该文件（`grep` 全仓 `db.prepare|db.exec|CREATE TABLE` 命中 6 个文件，其中 5 个为归档件或文档）。

| 表 | 行数（2026-10-20 实测） | 用途 |
|:---|---:|:---|
| `sessions` | 65 | 会话（标题、当前模型、SDK 会话 id、时间戳） |
| `messages` | 129 | 消息（角色、正文、产生时模型、时间戳、工具调用 JSON） |
| `feedback` | 0 | 用户反馈（up/down + 批注） |

同层并存的**非表存储面**：`data/audit.jsonl`（写操作审计，JSONL 追加）、`scripts/output/neo4j_seed.cypher`（一次性图谱种子脚本）。

### 2.2 现役库基线（实测）

```
库文件  : xiyouji-agent-web/data/chat.db（184320 B）
journal_mode = wal        foreign_keys = 0        user_version = 0
page_size = 4096          page_count = 45         freelist_count = 0
integrity_check = ok
孤儿行  : messages 无父会话 = 0 · feedback 无父消息 = 0 · feedback 无父会话 = 0
```

**关键事实**：`foreign_keys = 0` 而 `user_version = 0`——前者说明外键从未启用，后者说明无迁移版本追踪。这两个 0 是本报告 §三与 §六 的根。

### 2.3 取证方法与安全约定

全部取证由 `scripts/_w823_db_schema_probe.py`（本批入库）产出，四个子命令 `schema` / `faults` / `bench` / `hygiene`：

1. **原库只读**：凡涉及写入的取证一律先经 `PRAGMA wal_checkpoint(TRUNCATE)` + sqlite3 `backup()` API 落副本，缺陷复现全部在副本上进行；
2. **判据未执行即非零退出**：库不存在 / 不可读 / 副本失败一律 exit 2，不静默跳过；
3. **测量附行数校验**：每次计时同时打印实返行数，行数与预期不符即标注该行数字作废（防"单位错 / 口径错"型假数——本批自身踩过一次，见附录 C）；
4. **仅标准库**：无第三方依赖，Windows / Linux / macOS 可直接跑。

## 三、字段类型与约束

### 3.1 【P0】外键强制从未启用 —— `ON DELETE CASCADE` 是死代码

`db.ts:22` 只开了 WAL：

```ts
db.pragma('journal_mode = WAL');   // ← 缺 db.pragma('foreign_keys = ON')
```

SQLite 的外键强制**默认关闭**且**逐连接生效**。`messages` 表里那句 `FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE` 自建库至今一次都没有执行过——实测：

```
PRAGMA foreign_keys = 0（关闭）
删除会话 037de8a0-…：消息 before=2 → after=2     ← 级联未触发·孤儿行留存
写入悬空消息（父会话不存在）→ ★ 成功被接受
```

连带后果：`deleteSession()`（`db.ts:172`）**只删会话不删消息**。现役库此刻孤儿行 = 0，是因为删除操作目前只发生在测试会话上，且测试断言没覆盖"删会话后消息是否随之消失"。

### 3.2 【P0】`clearAllData()` 不清 `feedback` → 清库后反馈全部悬空

`db.ts:256-259`：

```ts
export function clearAllData(): void {
  db.exec('DELETE FROM messages');
  db.exec('DELETE FROM sessions');
  // ← 没有 feedback
}
```

`feedback` 表**根本没有外键**（`db.ts:52-59` 只有 `NOT NULL`），所以它既不会被级联清理，也不会被显式清理——清库后每一条反馈都指向一条已不存在的消息。实测（先播种 1 条反馈再清库）：

```
播种后 feedback 行数 = 1
清库后 sessions=0 · messages=0 · feedback=1
feedback 悬空行 = 1  ← 父消息已删
```

该函数当前在服务端**零调用点**（仅 `DEVELOPMENT.md:1257` 提及），所以缺陷尚未在生产触发；但它是"清库"语义的一部分，一旦启用即产生不可逆的悬空数据。

### 3.3 【P0】`feedback` 唯一索引维度错 —— 同一消息可同时 up 与 down

`db.ts:61`：

```sql
CREATE UNIQUE INDEX idx_feedback_message_verdict ON feedback(message_id, verdict);
```

注释写的是"同一消息同一 verdict 幂等"——但这个约束允许**同一消息同时存在 up 与 down 两行**。实测插入两行均成功：

```
同一 message_id 的反馈行 = [('f1','up'), ('f2','down')]
```

前端 `ChatMessages.tsx:36` 的 `if (feedbacks[messageId]) return;` 只是 React 内存态拦截，**刷新页面即失效**，用户可对同一条消息先赞后踩，两条记录都落库。语义上"同一条消息同时被赞和踩"是矛盾状态。

正确形态是 `UNIQUE(message_id)` + 切换赞踩时 UPDATE verdict（见 §7.2）。

### 3.4 【P0】客户端可控主键 + 孤儿行 → 旧会话历史泄漏进新会话

`chat.ts:159`：`id: sessionId || uuidv4()` —— **客户端传的 id 直接当主键**。`validation.ts:78` 的 `sessionIdSchema` 只限长 64、不校验形态，其注释明确说明这是**刻意保留的既有行为**（"查不到 → 以该 id 新建会话"）。

这条契约本身可讨论（§7.7），但它与 §3.1 的孤儿行叠加后产生数据串档：

```
1. 删会话 id=X              → 消息残留（FK 不触发级联）
2. 客户端再 POST 同一 id=X → getSession(X) 未命中 → createSession(id=X)
3. getMessagesBySession(X) 返回 → [('old-msg','SECRET OLD CONTENT')]
```

**旧会话的正文会复活并挂到新会话上**。启用 FK + CASCADE 即可消除这条链（删会话连带删消息 → 重建后历史为空），是治本手段；主键改由服务端生成是纵深防御。

### 3.5 【P2】`created_at` 无格式约束 —— 时间窗口会静默漏行

用 TEXT 存 ISO-8601 时间戳在 SQLite 下是**合理选择**（字典序 = 时间序，可读性好）。问题在于 DB 层没有 CHECK 兜底，完全靠调用方自觉 `toISOString()`。

现役数据 100% 合规（实测 4 列共 259 行，不合规 0 行）。但一旦某处写入空格分隔格式，字符串比较会静默出错——实测窗口边界 `2026-09-20T18:00:00.000Z`：

| 写入值 | 相对边界 | 30 天窗口结果 |
|:---|:---|:---|
| `2026-09-20T19:00:00.000Z` | 更新 | ✅ INCLUDED |
| `2026-09-20 19:00:00` | 更新 | ❌ **EXCLUDED（误排除）** |
| `2026-09-20 18:00:00` | 恰在边界 | ❌ EXCLUDED |
| `2026/09/20 19:00:00` | 更新 | ✅ INCLUDED |

原因：第 11 位空格 `0x20` < `'T'` `0x54`，同一时刻的非 ISO 写法排在窗口边界之前。`feedbackSummary()` 会**静默少统计**，无任何报错。

### 3.6 【P2】JSON 存 TEXT 无校验 + 消费端裸 `JSON.parse`

`messages.tool_calls` 是 JSON 文本，DDL 无 `json_valid()` 约束。消费端 `routes.ts:200`：

```ts
tool_calls: msg.tool_calls ? JSON.parse(msg.tool_calls) : null,   // 无 try/catch
```

一行脏数据 → 整个 `GET /api/sessions/:sessionId` 抛异常 → **该会话全部消息读不出来**（500）。现役 58 行 `tool_calls` 全部合法，但没有任何机制保证下一行也合法——`server/chat.ts:304` 直接 `JSON.stringify(toolCalls)` 落库，中途异常即可能写入半截 JSON。

### 3.7 【P2】约束只在 Zod 层，DB 层零防线

`title` / `model` / `session_id` / `message_id` / `comment` 的长度上限都在 `server/validation.ts` 的 Zod schema 里，DDL 层无对应 CHECK。两处细节：

- `feedback.comment` 列允许 NULL，但 `routes.ts:100` 恒传 `body.comment ?? ""` → **NULL 分支是死代码**，列可空性形同虚设；
- `messages.role` 的 CHECK 锁死 `('user','assistant')` → 将来加 tool / system 角色必须**表重建**（SQLite 不支持 ADD CONSTRAINT）。

### 3.8 字段类型其余部分评价（正面）

- `role` / `verdict` 用 CHECK 白名单而非裸 TEXT——写法正确，枚举扩展需表重建但值得；
- `content` / `tool_calls` 用 TEXT 而非 BLOB——正确（可读、可 grep、无编码依赖）；
- `sessions.sdk_session_id` 可空且与 `id` 分离——正确（SDK resume 已退役，该列保留为历史兼容位，`chat.ts:162` 恒写 null）。

## 四、索引与查询模式

### 4.1 【P1】会话列表 N+1，且全量物化正文

`routes.ts:69-72`：

```ts
return db.getAllSessions().map((session) => ({
  ...session,
  messageCount: db.getMessagesBySession(session.id).length,  // ← 拉全表正文只为取 .length
}));
```

每个会话跑一次查询，把**全部消息的 `content` 与 `tool_calls` 拉进内存**再取数组长度。实测：

```
会话数 = 65
N+1 路径   : 0.94 ms·66 次查询·物化 129 行消息
GROUP BY   : 0.06 ms·1 次查询
```

现役量级代价尚小，但它是**线性于会话数 × 每会话消息数**的复合增长，且拉取的字节量与消息总量成正比（与列表页真正需要的"一个数字"无关）。合成 2000 会话 × 5 消息 × 2 KB blob 场景下，N+1 为 103.8 ms，单条 GROUP BY 为 2.1 ms（**49×**）。

### 4.2 【P1】会话列表无 LIMIT、无分页

`getAllSessions()`（`db.ts:121`）返回**全部**会话，`GET /api/sessions` 无分页参数，前端 `useSessions.ts:39` 一次性拉全量渲染进侧边栏。5 万会话合成实测：

| 形态 | 耗时 | 实返行数 |
|:---|---:|---:|
| 无索引 · 全量 `ORDER BY updated_at DESC` | 81.63 ms | 50000 |
| 无索引 · `LIMIT 50` | 21.60 ms | 50 |
| 有索引 · 全量 | 67.44 ms | 50000 |
| **有索引 · `LIMIT 50`** | **0.06 ms** | 50 |
| 有索引 · keyset（`WHERE updated_at < ?` · `LIMIT 50`） | 0.08 ms | 50 |

> **口径说明**：本表为 2026-10-20 当批实测（每项 n=20 轮取均值·合成 5 万会话·同机同脚本）。**绝对值有运行间抖动**——复跑区间为「无索引全量 72.67–85.89 ms」「有索引 LIMIT 50 为 0.06–0.12 ms」；**倍数关系稳定**（有索引 + LIMIT 50 相对「无索引无 LIMIT」快 700×–1400×）。探针脚本每次计时均同时打印实返行数，行数与预期不符即标注该行数字作废（防「单位错 / 口径错」型假数，见附录 C）。

一个反直觉但重要的点：**单加索引只从 81.63 → 67.44 ms，收益有限**（`SELECT *` 仍要回表取全部行）。**LIMIT / 分页才是关键杠杆**（0.06 ms，较"无索引无 LIMIT"快 **1360×**），索引是它的放大器而非替代品。

### 4.3 【P1】缺失索引（EXPLAIN QUERY PLAN 实证）

| 查询 | 现役计划 | 缺什么 |
|:---|:---|:---|
| `sessions ORDER BY updated_at DESC` | `SCAN sessions` + `USE TEMP B-TREE FOR ORDER BY` | `idx_sessions_updated_at` |
| `messages WHERE session_id=? ORDER BY created_at` | `SEARCH … USING INDEX idx_messages_session_id` + **`USE TEMP B-TREE FOR ORDER BY`** | 复合索引 `(session_id, created_at)` |
| `feedback WHERE created_at >= ? GROUP BY verdict` | `SCAN feedback` + `USE TEMP B-TREE FOR GROUP BY` | `idx_feedback_created_at` |
| 按会话查反馈 | — | `idx_feedback_session_id`（实测含 `session_id` 的 feedback 索引数 = **0**） |

第 2 条最值得修：现有单列索引命中了过滤，但排序仍走临时 B 树。改复合索引后计划从「SEARCH + TEMP B-TREE」变为**纯 SEARCH**（实测对照见附录 B / 探针 B-03）。

### 4.4 【P2】每轮对话全量读历史只为判 `length <= 2`

`chat.ts:308`：

```ts
const messages = db.getMessagesBySession(session.id);
if (messages.length <= 2) { /* 首轮才改标题 */ }
```

每轮对话把整个会话历史拉进内存，实际只需要一个 COUNT。与 §4.1 同源。

### 4.5 死代码（附带发现）

`deleteMessage`、`updateMessage`、`createMessages`、`clearAllData` 在服务端**零调用点**（仅 `db.ts` 定义 + `DEVELOPMENT.md` 提及）。其中 `updateMessage` 与 `createMessages` **均不同步 `sessions.updated_at`**——一旦被启用就会引入"会话列表排序不更新"的隐性 bug。建议要么删除，要么补齐语义再启用。

## 五、范式与冗余取舍

**总体判定：范式选择基本正确。** 三张表的划分（会话 / 消息 / 反馈）没有该拆没拆、该合没合的问题；没有多值依赖、没有传递依赖违例、没有混合粒度。需要讨论的只有两处冗余，结论都是"保留，但把语义与约束补上"。

### 5.1 `messages.model` 冗余于 `sessions.model` —— **保留，且应固化语义**

形式上是 2NF 违反，但语义**不同**：`messages.model` = 消息产生时使用的模型，`sessions.model` = 会话当前选择的模型。用户中途换模型时两者必须有差异，否则历史回放会串味。这是**有意为之的历史快照**，不是冗余。

建议在 `db.ts` 补一行注释固化该约定——现在它是隐式的，下一个维护者极可能把它当冗余"清理"掉。

### 5.2 `feedback.session_id` 冗余（可由 message 推导）—— **保留，但必须补外键**

功能上是纯冗余。保留它的唯一价值是"按会话聚合反馈"时少一次 JOIN。代价是双写一致性风险——而现在它**既没有外键、也没有同步逻辑**，§3.2 的清库场景下直接变成悬空行。

取舍结论：**保留该列 + 补 FK 到 `sessions`**，优于"删列 + 每次 JOIN"。

### 5.3 `tool_calls` 是否拆成独立行式表 —— **不拆**

行式存储在关系模型上更"正确"，但本项目是**单文件 SQLite 本地部署**形态（Electron 桌面端打包），聊天记录是一次性追加、极少查询内部结构的负载类型。拆表会引入 JOIN 成本与迁移复杂度，收益很低。**保持 JSON 内联 + 加版本号字段**（§6.3）即可。

## 六、扩展性与历史数据处理

### 6.1 【P3】没有迁移框架 —— `PRAGMA user_version = 0`

现状是 `db.ts:65-74` 的手写模式：

```ts
try {
  const tableInfo = db.prepare("PRAGMA table_info(sessions)").all() as Array<{ name: string }>;
  if (!tableInfo.some(col => col.name === 'sdk_session_id')) {
    db.exec("ALTER TABLE sessions ADD COLUMN sdk_session_id TEXT");
  }
} catch (e) {
  // 忽略错误（列可能已存在）   ← 吞掉所有异常
}
```

三个问题：

1. **异常被吞** —— ALTER 若因真实原因失败（磁盘满、锁冲突），代码静默继续，此后每次 INSERT 都报 `no such column: sdk_session_id`，错误现场漂移到离根因很远的地方；
2. **无法判断某个库处于哪个版本** —— 两个 DB 文件可能 schema 不同却无从辨别；
3. **无回滚路径**。

### 6.2 【P3】`CREATE TABLE IF NOT EXISTS` 对已有库永远无效 —— 最易踩的坑

实测：改完表定义后重跑，`PRAGMA table_info` 列仍为 `['id','a']`，新列不出现。

含义：**改 `db.ts` 里的 CREATE TABLE，对任何已有数据库完全无效**。加 CHECK、改类型、改默认值，一律必须走显式迁移。

典型翻车路径：改表定义 → 本机新建库验证通过 → 别人机器上的旧库静默保持旧结构 → 行为分叉且**无任何报错**。

### 6.3 【P3】JSON 列无 schema 版本

`tool_calls` 的元素结构会随工具演进（工具名、参数、结果字段）。历史行没有版本标记，消费端只能靠"字段缺失"兜底，无法区分"旧形状"与"新形状"。

建议加 `tool_calls_version INTEGER NOT NULL DEFAULT 1`，或把关键可查询字段（如工具名）用 `json_extract` 抽出以便索引。

### 6.4 【P3】缺软删除 / 归档

硬删即物理消失，无法支撑"回收站""归档区""保留 N 天"这类需求。叠加 §3.2 的 `feedback` 无删除路径，会话删除后反馈**永久累积悬空行**。

### 6.5 【P3】`id TEXT PRIMARY KEY` 存随机 UUID

65 行量级无影响；到 10 万行量级，随机 UUID 的 B 树局部性差、写放大明显。建议（低优先）：`INTEGER PRIMARY KEY AUTOINCREMENT` + `uuid TEXT UNIQUE`，对外契约仍用 uuid。

### 6.6 反面结论：**不建议现在引入 PostgreSQL / MySQL**

本项目是本地单文件部署 + Electron 桌面端打包形态，SQLite 与交付形态匹配。瓶颈在查询模式（§4）与约束缺失（§三），不在存储引擎。换引擎会引入部署复杂度与迁移成本，却不降低任何一条 P0 风险。

## 七、处置建议与落地包

四个包，按依赖排序。**包一必须先行**——P0 四项互相耦合（FK 开启后 CASCADE 生效，§3.4 的串档链同时被切断）。

### 7.1 包一：数据正确性（不动查询模式，风险最低，收益最高）

```ts
// db.ts:22 之后补一行
db.pragma('foreign_keys = ON');
```

配套（SQLite 不支持 ADD CONSTRAINT，`feedback` 需**表重建**；重建期间 `PRAGMA foreign_keys` 必须为 OFF，完成后再打开）：

```sql
CREATE TABLE feedback_new (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  message_id TEXT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  verdict TEXT NOT NULL CHECK (verdict IN ('up','down')),
  comment TEXT,
  created_at TEXT NOT NULL
);
INSERT INTO feedback_new SELECT id, session_id, message_id, verdict, comment, created_at FROM feedback;
DROP TABLE feedback;
ALTER TABLE feedback_new RENAME TO feedback;

-- 唯一索引改维度：同一消息只允许一个 verdict
DROP INDEX idx_feedback_message_verdict;
CREATE UNIQUE INDEX ux_feedback_message ON feedback(message_id);
```

配套改 `insertFeedback`（`db.ts:87`）为切换语义：

```sql
INSERT INTO feedback (id, session_id, message_id, verdict, comment, created_at)
VALUES (?, ?, ?, ?, ?, ?)
ON CONFLICT(message_id) DO UPDATE SET verdict = excluded.verdict
```

配套改 `clearAllData`（`db.ts:256`）补 `DELETE FROM feedback`。

**迁移前置检查**：现役库孤儿行实测为 0（§2.2），**可直接重建，无需先清脏**。

### 7.2 包二：索引与查询模式（纯性能，无语义变更）

```sql
CREATE INDEX IF NOT EXISTS idx_sessions_updated_at      ON sessions(updated_at DESC);
CREATE INDEX IF NOT EXISTS idx_messages_session_created ON messages(session_id, created_at);
CREATE INDEX IF NOT EXISTS idx_feedback_created_at       ON feedback(created_at);
CREATE INDEX IF NOT EXISTS idx_feedback_session_id       ON feedback(session_id);
```

索引可用 `CREATE INDEX IF NOT EXISTS` 增量添加，**不像表定义那样有 §6.2 的陷阱**。

N+1 改写（`routes.ts:68-73` → `db.ts` 新增函数）：

```ts
export function listSessionsWithCount(): Array<Record<string, unknown>> {
  return db.prepare(`
    SELECT s.*, (SELECT COUNT(*) FROM messages m WHERE m.session_id = s.id) AS message_count
    FROM sessions s ORDER BY s.updated_at DESC
  `).all() as Array<Record<string, unknown>>;
}
```

分页：`GET /api/sessions` 增加 `limit`（默认 50，上限 200）与 keyset 游标（`WHERE updated_at < ?`），前端 `useSessions.ts:39` 改按需取页。

### 7.3 包三：约束收紧（需表重建，一次性做完）

```sql
created_at TEXT NOT NULL CHECK (created_at GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]T[0-9][0-9]:[0-9][0-9]:[0-9][0-9].[0-9][0-9][0-9]Z'),

```

同时给 `routes.ts:200` 的 `JSON.parse` 加 try/catch 降级（单行脏数据不应让整个会话不可读）。

### 7.4 包四：迁移框架与规范固化

```ts
const MIGRATIONS: Array<{ version: number; up(d: Database.Database) => void }> = [
  { version: 1, up(d) { d.exec('CREATE INDEX IF NOT EXISTS idx_sessions_updated_at ON sessions(updated_at DESC)'); } },
  // …
];
function migrate(d: Database.Database): void {
  const cur = (d.pragma('user_version')[0] as { user_version: number }).user_version;
  for (const m of MIGRATIONS) {
    if (m.version > cur) {
      d.transaction(() => m.up(d))();
      d.pragma(`user_version = ${m.version}`);
    }
  }
}
```

配套：删除 `db.ts:65-74` 的 try/catch 手写迁移；把"改表定义对已有库无效"写进 `docs/agent/agent-web.md`。

### 7.6 风险与顺序约束

1. **FK 开启不是纯增益**：`foreign_keys = ON` 后，任何现存违规行都会让写入失败。现役实测违规 = 0（§2.2），但生产库若已积累脏行，需先跑一次孤儿行体检再开。
2. **表重建须在 FK 关闭态执行**（SQLite 官方 12 步流程要求），重建与 `PRAGMA foreign_keys = ON` 的先后顺序不能颠倒。
3. **`messages.role` 未来扩展需再次表重建**——若近期有加 tool 角色的计划，应与包三合并为一次重建，摊平成本。
4. **包二的分页是接口契约变更**：`GET /api/sessions` 的响应结构变化会波及前端 `useSessions.ts` 与 `api.ts` 类型定义，需同批落地。
5. **主键策略（§3.4）涉及既有对外契约**（"查不到 → 以该 id 新建会话"是 `validation.ts:75` 明确保留的行为），改动需用户裁决；**不改动亦可**——包一的 FK + CASCADE 已能切断串档链。

## 附录 C：本次审查自身的两处测量错误与修法

本批取证脚本首版有两处缺陷，**均由实跑输出与预期不符暴露**，修正过程留档（与仓库"声明≠落地=假收敛"同源的自证纪律）：

| # | 错误 | 暴露方式 | 修法 |
|:---:|:---|:---|:---|
| C-01 | 计时助手把**秒当毫秒打印**（漏 `×1000`） | 5 万行全表扫描打印出 0.08 ms——与 76 ms 的独立单次计时矛盾 | 计时统一 `×1000`，并**每次打印实返行数**；行数与预期不符即标注该行数字作废 |
| C-02 | F-02 未播种数据就断言悬空 | 现役 `feedback` 表 0 行 ⇒ 测出「悬空行 = 0」，看似正常实则**什么都没测到** | 先播种 1 条指向真实消息的反馈再清库，判据才有意义 |

C-01 的排查过程还排除了一个**错误假设**：曾怀疑"复用同一 cursor 导致结果被缓存"，但改用每次新建 cursor 后数字依旧（0.076 ms），而独立单次计时稳定在 76 ms——最终定位为单位换算错误。**教训：性能数字必须附口径校验（实返行数 / 单位换算），否则"跑得很快"往往意味着"测错了"。**
