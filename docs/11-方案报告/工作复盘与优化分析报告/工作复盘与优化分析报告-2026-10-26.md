## 7. 工作流优化

### 7.1 WF-08 登记面自愈 + 复盘触发器（FAM-40/FAM-41 载体）

**WF-08-a 状态字段机器化**：批次收官时，**状态字段由脚本从 git 反填**（读该 W 号的提交是否存在 + 首个提交 hash），不再由人工在段内/行内手写「已收官（hash…）」。配套：preflight 的「在途」判定加 git 条件——`台账标在途 AND git 无该 W 提交` 才算在途；台账标在途但 git 已有提交 ⇒ 判为**登记滞后**（告警不拒绝），从而**不阻塞新批次**。落地位置：`scripts/preflight_check.py` 的 `parse_ledger` + 收官回填脚本（`backfill_changelog.py` 同族）。

**WF-08-b 复盘触发器**：当「累计批次 ≥ 30」或「距上篇复盘 ≥ 3 天」或「累计提交 ≥ 80」任一成立 ⇒ 在对账表相关行标「待复盘」并输出触发清单。**触发器与 P-43-01 同批落地**——若登记面状态不可信，触发器会同样误判（这不是理论风险：本期 91 批状态滞后即反例）。

**WF-08-c 段状态错位防护**：任何写入段内「状态」字段的动作，断言其文本中出现的 W 号等于所在段的 W 号，不等即报错（E-28 的机械化）。

### 7.2 WF-09 素材线人眼关前置化（FAM-42 载体）

把 W942/W953 依赖人眼的「题材辨识度 + 形制正确性」两关，前置为**出图前逐张自检表**（每张须写明「靠哪个西游元素认出」「形制关键特征是什么」）+ **重出时逐条对照**；并把 W949 堵掉的数据源回归漏洞（资产在、页面没同步）纳入出图批的固定检查项——即 W950 已实现的图形同步器**前置到每次出图**而非打磨批才建。

### 9.2 知识缺口

1. **「登记面」尚未被定义为独立概念**——仓内有「事实源」的局部实践（W739 规则③），但没有「声明面 vs 事实面」的系统表述，本篇 FAM-40 是其第一次成规模量化。
