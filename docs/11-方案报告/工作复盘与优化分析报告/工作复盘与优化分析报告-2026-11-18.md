## 1. 时间账：一次巨批收官 verify 被跑了三遍

W1266 收官提交周期的实际门禁耗时（逐项计时）：

| 遍 | 触发点 | 内容 | 耗时 |
|---|---|---|---|
| 1 | 提交前 pre_push_gate（finalize 脚本惯例） | guardrails + verify 全量 + pytest 全量 + ci_sim（SKIP） | 395s |
| 2 | 提交时 pre-commit 钩子 | verify `--scope auto`（246 件巨批命中多数段） | 数分钟 |
| 3 | （原计划）提交后再跑一次全量 | 只为让 ci_sim 真跑 | ≈400s |

**根因**：流程顺序让「全量」出现在提交前与提交后各一次，而提交前的全量对提交动作本身没有增量价值——提交期防线是钩子的 scope 子集，推送判据才是全量的合法位置（且 ci_sim 只能在干净树上真跑）。**修法（顺序反转·零工具改动）**：提交只靠钩子 → 提交后跑一次 pre_push_gate（ci_sim 顺带真跑·即推送判据）⇒ verify 从 3 遍降 2 遍，巨批每批省 ≈6–8 分钟。本会话自 W1271 起按反转序执行。若把该序写进 finalize 脚本与流水线 §九，即整类消灭。

## 4. 主题复盘三：三哨同批到期——WARN 债单失灵的再确认与清偿形态

本批 preflight 同时命中三个周期哨：对抗审查 38 批（≥20 软警）· Backlog 对账 55 批（≥50 硬拦）· 复盘周期 6 天 50 批（≥30 批硬拦）。**为什么集中到期**：W1164 之前的 WARN 债单对「重要不紧急」欠账无强制力，各会话按自身批次节奏推进、谁都不欠「自己的」哨，债务在跨会话尺度上复利。**清偿的最小形态**（本批采用）：① 对抗审查 = 按模板派发只读 subagent（与修复分离·审查者不修）+ 认领行状态列 token；② Backlog = 按 git/测试实况核 HANDOVER §四 + 注记 token（本轮实况：唯一未决项 P-43-01 复核仍开放——`wnum_commit_index` 自 W1211 根修后零改动，缺口如实留存）；③ 复盘 = 目录面落盘本篇 + CHANGELOG 段认领复盘批角色（双源判据 T1）。**结构结论**：三哨的判据面各自独立但清偿动作可以同批叠加——「触发器到期」不该被当成阻塞噪声，它是治理义务的到期通知，集中清偿的边际成本远低于分散补。

## 5. 经验沉淀

- **门禁分层的精确表述**（修正 E-265 的初版措辞）：全量 verify 的合法位置是「提交后、推送前恰一次」；收官链的 gate 步保持 `--skip-gate`，提交靠钩子 scope 子集，ci_sim 自然在唯一一次全量里真跑。
- **手工级联的三件套**：`rebuild_section.py`（CHANGELOG/file-index 面·无锚点断言）+ `version_surface.advance_all`（版本六面·幂等·与段插入解耦）+ 台账/脚注/页脚手工面——跳号批的完整闭环不需要触碰 `batch_cascade` 本体（禁擅改面）。
- **占号候选面覆盖计划序列**：`reserve_w.py` 返回号已含「清单预留位」语义；开批凭直觉取号在预留序列活跃期必撞号。
- **清偿 token 的位置语义**：对抗审查 token 只在台账**状态列**被认（W1004）且**在途行不计**（W1022）⇒ 派发批自己的行要在收官前保持 token 在状态列，事件以「行闭合」生效。
