#### 《skill-creator 技能优化任务卡》

**S-10 引擎全链路冒烟模板**
- 定义：对「LLM→工具集→SSE 契约」服务端做 mock 驱动的机判断言（mock LLM 起服→真实引擎→事件序列/工具实执行/安全守卫/增量拼接）。
- 现状与差距：engine.smoke.mjs 已实现（12 断言），但为 agent-web 专用手写——差距=未模板化，下一个含 LLM 工具环的端点（如 scripts/rag 档B 强化）需重写。
- 优化目标：新服务端冒烟搭建耗时 4 小时→1 小时（-75%）；断言族覆盖 ≥4 类（序列/真实执行/守卫/拼接）自动派生。
- 规格（交 skill-creator）：输入=服务端启动命令+LLM 协议形态+工具清单+守卫规则表；输出=可执行 smoke 脚本（含 S1 序列/S2 真实执行/S4 越界/S5 敏感路径/S6 权限模式五族断言）+ 退出码语义；约束=不引新依赖、Windows 拆卸顺序（closeAllConnections→close→wait）；示例=engine.smoke.mjs 全文；异常=服务 30s 未就绪/断言失败均 exit 1。
- 时间表：W1 初版→W2 试运行（用于 W681 联调回归）→W2 末验收。
- 验收：W681 联调批次直接消费该模板产物且零改动跑通；断言族 ≥4。
- 责任人：Owner=引擎维护 Agent；操作=skill-creator；验收=用户。

**S-11 告警裁决流水线**
- 定义：code-scanning/依赖告警的「分组→定性→真修→按族 dismiss（理由注）→复验」闭环。
- 现状与差距：首账用一次性 bash+gh api 手工完成（37 条 dismiss 脚本即弃）——差距=无可复用脚本、jq 输出错（number+string 拼接）未修。
- 优化目标：新告警批处置耗时 2 小时→30 分钟（-75%）；dismiss 理由注覆盖率 100%。
- 规格：输入=repo+state=open；输出=按 rule.id 分组 CSV + 按「族理由表」批量 PATCH + 终态计数对账；约束=dismiss 理由必须含证据指针（文件:行或防线名）；异常=API 限流重试/未知规则回落人工。
- 时间表：W2 初版（挂在 W681 联调批）→W3 验收。
- 验收：对 scorecard 下轮增量告警实跑一次，0 手工单条操作。
- 责任人：Owner/操作/验收=Agent（用户抽验）。

**S-12 手工级联生成器**
- 定义：由「认领批号+现役段批号+spec」自动生成 `_wNNN_close_cascade.py`（复刻原生工具全部锚点断言+批号硬编码+偏差声明）。
- 现状与差距：五次手工复制改造（每次改 4 处常量+2 处断言）——差距=纯复制粘贴，存在 W683 链尾 marker 被抹类隐患（本周期已发现：累积链插入破坏「无 workflow 结构改动）。」唯一性，需级联脚本内置链尾感知）。
- 优化目标：生成耗时 30 分钟→5 分钟（-83%）；marker/链尾类断言失配 0。
- 规格：输入=批号/版本/日期/spec 路径/现役 cur_w/累积链尾现状（自动读 workflows README 判定插入点）；输出=可 ruff 通过的 cascade 脚本；约束=保留全部原生断言语义+写后自检+清单输出；异常=链尾无 marker 时改「链尾插入+重建 marker」并声明。
- 时间表：W2 初版→W3 用下一跳号批（批次四 W676 或联调批）实战验收。
- 验收：生成的脚本 dry-run 一次通过；写后自检 0 项。
- 责任人：Owner/操作=Agent；验收=用户。

## 七、工作流优化方案

### 7.1 WF-01 引擎更换批交付主流程（已执行复盘）

```
蓝图量化（集成面实读）→ 引擎四模块 → 重接线（SSE 契约对拍）→ 冒烟 12 断言
→ 去依赖 → 独立安全审查（并行可）→ 确认项复修 → 级联+两段提交 → CI 对账
```

- 瓶颈实测：安全审查发现的复修占本批提交量 3/7（4b9e85d 单笔 204 行）——**审查前移（E-01）可将复修并入首写**，预计省 1 轮提交+1 轮 CI（约 40 分钟墙钟）【假设：按本批实测外推】。
- 冗余消除实证：旧引擎每批「真跑验证需真 key」的隐性阻塞，被 mock 冒烟消除——机判不再依赖外部凭证。
- 量化：W680 全程（蓝图→五工作流绿）单日完成；复修批（review 后）验证耗时 = smoke 12 断言秒级 vs 人工多页走查小时级。

### 7.2 WF-02 告警与评分处置流程（新增，固化目标 ≥20% 效率提升）

现状（首账）42 条手工逐条 → 优化：按族分组（rule.id）→ 族理由模板 → 批量 PATCH → 终态对账（S-11 流水线化）。测算模型：首账 2 小时 → 增量批 30 分钟（-75%，满足 ≥20% 目标）；验证=scorecard 下轮增量批实跑。

**本章结论**：两条流程均有实测/测算支撑。**待确认事项**：WF-02 的 30 分钟口径待 S-11 首跑实测确认。
