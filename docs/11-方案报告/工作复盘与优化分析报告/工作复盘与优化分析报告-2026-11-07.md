## 2. 主题复盘一：治理重组批的移动-删除-改写三分决策

治理重组批的每个对象必须落进三档，**每档走不同的门禁链**：

- **移动**（git mv）：TOP_DIRS/白名单声明 → INDEX 家族刷新（gen_folder_docs tracked-basis 依赖暂存态·先 add 后 refresh）→ 活性引用 grep 更新（历史段/归档/spec 不动）。保真靠 rename diff。
- **删除**：先分「本地未跟踪（直删）/ 跟踪孤儿（git rm+级联刷新）/ 裁决件（CHANGELOG 记决策）」。**每件删除前必须引用精验**——本批 og-cover.png 被侦察判孤儿、精验翻案为 SEO 门禁 R4 在管回退件保留；promo 中间层侦察判「本地垃圾」、实为被跟踪的留档原件，披露新事实后二次确认才删。**侦察结论≠删除授权**。
- **改写**：坑表 E-199 三重防线（锚点唯一性预检/改后完整性断言/结构档红灯逐条归因），机器判据见经验 2。

本批踩过的门禁联动（后续重组批照单）：索引家族刷新顺序（add→refresh）、stats --w 计数跟随、stash pop 打回暂存态的恢复流程（存在→add/不存在→rm --cached）、porcelain rename 行逐段剥引号。

## 3. 主题复盘二：坑表落载与机器判据的时序（本日最大教训）

W1159 第一刀只落了坑表+计数链（软载体），用户两连问「只落坑吗？以后再犯怎么办？」暴露时序缺陷——第二刀才补机器判据。**正确时序 = 坑表条目与机器判据同一批次落地**，验收形态 = 负样本自测必红 + 端到端接线实跑。

判定问句：*另一个会话不看坑表，门禁会不会拦住这类事故？* 答否 = 未完成。本批答案：`check_rewrite_integrity.py`（C1 语法可编译/C2 公开函数集 vs HEAD 不缩水/C3 模块级双定义）接铁律 20 链——每次改 .py 必跑，pre-commit strict-api 路径自动生效。其上 W1159 批内 C4 判据还真实拦截了一次「开批漏登记认领行」——门禁拦得住的前提是门禁在跑且判据对得上实况。

## 4. 主题复盘三：触发器欠账的清偿模型

preflight 每批打印的复盘/对抗审查/Backlog 三条 WARN 是**带阈值计数的债单**，但长期无人响应——缺的不是提醒，是「清偿动作的落位约定」。W1160 清偿模式：**同一批内三债全清**（复盘落盘+派发登记 token+实况对账注记），比分三批各还一债省两批开销。

配套根修：19 条「登记滞后」WARN 里 17 条是真滞后（--from-git 反填清偿）、2 条是**词表误报**（`is_inflight` 不识别「已合并」形态）——触发器噪音淹没真信号的标本。根修 = DONE_PREFIXES 词表扩展 + 回归锁。推广：凡按状态词分类的判据，词表必须 grep 台账状态列实测枚举实际形态全集，不凭想象。

## 5. 经验沉淀

1. **治理重组三分决策表**（移动/删除/改写各走各的门禁链）——可迁移到任何仓的大重构批。
2. **「侦察结论≠删除授权」**：删除前的逐件引用精验是独立工序，侦察报告的孤儿判定必须复核（本批两起翻案）。
3. **坑表与机器判据同批落地**：软载体（条目）与硬守卫（判据）的时序契约，验收问句见 §3。
4. **触发器债单同批清偿模型**：三条周期性 WARN 一批清零优于分批；词表误报与真欠账分流处置。
5. **存量欠账显式化**：坑表记教训不记欠账，欠账散落触发器/门禁待办行——渐进暴露型欠账（如存量复杂度 64 处）需要显式清单+棘轮批维护（W1161 起）。
6. **复盘写法纪律（本篇自返）**：写系列续篇前先读同系列近篇的结构模板，不自创章节——本篇首版偏离模板被用户当场指出后按第 52 篇结构重写。
