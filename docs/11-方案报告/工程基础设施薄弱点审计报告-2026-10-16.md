## 4. 四条新发现硬缺陷（含证据链）

### 4.1 D1：第 43 门禁在 CI 中必红 🔴

**缺陷描述**：`verify_delivery.py` 第 43 槽委托 `check_chart_values.js --gate`；该脚本第 904 行硬依赖 `require('playwright')`。而 `ci.yml` 的 `verify-delivery` job（原 306-334 行）步骤序列为：

```
checkout → setup-python → pip install → setup-node → run_all.py → verify_delivery.py
                          ↑ 全程无 npm ci / 无 playwright install
```

`scripts/node_modules/` 被 `.gitignore:24` 忽略，CI 上不存在。因此 `require` 抛 `MODULE_NOT_FOUND` → 被 `main().catch`（`check_chart_values.js:1398`）捕获 → 打印 `crashed` + `---- 第 43 门禁 可视化数据断言：1 FAIL ----` → exit 1 → `_StrictGate`（`verify_delivery.py:636`）记 FAIL → **`verify_delivery.py` 整体 FAIL**。

**证据链**：

| 证据 | 命令 | 结果 |
|---|---|---|
| CI job 无 Playwright 步骤 | `read .github/workflows/ci.yml`（306-334） | 确认无 `playwright install` |
| 门禁硬依赖 | `read scripts/check_chart_values.js`（904） | `const { chromium } = require('playwright');` |
| 缺失即 crash 且打印 1 FAIL | `read`（1398-1405） | `.catch` → `console.log('...：1 FAIL ----')` |
| crash 记 FAIL 不记 WARN | `read scripts/verify_delivery.py`（633-635） | `_StrictGate` 用 `ctx.rep.fail` |
| **本地有浏览器则全绿** | `node scripts/check_chart_values.js --gate` | **0 FAIL**（87 页 / 20.2s） |

**为何长期未被发现**：本地 HEAD 领先公开 main 63 提交，CI 最后一次 main 运行是 W727（2026-10-12）——第 42/43 门禁（W751/W753 新增）**从未在 CI 环境执行过**。

**违反的项目铁则**：`AGENTS.md` E36-E42 铁则②「**门禁建置即绿**（不允许"从未运行/从未通过"的门禁存在）」；HANDOVER 亦载「E36-E42 workflow/CI 类 7 条」。

### 4.2 D2：W752 安全单测未接线 🟠

**缺陷描述**：`xiyouji-agent-web/package.json:15` 定义：

```
"test:server": "node --import tsx --test server/engine/tools.test.ts server/audit.test.ts server/citationGuard.test.ts"
```

三个文件分别覆盖：`tools.test.ts`（377 行·权限边界/写入允许域）、`audit.test.ts`（171 行·审计落盘）、`citationGuard.test.ts`（引文守卫）。

**全 workflow grep `test:server` / `npm test` / `--test ` → 零命中**。`agent-web-build` job 只做 `build` + `evals/validate.mjs`（golden-50 结构校验，非安全测试）。即：W752 建立的安全防线**在 CI 中完全不设防**。

**证据**：`Select-String -Path .github/workflows/*.yml -Pattern "test:server|npm test|--test "` → 无输出；本地 `npm run test:server` → **44/44 通过**（0.5s）。

### 4.3 D3：安全扫描覆盖盲区 🟠

**缺陷描述**：`scripts/security_scan.py` 的 `discover_files()`（原 160-178 行）：

```python
roots = [SITE_DIR, SCRIPTS_DIR, ROOT / "tests", ROOT / "mcp-server"]
exts  = {".html", ".js", ".py", ".jsx", ".yml", ".yaml", ".txt"}
```

**既不含 `xiyouji-agent-web/`，也不含 `.ts/.tsx/.mjs`**。该目录是「能读写仓库文件、运行 Python 脚本」的 React 19 + Express 5 服务——项目自身 HANDOVER 称其为安全风险最集中处——却对 XSS/密钥类门禁**零覆盖**。

**证据**：`grep -c "agent-web" scripts/security_scan.py` → **0**；而 `security.yml` 的 XSS job 在 push+PR 双触发运行 `--all`，给人"已全覆盖"的印象。

### 4.4 D4：63 提交未推送（放大因子）🔴

| 项 | 值 |
|---|---|
| 本地 HEAD | `2c1ec6cd`（W756，2026-10-16） |
| 公开 main | `80f77dd3`（W727，2026-10-12） |
| 领先 | **63 提交** |
| 公开侧最后一次 ci.yml 运行 | `38296732621`（W727，2026-10-12，conclusion=success） |

**后果**：D1-D3 均属"只有 CI 真跑才能暴露"的缺陷，而 CI 已有 63 提交未覆盖；同时第 42/43 门禁、W751-W753 三批防护**在公开侧完全不存在**——用户基于公开仓库评估，必然读不到这些已落地的加固（解释了 §3 中 8 条"已消解"）。

**证据**：`git merge-base --is-ancestor 80f77dd3 HEAD` → exit 0；`gh run list --branch main --workflow ci.yml --limit 20` → 最新为 W727。

### 4.5 本章结论

四条缺陷同属**「声明与落地不一致」**族（与项目 E1 铁律同源）：门禁声明存在但 CI 跑不起来（D1）、安全测试存在但 CI 不执行（D2）、扫描器存在但覆盖面缺失（D3）、防护已落地但公开侧不可见（D4）。共同特征——**不会在批次驱动的主动审查中暴露，只在"某次未被触发的 CI 恰好是唯一防线"时显现**，与用户第三轮的判断框架吻合，但具体落点用户未命中。

**待确认事项**：D4 是否推进（推送 63 提交）需用户单独决策——涉及远端写操作与发布动作。
