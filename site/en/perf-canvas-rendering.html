II · Three Key Optimization Techniques

THREE OPTIMIZATION TECHNIQUES
① requestAnimationFrame batched updates
Merge the force simulation's tick callbacks into a single-frame draw to avoid DOM writes on every tick; in Canvas mode go further — trigger only one redraw after all node coordinates are computed.
simulation.on('tick', () => { // ❌ 传统：每个 tick 都触发 DOM 重排 // svgNodes.attr('cx', d => d.x).attr('cy', d => d.y); // ✅ 优化：rAF 合并 + Canvas 单帧重绘 if (!rafPending) { rafPending = true; requestAnimationFrame(() => { rafPending = false; drawCanvas(); // one beginPath + stroke }); } });
② Canvas offscreen rendering (OffscreenCanvas + caching)
Use document.createElement('canvas') to create an offscreen canvas and pre-draw the static background (grid, decorations, label layer); the main canvas only needs a drawImage copy, reducing per-frame redraw cost. Browsers supporting OffscreenCanvas can move it to a Worker thread.
// offscreen canvas pre-draws the static layer const offscreen = document.createElement('canvas'); offscreen.width = W; offscreen.height = H; const offCtx = offscreen.getContext('2d'); // pre-draw background, axes, decorative textures ... // the main canvas redraws only dynamic nodes + copies the static layer function drawCanvas() { ctx.drawImage(offscreen, 0, 0); // one blit ctx.beginPath(); for (const n of visibleNodes) { ctx.moveTo(n.x + r, n.y); ctx.arc(n.x, n.y, r, 0, 2 * Math.PI); } ctx.fill(); // single fill batch-submits }
③ Virtualization (render only the visible region)
For large graphs exceeding 1000 nodes, cull off-screen nodes by viewport; filter edges by distance threshold; on zoom/pan switch render fidelity by LOD (Level of Detail) — far view draws only dots, near view draws labels.
const visibleNodes = nodes.filter(n => n.x >= viewX0 && n.x <= viewX1 && n.y >= viewY0 && n.y <= viewY1 ); const visibleEdges = edges.filter(e => visibleNodes.includes(e.source) && visibleNodes.includes(e.target) ); // 1000+ nodes → actually draws only ~200 visible nodes // performance drops from O(N) to O(visible N)

III · Key Insights and Applicability Bounds

KEY INSIGHTS & APPLICABILITY
Rendering mechanism difference: In SVG every node is a real DOM element (<circle>); the browser must maintain event bubbling, style computation, and layout. Canvas is all bitmap pixels with no DOM overhead after drawing.
Inflection at 500: Below 200 nodes the SVG/Canvas gap is small (~10ms); above 500 nodes SVG time spikes to 100-300ms while Canvas stays at 10-30ms.
Interaction trade-offs: SVG has built-in event binding (onClick per element); Canvas requires custom hit-testing (distance checks / quadtree). If high interactivity is needed, prefer SVG below 300 nodes; otherwise switch to Canvas with custom hit-testing.
Project application: This project character-semantic-network.html / intertextuality-network.html / narratology-13d-network.html already exceeds 300 nodes, so a Canvas rendering branch is recommended in the future; graphs below 100 nodes (such as guanyin-six-roles-network.html) keep SVG.
Animation scenarios: Force-simulation iterations are where Canvas shines most — SVG updates N DOM properties per frame while Canvas only redraws a bitmap. For this project's animated curves such as timeline / sentiment-arc, enable Canvas + rAF throttling too.
Mobile: iOS Safari visibly stutters when scrolling SVG with > 500 nodes, while Canvas holds 60fps. After this project goes PWA, migrate large graphs to Canvas first.
