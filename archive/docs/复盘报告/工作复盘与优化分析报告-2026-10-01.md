## 六、工作流优化方案

### 核心流程：W 批次端到端（从裁决到推送）

**现有流程**（19 批实践后的实际形态）：

```
裁决/指令 → 取证 → 改动 → 生成器重生成(如有) → 级联 dry-run → 级联 apply
→ verify_delivery 全量 → scoped commit → push → CI 确认 → memory 沉淀
```

**各环节耗时实测**：

| 环节 | 耗时范围 | 瓶颈分析 |
|---|---|---|
| 取证/改动 | 10-60 min | 取决于批次复杂度·弹性最大 |
| 生成器重生成 | 1-3 min | 无瓶颈 |
| 级联 dry-run | <1 min | 无瓶颈 |
| 级联 apply | <1 min | 无瓶颈 |
| verify_delivery 全量 | 3-5 min | **瓶颈**：27 门禁串行执行 |
| scoped commit | 1-5 min | **易出错**：4/19 批在此出错 |
| push | 1-3 min | 偶有网络重试 |
| CI 确认 | 5-15 min | **等待瓶颈**：Screenshot Review ~10 min |
| memory 沉淀 | 3-5 min | 无瓶颈 |

**优化建议**：

| 建议 | 措施 | 预期效果 | 优先级 |
|---|---|---|---|
| CI 等待并行化 | push 后立即开始下一批取证，不等 CI——CI 失败时 revert+追补（W632 模式已验证） | 总吞吐量提升 ~30% | P1·已隐性执行 |
| scoped commit 脚本化 | `scripts/commit_check.py` 读级联 spec→输出 add 清单+校验 | 提交出错率 21%→0% | P1·见 §二 |
| verify_delivery 并行门禁 | 27 门禁按依赖关系分组并行（互不依赖的门禁组同时跑） | verify 耗时 5 min→2 min（估算） | P2·需改 verify_delivery（禁擅改清单内·须裁决） |
| computer-use 流程标准化 | 翻译扩展禁用→操作→启用的 SOP 文档化 | GUI 操作轮次 12→5 | P2 |

**结论**：当前流程整体效率已高（19 批 2 天·平均 ~2.5h/批含 CI 等待）。最大的吞吐量瓶颈不在流程本身而在 **CI 等待时间**——通过「不等 CI 继续下一批」的流水线模式已隐性解决。结构性优化空间有限。
