# 西游记项目方案/文档评估

给 xiyouji 项目（`D:\1\xiyouji`）的方案、路线图、治理文档做评估的固定流程。核心原则是项目 E1 铁律：**声明 ≠ 落地**——方案里的每一个数字、每一处文件/脚本引用，都必须先在仓库实测核对，然后才允许下评估结论。禁止空对空评估。本流程每一步都在 Phase 3 量化路线图评估中逐字跑通过，当次靠它发现了 6 处方案与实测的偏差。

## 何时触发

触发（正向）：

- 用户要求"评估方案"、"方案评估"、"评估这个路线图"、"文档评估"、"plan review"、"方案审查"、"评审方案"。
- 用户给出一份或多份方案文档（如 `docs/superpowers/plans/` 下的 roadmap、`新Agent启动Prompt.md`），问"能不能落地"、"有没有问题"、"给个评估意见"。
- 用户要求输出五维（可行性/结构/可维护性/性能/风险）+ 优势 + 不足 + 改进建议的固定规格评估文档。

排除（反向）：

- 撰写新方案（那是写方案，不是评估，不要套本流程）。
- 检验新版本能否交付（那是 `xiyouji-version-bump` 技能的 verify_delivery 门禁）。
- 学术论文投稿前处理（那是 `xiyouji-s4-submission` 技能）。
- 评估外部工具/库/SDK 是否可用（那是 `tech-choice-verification` 技能；理念同源但对象不同，不要混用）。

## 前置条件

- 项目在 `D:\1\xiyouji`，git 分支 `main`。shell 为 git-bash，命令用 `cd D:/1/xiyouji` 风格。
- **多 session 并发是常态**：仓库状态随时可能被其他 session 改动，一切以本 session 当场实测为准，勿信任何快照、记忆或方案里抄来的旧数字。
- 评估产物默认输出为 .md 文档：项目内方案评估落 `D:/1/xiyouji/docs/`（或用户指定位置）；纯咨询类评估落工作区 outputs 目录。
- 完整取证命令库与评估文档模板见同目录 `reference.md`——执行阶段 1 前建议先过一遍。

## 标准流程（取证硬门槛 + 五阶段）

严格按顺序执行。**阶段 1 取证未完成前，禁止输出任何评估结论。**

### 阶段 0：定位评估对象，登记"声称清单"

1. 用 Read 通读全部待评估文档（一篇都不要漏，多文档时注意交叉引用关系）。
2. 边读边登记三张清单（后面取证逐项核对）：
   - **声称数字**：所有量化数字（页数、JSON 数、sitemap URL 数、预算 KB 数、工时估算等），记录原文表述。
   - **声称引用**：所有引用的脚本、文件、目录、门禁、外部服务。
   - **声称基线**：方案声明的适用基线（版本号 + git HEAD），若方案没写基线，这本身就是一条不足。
3. 留意"新增 vs 已有"措辞：方案说某脚本"新增"则该文件**应当尚不存在**，说"已有/已落地"则**必须存在**——两种声称的核对方向相反。
4. 登记**目标性质**：方案目标若属感知型（"高级感/更好看/观感升级/体验提升"之类主观观感），在清单里打标"感知型目标"。感知型目标方案的验收必须含"可感知验证"手段（前后对比截图/目视清单/A-B 对照），否则判定为验收缺陷（见阶段 1 动作 6、陷阱 9）。

### 阶段 1：取证（硬门槛）

五个取证动作，命令模板全部在 `reference.md`，这里给要点：

1. **git HEAD 对齐校验**：`git rev-parse --short HEAD` + `git log -1 --oneline` 实测，与阶段 0 登记的声称基线比对；`git status --porcelain` 重验工作区，若有未提交改动先看 diff 判断来源（可能是其他并发 session 的活，不要动也不要算进评估基线）。HEAD 对齐 → 评估结论才有基线效力；不对齐 → 评估文档首部必须醒目声明差异。
2. **目录/页面实测计数**：`site/data/*.html`（⚠️ 含 `_shell.html` 模板，实际可视化页数要减 1）、`site/en/*.html`、`dataset/*.json`、`site/sitemap.xml` 的 `<loc>` 计数。与声称数字逐一比对。
3. **引用脚本/文件存在性**：对声称引用清单逐个 `ls` 核实（⚠️ Glob 工具对该仓库可能漏匹配，必须用 Bash `ls` 复核）。"已有"的必须存在；"新增"的应当不存在，若已存在还要打开看内容版本是否最新——文件存在 ≠ 内容有效。
4. **关键链路 grep 抽查**：方案涉及的机制抽 2–4 个点位实测。例如脚本加载方式（async/defer）、功能覆盖率（`grep -l '特征' 目录/*.html | wc -l`）、meta description / JSON-LD 全站覆盖数、visit-log 引用页数等。
5. **声称值 vs 实测对照表**：把阶段 0 登记的声称数字逐项汇总成表，每行标注 ✅一致 / ❌不符 / ⚠️口径偏差（附实测值与说明）。这张表是评估文档的证据基线表，缺一不可。
6. **感知型目标验收可行性**（仅当阶段 0 打标"感知型目标"）：检查方案的验收指标是否含**可感知验证**——逐条核对其验收条款，若全部是工程卫生指标（对比度 ≥4.5 / 裸色=0 / 体积预算 / pageerror=0 / 覆盖率%），没有任何前后对比截图、目视清单或 A-B 对照，则记录为缺陷（"验收无法检测视觉变化"）。再用 worktree 实测目标观感的实际渲染差异：`git worktree add --detach <临时路径> <基线提交>` 取方案前后各一个版本，对目标页面截图对比（命令模板见 reference.md §1.6）——实测"前后视觉差异不可辨"即为该方案目标未达成的硬证据。

取证中每发现一处偏差，当场记录"偏差 + 影响判断"，供阶段 3 使用。

### 阶段 2：五维评估

按五个维度逐一评估，**每个维度的论断必须引用阶段 1 的实测证据**，写不出证据的论断就降级为"待验证"并如实标注：

1. **技术可行性**：方案是否切实可落地——依赖的脚本/机制是否存在或可造、工时估算与实测工作量是否匹配（例：声称 3–6h 但实测需批量处理 200+ 页即为低估）、前置条件是否满足。**感知型目标方案的验收可感知性**：若目标为"高级感/观感升级"而验收指标全是工程卫生指标（对比度/裸色=0/体积/报错），可 100% 完成却零感知变化，判为可行性缺陷（引用阶段 1 动作 6 的截图证据）。
2. **结构合理性**：模块/批次划分与依赖关系是否清晰、编号体系是否可追溯、与既有体系（门禁、文档、令牌架构）的挂接是否明确。
3. **可维护性**：扩展与调试成本——新机制是否沉淀为可复跑的门禁/脚本、文档同步面有多大、交接给新 Agent 是否自足。
4. **性能表现**：体积预算、加载约束（file://、CSP、内联架构的放大效应：tokens 每增 1KB × 全站页数）、与既有预算文件的冲突检查。
5. **潜在风险**：技术债、数据污染（如 CI 浏览器访问计入统计）、口径歧义、并发冲突、外部依赖不确定性。

### 阶段 3：优势总结 + 不足-改进对照表

1. **优势总结**：先说方案做对了什么（真实、可复算、挂接既有体系等优点要具体点名，不空夸）。
2. **不足清单**：每项不足必须含——问题描述、阶段 1 的实测证据、影响程度（高/中高/中/低）。
3. **一一对应改进建议**：每条不足配一条具体、可操作的改进（改哪个文件/哪一节、改成什么、或补什么验证），禁止"建议完善 XX"式空话。

### 阶段 4：输出评估文档

按 `reference.md` 的评估文档模板撰写，硬性要求：

- 结论先行：首部即总体判断（一段话，可执行/有条件可执行/需返工）。
- 文档首部带**评估基线声明**（实测 git HEAD + 与方案声称基线是否一致）。
- **证据基线表**（声称 vs 实测对照表）必须完整收录，这是评估的信用基础。
- 五维分段、优势、不足-改进对照表、**优先行动前三条**（可直接回填进方案的修订建议）。
- 语言克制：偏差就是偏差，不用"略有瑕疵"之类软化；方案好的地方也明确说好。

### 阶段 5：自我交叉复核

交付前把评估文档里出现的关键数字（实测计数、覆盖率、版本号）再核一遍，确认没有抄错、没有把"声称值"误写成"实测值"。复核通过后再 present 文件给用户，回复正文给结论先行的精炼摘要（总体判断 + 前三优先项）。

## 五维评估要点速查表

| 维度 | 核心问题 | 典型取证点 |
|---|---|---|
| 可行性 | 依赖是否真实、工时是否匹配实测工作量；感知型目标是否有可感知验收 | 脚本存在性、覆盖页数 vs 声称工时、验收条款是否含前后对比截图 |
| 结构 | 划分/依赖/编号是否清晰可追溯 | 批次依赖链、与既有门禁的挂接 |
| 可维护性 | 扩展调试成本、知识是否沉淀 | 验收能否沉淀为门禁、文档同步面 |
| 性能 | 体积/加载约束是否守住 | perf-budget 冲突、内联放大效应 |
| 风险 | 技术债、数据污染、口径歧义 | CI 污染统计、N 口径、并发冲突 |

## 陷阱清单

1. **Glob 漏匹配**：Glob 工具对 `D:/1/xiyouji/scripts/*.py` 曾返回空（实际存在大量脚本）。存在性核实一律用 Bash `ls`，Glob 只作辅助。
2. **计数口径陷阱**：`site/data` 87 个 HTML 含 `_shell.html` 模板 → 实际可视化页 86；EN 站**没有** `data/` 子目录，可视化页平铺在 `site/en/` 下；EN 与 CN 同名可视化页只有 85 个（缺 `journey-geo-3d`）。报数前先想清楚口径。
3. **"全覆盖"≠特征字符串全命中**：例如"86 页动效全覆盖"实测只有 40 页含 `.duration(`（静态页豁免、动效合规 ≠ 每页 D3 transition）。评估"覆盖率"声称时先弄清方案对该特征的真实定义。
4. **文件存在 ≠ 内容有效**：`perf-baseline.json`/`perf-budget.json` 存在但版本停留在 W267。声称"已有"的文件要打开看内部版本/日期字段。
5. **预算冲突要交叉验证**：如 perf-budget total 900KB 与内嵌 2MB JSON 的 text-search 页直接冲突——拿方案里的预算数字去乘/除实际文件体量，冲突会自己浮出来。
6. **并发 session 污染**：git 状态必须当场重验；工作区有未提交改动时先看 diff 判断归属，不要替别的 session 提交，也不要把别人的改动算进评估基线。
7. **观测数据污染**：GitHub Actions 的 Playwright/LHCI 以真实浏览器访问线上站，会被 GoatCounter 记成访客——凡方案以访客数做决策闸门输入，必须检查 CI 是否已拦截，否则数据虚高。
8. **措辞精度**："新建"与"更新"不可混用（文件已存在却说"新建"属表述失真，虽小必记）。
9. **视觉目标 ≠ 工程卫生验收（2026-08-22 Phase E 实测教训）**：Phase E「视觉高级感升级」（W476–W478）验收 M1-M7 全是工程卫生指标（对比度/裸色=0/体积/报错），明文"不认看起来更好"；worktree 前后截图实测——E1 仅 index 一页有可见变化、E2 56 页是严格等值迁移零感知。判定规则：方案目标是感知型（"高级感/观感/体验"）而验收全是工程卫生指标 → 直接判为验收缺陷，且要 worktree 截图实测目标观感的实际渲染差异（参考 §1.6）。

## 验证（评估文档合格标准）

- [ ] 文档首部有实测 git HEAD 基线声明，且与方案声称基线做过比对。
- [ ] 证据基线表覆盖阶段 0 登记的**全部**声称数字，每行有 ✅/❌/⚠️ 判定与实测值。
- [ ] 五维每一维至少引用一条实测证据；无证据的论断已标"待验证"。
- [ ] 每条不足都有对应的可操作改进建议，一一对照无遗漏。
- [ ] 优先行动恰好三条以内、可直接回填进方案。
- [ ] 感知型目标方案：已核对验收条款是否含可感知验证（前后对比截图/目视/A-B），且已完成 worktree 前后渲染差异实测并收录结论（如适用）。
- [ ] 阶段 5 复核完成：文档内数字与实测记录无出入。
