# 西游记项目全仓文件漂移体检

给 xiyouji 项目（`D:\1\xiyouji`）做任意时刻全仓漂移体检的固定流程：对全仓治理文档/索引/引用层做取证式检查，抓出六文档版本行、file-index、方法论 README、skills 双轨、治理文档内容引用等维度的漂移，按 P0-P3 分级后由用户确认修复范围。

本流程源自 2026-08-24 W499 全面审查三轮回溯（chatId mt76g25i7lwvkoe5）：第一轮抓出 file-index 结构损坏 / 方法论 README 滞后 / 批次未登记 3 类 P1；用户追问"全面审查为什么没查出来"暴露盲区——**审查清单锚定在已知漂移模式，漏了内容引用型漂移**（文档里写的门禁数/脚本清单/行号与实际不符）；第二轮抓出 `.github/workflows/README.md` 旁文档滞后（P1，48 批次零同步）；第三轮"举一反三"抓出 day-review 内部"15 条门禁"数字引用滞后（P2）。

核心信条（项目 E1 铁律延伸）：
- **门禁全绿 ≠ 无漂移**——verify_delivery 门禁只覆盖已自动化的结构检查；内容引用型漂移（门禁数/脚本清单/行号/版本行/旁文档）只能靠人工逐份核对，这是本技能的主战场。
- **先取证、后假设**——每个结论必须有 git/文件实测支撑，禁止凭记忆判断（W499 教训：预设清单不完整导致"先假设再取证"）。
- **声明 ≠ 落地**——文档里写的"已同步/已入库/残留 0"都要逐个实测核对。

## 何时触发

触发（正向）：

- 用户要求"全面审查"、"漂移体检"、"文件漂移审查"、"仓库健康检查"、"六文档一致性"、"索引核验"、"全仓体检"、"全仓库审查一遍"、"再全面审查一遍，举一反三"。
- 周期性全仓体检（周度/批次间隙），或发现疑似漂移后要求系统排查（含用户追问"为什么没查出来"后的补查）。
- 任意时刻——本技能不锚定当日，任何时刻调用都是全仓现状体检。

排除（反向）：

- 当日批次收尾审查（那是 `xiyouji-day-review` 技能，含 Playwright 渲染抽查、时间锚定当日；本技能是它的互补面，纯文档/索引/引用层）。
- 评估某份方案/路线图文档（那是 `xiyouji-plan-review` 技能，对象是文档不是仓库状态）。
- 发新版本做六文档同步（那是 `xiyouji-version-bump` 技能；本技能是它的检查者，不是执行者）。
- 会话收尾/DRL 深度复检（那是 `agent-session-loop` / `deep-review-loop` skill，对象是内容质量与流程收敛）。
- 单日工作结束时做当日体检（用 `xiyouji-day-review`，更快更聚焦）。

## 与 day-review 的分工

| 维度 | xiyouji-day-review（当日批次） | xiyouji-drift-audit（本技能，任意时刻） |
|---|---|---|
| 时间锚定 | 当日 00:00 起的提交 | 任意时刻的全仓现状 |
| 核心检查 | 当日提交体量 + Playwright 渲染抽查 + 当日文档同步 | 六文档版本行 / file-index / 方法论 README / skills 双轨 / 治理文档引用一致性 |
| 渲染层 | 有（styled 断言 + dark 截图 + 断点实测） | 无（纯文档/索引/引用层） |
| 重叠点 | 步骤 4 含"治理文档内容引用核验" | 同维度——day-review 查"当日批次有没有同步到位"，本技能查"全仓现在有没有漂移" |

发现 P0/P1 且用户确认修复时：若涉及版本同步接 `xiyouji-version-bump`，登记接双索引铁律（file-index + CHANGELOG），修复完成必须重跑 verify 确认不引入新漂移。

## 前置条件

- 项目在 `D:\1\xiyouji`，git 分支 `main`。shell 为 git-bash，命令用 `cd D:/1/xiyouji` 风格（**`cd /d` 是 cmd 语法，会报错**）。
- **多 session 并发是常态**：一切以本 session 当场实测为准，勿信快照；工作区未提交改动先看 diff 判断归属，不替别的 session 收尾。
- 审查报告落工作区 outputs 目录（或用户指定位置）；修复治理文档后按双索引铁律登记，否则修复本身造成新漂移。
- 完整命令库与案例库见同目录 `reference.md`，步骤 1 前先过一遍。

## 标准流程（八步，严格按序）

**步骤 1 取证未完成前，禁止输出任何审查结论。**

### 步骤 1：取证硬门槛

1. **git 现状**：`git log --oneline -3` 记 HEAD 与最近批次；`git rev-parse --short HEAD`；`git status --porcelain` 区分暂存区/工作区批次归属（W499 教训：暂存+工作区双批未提交是常态待办，不是漂移）。
2. **六文档版本行全量 grep**（七处必须同 v/W）：
   - CHANGELOG.md 头部"当前版本"行
   - 交接文档.md 头部"当前 HEAD"行
   - README.md / STRUCTURE.md / docs/00-导读/项目说明.md 版本行——**项目说明还有次级行**（bump_version.py `--desc` 曾向上一版本行追加而非替换，导致主描述/次级行双行不一致，W496 坑）
   - scripts/output/file-index.md 最新段"当前版本"快照行
   - AGENTS.md 版本脚注（尾部 *...* 行）
3. **未跟踪归属**：`git ls-files --others --exclude-standard`，逐一核对——`_` 前缀脚本=一次性豁免；非 `_` 前缀脚本/文档必须入库（未入库=红旗）；大文件待决项（如大厂分析.txt 70KB）标记待决不判漂移。

### 步骤 2：门禁基线

`python scripts/verify_delivery.py` 跑一遍，记录退出码与失败项。**注意**：退出码 0 只代表全部门禁通过（随批次递增、以 verify 输出为准）。门禁不覆盖的部分才是本技能主战场——文档规范.md 整个在 verify 保护范围外（W499 教训：16 门禁全绿时它已 6 处漂移）。

### 步骤 3：file-index 段完整性

第 17 门禁（check_index_health）已自动化核心检查——W526 起新增**段倒序断言**（豁免区外段必须 W 号严格递减，防 W522-W524 式尾部追加）+ **段缺失检测**（CHANGELOG 每个现役版段须均有 file-index 登记段，防 W504 式漏登记）；豁免区（W449-W463 历史损坏区）内维持现状不重排。门禁外人工复核聚焦：豁免区边界 + 双向核对 + 新增/既有错位判级区分：

1. 段缺失（双向交叉核对）：file-index 登记的 W 号是否都有对应 CHANGELOG 版段（原有方向）**且** CHANGELOG 每个现役版段都登记进了 file-index（W526 补方向）——任一方向缺失 = 双索引铁律违反（W504 实证：CHANGELOG 有 v2.3.103 段而反向索引无 W504 登记段）= **P1**。
2. 顺序错位复核：`grep -n "^## W"` 人工核对倒序（最新在前）——豁免区外**新增**倒序错位（W522-W524 曾被追加到文件尾部的同型复发）= **P1**（W525 实证判级并修复）；**既有**错位（W464 式非新增历史遗留）静默存在 = P3；重排历史段与"历史段禁改"契约冲突，需用户明确授权后手动剪切-插入（段内容零改动）+ 备份留档 + verify 验证（见 reference.md 类型 I）。
3. 最新段残留：最新 W 段是否残留"当前版本"快照行（bump 历史段残留的豁免区不判）。
4. 段完整性：豁免区外是否存在空壳段/重复 W 号（门禁只防新增，历史损坏区维持现状不重排）。

### 步骤 4：方法论 README 双向覆盖

`docs/10-方法论沉淀/README`（或对应索引）目录 md 清单 ↔ 索引表链接差集；"待创建"占位必须 0；引用的方法论文档是否存在（W499 曾抓出索引链接陈旧）。

### 步骤 5：skills 双轨 --check

`python scripts/sync_skills.py --check` + 全量 diff（仓库版 skills/ vs 全局版）：

1. 双轨 0 漂移（单侧修改 = 漂移；仓库是主源，改仓库后 --sync 同步全局）。
2. 新技能未入库仓库（check_skills_index 门禁覆盖，但人工复核 README 索引数 == 目录数）。
3. frontmatter name == 目录名。
4. **skill 内部数字引用 vs 权威值比对**（举一反三维度的固化扩展，W499 第三轮 + W520 固化）：skill 内文（SKILL.md + reference*.md）的门禁数、篇数/页数/skill 数、计数口径、版本引用，逐项对照权威源核实——门禁数以 verify 输出为准、内容规模以 README/统计口径说明为准、skill 数以 skills/README.md 对照目录实测为准；随批次演化的计数应为引用式表述或绑定实测时点，无时点锚的裸字面量 = P2（**门禁依赖豁免**：verify_delivery 强制 README/STRUCTURE/项目说明/交接文档字面含「A4 209 篇」「共 N 篇」——此类受门禁保护的快照行禁改引用式；W519 复盘确认：skills 内文数字游离于六文档同步契约与计数门禁两道防线之外——check_skills_index 只管结构不管内文数字，须靠本维度人工兜底；排查命令见 reference.md 步骤 5）。

### 步骤 6：治理文档内容引用核验（W499 盲区类型的核心防线，本技能价值所在）

逐份打开核对数字引用 / 脚本清单 / 行号引用 / 版本行：

1. **docs/00-导读/文档规范.md**：§8 门禁表 / §11.1 门禁列 / §11.2 禁改清单——门禁数、引用的 scripts/ 脚本名、行号引用（如"第 45 行"）与仓库实际对照。
2. **AGENTS.md §4.2 门禁清单**：清单与仓库实际逐条比对（W499 教训：第 17 门禁只进了脚注、正文漏录）。
3. **.github/workflows/README.md 旁文档**：头部版本行 + 里程碑行（文档规范 §11.1 第 8 项要求里程碑同步；W499 曾 48 批次零同步停在 W426/W449）。
4. **新Agent启动Prompt.md**：计数引用（615/209/86，随批次校正、以该文件与 README/统计口径说明实际为准）、LHCI 阈值——设计上"不维护版本清单"则天然防漂移。
5. **DESIGN.md**：一般无门禁数字引用（批次引用为来源注记）。
6. **skills/README.md**：技能索引（第 16 门禁覆盖）。
7. **统计口径说明.md / 观测基线快照.md**：计数口径；快照语义（生成时点快照，计数与当前一致即无漂移）。

**E2 判据（关键）**：历史事件描述保留旧值——"W493 事发时是 14 门禁"、"W495 第 15 门禁转正"是历史事实，**不是漂移**，禁止改写；只有**现役状态描述**滞后（如"退出码 0 只代表 15 条门禁通过"）才算漂移。

### 步骤 7：孤儿提交与批次归属核对

1. `git log --oneline` 中无法对应 CHANGELOG 版段的提交（孤儿提交 = 无 W 段 = P1/P2）。
2. 暂存区 vs 工作区批次归属（W499/W500 式双批待提交：确认归属清晰即非问题）。
3. 已归档批次（CHANGELOG-ARCHIVE 等）与现役文档的边界确认。

### 步骤 8：P0-P3 分级报告 + 修复确认

分级标准：

- **P0**：全站/核心产物损坏（如全站 INLINED CSS 清空）、verify 门禁阻断、版本行大面积错乱。
- **P1**：治理文档严重滞后（六文档不一致、旁文档多批零同步、file-index 豁免区外新增损坏——段缺失/空壳段/重复 W/倒序错位、批次未登记、孤儿提交）。
- **P2**：内部引用滞后（skill 门禁数、辅助文档过期行、行号引用漂移）——不影响门禁但会误导后续维护。
- **P3**：卫生项（未跟踪杂项、待决文件、历史损坏区残留）——记录不阻塞。

报告结构：证据基线表（检查项 / 实测结果 / 判定）→ 发现清单（含复现命令）→ 修复建议（含登记要求）→ AskUserQuestion 确认修复范围（全部/仅 P0-P1/P2 也修/不修）。修复后必须重跑 verify + 双轨 --check 验证不引入新漂移。

## 陷阱

1. **E1 铁律**：声明 ≠ 落地——修复后必须 Grep spot-check 验证，禁止假收敛。
2. **E2 历史保留判据**：历史事件描述保留旧值，禁改；只改现役状态描述（W499 教训：差点把历史"14 门禁"当漂移改掉）。
3. **门禁全绿 ≠ 无漂移**：verify 不覆盖的文档（文档规范.md、旁文档、skill 内部）才是主战场。
4. **多 session 并发**：勿替别的 session 收尾；未提交改动先看 diff 判断归属。
5. **验收数字当批现测**：修复/登记 CHANGELOG 的 M 指标、内联字节数必须当批现测（acceptance_snapshot.py），禁跨批复制（W493「28385B」教训）。
6. **修复治理文档必须按双索引登记**：file-index + CHANGELOG 同步登记，否则修复本身造成新漂移（W500 教训）。
7. **bump --desc 坑**：若用 bump_version.py 补齐版本行，必须 Grep 校验项目说明次级行 + STRUCTURE 头部 + 版本行三处，`--desc` 会追加而非替换。
