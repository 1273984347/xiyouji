# 西游记项目当日 W 批次工作审查

给 xiyouji 项目（`D:\1\xiyouji`）做当日收尾审查的固定流程：对当日全部 W 批次提交做取证式检查，抓出门禁漏网的问题，按 P0-P3 分级后由用户确认修复范围。本流程在 2026-08-22（W496 当日）首跑逐字验证，当次抓出 **P0 全站 224 页失样式回归（14 门禁全绿漏网）**、baseline_snapshot 从未入库、5 方案档缺回填等多处卫生遗漏。

核心信条（项目 E1 铁律延伸）：
- **门禁全绿 ≠ 无问题**——文本门禁测不出"样式块是否为空"，只有渲染抽查能抓渲染回归。
- **先取证、后假设**——每个结论必须有 git/文件/截图实测支撑，禁止凭记忆或经验判断。
- **声明 ≠ 落地**——方案档/交接文档里写的"已回填/已入库/残留 0"，都要逐个实测核对。

## 何时触发

触发（正向）：

- 用户要求"审查今天的工作"、"当日审查"、"今日复盘"、"收尾审查"、"day review"、"审查今日提交"、"看看今天做得怎么样"、"当日工作有没有问题"、"今天做了什么"。
- 一天的工作结束时，用户希望对当日全部 W 批次做一次收尾体检（发现问题 → 确认修复范围 → 当批修复）。

排除（反向）：

- 评估某份方案/路线图文档（那是 `xiyouji-plan-review` 技能，对象是文档不是当日提交）。
- 发新版本做六文档同步（那是 `xiyouji-version-bump` 技能；本技能是它的检查者，不是执行者）。
- 会话收尾/DRL 深度复检（那是项目内 `agent-session-loop` / `deep-review-loop` skill，对象是内容质量与流程收敛，不是 git 取证式批次审查）。
- 任意时刻的全仓漂移体检（非当日批次，查六文档版本行/file-index/方法论 README/skills 双轨/治理文档引用一致性，那是 `xiyouji-drift-audit` 技能；本技能时间锚定当日，是它的互补面——day-review 查"当日批次有没有同步到位"，drift-audit 查"全仓现在有没有漂移"）。

## 前置条件

- 项目在 `D:\1\xiyouji`，git 分支 `main`。shell 为 git-bash，命令用 `cd D:/1/xiyouji` 风格（**`cd /d` 是 cmd 语法，会报错**）。
- **多 session 并发是常态**：一切以本 session 当场实测为准，勿信快照；工作区未提交改动先看 diff 判断归属，不替别的 session 收尾。
- 审查报告落工作区 outputs 目录（或用户指定位置）；发现 P0/P1 问题且用户确认修复时，修复按当批流程执行（涉及版本同步时接 `xiyouji-version-bump`）。
- 完整命令库与案例库见同目录 `reference.md`，步骤 1 前先过一遍。

## 标准流程（五步，严格按序）

**步骤 1 取证未完成前，禁止输出任何审查结论。**

### 步骤 1：取证（硬门槛）

1. **当日提交清单**：`git log --since "当日 00:00" --oneline`（或 `--since 今日`），识别当日 W 批次（W###）+ 收尾文档提交；`git log -1 --oneline` 记当日末提交。
2. **工作区状态**：`git status --porcelain`。**未跟踪文件逐一核对归属**——项目约定非 `_` 前缀的脚本/文档必须入库（`_` 前缀=一次性不入库）；`scripts/baseline_snapshot.py` 之类非 `_` 前缀却未跟踪 = **从未入库红旗**，直接记问题。
3. **门禁基线**：`python scripts/verify_delivery.py` 跑一遍，记录退出码与失败项。**注意**：退出码 0 只代表 verify_delivery 全部门禁（现 17 条，随批次递增、以 verify 输出为准）通过，不代表当日工作无问题（见步骤 3）。
4. **遗留物检查**：`git worktree list` 看是否有该清理未清理的 worktree。

### 步骤 2：逐提交体量与文档同步核对

1. **体量红旗**：对当日每个提交跑 `git show --stat <commit>` 看 +/- 行数。**删除量异常大（如 >10 万行）是红旗**——往往意味着批量重写/清空操作（W493 删 21 万行 = 全站样式清空事件现场）。
2. **CHANGELOG 四件套核对**：当日每个 W 批次是否在 CHANGELOG.md 有对应版段、版段数字（M 指标/内联字节数等）是否与仓库实测一致（可跑 `python scripts/acceptance_snapshot.py` 现测核对，禁信跨批复制的旧数字）。
3. **六文档同步**：核心 2（CHANGELOG + 交接文档）必须含当日最新 v/W；辅助 4（README / STRUCTURE / 项目说明 / file-index）里程碑时同步。漏同步 = P1。

### 步骤 3：渲染抽查（文本门禁抓不到的部分，本流程价值所在）

文本门禁（体积/语法/对比度/CSP 等）测不出"样式是否真的渲染"。必须实测：

1. **styled 断言（关键）**：用 Playwright 对抽查页跑 `getComputedStyle` 断言——检查 body/卡片实际生效的样式（背景色、字体族、按钮色）。**若页面呈现白底+蓝链接+裸文本 = 样式块为空**，这是 P0 全站失样式的前兆（W493 案例：224 页 INLINED CSS 块被清空，14 门禁全绿漏网）。抽查列表用当日改过的页面 + 每个 type 至少 1 页（根页/data/EN/3D）。
2. **dark 模式截图目视**：`scripts/_shot_check.js`（或等价 Playwright 截图）切暗色模式截图，Read 目视确认渲染正常（对比度/令牌生效/无裸色）。
3. **断点实测**：跑当日未覆盖的常见宽度（如 390/414px iPhone 宽，不在回归测试 5 视口内），确认断点映射无实机回归。

### 步骤 4：文档同步清单

1. **AGENTS.md 脚注**：版本行（vX.Y.Z W###）与当前 HEAD 一致；若当日改了流程/门禁但 AGENTS.md 未同步 = P1。
2. **方案档落地回填**：`docs/superpowers/plans/` 下当日方案档的"遗留项/待办"行是否已回填关闭；宣称"已落地"的每一项要实测存在。
3. **交接文档过期行**：声称值 vs 实测对照（如"残留 0"vs 实际仍有多处），过期/失实行 = P1/P2。
4. **宣称入库脚本真在 git**：方案档/交接文档里宣称"新建了 xx 脚本"，用 `git ls-files scripts/xx.py` 核实真入库（防 baseline_snapshot 式"做了但从未提交"）。
5. **治理文档内容引用核验**：`docs/00-导读/文档规范.md` §8 门禁表 / §11.1 门禁列 / §11.2 禁改清单引用的脚本名、门禁数、行号（如"第 45 行"），以及 AGENTS.md §4.2 门禁清单，与仓库实际对照——新增门禁/脚本后治理文档描述滞后 = P1/P2（W499 教训：文档规范.md 6 处漂移 + AGENTS §4.2 缺第 17 门禁，纯文本门禁与首轮人工审查均漏网）。

### 步骤 5：问题分级 + AskUserQuestion + 报告

1. **按分级标准汇总问题**（见下节），输出报告：问题清单（每项含证据）+ 分级 + 建议修复动作。
2. **用 AskUserQuestion 让用户确认修复范围**（"当批全部修复 / 只修 P0+P1 / 先出报告不修"）。
3. 用户确认后执行修复（修复完重跑 verify_delivery 全绿 + 渲染抽查复验）；若用户只要报告，报告落 outputs 目录并 present。

## 问题分级标准

| 级别 | 定义 | 案例 |
|---|---|---|
| P0 | 数据丢失/全站功能失效/门禁假绿 | 224 页 INLINED CSS 清空全站失样式（门禁仍绿） |
| P1 | 文档同步缺失/脚本未入库/声明与实测不符 | 六文档漏同步、AGENTS 脚注过期、baseline_snapshot 从未入库、方案档缺回填 |
| P2 | 卫生问题/口径瑕疵 | 遗留 worktree 未清、交接文档过期行、格式小问题 |
| P3 | 可选优化建议 | 可复利改进点（如把某检查固化为门禁） |

## 陷阱清单

1. **门禁全绿 ≠ 无问题（2026-08-22 失样式事件）**：W493 批量脚本清空了全部 224 页 data+EN 的 INLINED CSS 块（28KB/页），14 条门禁全部通过——文本门禁只查"块存在/体积/哈希"，不查"样式真的渲染"。**必须做渲染抽查**（步骤 3），这是本流程与纯文本审查的本质区别。
2. **`cd /d` 是 cmd 语法**：git-bash 环境用 `cd D:/1/xiyouji`；门禁首次跑退出码非 0 时先看输出，可能是命令本身写错而非门禁失败。
3. **非 `_` 前缀未跟踪 = 漏入库红旗**：`_` 前缀才是一次性不入库；`baseline_snapshot.py` / `observation-baseline-snapshot.md` 无前缀却未跟踪 = 做了但从未提交。
4. **大删除量红旗**：单提交删除 >10 万行几乎必然是批量重写/清空操作，必须当场确认是有意为之还是事故。
5. **"残留 0"要查口径**：声称"断点残留 0"但 grep 出 4 处时，先分辨是 `@media` 查询还是 `max-width` 属性声明（后者可能本就不在白名单口径内），再下结论。
6. **回归视口要补实测**：门禁测试的视口列表之外的常用宽度（390/414px）也要实测，断点映射改动可能只在这些宽度暴露回归。
7. **验收数字禁跨批复制**：CHANGELOG 的 M 指标/内联字节数必须当批现测（acceptance_snapshot.py），跨批复制会掩盖事故（W493「28385B」跨批复制曾掩盖全站 INLINED 清空）。
8. **治理文档内容引用会漂移**：文档规范.md 的 §8 门禁表 / §11 清单引用的脚本名、门禁数、行号随项目演化滞后；新增门禁/脚本后必须同步治理文档 + 跑 check_index_health（W500 教训：文档规范.md 6 处漂移、AGENTS §4.2 缺第 17 门禁，首轮全面审查漏检）。
